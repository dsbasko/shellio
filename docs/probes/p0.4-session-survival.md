# P0.4 probe-session-survival: отчёт пробы выживания сессий

- Статус: в работе. Прогнаны рубеж A на zmx (задача 7), ранняя проверка C API `libghostty-vt` (задача 8) и headless-матрица zmx B, D, E, F, G (задача 9). Свод для рубежа решения (задача 10) готов, решение владельца не принято. Остальные разделы заполняются по задачам плана.
- Шаг P0.4 [дорожной карты](../roadmap.md), правила проб — [ADR-0034](../adr/0034-probe-code.md) и [ADR-0035](../adr/0035-probe-ffi-tests.md). План — `docs/plans/20261116-probe-session-survival.md` (в git не входит).
- Вопрос: какой хост сессии выбрать по [ADR-0005](../adr/0005-session-backend.md). Кандидатов два: закреплённый zmx с патчами — эталон и запасной вариант, минимальный Rust-хост на `libghostty-vt` — предпочтительная цель. Rust-хост принимается, только если пройдёт все рубежи. Проба проверяет три свойства живой сессии из [ADR-0004](../adr/0004-process-model.md): процесс жив, вывод читается, а при повторном подключении состояние показывается корректно.
- Код пробы — `spikes/probe-session-survival`. В продукт он не переносится: P2.1 пишет хост заново по выводам отчёта.

## Команды

```sh
make probe-session                                  # headless-матрица и замеры, выход в target/probes/session-survival/<время>-<pid>/
make probe-session SCENARIOS="smoke"               # выбранные сценарии
make probe-session SCENARIOS="lifecycle"           # рубеж A на zmx
make probe-session SCENARIOS="capi"                # ранняя проверка C API libghostty-vt без хоста
spikes/probe-session-survival/run.sh check vt       # clippy --all-targets -D warnings и тесты с одной функцией
spikes/probe-session-survival/scripts/zmx.sh ensure zmx   # сборка или сверка одного набора zmx
spikes/probe-session-survival/scripts/zmx.sh --verify zmx-prev
spikes/probe-session-survival/scripts/test-zmx.sh   # тест скрипта наборов, он же входит в make check
spikes/probe-session-survival/scripts/vt.sh ensure        # сборка или сверка набора libghostty-vt
spikes/probe-session-survival/run.sh bindings       # перегенерация src/vt/bindings.rs по набору vt
spikes/probe-session-survival/run.sh bindings-check # сверка привязок, её же выполняет make probe-session
```

`make probe-session` набор ghostty не читает, блокировку `vendor/ghostty.lock` не берёт и в `make check` и CI не входит. Цель `make probe-session-surface` появится в задаче 15.

## Стенд

- Функции cargo пробы — `vt` (FFI над набором `libghostty-vt` и раннер `probe-session`), `surface` (поверхность libghostty) и `proto-v1` (хост с замороженным протоколом). По умолчанию все выключены, `make check` собирает и тестирует только чистую библиотеку (ADR-0035). `run.sh` передаёт функции cargo только сам и отказывает, если в одном вызове включены `vt` и `surface`.
- Каждый сценарий на каждом своём кандидате идёт отдельным процессом. Его запускает режим `--launch` того же исполняемого файла. Окружение собирается с нуля: белый список `HOME`, `USER`, `LOGNAME`, `PATH`, `TMPDIR`, `SHELL`, `LANG=en_US.UTF-8`, сведения о сборке от `run.sh` и временный `SHELLIO_STATE_DIR` вида `$TMPDIR/shellio-probe-state.<nonce>`.
- До работы процесс сценария сверяет своё окружение. Нужны nonce и каталог состояния этого запуска. Переменных `GHOSTTY_*`, `TERM*`, `LC_*`, `AGTERM_*`, `NVIM*` и `ZMX_*` быть не должно: так сценарий не попадёт в настоящие сессии пользователя. Нарушение — ошибка исполнения.
- Внешний сторож снимает процесс по сроку сценария плюс 10 с. После выхода ошибкой исполнения считаются падение, отсутствие `result.json`, оставшиеся процессы с nonce в аргументах и непустой `SHELLIO_STATE_DIR`.
- Сценарий стенда `smoke` записывает окружение в `environment.json` и `result.json` с одной клеткой стенда. Клетка получает `fail`, если в окружении нет сведений об ОС, железе, запуске или версий и штампов наборов пробы, которые передаёт `run.sh`.
- Сценарий стенда `capi` проверяет C API `libghostty-vt` без хоста. Его клетки — клетки стенда `capi-B1`…`capi-B9`, `capi-D1`…`capi-D4` и `capi-budget`, частями по способу восстановления и варианту сюжета. Это доказательство осуществимости, а не `pass` клеток кандидата, поэтому в столбце «стенд» сводки.

### Адаптер zmx

- Трейт `Backend` (`src/backend/mod.rs`) повторяет операции `SessionBackend` из ADR-0005: `ensure`, `attach_command`, `snapshot`, `input`, `resize`, `stop`, `list`. К ним добавлены наблюдения стенда (запись сессии, состояние «жива, недоступна, потеряна, завершена», ревизия обработки, префикс сообщения о роли) и управление сбоями (`kill_host`, `kill_client`, `stall_client`). Это форма контракта для матрицы, а не продуктовый `shellio-session`.
- Каждая команда zmx — отдельный процесс с окружением, собранным с нуля, и изолированным `ZMX_DIR`. Путь каталога процесса сценария длиннее `sun_path`, поэтому `ZMX_DIR` — короткая ссылка `/tmp/pss-<nonce>/z` на `<каталог процесса>/zmx`. Сокеты и журналы демонов остаются в выходе прогона. Адаптер отказывает до запуска, если сокет сессии или путь подготовки `0003` `<ZMX_DIR>/.s/<pid>` не помещается в 103 байта: иначе `0003` молча публикует сокет неатомарно, а это предмет E5. Сокет квитанций фикстур лежит вне `ZMX_DIR`, иначе `zmx list` принял бы его за сессию.
- `ensure` без скрытого attach. Команды «создать без подключения» у zmx нет. `zmx attach <имя> <нагрузка>` сначала создаёт демона: тот публикует сокет и запускает нагрузку. Клиентом команда становится только после первой записи в stdout: «session created» у новой сессии, очистка экрана у готовой. Адаптер отдаёт ей stdout — канал с уже закрытым концом чтения. Первая запись получает `EPIPE`, процесс выходит с кодом 1 и не посылает `Init`. Размер PTY нагрузки демон берёт из stdin — ведомой стороны PTY нужного размера. Успех определяется не по коду, а по списку и процессам: нагрузка в `zmx list`, её родитель — демон этой сессии (`attach <имя>` в аргументах). Признак «создана этим вызовом» — `argv` нагрузки совпадает и её ключ новый.
- Клиент текущей комбинации запускается с `ZMX_MANAGED=<токен>` и ведёт сессию, только если её никто не ведёт (`Lead::IfFree`), или по захвату (`ZMX_MANAGED_CLAIM`). Роль клиент сообщает заголовком `OSC 2;zmx-role;<токен>:<роль>:<поколение>`. Стенд ждёт роли «лидер» как квитанции: `Init` обработан. У `zmx-prev` управляемого лидерства, `screen` и `type` нет, адаптер отвечает на них `unsupported`. Ресайз без клиента у zmx тоже `unsupported`: размер задаёт лидер.
- `stop` — `zmx kill`, затем ожидание гибели хоста, нагрузки и её потомков через `kqueue`. Подтверждение — пустой список выживших по ключам процессов, а не исчезновение сокета. Процессы сессии на момент `stop` берутся из записи `ensure` и дерева потомков живого хоста.
- Наблюдатель считает процесс с признаком `PROC_FLAG_INEXIT` уже не исполняющимся. `kqueue` сообщает о выходе раньше, чем `p_stat` становится `SZOMB` и потомки переходят к `launchd`. Без этого признака выходящая нагрузка в A6 выглядела бы живой, а родителем её потомка оставалась бы она сама. Родитель потомков после сбоя поэтому записывается наблюдением, а не проверкой.

## Схема результатов

- `result.json`: `scenario`, `backend` (`zmx`, `rust` или `null` у сценария стенда), `variant`, `environment`, `execution`, `cells`, `metrics`, `diagnostics`. `launch.json` записывает факты запуска, а также сценарий, кандидата и вариант, поэтому сводка знает их и без `result.json`.
- Статусы клетки: `pass`, `fail`, `not_run`, `unsupported`. У `not_run` всегда есть причина: `excluded` (кандидат исключён на рубеже), `stand` (стенд не доказал условие клетки) или `pending` (клетка ещё не реализована, к концу плана таких не остаётся). `unsupported` значит, что у кандидата доказанно нет возможности. Невозможность наблюдения — `not_run`.
- У клетки записаны обязательность (`required` или `research`), стимул, оракул, условие завершения, доказательство и ссылки на сырые артефакты в каталоге процесса. У `pass`, `fail` и `unsupported` хотя бы одна ссылка обязательна. Происхождение дефекта (`vt`, `host`, `attach`, `unknown`) бывает только у `fail` и `unsupported` и статус не меняет.
- Клетка может состоять из частей: разрезов, режимов клиента, headless и поверхности. Сводка сводит части клетки на кандидате так: `fail` важнее `unsupported`, `unsupported` важнее `not_run`, а `pass` получается только при `pass` всех частей.
- Ошибка исполнения отделена от вывода. Это падение, тайм-аут, сторож, нарушенное предусловие, а также повреждённый или несогласованный `result.json` или `launch.json`. Она роняет цель, и клетки такого процесса в сводку не идут. `fail`, `not_run` и `unsupported` цель не роняют.
- `--aggregate` пишет `summary.json` и печатает сводку: исполнение, таблицу клеток по кандидатам, выводы кроме `pass` с причинами и замеры (медиана, разброс, p95 по ближайшему рангу).

## Кандидаты

- zmx — эталон и запасной вариант. Текущее поколение — набор `zmx`, предыдущее для G1 и G2 — набор `zmx-prev` той же ревизии без патчей `0001` и `0004`.

### Отличия `zmx-prev`, записанные до прогона

Обе комбинации печатают одинаковый `zmx version` (`0.8.1`, ghostty `1.3.2-dev-…+agterm`): ревизия одна, а строку ghostty пишет `0002`, который есть в обеих. Различает их только штамп набора. Чего нет в `zmx-prev`:

- управляемого лидерства `0001`: переменных `ZMX_MANAGED` и `ZMX_MANAGED_CLAIM`, сообщений `Manage` и `Role` (теги 22 и 23), заголовка `OSC 2;zmx-role;<token>:<роль>:<поколение>`. Лидером становится клиент, который последним вводил, как в upstream;
- команды `zmx screen` (тег 24) с заголовком «ревизия, колонки, строки, курсор, alternate». Ревизии обработки нет, поэтому протокол разреза на `zmx-prev` неприменим;
- команды `zmx type` (тег 25) с подтверждением `accepted` или `rejected`;
- сохранения экрана при выходе управляемого клиента `0004`: любой выход attach-клиента пишет RIS.

Ожидания G1 и G2 для пары «клиент `zmx`, демон `zmx-prev`»:

- заголовок `tag+len` общий, поэтому attach текущего клиента к старому демону работает, живой поток и ввод проходят, нагрузка не перезапускается (G1);
- старый демон пропускает незнакомые теги 22–25 с записью в журнал. `zmx screen` и `zmx type` текущего клиента ждут ответа 2 с и завершаются ошибкой `Timeout`; управляемый клиент роли не получает;
- согласования версий нет, поэтому отдельного явного состояния несовместимости у zmx нет: признак старого демона — только тайм-аут команды (G2).
- Rust-хост — задачи 11–14 после рубежа решения.

## Наборы пробы

- Наборы `zmx` и `zmx-prev` собирает `scripts/zmx.sh` пробы по `scripts/zmx-pin`: Zig 0.16.0 архивом с закреплённым SHA-256, zmx `8bab1f0` и его ghostty `8af6897` по ревизиям из git-копий `SHELLIO_CACHE_DIR/zmx/`, патчи agterm из `zmx-patches/` (уведомления MIT zmx и agterm — `zmx-patches/NOTICE`). Продуктовые Zig 0.17.1, кэш исходников ghostty и `vendor/` не меняются.
- Деревья `zmx` и `zmx-ghostty` лежат рядом: `0002` направляет зависимость zmx на `../zmx-ghostty` с патчем formatter. Каждый патч сначала проверяется `git apply --check` на чистом дереве после предыдущих. Комбинация проверяется до загрузки и сборки: `0004` требует `0001` раньше себя, потому что импортирует `role.zig` из `0001` и без него, хоть и накладывается, не собирается.
- Набор — `target/probes/session-survival/<набор>/`: `bin/zmx`, `LICENSE` zmx, `LICENSE.ghostty`, `manifest` и `stamp`. Штамп — значения pin, комбинация набора и SHA-256 её патчей, патчи ghostty, флаги, рецепт (`zmx.sh` и `set.sh`), архитектура, Xcode и SDK. Сборка проверяет архитектуру `arm64`, минимум macOS 14.0 и `zmx version`.
- Сборка идёт рядом с наборами, затем набор целиком переносится на место переименованием: прерванная публикация оставляет прежний набор. У каждого набора своя блокировка `<набор>.lock`, занятая блокировка сразу даёт отказ. `--verify` сверяет штамп и манифест без сети и без Zig.
- `make probe-session` перед сценариями выполняет `zmx.sh ensure` для обоих наборов: собирает только расходящийся набор, иначе сверяет. Холодная сборка набора на M-серии занимает около минуты, плюс загрузка Zig и исходников при пустом кэше.
- Набор `vt` собирает `scripts/vt.sh` пробы: ревизия, версия, Zig и патчи — из `scripts/ghostty/pin` и `scripts/ghostty-patches/`, второго pin нет. Исходники берутся из git-копии `SHELLIO_CACHE_DIR/ghostty-src.git` только чтением: ref ревизии заводит `make ghostty`, без него сборка отказывает с этой подсказкой. Рабочая копия — `target/probes/session-survival/.vt.build.*/`, после сборки удаляется. Пакеты Zig общие с набором ghostty (`SHELLIO_CACHE_DIR/zig-global`), поэтому после `make ghostty` сеть не нужна. Продуктовые `vendor/ghostty/` и `make ghostty` не меняются.
- Флаги в штампе: `-Demit-lib-vt=true -Doptimize=ReleaseFast -Demit-xcframework=false -Dlib-version-string=1.4.0`, цель нативная (build.zig ghostty сам берёт generic-процессор macOS). Без явного `-Demit-xcframework` его значение в режиме lib-vt зависело бы от наличия `xcodebuild`, без `-Dlib-version-string` версия бралась бы из git рабочей копии.
- Набор `target/probes/session-survival/vt/`: `lib/libghostty-vt.a` (12 МБ, архив уже объединён с SIMD-зависимостями, `Libs.private` пуст — других библиотек линковка не требует), `include/ghostty/vt.h`, `include/ghostty/vt/`, `LICENSE` ghostty, `manifest` и `stamp`. Сборка проверяет архитектуру `arm64`, минимум macOS 13.0 у каждого объекта, символ `_ghostty_terminal_new` и совпадение установленных заголовков с исходниками ревизии. Тёплая сборка — около 45 с. Публикация, блокировка `vt.lock` и `--verify` — те же, что у наборов zmx (`scripts/set.sh`).
- `build.rs` пробы без функции `vt` ничего не ищет и не линкует. С `vt` он вызывает `vt.sh --verify` и линкует только `lib/libghostty-vt.a` набора (`static:-bundle`); собирает набор только `vt.sh ensure` из `run.sh`. Привязки `src/vt/bindings.rs` генерирует `scripts/vt-bindings.sh` по трём спискам — функций, типов и констант; там же записан сознательно неиспользуемый API. `make probe-session` сверяет привязки до `clippy` и тестов.

## Профиль нормализаций

Версия 1, заморожена до первого прогона матрицы (задача 6, `src/oracle/model.rs`). Правка профиля — новая версия с перепрогоном и записью здесь. Тест `profile_v1_is_frozen` держит описание профиля дословно, а `smoke` получает `fail`, если версия профиля в окружении результата не текущая.

- Оракул восстановления — два независимых экземпляра `libghostty-vt` ревизии поверхности с одинаковой конфигурацией: 10 000 строк истории, клетка 10×20 пикселей, цвета по умолчанию заданы. Эталон получает исходные байты фикстуры и ресайзы, обратного маршрута у него нет: `WRITE_PTY` не ставится, поэтому он не отвечает даже на DA. Приёмник получает только вывод attach-клиента, а его ответы поток маршрута пишет обратно в PTY attach-клиента, откуда они идут через кандидата в PTY нагрузки. У каждого клиента свой приёмник и свой журнал: ответы с числом полученных до них байтов, запись и чтение буфера обмена, звонок, смена заголовка.
- Сравниваются напрямую: клетки активной области и истории (текст, ширина, стиль, URI гиперссылки, защита), признаки мягкого переноса строк, длина истории, курсор (позиция, отложенный перенос, видимость, перо), активный экран, все 43 режима из `modes.h`, текущие флаги Kitty, текущие цвета и палитра, заголовок, pwd, состояние разборщика (ground или внутри последовательности) и кодирование 12 событий ввода кодировщиками ghostty по режимам терминала (клавиши, в том числе keypad и стрелки, нажатие, отпускание и движение мыши).
- Сохранённый курсор и стек Kitty C API не отдаёт. Они снимаются на копии терминала, которая получает тот же журнал ввода заново: `CAN` обрывает начатую последовательность, восемь снятий вершины стека Kitty (`CSI < u`) дают стек, затем `DECRC` даёт сохранённый курсор. Снимок `GHOSTSNP` для копии не используется: его полнота сама проверяется пробой. Журнал ограничен 64 МиБ; сверх предела, как и при снятии без скрытого состояния, эти поля записываются как ненаблюдённые с причиной.
- Только суффиксом видны неактивный экран, табуляторы, поля прокрутки, незавершённая последовательность и перенос строк при ресайзе. Каталог суффиксов (`src/oracle/suffix.rs`): `alt-exit` (B2), `decrc` (B3), `kitty-pop` (B4), `pending-wrap` (B6), `tab` и `margins` (B5), `resize` (B9). Каждый печатает метку там, где оказался курсор. Эталону суффикс подаётся напрямую, приёмнику — через кандидата: вывод пишет фикстура нагрузки, ресайз идёт от окна attach-клиента, и каждый шаг заканчивается барьером — DSR `CSI 5 n`, ответ приёмника на который фикстура подтверждает квитанцией. Барьер ставится только на границе последовательности и требует, чтобы кандидат передавал DSR клиенту.
- Правило нормализации одно: `palette-as-rgb` — цвет по индексу палитры равен RGB того же цвета в палитре терминала, который хранит индекс. Не нормализуются пустая клетка против напечатанного пробела, отложенный перенос, признаки мягкого переноса и URI гиперссылки: их проверяют B1 и B6. Расхождение вне профиля — `fail` клетки независимо от причины.
- Вне профиля и не сравниваются: ID гиперссылки (C API клетки отдаёт только URI), форма курсора DECSCUSR (терминал C API её не отдаёт), форма указателя OSC 22, выделение и положение прокрутки области просмотра (состояние клиента), изображения Kitty, наборы символов G0–G3 (их не проверяет ни одна клетка).
- Сообщения о роли управляемого клиента zmx (`OSC 2;zmx-role;<токен>:…`) — часть протокола клиента с терминалом, а не заголовок нагрузки. Приёмник клиента, объявившего префикс роли, ведёт себя как терминал, знающий протокол: пишет такое сообщение в журнал ролью, а заголовком состояния остаётся последний заголовок нагрузки. Это свойство профиля колбэков приёмника, а не правило сравнения, поэтому версия профиля нормализаций не меняется. Объявлено до первого прогона матрицы (задача 7); от него зависит сравнение заголовка в A2 и A7. Чужой токен и клиент без префикса роли дают обычный заголовок.
- Итог сравнения: `equal`, `differs` (есть расхождение вне профиля) или `incomplete` (расхождений нет, но часть состояния не наблюдалась). Ненаблюдённое не равно никакому значению, клетка не проходит отсутствием наблюдения. Первые 100 расхождений и нормализаций записываются путём и обоими значениями, остальные считаются.

## Возможности C API `libghostty-vt`

Задача 8, сценарий стенда `capi` (`src/matrix/capi.rs`), без хоста. Прогнан четыре раза подряд, 2026-11-17, с одинаковыми итогами по каждой части. Это доказательство осуществимости, а не `pass` клеток кандидата.

Стенд. Фикстура `emitter` сидит в PTY стенда. Модель хоста — исходный терминал `libghostty-vt` ревизии поверхности с колбэками ответов (профиль приёмника с именем `host`) и бюджетом continuation 1 МиБ. Она читает мастер PTY потоком маршрута оракула и пишет ответы обратно, а эталон получает те же байты напрямую. Перед каждой точкой восстановления стенд сверяет исходный терминал с эталоном, расхождение — ошибка исполнения. В точке восстановления из исходного терминала строятся два приёмника:

- `formatter`: вывод formatter VT со всеми дополнениями (палитра, режимы, поля прокрутки, табуляторы, pwd, режимы клавиатуры, курсор, перо, гиперссылка, защита, Kitty, наборы символов), затем continuation;
- `snapshot`: полный снимок `GHOSTSNP` с continuation внутри, декодированный с пределом 1 МиБ. Колбэки клиента включаются после декодирования. Предел истории, цвета по умолчанию и размер клетки клиента задаются поверх снимка, а сохранённый курсор и стек Kitty оракул снимает повтором от того же снимка.

Приёмник сравнивается с эталоном сразу, затем после суффиксов (раздел «Профиль нормализаций»). Живой поток после точки восстановления получают эталон, исходный терминал и приёмники одинаково.

| --- | --- | --- |
| B1 | не восстанавливает: признаки мягкого переноса в истории и активной области, заголовок OSC 2 | восстанавливает |
| B2 | ловится только суффиксом: активный alternate совпадает, но после выхода из него основной экран пуст, курсор не на месте (83 расхождения) | восстанавливает |
| B3 | не восстанавливает сохранённый курсор: позицию и перо `DECSC` | восстанавливает |

| B6 | не восстанавливает spacer head широкого символа на конце строки и признаки переноса | восстанавливает |

- Formatter выдаёт активный экран вместе с его историей (полезная нагрузка растёт с историей: 5,6–36,8 КБ в B8), но не неактивный экран. Перенесённые строки он печатает подряд, а клиент получает их жёсткими. Заголовка, сохранённого курсора и стека Kitty в его выводе нет. Обход на formatter стоил бы своего кодировщика этих частей поверх C API. Снимок закрывает их сам, поэтому для хоста выбирается снимок.
- Continuation — ровно незавершённая часть потока. Печатные байты перед ней в неё не входят: у UTF-8 из префикса `ab\xe4\xb8` это два байта.
- B8 локально: поток 300 нумерованных строк по 100 колонок (102 байта, каждая мягко переносится) идёт из фикстуры. В одном процессе исходный терминал получает байты до среза, приёмник восстанавливается и получает остаток. Срезы — каждый байт двух строк середины потока (210) и 18 срезов выборки. Оракул — счётчик строк потока у приёмника без пропуска и повтора и построчное совпадение с эталоном. Межпроцессная часть B8 — задачи 9 и 12.
- Восстановление режима 2048 через formatter заставляет клиента сразу отправить отчёт размера `CSI 48 ; 24 ; 80 ; 480 ; 800 t` — лишний ввод в сессию (к C2). У снимка колбэки включаются после декодирования, ответа нет. Остальные сюжеты B восстановлением ответов и эффектов не вызывают.
- Снимок переносит цвета по умолчанию хоста и динамические цвета OSC 10 и 11, но не предел истории. Клиент после декодирования задаёт свой предел и, если тема клиента не совпадает с хостом, свои цвета по умолчанию (тест `snapshot_carries_default_and_dynamic_colors_but_not_scrollback_limit`).
- `snapshot.h`: формат снимка версии 1 «work in progress» без гарантии двоичной совместимости. Хост и клиент разных ревизий `libghostty-vt` могут не понять снимок друг друга, поэтому формат снимка — часть версии протокола хоста для G1 и G3 (задача 14).
- Вне профиля v1 и поэтому не проверено: ID гиперссылки, форма курсора, форма указателя, изображения Kitty, наборы символов.

- Цена обхода D1. Хост, который отвечает сам, должен вырезать обслуженные запросы из потока клиенту: терминал клиента, то есть поверхность, отвечает на них сам. Нужен собственный разбор запросов с состоянием между чтениями, по образцу `src/fixture/query.rs` пробы (около 300 строк с тестами), и правило для начатого запроса в continuation. Хост либо ждёт ground перед снимком, либо не отдаёт клиенту continuation, начатую как обслуживаемый запрос. Это работа хоста (задача 12), а не дефект C API.
- Схема ответа GUI на чтение буфера обмена для задачи 12. Колбэк C API синхронный, ответ после возврата невозможен. Поток разбора ждёт ответа GUI ограниченно (в модели 1 с) с номером поколения, а PTY читает отдельный поток в очередь, ограниченную байтами (в модели 4 МиБ). Если GUI не ответил в срок, отсутствует или отказал, колбэк возвращается без ответа, и программа получает пустой ответ — ровно один. Поздний ответ старого поколения ожидание отбрасывает: ответ поколения 2, пришедший во время ожидания поколения 3, отброшен, программа получила ответ своего поколения.
- Измерено на этой схеме. Пока поток разбора ждал GUI 1005 мс, фикстура записала 160 КБ без единой задержки записи и закончила поток примерно за 1 с до ответа. Контроль без отдельного потока чтения: запись фикстуры стояла 1005 мс.
- Следствие схемы: пока поток разбора ждёт, вывод копится в очереди и до тайм-аута не доходит до VT, снимков и клиентов. Полная очередь останавливает чтение PTY, и это обратное давление на нагрузку. Тайм-аут и предел очереди — объявленные параметры хоста. Отвергнут собственный перехват OSC 52 до VT: он требует второго разбора OSC с состоянием между чтениями, а C API ответа после возврата из колбэка не допускает.

Бюджет continuation и порядок восстановления:

- Бюджет модели хоста — 1 МиБ (`GHOSTTY_TERMINAL_OPT_CONTINUATION_MAX_BYTES`). Незавершённый OSC 2 длиной 1 048 512 байт в пределах бюджета экспортируется continuation той же длины, снимок — 1 049 675 байт, экспорт обоих — около 39 мс. После остатка оба способа совпали с эталоном. Декодер снимка с пределом меньше continuation отказывает `GHOSTTY_LIMIT_EXCEEDED`, с равным — принимает.
- Сверх бюджета (незавершённый OSC 2 длиной 1 049 600 байт) continuation и снимок отказывают `GHOSTTY_INVALID_VALUE`. Formatter работает, но клиент без continuation печатает хвост последовательности текстом (6 расхождений: текст и курсор). Исходный терминал разбирает последовательность правильно, а после её конца continuation и снимок снова доступны. Значит, пока идёт последовательность сверх бюджета, хост не может снять снимок: attach ждёт ground или получает явный отказ. Выбор — задача 12.
- Порядок восстановления. Formatter: вывод formatter, затем continuation, затем живой поток с байта, на котором сделано восстановление. Граница — число байтов, полученных исходным терминалом. Снимок: continuation внутри снимка после страниц активного экрана, до маркера READY, затем живой поток с той же границы. B7, B8 и бюджет подтверждают порядок: при точной границе живой поток не теряет и не повторяет байты.

Для рубежа решения (задача 10):

- Клетки `capi-*` читаются по частям. В сводке `capi-B1`, `B2`, `B3`, `B4`, `B6` и `B9` стоят `fail` только из-за части `formatter`, часть `snapshot` у всех `pass`. `capi-D1` — `fail` частей `client-stream` и `restore-boundary-*`, часть `host` — `pass`.
- Клеток B, которые C API не закрывает, в пределах профиля v1 нет: снимок восстанавливает всё проверенное. D1 закрывается только фильтром обслуженных запросов на стороне хоста, цена описана выше. D3 и D4 закрываются выбранной схемой ответа GUI.


Найдено при обёртке C API (задача 5, FFI-тесты `src/vt/tests.rs`):

- Запрос DA при установленном `WRITE_PTY` не глушится. `terminal.h` обещает молчание, если колбэк `DEVICE_ATTRIBUTES` вернул `false` или не задан, но C API всегда ставит обработчику свой трамплин, а тот без ответа колбэка отдаёт атрибуты по умолчанию: `CSI ? 62 ; 22 c` (`deviceAttributesTrampoline` в `src/terminal/c/terminal.zig`). Для правила «отвечает ровно одна сторона» это значит: экземпляр `libghostty-vt` с `WRITE_PTY` всегда отвечает на DA, и молчащий приёмник или хост должен не ставить `WRITE_PTY` либо не передавать его вывод. Запросы размера (`CSI 14/18 t`) и цветовой схемы (`CSI ? 996 n`) без ответа колбэка молчат, как обещано; XTVERSION без колбэка отвечает `DCS > | libghostty ST` (тест `xtversion_without_callback_answers_libghostty`, задача 8).
- Кроме formatter и continuation в C API есть полный снимок `ghostty_snapshot_encode` и декодер `ghostty_snapshot_decoder_*`: двоичный формат `GHOSTSNP` с CRC, восстанавливает экран, историю и незавершённую последовательность. Разрезанный CSI переживает снимок: восстановленный терминал отдаёт ту же continuation, и после остатка клетка совпадает с исходной вместе со стилем и курсором.
- Continuation, включённая уже посреди последовательности, недоступна: `ghostty_terminal_continuation_*` возвращает `INVALID_VALUE`, как и описано.

Найдено при оракулах (задача 6, FFI-тесты `src/oracle/vt/tests.rs` и `tests/oracle_vt.rs`):

- Включение режима 2048 сразу отвечает текущим размером (`CSI 48 ; строки ; колонки ; высота ; ширина t`) через `WRITE_PTY`, ресайз при включённом режиме — тоже. Для D5 и правила «отвечает ровно одна сторона» это ответ без запроса: его даёт любой экземпляр `libghostty-vt` с `WRITE_PTY`, который видит `CSI ? 2048 h`.
- OSC 10, 11 и 4 терминал C API отвечает сам по своим цветам; OSC 10 и 11 — только если цвет задан (`GHOSTTY_TERMINAL_OPT_COLOR_FOREGROUND` и `_BACKGROUND`). Отчёты фокуса режима 1004 терминал не порождает: их кодирует `ghostty_focus_encode` по событию окна, а включён ли режим, проверяет вызывающий.
- Флаги Kitty главнее DECCKM при кодировании клавиш: при флагах 3 стрелка вверх кодируется `CSI 1 ; 1 : 1 A`, а не `ESC O A`.
- Колбэк чтения буфера обмена отвечает через `reply` синхронно, и ответ сразу уходит через `WRITE_PTY` в тот же колбэк состояния. Обёртка пробы копирует нужное и не держит ссылку на состояние во время `reply`.

### Рубеж A на zmx

Сценарий `lifecycle` (`src/matrix/lifecycle.rs`), набор `zmx`, задача 7. Стенд играет GUI: attach-клиент сидит в PTY стенда, его вывод идёт в приёмник, ответы приёмника — обратно в PTY клиента. Нагрузка — фикстура в PTY демона, размер PTY нагрузки равен размеру окна стенда. Каждая часть клетки идёт на своей сессии, артефакт части — `a<N>-<часть>.json` с проверками и наблюдениями, рядом журнал демона `zmx/logs/<сессия>.log`. Прогнан четыре раза подряд с одинаковыми итогами.

- A1, части `client-sigkill` и `gui-hangup`: после `SIGKILL` клиента и после закрытия всех дескрипторов мастера PTY клиента (ядро шлёт ему `SIGHUP`) хост и нагрузка — те же живые процессы по PID и времени старта, сессия в списке, новый клиент становится лидером и передаёт ответ барьера DSR. Настоящий `SIGKILL` процесса GUI — клетка C1.
- A2: клиент отключается клавишей `Ctrl-\`, без клиентов фикстура пишет 4000 строк по 80 колонок и ED 3, затем подключается второй клиент. Поток в 328 КБ закончен за миллисекунды: запись фикстуры упиралась в полный PTY лишь несколько раз, суммарно меньше миллисекунды, то есть демон без клиентов читает PTY постоянно. Ревизия обработки выросла, приёмник второго клиента совпал с эталоном. Перенос истории — клетка B1, сессия без единого клиента — A7.
- A3: через клиент, ведущий сессию, — `run /bin/sleep 600`, `Ctrl-Z`, `bg 1`, `fg 1`, `Ctrl-C`. Квитанции фикстуры `shell` и `tcgetpgrp` внутреннего PTY совпали с ожиданием на каждом шаге, клиент всё время остаётся группой переднего плана своего PTY.
- A4: повторный attach и повторный `ensure` не запускают нагрузку заново. Восемь одновременных `ensure` одной сессии с разными нагрузками дают один хост, одну нагрузку, один сокет и пустой каталог подготовки `0003`; нагрузку запустил ровно один вызов, готова фикстура победителя.
- A5: штатный выход нагрузки при подключённом клиенте завершает нагрузку и демона, клиент выходит. `zmx kill` подтверждён гибелью хоста и нагрузки по ключам.
- A6, части `shell`, `agent` и `background`: после `SIGKILL` демона нагрузка выходит по потере PTY, адаптер видит «хост потерян» (ключ хоста мёртв, сокет остался), каждый живой процесс с nonce нагрузки есть в записи `ensure`. Процесс, игнорирующий HUP (потомок `agent` и фоновое задание `shell`), найден по сохранённому PID и времени старта и отвечает на команду. Его родитель в момент проверки — `launchd` или ещё выходящая нагрузка: в шести частях `agent` и `background` из восьми нагрузка уже в `exit()` (`PROC_FLAG_INEXIT`, `p_stat` ещё не `SZOMB`), но потомок ещё не передан `launchd`. Поэтому родитель записан наблюдением, а выходящая нагрузка считается не исполняющейся.
- A7 — `fail`, происхождение — хост. Сессия создана `ensure` и ни разу не имела клиента, фикстура пишет заголовок, перо, 62 строки, позиционирование и режимы. `zmx screen` показывает это состояние, повторный `ensure` нагрузку не создаёт, лидера до attach демон не назначал: скрытого attach нет. Но первый клиент получает только живой поток после подключения: в журнале демона одно назначение лидера и ни одной отправки снимка, у приёмника пустой экран против 24 строк эталона (411 расхождений). Это известный риск из контекста плана: пока `has_had_client = false`, первый attach снимок не воспроизводит. Исправление — патч zmx в P2.1, если будет выбран zmx.

Восстановление (B). Клиент c1 подключается и отключается до сцены, иначе любой B упал бы по причине A7. Сцена пишется без клиентов, затем подключается c2, эталон сравнивается с его приёмником сразу и после каждого суффикса через кандидата. Сцены и суффиксы — те же, что у сюжетов `capi`, поэтому строки сопоставимы с таблицей возможностей C API.

- B1–B6 и B9 — `fail`, происхождение — VT: снимок zmx строится formatter его ghostty 1.3.2-dev, и потери совпадают с частью `formatter` сценария `capi` на ghostty 1.4. Теряются мягкие переносы (B1, B6, B9: после ресайза reflow расходится на 2302 клетки), гиперссылки (B1), курсор и сохранённый курсор основного экрана под alternate (B2), сохранённый курсор `DECSC` (B3), нижние уровни стека Kitty (B4: после pop кодирование `Ctrl-A` и `Esc` у приёмника устаревшее), позиция курсора при `DECOM` с полями (B5: строка 9 вместо 5, суффикс табуляции печатает не там), spacer head широкого символа на границе (B6). Пустые клетки становятся напечатанными пробелами (B2, B6).
- B7 — `fail` во всех пяти частях (`csi`, `osc`, `dcs`, `utf8`, `esc`), происхождение — хост. Граница доказана протоколом разреза: ревизия обработки выросла ровно на единицу после префикса, других чтений, ресайзов и подключений не было. Начатая последовательность в снимок не попадает, поэтому остаток печатается у приёмника как текст: `1mX` вместо красного `X`, хвост заголовка OSC, `�` вместо `世`, `7X` вместо `DECSC`.

Весь поток помещается в историю приёмника, поэтому шов «снимок → живой поток» лежит в проверяемом окне: номера строк у приёмника идут подряд с 22-й по 800-ю, первая сохранённая строка раньше строки, записанной к запуску c2. Активная область совпадает с эталоном. Попутное наблюдение: строк 1–21, записанных до подключения, у приёмника нет — снимок zmx в этом прогоне нёс только видимый экран.

Ввод и геометрия (F1, F3) — `pass`. Подключение ведомого клиента другого размера и его ресайз до нагрузки не доходят, захват лидерства клиентом c3 передаёт нагрузке его размер, прежний лидер становится ведомым, его ресайз не доходит. Отсутствие ресайза доказано квитанцией следующего ресайза лидера: между отметкой и ней других квитанций размера нет. Ввод через `zmx send` и `zmx type` доходит до нагрузки, не меняет размер, не назначает лидера и не добавляет клиента.

Запросы и эффекты (D). Ответы считает фикстура по своему входу. Отсутствие ответа доказывает только следующее упорядоченное событие: барьер DSR через лидера или, без клиента, контрольный DA, на который zmx отвечает сам. Ввод ведомого управляемого клиента демон отбрасывает целиком (`handleInput` в `src/loop.zig` и патч `0001`), поэтому при двух клиентах барьер — ответ лидера у фикстуры, ответ ведомого в журнале его приёмника и второй барьер через лидера.

- D1 — `fail`, происхождение — хост. С одним и с двумя клиентами на каждый из девяти запросов ровно один ответ: отвечает терминал лидера, ответ ведомого демон отбрасывает. Без клиента zmx сам отвечает только на DA1 и DA2, а на DSR позиции, DECRQM, OSC 10/11/4 и XTVERSION ответа нет. Если лидер остановлен между запросом и ответом и затем убит, ответа нет ни на один запрос: ни без ведомого, ни при живом ведомом, ни после подключения нового лидера.
- D2 — `fail` в 16 частях без клиента, `pass` в 16 частях с клиентом; происхождение — хост. Граница каждого разреза доказана ревизией обработки. С клиентом разбор с состоянием ведёт его терминал. Без клиента разрезанный DA1 остаётся без ответа: `respondToDeviceAttributes` ищет DA в каждом прочитанном куске без состояния между чтениями; DSR позиции, XTVERSION и OSC 11 без клиента не отвечаются и целиком.
- D3 — `pass`: запись OSC 52 при живом клиенте даёт эффект в журнале его приёмника ровно один раз, при новом подключении эффект не повторяется, запись без клиента не повторяется больше одного раза.
- D4 — `fail`, происхождение — хост. При клиенте на чтение OSC 52 один ответ, повторного при новом подключении нет; поздний ответ прежнего лидера после захвата лидерства до нагрузки не доходит — его отбрасывает роль ведомого, а не поколение запроса. Без GUI ответа нет совсем, тайм-аута с явным ответом у zmx нет. Часть «поколение и тайм-аут» — `not_run`: поздний ответ отброшен ролью, поэтому отсутствие поколения в самом протоколе стендом не доказано.
- D5 — `fail`, происхождение — хост. Включение 2048 даёт один отчёт размера, фокус окна — один FocusIn. Но демон сам пишет в PTY FocusIn при подключении первого клиента и FocusOut при уходе последнего (`src/loop.zig`, режим 1004), поэтому фокус окна нового клиента даёт второй FocusIn: отвечают обе стороны.
- D6 — `pass`: без клиента и при остановленном (`SIGSTOP`) лидере `zmx screen`, `zmx list`, `zmx send` и `zmx type` завершаются в пределах 5 с, ввод доходит до нагрузки.

Ввод-вывод (E).

- E1 — `fail`, происхождение — хост. При остановленном клиенте поток 32 и 64 МиБ дописан целиком и демон читал PTY до конца (последняя строка в `zmx screen`), но клиент не отключён и обратного давления нет: вывод копится в `write_buf` клиента без предела. Прирост `phys_footprint` демона — 41,8 и 76,6 МБ, удвоение объёма добавило 34,8 МБ при объявленном пределе 8 МиБ.

### C API: что он не закрывает сам и цена обхода

Снимок `GHOSTSNP` в `capi` восстанавливает всё проверенное в B1–B9 в пределах профиля v1. Остальное ложится на хост:

| Что | Цена обхода | Где |
| --- | --- | --- |
| D1: C API не помечает в потоке клиенту запросы, на которые уже ответил | Хост вырезает обслуженные запросы из потока своим разбором с состоянием между чтениями (образец — `src/fixture/query.rs`, около 300 строк с тестами). Плюс правило для запроса, начатого внутри continuation: ждать ground перед снимком или не отдавать такую continuation | задача 12 |
| D4: колбэк чтения буфера обмена синхронный | Ограниченное ожидание ответа GUI в потоке разбора (в модели 1 с, с поколением) и чтение PTY отдельным потоком в очередь, ограниченную байтами (в модели 4 МиБ). Пока поток разбора ждёт, вывод до VT, снимков и клиентов не доходит. Полная очередь останавливает чтение PTY | задача 12 |
| Последовательность сверх бюджета continuation | Пока она идёт, снимка нет: attach ждёт ground или получает явный отказ | задача 12 |
| Формат `GHOSTSNP` версии 1 без гарантии двоичной совместимости | Формат снимка входит в версию протокола хоста, обновление ревизии VT меняет её | задачи 14 и 16 |
| Экземпляр с `WRITE_PTY` всегда отвечает на DA (трамплин C API) | Отвечает только хост. Клиентский экземпляр либо без `WRITE_PTY`, либо его вывод не передаётся | задача 12 |
| Включение режима 2048 и ресайз при нём сами шлют отчёт размера | Ответ без запроса. Учитывается в D5 и C2 | задачи 12 и 15 |

**Открытый пункт: мост снимка в поток байтов.** `capi` проверил снимок, декодированный прямо в приёмник `libghostty-vt` (`Receiver::from_snapshot`), но не проверил его прохождение через поток байтов. Обычным путём attach снимок так не попадает:

- в `ghostty.h` поверхности импорта снимка нет, поверхность получает только байты из PTY своей команды;
- attach-клиент по раскладке cargo собирается без VT и воспроизводит снимок байтами в свой PTY;
- приёмник headless-матрицы тоже читает байты из PTY attach-клиента.

Значит, у Rust-хоста состояние в B и C доходит до клиента повтором VT-байтов. Есть два способа:

- Formatter. Его потери известны: мягкие переносы, заголовок, сохранённый курсор, стек Kitty, неактивный экран и spacer head. Это те же клетки B1–B4, B6 и B9, что у zmx.
- Собственный кодировщик поверх formatter. Мягкие переносы — строками во всю ширину без CR LF. Заголовок — из `GHOSTTY_TERMINAL_DATA_TITLE` в OSC 2. Неактивный экран, сохранённый курсор и стек Kitty C API не отдаёт. Их можно снять пробными последовательностями на копии, декодированной из того же снимка (переключение экрана, `DECRC`, снятия `CSI < u`), как это делает оракул, или вести своим разбором в хосте. Кроме того, нужно решить, где живёт кодировщик: в хосте (attach-клиент остаётся без VT) или в attach-клиенте (тогда он линкует `libghostty-vt`).

Цена кодировщика не оценена, и до задачи 12 он ничем не доказан. Если он не закроет B1–B4, B6 и B9, Rust-хост получит в них те же `fail`, что и zmx, только с происхождением «хост» или «attach». Эта задача общая для обоих кандидатов: чтобы исправить VT-провалы zmx, нужен такой же кодировщик, только на Zig.

### Исходы

- **«идём»**: задачи 11–18 выполняются. План уточняется: мост снимка в байты становится явной работой задачи 12, а раскладка cargo меняется, если кодировщик живёт в attach-клиенте. Rust-хост по-прежнему принимается только после всех рубежей.
- **«Rust-хост исключён»**: задачи 11–14 не выполняются, клетки Rust-хоста получают `not_run` с причиной `excluded`, задачи 15–18 идут на zmx. ADR-0005 получает выбор zmx с перечнем 18 провалов и патчей для P2.1 из таблицы выше. Выбор кандидата с `fail` в обязательных клетках записывается как условный, с явно принятыми отклонениями (задача 20).
- **«не подходит ни один»**: оставшиеся задачи сокращаются до записи выводов. ADR-0005 получает отрицательный вывод и обращение к условию пересмотра, решение владельца оформляется новым ADR.

Рекомендация исполнителя, не решение: «идём», но первым шагом задачи 12 проверить мост снимка в байты на стенде `capi` (кодировщик, затем приёмник через байты по сюжетам B1–B9), до протокола, очередей и версий. Основания:

- провалы zmx с происхождением «хост» — это 11 клеток в чужом форке на Zig;
- у Rust-хоста те же свойства — решения собственного кода, и C API их не запрещает;
- кодировщик снимка нужен обоим кандидатам, так что выбор zmx от него не избавляет, если не принять B1–B6 и B9 отклонениями.

Если мост не сходится, ветка «Rust-хост исключён» остаётся доступной без потерь: headless-клетки zmx уже закрыты.
