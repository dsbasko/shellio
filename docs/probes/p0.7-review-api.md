# P0.7 — проба API ревью GitHub и GitLab

Шаг P0.7 `probe-review-api` [дорожной карты](../roadmap.md), план [20261120-probe-review-api.md](../plans/20261120-probe-review-api.md). Проба проверяет [ADR-0015](../adr/0015-forge-review.md) на локальном `forge-fake` (обязательный стенд) и в живых песочницах. Код — `spikes/probe-review-api` ([ADR-0034](../adr/0034-probe-code.md)).

## Запуск

- `make probe-review [SCENARIOS="…"] [SERIES=<id>]` — столбец `fake`, обязательная цель.
- `make probe-review-live [HOSTS="…"] [SCENARIOS="…"] [SERIES=<id>]` — живые столбцы `github_cloud`, `gitlab_cloud`, `gitlab_ce`, `ghes`.
- `run.sh` берёт замерную блокировку `${SHELLIO_CACHE_DIR:-$HOME/.cache/shellio}/measure.lock` на весь рецепт (`lockf -k -t 300`). Не дождался — код 4 «не начат», повтор в следующей итерации. Код 1 — ошибка исполнения, код 2 — неверный вызов.
- Каталог прогона: `target/probes/review-api/<время>-<pid>/`, в нём `run.json` (серия, хеш бинаря, пары, уборка docker), каталог процесса на пару `<сценарий>-<столбец>/` с `result.json`, `done.json` в конце, `summary.json` и `summary.md` агрегатора.
- `SERIES` объединяет каталоги нескольких вызовов в одну серию. Агрегирование серии: `probe-review --aggregate --pairs "<столбец>:<сценарий> …" --out <каталог> <каталог прогона>…`.

## Ожидания

Ожидания записываются до первого прогона сценария и после результатов не меняются.

### `smoke` (стенд, столбец `fake`)

- Процесс сценария получает временный `SHELLIO_STATE_DIR`, серию и хеш бинаря, пишет `result.json` с итогом `pass` и без ошибки исполнения.
- Агрегатор собирает `summary.json` по каталогу прогона с ожидаемой парой `fake:smoke`, без пропусков, дублей и ошибок исполнения; `smoke` — строка стенда, в матрицу возможностей не входит.
- Уборка docker в `run.json`: при доступном docker — `cleaned` без оставшихся контейнеров с меткой `shellio.probe.run-id`, иначе `not_observed`.

### Столбец `fake`: общее для строк матрицы

Записано в задаче 10 до первого прогона сценариев.

- Процесс сценария поднимает `forge-fake` на `127.0.0.1:0` у себя, журнал лежит в его `SHELLIO_STATE_DIR`. Ветви одной строки (три итога, режимы мутации, пути смены head) идут в том же процессе, каждая со своим сервером и своим файлом журнала.
- Ожидание проверяется независимо от клиента: по журналу вызовов `forge-fake` (ключ, тело запроса, код) и по его состоянию, включая видимые только оракулу поля (`origin`, `from_draft`). Значения для сравнения — литералы сценария (путь, строка, сторона, SHA), а не пересчёт через модель пробы и не отчёт исполнителя.
- Число записей закреплено по ключам; число чтений не закрепляется.
- Перед проверкой журнала и сервера после потерянного ответа или сбоя сценарий ждёт квитанцию `FakeServer::wait_calls`.
- В `result.json` идут очищенный след вызовов всех ролей, число вызовов, снимок сервера до и после и журнал после переоткрытия. Нет следа, журнала или снимка — ошибка исполнения.
- Любой итог столбца `fake`, кроме `pass`, — ошибка исполнения. `bulk_publish` не вызывается ни в одной строке.

Ключи записей ниже: GitHub — `POST …/reviews` (Create review и создание `PENDING`), `POST …/events` (Submit), `POST …/replies`, GraphQL по имени поля; GitLab — `POST …/draft_notes`, `PUT …/draft_notes/:id/publish`, `PUT …/draft_notes/:id`, `DELETE …/draft_notes/:id`, `POST …/notes`, `POST …/approve`, GraphQL `mergeRequestRequestChanges`.

### `gh-local-create` (GitHub)

- Три ветви: `COMMENT`, `APPROVE`, `REQUEST_CHANGES`. В каждой два локальных черновика на новой стороне, ветвь «только локальные черновики» исполнителем.
- Записи ветви: ровно один `POST …/reviews`, в теле `event` ветви, непустой `body`, `commit_id` = head PR и `comments[]` из двух элементов с `path`, `line`, `side`; `POST …/events` и мутаций GraphQL нет.
- Сервер: один review ревьюера в состоянии `COMMENTED`, `APPROVED` или `CHANGES_REQUESTED` на head PR, происхождение `api`, два его комментария на якорях черновиков с их текстами.
- Журнал после переоткрытия: элемент `github.create_review` в `confirmed` с ID review, итог «полностью», восстановленных элементов нет.

### `gh-pending-cycle` (GitHub)

- Два черновика, ветвь «серверный `PENDING`». Первый Submit получает явный отказ 422 без применения; затем текст первого черновика меняется в журнале, и новая отправка того же `PENDING` состоит из изменения комментария и Submit.
- Записи: `POST …/reviews` 1 без `event` и без `comments`; `addPullRequestReviewThread` 2 с `pullRequestReviewId` = node ID созданного review; `updatePullRequestReviewComment` 1 с node ID первого комментария; `POST …/events` 2, тело каждого с `event` и `body` и без `comments`.
- Сервер: один review ревьюера в состоянии `COMMENTED`, в нём два комментария; у первого после изменения прежние ID и node ID и новый текст; второго review нет.
- Журнал после переоткрытия: первая отправка закрыта, Submit `failed`, итог «не отправлено»; вторая — изменение и Submit `confirmed`, итог «полностью».

### `gh-pending-foreign` (GitHub)

- До сессии сервер получает `PENDING` ревьюера от другого клиента со 101 комментарием (две страницы по 100).
- Отправка без принятия останавливается на чтении до записи ошибкой «`PENDING` существует», записей 0; найденный `PENDING` прочитан целиком: 101 ID, равные подложенным. Сценарий закрывает эту отправку.
- Явное принятие (`adopt`) и отправка с ним: записи `addPullRequestReviewThread` 1 с `pullRequestReviewId` = node ID подложенного review и `POST …/events` 1; `POST …/reviews` 0 за весь сценарий.
- Сервер: подложенный review в состоянии `COMMENTED`, его 101 комментарий с прежними текстами и один наш; других review нет.
- Журнал после переоткрытия: первая отправка закрыта без элементов в `in_flight`, `unknown` и `confirmed`; вторая «полностью», в её параметрах 101 чужой комментарий.

### `gh-anchors` (GitHub)

- Diff с удалённой, изменённой и добавленной строками. Три черновика: старая сторона (`LEFT`, удалённая строка), новая сторона (`RIGHT`, добавленная строка), диапазон на новой стороне в одном блоке. Ветвь локальных черновиков, затем ответ в треде первого комментария и resolve его треда.
- Записи: `POST …/reviews` 1, в `comments[]` три элемента с ожидаемыми `side`, `line`, `start_line`, `start_side`; `POST …/replies` 1; `resolveReviewThread` 1.
- Сервер: три комментария review с этими полями и `commit_id` = head; ответ с `in_reply_to` = ID первого комментария в том же треде; тред разрешён.
- Журнал после переоткрытия: `github.create_review` в `confirmed`, итог «полностью».

### `gh-viewed` (GitHub)

- `markFileAsViewed`, чтение состояния, `unmarkFileAsViewed`, чтение состояния.
- Записи: `markFileAsViewed` 1 и `unmarkFileAsViewed` 1 с node ID PR и путём файла.
- Сервер: после первой записи файл у ревьюера `VIEWED`, после второй отметки нет; адаптер читает `VIEWED`, затем `UNVIEWED`.
- Журнал после переоткрытия: сессия без отправок (просмотренные файлы через журнал отправки не идут).

### `gl-draft-publish` (GitLab)

- Два черновика и сводка исполнителем.
- Записи: `POST …/draft_notes` 2, `PUT …/publish` 2 — по ID из ответов на создание, `POST …/notes` 1 после последней публикации, `bulk_publish` 0.
- Сервер: черновиков нет; две заметки с позициями, связанные (`from_draft`) с созданными черновиками; одна заметка без позиции с текстом сводки.
- Журнал после переоткрытия: все элементы `confirmed`, у черновиков ID GitLab, итог «полностью».

### `gl-foreign-draft` (GitLab)

- До отправки сервер получает черновик ревьюера от другого клиента с позицией на том же diff. Один свой черновик исполнителем.
- Записи: `POST …/draft_notes` 1, `PUT …/publish` 1 только с ID своего черновика, `bulk_publish` 0.
- Сервер: подложенный черновик остался черновиком с происхождением `planted` и прежним текстом; одна опубликованная заметка из своего черновика.
- Журнал после переоткрытия: итог «полностью», ID подложенного черновика в журнале нет.

### `gl-approve-sha` (GitLab)

- Ревьюер одобряет MR исполнителем с актуальным head. Затем head сменяется, второй ревьюер с сессией на прежней ревизии: исполнитель останавливается на шаге 1 без записей, прямой вызов адаптера с устаревшим `sha` получает 409.
- Записи: `POST …/approve` 2, тело каждого `{"sha": <прежний head>}`; первый — 201, второй — 409.
- Сервер: после первого вызова ревьюер в одобривших; второй ревьюер в одобривших не появился.
- Журнал после переоткрытия: `gitlab.approve` первого ревьюера `confirmed`, итог «полностью»; отправка второго — элемент в `planned`, в `in_flight` не входил.

### `gl-request-changes` (GitLab)

- Ветви, каждая со своим сервером: мутация есть, права есть, пользователь — ревьюер MR (исполнителем); мутации нет в схеме; роль ниже Developer; ответ «не существует или нет прав»; ошибка верхнего уровня при HTTP 200; `payload.errors`; пользователь не ревьюер MR.
- Первая ветвь: `mergeRequestRequestChanges` 1, повторное чтение ревьюеров даёт `REQUESTED_CHANGES`, элемент `confirmed`.
- Мутации нет и роль ниже Developer — отказ без вызова мутации, разные итоги («нет возможности», «нет прав»). «Не существует или нет прав» — общий итог без точной причины. Ошибка верхнего уровня и `payload.errors` (в том числе «не ревьюер») — итог ошибки, отличный от двух предыдущих.
- Во всех ветвях `POST …/notes` 0: запрос изменений заметкой не подменяется. Вне первой ветви состояние ревьюера не `REQUESTED_CHANGES`.
- Журнал после переоткрытия (первая ветвь): `gitlab.request_changes` в `confirmed`, итог «полностью».

### `gl-anchors` (GitLab)

- Diff с удалённой, изменённой, добавленной и неизменённой строками. Четыре черновика: удалённая строка (только `old_line`), добавленная (только `new_line`), неизменённая (обе), диапазон в одном блоке с `line_range`. Отправка исполнителем.
- Записи: `POST …/draft_notes` 4, у каждой позиции `position_type: text` и тройка SHA = `diff_refs` MR; `PUT …/publish` 4.
- Сервер: четыре заметки с позициями этих видов, у диапазона `line_range` с концами `line_code` `<SHA-1 пути>_<старый>_<новый>` и `type`; тройка — `diff_refs`.
  - ⚠️ Дописано после первого результата (план, задача 10). Ожидание не уточняет, у каких концов есть `type`. Проверка требует `type: new` у добавленного конца и отсутствие ключа у неизменённого начала. Основание — документация Discussions API, раздел «Parameters for multiline comments»: у `position[line_range][start][type]` и `position[line_range][end][type]` в столбце Required стоит «No», описание — «Use `new` for an added line and `old` for a removed line. Omit for an unchanged line.». Draft Notes API описывает только `position[line_range]` (hash, не обязателен) без полей концов. Текст сверен по исходнику `doc/api/discussions.md` ветки `master` проекта `gitlab-org/gitlab` 2026-11-20.
- Журнал после переоткрытия: итог «полностью».

### `head-change` (GitLab)

- Сессия S на ревизии v1 с тремя черновиками: на неизменной строке и на двух строках, которые изменятся; сессия T на v1 с одним черновиком. Затем новая версия MR с новой базой и head (v2).
- Исполнитель для S останавливается на шаге 1 предупреждением о смене head, записей 0.
- Классификация: якорь на неизменной строке сохраняется, оба других устарели (строки изменились).
- «Остаться» (T): черновик создаётся и публикуется адаптером на v1, позиция с тройкой v1 принята.
- «Перепривязать» (S): сохранившийся якорь переходит на v2, один устаревший получает явный якорь v2, второй остаётся устаревшим на v1 и в отправку не входит («перейти»). Отправка исполнителем — два черновика.
- Записи: `POST …/draft_notes` 3, `PUT …/publish` 3; ответов 400 нет. Тройка каждой исходящей позиции — целиком v1 (только T) или целиком v2 (только S после смены), смешанных и чужих троек 0.
- Журнал после переоткрытия: S на v2, неперепривязанный черновик на v1 с пометкой устаревшего; T на v1.

### `journal-crash` (GitLab)

- Сбой до запроса: элемент переведён в `in_flight`, журнал закрыт без запроса. После переоткрытия элемент среди восстановленных, сверка — «не выяснено», элемент `unknown`, `POST …/draft_notes` 0.
- Сбой после принятой записи: поток исполнителя падает после доставки `POST …/draft_notes`. После квитанции сервер записал один черновик; после переоткрытия элемент среди восстановленных, сверка даёт кандидата (ID записанного черновика), элемент `unknown`, а не `confirmed`; `POST …/draft_notes` 1, повтора нет.

### `reconcile-ambiguous` (GitLab)

- Два черновика с одинаковым текстом на одной строке. Вторая публикация принята сервером, ответ потерян (502 после применения).
- Записи: `POST …/draft_notes` 2, `PUT …/publish` 2, повтора нет.
- Сверка: два кандидата, «неоднозначно»; элемент второй публикации `unknown`.
- Сервер: две заметки с одинаковым текстом и позицией.
- Журнал после переоткрытия: элемент `unknown`, итог «частично».

### `reconcile-foreign` (GitHub)

- Один черновик, ветвь локальных черновиков. Create review не применён, клиент получает 502. Другой клиент того же пользователя (свой транспорт, тот же токен) создаёт такой же review: тот же итог, текст итога и комментарий на том же якоре с тем же текстом.

- Сверка: кандидат — review второго клиента; элемент `unknown`, а не `confirmed`.
- Журнал после переоткрытия: элемент `unknown` с кандидатом, итог «частично».

### `reconcile-deleted` (GitLab)

- Один черновик создан; публикация не применена, клиент получает 502. Второй клиент того же пользователя удаляет этот черновик по ID.
- Записи: `POST …/draft_notes` 1, `PUT …/publish` 1, `DELETE …/draft_notes/:id` 1 от второго клиента; повтора публикации нет.
- Сверка: «не выяснено» (404 черновика публикацию не доказывает), кандидата нет; элемент `unknown`.
- Сервер: ни черновика, ни заметки.
- Журнал после переоткрытия: элемент публикации `unknown`, итог «частично».

### `reconcile-paged` (GitLab)

- До отправки другой клиент того же пользователя публикует 100 заметок с другими текстами. Один черновик с текстом с `\r` и хвостовыми пробелами; публикация принята сервером, ответ потерян.
- Записи: `POST …/draft_notes` 1, `PUT …/publish` 1, повтора нет.
- Сверка читает вторую страницу заметок (неполную) и находит заметку с нормализованным сервером текстом: кандидат, элемент `unknown`.
- Сервер: 101 заметка, у последней нормализованный текст без `\r` и хвостовых пробелов.
- Журнал после переоткрытия: элемент `unknown` с кандидатом, итог «частично».

### `partial` (GitLab)

- Три черновика; вторая публикация получает явный отказ 403.
- Записи: `POST …/draft_notes` 3, `PUT …/publish` 2, `bulk_publish` 0.
- Сервер: одна заметка из первого черновика, второй и третий остались черновиками.
- Журнал после переоткрытия: создания и первая публикация `confirmed`, вторая `failed`, третья `planned`; отправка закрыта, итог «частично».

### `capabilities` (GitHub и GitLab)

- GitHub: возможности по чтению — серверный `PENDING`, просмотренные файлы и resolve есть, запрошенная версия API `2022-11-28` есть в списке версий хоста, репозиторий приватный. После удаления мутации `addPullRequestReviewThread` из схемы повторное чтение даёт «серверного `PENDING` нет» на том же адресе.
- GitLab: версия и редакция из `GET /metadata`, мутация `mergeRequestRequestChanges` есть, роль Developer; после удаления мутации из схемы повторное чтение даёт «нет»; аккаунт с ролью Reporter — «права ревью нет».
- Записей 0. Версии хостов записываются в `result.json`.
- Журнал не используется: после переоткрытия сессий нет.

### `capabilities` (столбец `gitlab_ce`)

Записано в задаче 12 до первого прогона `make probe-review-live HOSTS=gitlab_ce SCENARIOS=capabilities`.

- Предусловие: GitLab CE из `spikes/probe-review-api/gitlab/pin` (`19.6.1-ce.0`, `linux/arm64`) поднят и настроен `run.sh`. Docker недоступен, в ВМ docker свободно меньше 6 ГБ, образа `linux/arm64` нет или `/-/readiness` не ответил за 15 минут — пара идёт в `skipped` с причиной (`not_run`). Ошибка настройки после подъёма — ошибка исполнения.
- Адаптер GitLab читает возможности токенами ревьюера и автора через сторожа записи с `WriteScope::Loopback`: `GET /user`, `GET /metadata`, `GET /projects/:id`, `GET /namespaces/:id`, introspection `__type(name: "Mutation")`.
- `pass`: версия по `GET /metadata` — версия закреплённого тега (`19.6.1` или `19.6.1-…`), `enterprise: false`, проект приватный, роль ревьюера Developer (`access_level` 30, как настроено), логин токена ревьюера — заведённый ревьюер, записей REST нет, сторож не отказал.
- Расхождение с этими фактами стенда, отказ транспорта, 5xx и отказ сторожа — ошибка исполнения: стенд не совпал с закреплением или настройкой. Прочий отказ чтения (ошибка GraphQL, ответ не той формы, 4xx) — `fail` «возможности не определились чтением».
- Наблюдения, не условие итога: наличие `mergeRequestRequestChanges` в схеме CE (гипотеза: есть, ADR-0015 и документация GraphQL не помечают мутацию как EE), роль автора в своём проекте (гипотеза: Owner, 50), тариф (гипотеза: не виден, у CE поля `plan` нет), способ получения токена root (OAuth password grant или `gitlab-rails runner`). Версия хоста идёт в `host.version` клетки.

Записано в задаче 13 до первого прогона живых клеток, кроме `capabilities` × `gitlab_ce` (задача 12).

- Клетки по столбцам. Строки GitHub (`gh-*`, `reconcile-foreign`) идут в `github_cloud` и `ghes`, строки GitLab (`gl-*`, `head-change`, `journal-crash`, `reconcile-ambiguous`, `reconcile-deleted`, `reconcile-paged`, `partial`) — в `gitlab_cloud` и `gitlab_ce`, `capabilities` — во всех четырёх живых столбцах. Провайдер строки тот же, что в столбце `fake`. Строка провайдера другого хоста в столбце — «—» матрицы, а не клетка.
- `ghes`: каждая клетка — `not_run` «нет инсталляции GitHub Enterprise Server», передача P4.1; процесс сценария в сеть не ходит.
- `github_cloud` и `gitlab_cloud`: нет `sandbox.toml` — `not_run` «нет sandbox.toml», нет таблицы хоста — `not_run` «нет хоста <столбец> в sandbox.toml», нет токена роли — `not_run` «нет автора: …» или «нет ревьюера: …», `security` ждёт дольше 10 с — `not_run` «Keychain ждёт диалога». Испорченный `sandbox.toml` — ошибка исполнения. Ошибка доступа из-за прав токена — `not_run` «токен без прав».
- `gitlab_ce`: не поднявшийся GitLab — пары в `skipped` (`not_run` с причиной), как у `capabilities`. Ошибка настройки — ошибка исполнения.
- Каждая клетка открывает свои ветки и PR/MR (задача 11) и убирает их в любом случае. Не подтверждённое чтением после уборки — `leftovers` в `result.json`. Отказ сторожа записи (`Guarded::refusal` или непустой `refused_writes`) — ошибка исполнения клетки.
- Оракул живой клетки — независимое чтение автором того, что стало видимым в PR/MR, чтение ревьюером своих черновиков и `PENDING`, и очищенный след (ключ, тело, код каждой записи). Видимых только оракулу полей `forge-fake` (`origin`, `from_draft`, `planted`) у живого хоста нет; связь заметки с черновиком GitLab наблюдается только косвенно (текст, позиция, исчезновение черновика) и записывается как наблюдение.
- Инъекции. Серверных отказов (5xx после применения, отказ по ключу, молчание, лимит) живой хост не даёт: ветви, которым они нужны, получают `not_run` «инъекция недоступна на живом хосте». Клиентские сбои воспроизводятся на живом хосте, потому что сервер в них настоящий: сбой до запроса, паника потока после доставки запроса, потерянный ответ (запрос доставлен и ответ получен, обёртка транспорта отдаёт движку таймаут), недошедший запрос (обёртка не отправляет запрос и отдаёт движку таймаут — «мог дойти»). Серверная запись после потерянного ответа засчитывается, только если наблюдена чтением; не наблюдена — клетка `not_run`.
- Естественный таймаут живого хоста засчитывается вместо инъекции, только если факт серверной записи наблюдён чтением, иначе клетка `not_run`.
- «Браузерный черновик» создаёт второй API-клиент отдельным процессом пробы от имени ревьюера (токен — окружением процесса, не аргументом). Клетка «создан в браузере» — `not_run` «браузер не наблюдался» отдельной записью отчёта для каждого облачного столбца и `gitlab_ce`, а не сценарием: у каждого сценария матрицы есть столбец `fake` с итогом `pass`.
- Итог клетки: `pass` — все проверки клетки прошли; `fail` — опровергнута гипотеза ADR-0015 о хосте (отрицательный вывод с передачей P4.1); `absent` — у проверенной роли или редакции нет возможности (с версией и тарифом); `not_run` — не наблюдалось, причина записана. Отказ транспорта без ответа на чтении, 5xx на чтении, потеря следа, журнала или снимка — ошибка исполнения.
- Сверка контракта `forge-fake`: поля ответов, которые читает адаптер, сравниваются с теми же полями в очищенном следе живой клетки. Расхождение — запись в отчёт, вход P4.1; итог клетки оно не меняет и оракул `forge-fake` не правит.

### Живые клетки GitHub (`github_cloud`)

- `gh-local-create`: три ветви на одном PR — `COMMENT`, `APPROVE`, `REQUEST_CHANGES` от ревьюера, по два локальных черновика на новой стороне. Записи ветви: один `POST …/reviews` с `event`, `body`, `commit_id` = head и двумя `comments[]`. Автор читает три review ревьюера в состояниях `COMMENTED`, `APPROVED`, `CHANGES_REQUESTED` на head и их комментарии на якорях черновиков. Журнал: `github.create_review` `confirmed`, итог «полностью».
- `gh-pending-cycle`: создание `PENDING` без `event`, два треда `addPullRequestReviewThread`, изменение первого комментария, Submit без `comments[]`. Ветвь «первый Submit получает 422» — `not_run` «инъекция недоступна на живом хосте». До Submit автор `PENDING` не видит; после — один review `COMMENTED` с двумя комментариями, ID и node ID первого прежние, текст новый.
- `gh-pending-foreign`: второй клиент отдельным процессом создаёт `PENDING` ревьюера со 101 комментарием одним `POST …/reviews` без `event`. Отправка без принятия останавливается на чтении до записи («`PENDING` существует»), прочитан 101 ID; после `adopt` — один тред и Submit. Гипотеза для живого хоста: второй `PENDING` того же пользователя GitHub не создаёт (422) — наблюдение записывается.
- `gh-anchors`: старая сторона (удалённая строка 03), новая (добавленная 24a), диапазон на новой стороне в одном блоке; затем ответ в треде и resolve. Node ID треда для resolve берётся из чтения тредов PR автором (GraphQL `reviewThreads`), а не из `forge-fake`. Автор читает поля `side`, `line`, `start_line`, `start_side`, `in_reply_to` и `isResolved`.
- `gh-viewed`: `markFileAsViewed`, чтение `viewerViewedState` `VIEWED`, `unmarkFileAsViewed`, чтение `UNVIEWED`.
- `reconcile-foreign`: недошедший Create review (клиентская инъекция) и такой же review второго клиента отдельным процессом. Сверка — кандидат, элемент `unknown`, а не `confirmed`; записей пробы `POST …/reviews` 0.
- `capabilities`: версия API `2022-11-28` в `GET /versions` (404 у github.com — «версии не читаются», не отказ), серверный `PENDING`, просмотренные файлы и resolve в схеме, репозиторий приватный, записей 0. Гипотеза: всё есть, `pass`.

### Живые клетки GitLab (`gitlab_cloud`, `gitlab_ce`)

Фикстура клетки (задача 11): 30 строк, у ветки клетки строка 03 удалена, 05 изменена, после 24 добавлены 24a и 24b. Ревьюер назначен reviewer у MR. `diff_refs` и версии нового MR GitLab заполняет асинхронно (документация Merge requests API, «Empty API fields for new merge requests»): каждая клетка до первого снимка опрашивает MR, пока `diff_refs` не заполнены и среди версий нет той же тройки, с крайним сроком 120 с; не дождался — клетка `not_run` «MR не готов за 120 с», уборка идёт как обычно. Тот же опрос до нового `head_sha` идёт после каждой смены head.

- `gl-draft-publish`: два черновика и сводка исполнителем. Записи: `POST …/draft_notes` 2, `PUT …/publish` 2 по ID из ответов, `POST …/notes` 1, `bulk_publish` 0. Ревьюер после отправки не видит своих черновиков; автор читает две заметки с позициями и текстами черновиков и одну заметку сводки.
- `gl-foreign-draft`: второй клиент отдельным процессом создаёт черновик ревьюера на том же diff. Один свой черновик исполнителем. Записи пробы: `POST …/draft_notes` 1, `PUT …/publish` 1 только со своим ID, `bulk_publish` 0. Ревьюер видит черновик второго клиента с прежним текстом; автор видит одну заметку и не видит текста чужого черновика.
- `gl-approve-sha`: ревьюер одобряет с актуальным head (2xx, автор видит ревьюера в одобривших), снимает одобрение, автор меняет head, сценарий опрашивает MR до нового `head_sha` (крайний срок 120 с, не дождался — `not_run` «MR не обновил diff_refs за 120 с»: иначе устаревший `sha` мог бы прийти раньше, чем MR учтёт коммит), ревьюер одобряет с прежним `sha`. Гипотеза: 409, ревьюера в одобривших нет. Целевая ветка клетки в это время не меняется. Отказ одобрения по правам или тарифу — `absent` с версией и тарифом.
- `gl-request-changes`: ревьюер вызывает `mergeRequestRequestChanges` исполнителем, повторное чтение даёт `REQUESTED_CHANGES` — `pass`. Гипотеза для CE и gitlab.com Free: мутация есть и работает. Отказ с признаком тарифа или лицензии — `absent`; другой отказ — `fail` с текстом ответа. Наблюдения, не условие итога: тот же вызов токеном автора (не ревьюер MR) и различим ли его ответ. Ветви «мутации нет в схеме» и «ошибка при HTTP 200» — `not_run` «инъекция недоступна на живом хосте». Во всех ветвях `POST …/notes` 0.
- `gl-anchors`: пять черновиков — удалённая строка 03 (только `old_line`), добавленная 24a (только `new_line`), неизменённая строка 01 (обе), диапазон 03–04 (удалённое начало, неизменённый конец) и диапазон 24–24a (неизменённое начало, добавленный конец), каждый в одном блоке с `line_range`. Записи: `POST …/draft_notes` 5 с `position_type: text` и тройкой `diff_refs`, `PUT …/publish` 5. Автор читает пять заметок с этими позициями. Наблюдения рядом с ожиданием (итог не меняют): `line_code` концов `line_range`, который вернул GitLab, против вычисленного моделью (`<SHA-1 пути>_<старый>_<новый>`, счётчики по разбору GitLab; документацией подтверждён только пример `_10_10`); `type` концов, который GitLab хранит и возвращает, против таблицы «Parameters for multiline comments» (у неизменённой строки не передаётся) и примера ответа той же страницы (`type: old` у неизменённого конца).
- `head-change`: сессия S с черновиками на строке 05 (первый блок) и на строке 27 (контекст второго блока), сессия T с одним черновиком. Автор меняет head коммитом, меняющим строку 27 (`Fixture::Moved`). `diff_refs` и версии MR обновляются асинхронно: сценарий опрашивает MR до нового `head_sha` с крайним сроком 120 с; не дождался — `not_run` «MR не обновил diff_refs за 120 с». Исполнитель S останавливается на шаге 1 без записей; черновик в первом блоке сохраняется, черновик на строке 27 устаревает; T публикуется на v1 адаптером; S перепривязывает устаревший явным якорем v2 и отправляет два черновика. Тройка каждой исходящей позиции — целиком v1 или целиком v2. Гипотеза: позиции на v1 после смены head GitLab принимает (старая версия MR существует).
- `journal-crash`: сбой до запроса (элемент `in_flight`, журнал закрыт без запроса) — после переоткрытия `unknown`, сверка «не выяснено», `POST …/draft_notes` 0; паника потока после доставки `POST …/draft_notes` — ревьюер видит один записанный черновик, сверка даёт кандидата, элемент `unknown`, повтора нет.
- `reconcile-ambiguous`: два черновика с одинаковым текстом на одной строке, ответ на вторую публикацию потерян (клиентская инъекция). Гипотеза: автор видит две одинаковые заметки, сверка «неоднозначно», элемент `unknown`, повтора нет. Публикация не наблюдена чтением — `not_run`.
- `reconcile-deleted`: публикация не дошла (клиентская инъекция), второй клиент отдельным процессом удаляет черновик по ID. Сверка «не выяснено», элемент `unknown`, повторов записи 0; автор не видит ни черновика, ни заметки.
- `reconcile-paged`: второй клиент публикует 100 заметок с другими текстами (вторая страница по 100), один черновик с `\r` и хвостовыми пробелами, ответ на публикацию потерян. Сверка находит на второй странице заметку с нормализованным текстом: кандидат, `unknown`. Нормализацию тела живым хостом сценарий записывает наблюдением; если хост не нормализует, а сверка всё равно находит кандидата — `pass` с наблюдением.
- `partial`: три черновика; второй до публикации удаляет второй клиент отдельным процессом, поэтому публикация второго получает настоящий отказ хоста (гипотеза: 404). Журнал: создания и первая публикация `confirmed`, вторая `failed`, третья `planned`, отправка закрыта, итог «частично»; автор видит одну заметку, третий черновик остаётся у ревьюера. Отказ 403 по ключу, как в `fake`, на живом хосте не воспроизводится.
- `capabilities` × `gitlab_cloud`: как у `gitlab_ce`, но факты песочницы вместо фактов стенда: проект приватный, роль ревьюера не ниже Developer, редакция и тариф записываются; тариф из пространства имён, иначе из `GET /metadata`.

## Транспорт и след

Задача 4, решения исполнителя вне правил плана (записаны в плане с ⚠️).

- Ответ HTTP с любым кодом — ответ: тело и заголовки 409, 403 и отказа по лимиту доходят до адаптера. Отказ транспорта бывает `not_sent` (запрос доказуемо не ушёл: неверный адрес, хост не найден, таймаут разрешения имени или соединения с рукопожатием TLS, отклонённое соединение, ошибка TLS) или «мог дойти» (`timeout`, `disconnected`, `malformed`). Только `not_sent` позволяет считать запись не принятой; остальное ведёт элемент в `unknown` и к сверке. Если заголовки ответа пришли, а тело оборвалось, код сохраняется. Виды отказов `ureq` 3.5.2 проверены на loopback: закрытый порт — `not_sent`, сервер прочитал запрос и молчит — `timeout`, сервер прочитал запрос и закрыл соединение — `disconnected`, ответ не по HTTP — `malformed`, сервер без TLS на адресе `https` — отказ без паники. `Error::NativeTls` приходит только из рукопожатия (после него `ureq` переводит ошибки TLS-потока в `Io`), `Error::Http` и прочие варианты считаются дошедшими.
- Перенаправления не выполняются, прокси из окружения не берётся, `ureq` запросы не повторяет. Записи идут агентом без пула соединений: устаревшее соединение из пула оборвалось бы после отправки и дало ложный `unknown`.
- Токен держит транспорт, запрос его не несёт. След пишет каждый вызов, в том числе отказавший: роль, метод, путь, тело запроса, код, вид отказа, тело ответа, заголовки лимитов (`x-ratelimit-*`, `ratelimit-*`, `retry-after`), длительность. Заголовки запроса в след не входят. На диск идёт только очищенная запись.
- Очиститель заменяет известные значения (токены и пароли, логины ролей, пути репозиториев и их пространства имён, адрес локального GitLab) без учёта регистра и в формах `%2F`, `%3A`, `%40`, `\/`, образцы (префиксы `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`, `glpat-` и другие префиксы GitLab, адреса почты) и значения секретных ключей (`access_token`, `refresh_token`, `token`, `password` и подобных) в JSON, строке запроса и теле формы. Метки: `<token>`, `<email>`, `<repo>`, `<namespace>`, `<gitlab-ce>`, `<author>`, `<reviewer>`. `github.com` и `gitlab.com` остаются.
- Тело ответа с полной интроспекцией `data.__schema` идёт в след сводкой вместо тела (задача 12, после первого живого прогона, где оно весило 9,4 МБ на вызов, а `result.json` — около 19 МБ): ключи верхнего уровня, размер тела в байтах, число типов, имя и число полей типа мутаций и наличие каждой мутации, которую читают адаптеры GitHub и GitLab. В сводке только имена схемы и числа. Короткие ответы, в том числе `__type`, идут телом через очиститель, как раньше. Сырой вызов в памяти для оракулов не меняется.

## forge-fake

Задачи 5 (GitHub) и 6 (GitLab). `forge-fake` — оракул пробы на `127.0.0.1:0` (`tiny_http`), а не продуктовый сервер. Расхождения с живыми хостами — вход P4.1.

Квитанция сервера — `FakeServer::wait_calls(n, срок)`: вызов записан в журнал после обработчика провайдера и парковки молчащего запроса. Срок клиента не означает, что сервер закончил обработку, поэтому проверки журнала, парковки и серверного состояния после отказа клиента ждут квитанцию, а не таймаут.

### Метод серверного `PENDING` GitHub

Решение исполнителя по правилу плана. У REST нет способа добавить комментарий в существующий `PENDING` review: у `POST /repos/{owner}/{repo}/pulls/{n}/comments` нет параметра review (тело: `body`, `commit_id`, `path`, `line`, `side`, `start_line`, `start_side`, `in_reply_to`, `subject_type`, устаревающий `position`), и документация `PENDING` при нём не упоминает. Поэтому выбран GraphQL:

- добавление — `addPullRequestReviewThread` с `pullRequestReviewId` (node ID review из ответа REST Create);
- обновление — `updatePullRequestReviewComment` с node ID комментария, `databaseId` сохраняется;
- создание `PENDING` — REST Create review без `event`, Submit — REST `POST …/reviews/{review_id}/events` с числовым ID.

Отвергнуты: REST `POST …/pulls/{n}/comments` (не привязывается к review), REST `PATCH …/pulls/comments/{id}` (правило связывает добавление и обновление одним методом), GraphQL `addPullRequestReviewComment` (документация выводит его в пользу `addPullRequestReviewThread` и `addPullRequestReviewThreadReply`).

### Подмножество API

- REST: `GET /user`, `GET /versions` (`["2022-11-28"]`), `GET /repos/{o}/{r}` (`private`, `visibility`, `permissions`), `GET …/pulls/{n}` (head и base SHA, `node_id`), `GET …/pulls/{n}/commits`, `GET …/pulls/{n}/files` (`patch`), reviews — список, Create, чтение, `PUT` текста, `DELETE` `PENDING`, Submit, комментарии review; опубликованные комментарии PR; ответ в треде (`…/comments/{id}/replies`, 201). Списки — `per_page` по умолчанию 30, не больше 100, `page`, заголовок `Link`.
- GraphQL `POST /graphql`: introspection `__type(name: "Mutation")` (поля — только реализованные мутации; имя типа из `variables`), `markFileAsViewed`, `unmarkFileAsViewed`, `addPullRequestReviewThread`, `updatePullRequestReviewComment`, `resolveReviewThread`, `unresolveReviewThread`, `node(id:)` для `PullRequest` (файлы с `viewerViewedState`, треды), `PullRequestReview` (состав) и `PullRequestReviewThread`.
- Видимость: `PENDING` и его комментарии видит только владелец — в списке reviews, при чтении review и его комментариев, в тредах GraphQL; список комментариев PR содержит только опубликованные.
- Якорь проверяется по `patch` коммита review собственным разбором блоков (независимо от модели пробы): строка на стороне, начало диапазона в том же блоке и раньше конца на той же стороне. После смены head старый `commit_id` из истории PR остаётся допустимым и проверяется по своему diff. Просмотренный файл, чей `patch` изменился, становится `DISMISSED`.
- Заголовки лимитов `x-ratelimit-*` на каждом ответе. Отказ по лимиту — 403 с `x-ratelimit-remaining: 0`.
- Управление сценарием: подложенный `PENDING` другого клиента того же пользователя (в обход HTTP, происхождение `planted` видят только оракулы), смена head, хост без мутации (`remove_mutation`: introspection её не показывает, вызов — `undefinedField`), правила отказов, журнал вызовов и счётчики по ключу `МЕТОД /шаблон` или `graphql <поле>`, снимок серверного состояния для `result.json`.
- Отказы: запись применяется или нет, клиент видит код, отказ по лимиту или молчание. Молчание паркует запрос (у `tiny_http` нет закрытия соединения без ответа, а `Drop` запроса отвечает 500), клиент получает `timeout` по своему сроку.

### Предположения оракула без опоры на документацию

Проверяются живыми клетками, расхождение — передача P4.1.

- Второй `PENDING` того же пользователя в том же PR — 422 «User can only have one pending review per pull request», в том числе для Create с `event`.
- Submit с `comments[]` — 422 (документация `comments[]` у Submit не перечисляет; живой хост может поле молча игнорировать).
- `body` обязателен для `COMMENT` и `REQUEST_CHANGES` и при Submit (документация требует его только у Create).
- Автор PR не может `APPROVE` и `REQUEST_CHANGES` свой PR — 422.
- Тексты ошибок 422 (`Line could not be resolved` и другие) — приближённые.
- Поля входов `UnmarkFileAsViewedInput` и `ResolveReviewThreadInput` не сверены со справочником GraphQL.

### Ограничения оракула

- GraphQL не разбирается целиком: аргументы только из `variables`, ответ полной фиксированной формы без учёта выбранных полей, соединения одной страницей без курсоров.
- Позиции комментариев при смене head не пересчитываются, `isOutdated` всегда `false`, `diff_hunk` нет.
- REST-комментарий вне review и ответ на комментарий `PENDING` не моделируются (404 и 422).
- `addPullRequestReviewThread` только с `pullRequestReviewId`, комментарии к файлу (`subject_type: file`) и `position` отвергаются.

### GitLab: подмножество API

Пути — `/api/v4/…` и `/api/graphql`. Проект адресуется числовым ID или путём `группа%2Fпроект`. Токен — `PRIVATE-TOKEN` или `Authorization: Bearer`. Тело запроса — только JSON.

- REST: `GET /user`, `/version`, `/metadata` (версия, `enterprise`), `GET /projects/:id` (`visibility`, `permissions.project_access.access_level`), MR (`sha`, `diff_refs`, ревьюеры), версии MR (новые первыми) и одна версия с `diffs`, `diffs` последней версии, ревьюеры со `state`.
- Draft Notes: список (только свои черновики), чтение, создание (201), изменение (200, позиция без `position` сохраняется), удаление (204), публикация одного (204 без тела), `bulk_publish` (204, с `note` и `reviewer_state`). `bulk_publish` публикует все черновики вызывающего, в том числе подложенные, и считается в журнале вызовов.
- Notes и Discussions: заметки MR (по умолчанию новые первыми, `sort=asc`), создание заметки (201), треды (список, чтение, создание с позицией, 201), ответ в тред (201), `PUT …/discussions/:id` с `resolved` (200, Developer и выше или автор треда).
- Approvals: `approve` с `sha` (201 с состоянием одобрения; несовпадение — 409), `unapprove` (201), `GET …/approvals`. После смены целевой ветки без нового head `approve` с `sha` даёт 409 до следующего коммита исходной ветки, без `sha` проходит (документация Approvals).
- GraphQL: `__type(name: "Mutation")` (introspection полей), `currentUser`, `project(fullPath) { mergeRequest(iid) { reviewers { … mergeRequestInteraction { reviewState } } approvedBy } }`, `mergeRequestRequestChanges(input: {projectPath, iid})` с `errors` и `mergeRequest`.
- Режимы `mergeRequestRequestChanges` — состояние сервера: есть (итог по правам и назначению ревьюером), нет в схеме (introspection без поля, вызов — `undefinedField` без `data`), «не существует или нет прав» при любых правах, ошибка верхнего уровня при HTTP 200 (`data.<поле>: null`), `payload.errors` при HTTP 200. Нет доступа к проекту, роль ниже Developer и несуществующий MR дают один и тот же ответ «does not exist or you don't have permission».
- Позиция `text` принимается, только если тройка SHA равна тройке одной из версий MR; пути и строки проверяются по diff этой версии собственным разбором со счётчиками GitLab: добавленная строка — только `new_line`, удалённая — только `old_line`, неизменённая — обе. `line_range` — `line_code` (`<SHA-1 нового пути>_<старый>_<новый>`), `type` и номера каждого конца, конец совпадает со строкой позиции, начало не позже конца в том же блоке.
- Нормализация тела по документации Notes API: без `\r`, без хвостовых пробелов и переводов строки в конце тела. Строки quick actions из короткого списка снимаются при публикации черновика и при создании заметки, сами действия не исполняются. Тело, пустое после нормализации, — 400.
- Списки: `per_page` по умолчанию 20, не больше 100, заголовки `x-page`, `x-per-page`, `x-total`, `x-total-pages`, `x-next-page`, `x-prev-page`, `link` с прочими параметрами запроса. Отказ по лимиту — 429 с `ratelimit-*` и `retry-after`, обычный ответ несёт `ratelimit-*`.
- Управление сценарием: черновик другого клиента того же пользователя (`plant_draft`), удаление черновика другим клиентом (`remove_draft`), заметка или тред, опубликованные другим клиентом (`plant_discussion`), новый head (`push_head`), новый head с новой базой (`push_version`), смена целевой ветки (`move_target`), режим `mergeRequestRequestChanges`, ревьюер MR. Частичный отказ публикации и «принято, ответ потерян» задаются общими правилами отказов (`skip`, `after_apply`). Связь опубликованной заметки с черновиком (`from_draft`) и происхождение видят только оракулы.

### GitLab: предположения оракула без опоры на документацию

Проверяются живыми клетками, расхождение — передача P4.1.

- Коды Draft Notes API в документации не указаны: создание 201, изменение 200, удаление, публикация одного и `bulk_publish` — 204 без тела. Публикация не возвращает ни заметку, ни её ID.
- Позиция с тройкой SHA, не равной ни одной версии MR, — 400 (документация говорит только о возможной ошибке #296829). Неизменённая строка только с одним номером и `line_range` через границу блока — 400.
- Отказ `approve` из-за прав, авторства MR или повторного одобрения — 401 `401 Unauthorized`; текст 409 — `SHA does not match HEAD of source branch: <head>`. Автор MR одобрить свой MR не может.
- `mergeRequestRequestChanges` требует роли Developer и выше (иначе ответ «не существует или нет прав»), пользователь не ревьюер MR получает `payload.errors` `Reviewer not found`, успешный запрос снимает одобрение пользователя. Поля входа и ответа мутации не сверены дословно со справочником GraphQL.
- Нормализация хвостовых пробелов применяется к концу тела, а не к каждой строке; quick actions черновика остаются в черновике до публикации; список quick actions сокращён.
- У конца `line_range` на неизменённой строке `type` нет (`null`), у добавленной — `new`, у удалённой — `old`; так же строит позицию модель пробы. Так велит документация Discussions API (раздел «Parameters for multiline comments»): `type` не обязателен, «Use `new` for an added line and `old` for a removed line. Omit for an unchanged line.». Пример ответа «List all merge request discussion items» в той же документации ей противоречит: конец с `old_line: 11` и `new_line: 11` (неизменённая строка) имеет `type: old`, а начало с `type: new` и `old_line: null` — `line_code` `…_10_10`. Какой `type` GitLab хранит и возвращает у неизменённой строки, проверяют живые клетки (задача 13).
- Список черновиков постраничен, как прочие списки.

### GitLab: ограничения оракула

- GraphQL не разбирается целиком: корневое поле из текста запроса, аргументы из `variables` (имя типа `__type` — также из текста), ответ полной фиксированной формы.
- Расхождение с живым GitLab CE 19.6.1 (первый живой прогон): на `__type(name: $name)` `forge-fake` отвечает `data.__type` по спецификации GraphQL, а CE ответил полной интроспекцией `data.__schema`; `GET /metadata` `forge-fake` не содержит `plan`, а CE отдаёт `plan: "free"`. Оракул не меняется: адаптер разбирает обе формы и оба источника тарифа, тесты встроенного транспорта проверяют форму CE. Вход P4.1.
- Позиции `image` и `file`, ответ в тред с позицией, ответ на отдельную заметку и исполнение quick actions не моделируются. Позиции заметок при смене head не пересчитываются.
- Тело формы и параметры строки запроса не принимаются, кроме `sha` у `approve`.

## Адаптер GitHub

Задача 7, `src/github/`. Адаптер строит запросы и разбирает ответы, журнал не трогает. Каждый метод записи — ровно один запрос, итог его ошибки для журнала задаёт `ApiError::write_fate`; чтения идут отдельными методами, их ошибки к итогу записи не относятся. Решения исполнителя вне правил плана записаны в плане с ⚠️.

- Возможности определяются чтением: `GET /user` (логин, `plan.name`, если тариф виден токену, `x-oauth-scopes` classic-токена), `GET /versions` (404 — хост версии не сообщает), `GET /repos/{o}/{r}` (`private`, `permissions.push`) и introspection `__type(name: "Mutation")`. Ветвь «только локальные черновики» есть всегда (REST), серверный `PENDING` — при `addPullRequestReviewThread` и `updatePullRequestReviewComment`, просмотренные файлы — при `markFileAsViewed` и `unmarkFileAsViewed`, resolve — при `resolveReviewThread` и `unresolveReviewThread`. Адреса REST и GraphQL — настройка, а не вывод из имени хоста.
- Версия API: каждый запрос REST несёт `X-GitHub-Api-Version: 2022-11-28` (по документации это и версия по умолчанию, неподдерживаемая версия даёт 410), записываются запрошенная версия и список `GET /versions`. Заголовок выбранной версии в ответе документация не описывает, адаптер его не читает.
- Ревизия GitHub: тройки SHA у PR нет, поэтому `base.sha` идёт в `base_sha` и `start_sha`, `head.sha` — в `head_sha`, все из одного ответа `GET …/pulls/{n}`. Снимок читает PR до и после списка файлов: ревизия сменилась — ошибка `HeadMoved`, файлы другого head с ревизией не смешиваются.
- `commit_id` ревизии сессии стоит на уровне review в Create обеих ветвей; в `comments[]` его нет. Без него сервер взял бы текущий head, то есть смешал бы свежий head со старыми якорями. GraphQL-тред наследует commit review, поэтому в `PENDING` на другом commit (в том числе в принятый чужой) комментарий не добавляется.
- Существующий `PENDING`: запись обеих ветвей требует значения `NoPending`, которое выдаёт только отдельное чтение `check_no_pending` — список reviews и состав найденного `PENDING` по всем страницам (`per_page=100`, страницу строит адаптер, `Link` — только признак следующей: транспорт подставляет токен в любой адрес). Найденный `PENDING` возвращается ошибкой `PendingExists` без единой записи и идёт в работу только через `ExistingPending::adopt`. Чтение вынесено из метода записи, чтобы отметка `in_flight` журнала охватывала только сам запрос записи: сбой чтения не оставляет неразрешимого `unknown`. Submit принятого отправляет весь состав, выборочной отправки нет; изменять можно только комментарии, добавленные адаптером.
- Ответ в треде и resolve — отдельные вызовы для строки `gh-anchors`: REST `…/comments/{id}/replies` (публикуется сразу отдельным review) и GraphQL `resolveReviewThread`, `unresolveReviewThread`. Черновик-ответ ни в Create review, ни в `PENDING` не входит: адаптер отвергает его до запросов.
- Пары ID: у review числовой ID (REST Submit и чтение) и node ID (`pullRequestReviewId`), у комментария node ID (изменение) и `databaseId`. Чтение `…/reviews/{id}` восстанавливает node ID по числовому. Изменение комментария с другим ID в ответе — неожиданный ответ.
- Итог записи. Не принята: запрос не ушёл, ответ 4xx, явный отказ по лимиту, ошибка GraphQL известного типа (разбор, схема, переменные, `NOT_FOUND`, `FORBIDDEN`, `UNPROCESSABLE`, `INSUFFICIENT_SCOPES`). Неизвестен: отказ транспорта после отправки, 5xx, ошибка GraphQL без известного типа, успешный ответ без ожидаемых полей или с другим итогом (состояние, commit, ID review или комментария, `thread: null`).
- Отказ по лимиту по документации: REST — 403 или 429 с `x-ratelimit-remaining: 0`, вторичный лимит — 403 или 429 с сообщением о нём или `retry-after`; GraphQL — HTTP 200 с ошибкой и `x-ratelimit-remaining: 0`. Тот же заголовок со значением 0 приходит и в ответе запроса, потратившего последнее очко, поэтому отказом по лимиту считается только ошибка с явным признаком (сообщение о лимите при `x-ratelimit-remaining: 0` или тип `RATE_LIMITED`); прочая ошибка классифицируется обычным порядком, без типа — итог неизвестен.

Предположения адаптера без опоры на документацию, проверяются живыми клетками:

- Тип ошибки GraphQL `RATE_LIMITED` тоже считается отказом по лимиту; сообщение ошибки лимита GraphQL содержит слова «rate limit».
- Список типов ошибок GraphQL, после которых мутация точно не исполнялась, собран по `type` и `extensions.code`; ошибка без типа считается неизвестным итогом.
- `addPullRequestReviewThread` возвращает тред с первым комментарием и его `pullRequestReview`; поля входов `UnmarkFileAsViewedInput`, `UpdatePullRequestReviewCommentInput` и `ResolveReviewThreadInput` дословно со справочником не сверены (входы `MarkFileAsViewedInput` и `AddPullRequestReviewThreadInput` сверены).

## Адаптер GitLab

Задача 8, `src/gitlab/`. Адаптер строит запросы и разбирает ответы, журнал не трогает; итог ошибки записи для журнала задаёт `ApiError::write_fate`. Перечисление итога записи (`WriteFate`) общее с адаптером GitHub, ошибки у каждого свои. Решения исполнителя вне правил плана записаны в плане с ⚠️.

- Адреса — `<корень>/api/v4` и `<корень>/api/graphql`, корень инсталляции — настройка. Проект в REST — один сегмент пути с кодированием `/` (подгруппы входят в путь), в GraphQL — путь как есть; `iid` в переменных GraphQL — строка.
- Возможности определяются чтением: `GET /user` (`username`), `GET /metadata` (версия, ревизия, `enterprise`; 404 у старых версий — `GET /version`, редакция неизвестна), `GET /projects/:id` (`visibility`, роль — большая из `project_access` и `group_access`), `GET /namespaces/:id` (`plan`, если тариф виден токену; 403 и 404 — не виден), introspection `__type(name: "Mutation")` (наличие `mergeRequestRequestChanges`). Имя профиля не записывается.
- После первого живого прогона (задача 12): если хост на `__type` ответил полной интроспекцией `data.__schema`, мутации берутся из типа `mutationType.name` в `__schema.types`; форма ответа (`__type` или `__schema`) записывается в возможности (`introspection`). Ответ без `__type` и без `__schema`, схема без `mutationType.name`, без такого типа или без его `fields` — `Unexpected`, а не «мутации нет». Тариф берётся из `plan` пространства имён, а если оно его не даёт — из `plan` ответа `GET /metadata` (CE 19.6.1 отдаёт `free`), источник записывается (`plan_source`: `namespace` или `metadata`). Отдельного чтения для тарифа нет: `GET /metadata` уже читается ради версии. `introspect_literal` отправляет `{ __type(name: "Mutation") { fields { name } } }` без `variables` и возвращает форму ответа, размер тела и наличие мутации: это наблюдение формы, в возможности оно не разбирается.
- Снимок MR: ревизия — `diff_refs`, diff — версии MR с той же тройкой (`base_commit_sha`, `start_commit_sha`, `head_commit_sha`) из `GET …/versions/:id`. Версии с этой тройкой нет — ошибка, а не ближайшая версия. Версия неизменна, поэтому файлы другого head с ревизией не смешиваются без повторного чтения MR.
- Черновики: позицию строит только сессия из своей ревизии целиком. Адаптер сверяет с ревизией сессии тройку исходящей позиции и то, что записал сервер: тройку, пути и строки; ответ с другой тройкой или строкой — неожиданный, итог неизвестен. Ответ в треде — `in_reply_to_discussion_id`, `resolve_discussion` допустим только у ответа. Изменение сохраняет ID черновика и берёт позицию из текущей ревизии сессии.
- Публикуется только `KnownDraft`: его выдаёт создание черновика этим клиентом или явный конструктор `KnownDraft::recorded` для ID из своего журнала. Чтение списка черновиков возвращает данные, а не `KnownDraft`: в списке есть черновики того же пользователя из другого клиента. Публикация — `PUT …/draft_notes/:id/publish` без тела, ответ 204 без тела; успешный ответ публикацию с заметкой не связывает, подтверждение — дело сверки (задача 9). 404 — обычный отказ, вывода «уже опубликован» адаптер не делает.
- Массовой публикации в адаптере нет: тест ищет её имя в исходниках адаптера, тесты встроенного транспорта проверяют точный набор запросов (только ID известных черновиков), сквозной тест против `forge-fake` — счётчик её вызовов 0 и подложенный черновик, оставшийся черновиком. Сводка — отдельная заметка `POST …/notes` после публикации.
- `approve`: тело всегда `{"sha": <head ревизии сессии>}`, без `sha` запрос не отправляется. 409 — `ShaRejected` без толкования причины: по документации он бывает и при том же head после смены целевой ветки (воспроизведено против `forge-fake`). 401 остаётся кодом без толкования «нет прав». Ответ без собственного одобрения токена (`user_has_approved`, без него — `approved_by`) — неожиданный.
- Запрос изменений. Без мутации по чтению возможностей — `Absent`, при роли ниже Developer — `NotPermitted`, в обоих случаях запросов нет. Ответы на вызов: `undefinedField` — `Absent`; ошибка «does not exist or you don't have permission» — `Unavailable`, точной причины ответ не даёт (объекта нет, нет доступа к проекту или роли не хватает); прочая ошибка верхнего уровня при HTTP 200 — `Graphql`; непустой `payload.errors` — `Payload` (в том числе `Reviewer not found`). Успех проверяется отдельным чтением `reviewers { mergeRequestInteraction { reviewState } }` после мутации: `REQUESTED_CHANGES` — успех, другое состояние — неожиданный ответ, сбой чтения — `Unverified`; в обоих случаях итог неизвестен. Метод — два запроса, исключение из правила «запись — один запрос» задачи 7. Заметкой запрос изменений не подменяется: тесты каждого исхода проверяют, что `POST …/notes` нет.
- Итог записи. Не принята: запрос не ушёл, 4xx, 429, 409 `approve`, ответ «объекта нет или нет прав», `payload.errors`, ошибка статической проверки GraphQL (`undefinedField` и подобные коды), отказ до запроса. Неизвестен: отказ транспорта после отправки, 5xx, ошибка GraphQL без кода, успешный ответ не той формы или не с тем итогом, сбой проверочного чтения.
- Списки — `per_page=100`, адрес страницы строит адаптер; следующая страница — по непустому `x-next-page`, без этого заголовка — по `link` с `rel="next"`.

Предположения адаптера без опоры на документацию, проверяются живыми клетками:

- Ошибка `ResourceNotAvailable` содержит слова «does not exist or you don't have permission». Кода у неё нет, и это единственный признак, отличающий её от прочих ошибок исполнения.
- Непустой `payload.errors` значит, что мутация не применена.
- Порог роли Developer для ревью и `mergeRequestRequestChanges` (общий с предположением оракула).
- Отказ по лимиту — только 429; тело — text/plain.
- Имена схемы: корень мутаций `Mutation`, вход `MergeRequestRequestChangesInput`, `reviewers(first: 100)` и `mergeRequestInteraction.reviewState`; дословно со справочником не сверены.
- `GET /namespaces/:id` отдаёт `plan` токену, которому виден тариф.
- `plan` в ответе `GET /metadata` в документации Metadata API не описан; наблюдён у GitLab CE 19.6.1 (`free`), поэтому адаптер берёт его только запасным источником тарифа.
- Ответ `approve` несёт `user_has_approved`; без него собственное одобрение ищется в `approved_by` по аккаунту сессии, поэтому аккаунт сессии GitLab — логин (`username`), как у `request_changes`.

## Отправка и сверка

Задача 9, `src/submit/`, журнал `src/journal/`. Таблица записана до кода сверки и задаёт её правило. Сверка читает сервер только методами адаптеров. Связь заметки с черновиком, происхождение объектов и прочие внутренние поля `forge-fake` видят только оракулы тестов.

Общие правила:

- `confirmed` — только связь с нашей операцией: ID из ответа на эту операцию или ожидаемый итог известного объекта, прочитанного по его ID. ID, полученный при создании `PENDING`, Submit не подтверждает.
- Совпадение по автору, якорю и тексту без такой связи — кандидат: такой объект мог создать другой клиент того же пользователя. Один кандидат записывается в элемент, у нескольких записывается описание «неоднозначно». Элемент остаётся `unknown`, повтора нет.
- `failed` по сверке (`Scope::refute`) — только операция над известным ID, прочитанным в исходном состоянии. Повтор такой операции дубля не создаёт. Отсутствие в списке и 404 доказательством не считаются.
- Сбой чтения при сверке даёт «не выяснено», а не «не найдено». Элемент не меняется.
- Тексты сравниваются после нормализации: без `\r` и без хвостовых пробелов и переводов строки в конце тела. Так GitLab по документации Notes API нормализует тело. Quick actions не снимаются, поэтому такой текст может не дать кандидата и остаться «не выяснено», но ложного подтверждения не даст.

| Операция | Чтение при сверке | `confirmed` | Кандидат | `failed` по сверке |
| --- | --- | --- | --- | --- |
| `github.create_review` | reviews аккаунта по всем страницам, комментарии подходящих | никогда: ответ потерян, ID нет | review аккаунта с итогом отправки на head ревизии сессии, с тем же текстом итога и комментариями на тех же якорях с тем же текстом | нет, операция создаёт объект |
| `github.create_pending` | reviews аккаунта | никогда | `PENDING` аккаунта (мог создать браузер) | нет |
| `github.add_pending_comment` | комментарии известного `PENDING` по его ID | никогда | комментарий не из журнала на якоре черновика с его текстом | нет |
| `github.update_pending_comment` | комментарии известного `PENDING`, комментарий по node ID | новый текст у известного комментария | — | прежний текст у известного комментария |
| `github.submit_review` | review по ID | известный review в ожидаемом отправленном состоянии | — | известный review всё ещё `PENDING` |
| `gitlab.create_draft_note` | свои черновики по всем страницам | никогда | черновик не из журнала с позицией черновика (тройка ревизии сессии, пути, строки) или тем же тредом и тем же текстом | нет |
| `gitlab.update_draft_note` | черновик по ID | известный черновик с новым текстом и, у черновика на строке, позицией черновика (у ответа — тем же тредом) | — | известный черновик с прежним текстом или другой позицией; позиция черновика не строится — «не выяснено» |
| `gitlab.publish_draft_note` | черновик по ID, затем заметки и треды MR по всем страницам | никогда: ответ публикации — 204 без тела, связи заметки с черновиком API не показывает, подтверждает только сам ответ 204 | после 404 черновика — заметка аккаунта с позицией черновика (или в его треде) с тем же текстом | известный черновик всё ещё черновик (чтение по ID — 200) |
| `gitlab.summary_note` | заметки MR по всем страницам | никогда | заметка аккаунта без позиции с текстом сводки, не записанная в журнале | нет |
| `gitlab.approve` | одобрения MR | одобрение токена есть (`user_has_approved`, без него — аккаунт в `approved_by`) | — | одобрения токена нет |
| `gitlab.request_changes` | ревьюеры MR со `reviewState` | `REQUESTED_CHANGES` у аккаунта | — | у аккаунта другое состояние |

Позицию и якорь ожидаемого итога сверка строит на ревизии черновика, а не на текущей ревизии сессии: черновик, который держит элемент, при смене head остаётся на прежней ревизии.

Исполнитель (`src/submit/mod.rs`):

- Шаг 1 — свежая ревизия (`GitHub::pull`, `GitLab::merge_request`) против ревизии сессии; сменилась — остановка до первой записи, путь выбирает вызывающий.
- Шаг 2 — планировщик по строкам журнала всех отправок сессии. Черновик входит, если он на ревизии сессии, с действующим якорем, не опубликован подтверждённой операцией (Create review, публикация `draft_note`, комментарий `PENDING` с подтверждённым Submit) и не удерживается элементом. Черновику GitLab с ID второе создание не планируется. Незавершённый `PENDING` сессии (после опровергнутого Submit) продолжается новой отправкой с тем же `pending_review` и теми же принятыми чужими комментариями, свои комментарии собираются по всем отправкам с этим `PENDING`.
- Шаги 3 и 4 — элементы по порядку: чтения → `begin` → одна запись → `confirm_with` с удалёнными ID, `fail` с закрытием отправки или `unknown` с остановкой. Отказ чтения оставляет элемент в `planned`. Продолжение идёт с первого `planned`, элемент в `unknown` останавливает продолжение до сверки. Свой `PENDING` после переоткрытия восстанавливает `GitHub::resume_pending`; перед Submit состав `PENDING` перечитывается, и чужой комментарий, не принятый явно, закрывает отправку без записи.
- Шаг 5 — итог из строк журнала: «полностью» (все элементы подтверждены), «не отправлено» (ничего видимого не подтверждено и нет `unknown`), иначе «частично».
- Планировщик не планирует операцию без одного черновика (сводка, Create review, создание `PENDING`, Submit, `approve`, запрос изменений), пока такая же операция сессии не сверена: запрет черновика её не держит.
- Сверка отправки исключает из кандидатов свои объекты из журнала: ID своих черновиков, свои комментарии `PENDING`, свои сводки.
- Смена head при элементе в `unknown`: удерживаемый черновик в смену не передаётся и остаётся на прежней ревизии со своим якорем, сессия переходит на свежую. После сверки такой черновик отправляется только после явной перепривязки к diff текущей ревизии (`rebind_stale`), у GitLab — с изменением позиции черновика до публикации.

Следствие для ADR-0015: у GitLab операция публикации `draft_note` с потерянным ответом сверкой не подтверждается. Исчезновение черновика после этого означает публикацию либо удаление другим клиентом, и ответ API эти случаи не различает. Элемент остаётся `unknown` с кандидатом или без него.

## Сценарии стенда

Задача 10, `src/scenario/fake.rs`. Каждая строка матрицы — сценарий столбца `fake` по разделу «Ожидания». Решения исполнителя вне правил плана записаны в плане с ⚠️.

- Процесс сценария поднимает `forge-fake` у себя. Журнал пробы лежит в его `SHELLIO_STATE_DIR` и проверяется после переоткрытия. Ветви одной строки идут каждая со своим сервером и файлом журнала.
- Проверки сравнивают журнал вызовов сервера (ключ, тело, код) и его состояние с литералами сценария, записи — по ключам точно. Итог `pass` только при всех прошедших проверках. Список проверок с наблюдёнными значениями идёт в `notes` в `result.json`.
- В `result.json` попадают очищенный след всех ролей, число вызовов, снимки серверов до и после по ветвям и дамп журнала после переоткрытия. Нет хотя бы одного из них — ошибка исполнения. Любой итог столбца `fake`, кроме `pass`, — тоже ошибка исполнения: так считают агрегатор и код выхода процесса.
- После потерянного ответа или сбоя сценарий ждёт квитанцию `wait_calls`: журнал сервера ветви дорос до своей длины на отметке плюс вызовы, отправленные клиентами с неё. Первая версия считала порог только по вызовам с отметки и выполнялась ещё до ожидаемого вызова, если до отметки сервер уже записал больше вызовов. Все 18 строк прошли и после исправления порога.
- Путь «остаться» в `head-change` идёт прямыми вызовами адаптера на прежней ревизии: исполнитель останавливается на шаге 1 при любой смене head. Node ID треда для resolve в `gh-anchors` берётся из состояния `forge-fake`, потому что чтения тредов PR у адаптера нет.
- Сверка публикации читает заметки MR в составе тредов (`GET …/discussions`), поэтому вторая страница в `reconcile-paged` — это страница списка тредов.

Первое исполнение сценариев — юнит-тест `every_matrix_row_passes_against_forge_fake`. В нём три строки не прошли проверки, и во всех трёх ошибка была в проверке сценария, а не в клиенте:

- `gl-anchors`: неверный порядок ожидаемого списка после сортировки. Кроме того, ключ `type` у начала `line_range` (неизменённая строка) не пришёл, хотя ожидание его называет. Проверка изменена на отсутствие ключа по контракту оракула. Изменение сделано после результата. Позже сверено с документацией Discussions API: у неизменённой строки `type` не передаётся, поэтому проверка осталась, а основание записано рядом с ожиданием `gl-anchors`.
- `reconcile-foreign`: POST-запросы чтения GraphQL считались записями.
- `reconcile-paged`: вторая страница искалась в списке заметок, а сверка читает треды.

После исправлений `make probe-review` проходит: все 18 строк столбца `fake` — `pass`, ошибок исполнения нет.

### Файл песочниц

`~/.config/shellio-probe-review/sandbox.toml`, вне git. Формат выбрала проба, владелец создаёт файл до живого прогона:

```toml
[keychain]                            # необязательно
service = "shellio-probe-review"      # по умолчанию

[github_cloud]
repo = "<владелец>/shellio-review-sandbox"
author = "github-author"              # аккаунт элемента Keychain, по умолчанию
reviewer = "github-reviewer"          # по умолчанию

[gitlab_cloud]
repo = "<пространство имён>/shellio-review-sandbox"
author = "gitlab-author"              # по умолчанию
reviewer = "gitlab-reviewer"          # по умолчанию
```

- Разбирается подмножество TOML: таблицы, строковые ключи в двойных или одинарных кавычках, комментарии. Неизвестная таблица или ключ, повтор, не строковое значение, неверный путь репозитория, одинаковые элементы автора и ревьюера — ошибка разбора с номером строки. Наполовину разобранный файл не даёт ни одного репозитория. Пакет TOML в общий `Cargo.lock` не добавлялся.
- Нет файла — клетки облачных хостов получают `not_run` «нет sandbox.toml». Нет таблицы хоста — `not_run` «нет хоста <столбец> в sandbox.toml». Испорченный или нечитаемый файл — ошибка исполнения: предусловие задано, но неверно.
- `[gitlab_ce]` в файле — ошибка: локальный GitLab CE настраивает сама проба (задача 12).

### Токены

- Вызов: `/usr/bin/security find-generic-password -s <сервис> -a <аккаунт> -w` со сроком 10 с, stdin закрыт. Токен читается из stdout и сразу становится `Secret`, у которого `Debug` без значения. В аргументах процесса только сервис и аккаунт, ошибки токена не несут.
- Код `security` при отсутствии элемента — 44 (`errSecItemNotFound`). Наблюдён на этой машине вызовом с несуществующим аккаунтом, диалога не было. Код 44 даёт клеткам аккаунта `not_run` «нет токена <аккаунт>».
- Срок истёк — процесс `security` снимается (`SIGKILL` и ожидание), клетки получают `not_run` «Keychain ждёт диалога». Поток чтения канала после снятия не ждут: внук с унаследованным каналом держал бы его открытым.
- Другой код выхода, пустой токен, пробел в токене или `security` не запустился — `not_run` «токен <аккаунт> не прочитан: …» с кодом и первой строкой stderr. Решение исполнителя: план называет только два исхода, а любой другой отказ — тоже отсутствие предусловия, а не ошибка стенда.
- Роли: «нет автора: …» и «нет ревьюера: …» — причины `not_run` клеток, которым нужна роль. Токены регистрируются в очистителе (`add_token`) до первого вызова.

### Сторож записи

- Сторож — транспорт-обёртка `Guarded`, через которую идут все запросы клетки: жизненного цикла и адаптеров ревью. Функцию проверки, которую сценарий мог бы забыть вызвать, сторожем не считаем.
- Чтения проходят сразу. Перед первой записью сторож проверяет репозиторий, если сценарий не сделал этого раньше. Для облачного хоста путь должен быть в `sandbox.toml`, для локального GitLab CE адреса REST и GraphQL — на `127.0.0.1`. Оба условия проверяются до запроса. Затем `GET` репозитория должен показать явное `private: true` (GitHub) или `visibility: "private"` (GitLab). Отсутствующее или не булево поле — отказ. Имя `full_name` или `path_with_namespace` должно совпасть с путём без учёта регистра, ветка по умолчанию должна быть.
- Отказ запоминается: все записи после него получают отказ `not_sent` и не уходят, а `refusal` и `refused_writes` дают сценарию основание для ошибки исполнения. После проверки запись REST допускается только под путём проверенного репозитория, GraphQL — только на адрес GraphQL хоста. Мутацию по node ID другого репозитория сторож не различает.

### Жизненный цикл клетки

- У клетки две ветки. Цель `probe/<run-id>-<клетка>-base` создаётся от головы ветки по умолчанию с исходной версией фикстуры `probe-review/fixture.txt`. Ветка клетки `probe/<run-id>-<клетка>` создаётся от цели с изменённой версией, PR/MR идёт из неё в цель. Решение исполнителя: в песочнице гарантирован только один коммит, а diff от ветки по умолчанию показал бы фикстуру целиком добавленной. Ветка по умолчанию не меняется, обе ветки попадают под общее начало `probe/<run-id>-` для проверки уборки задачи 15, а `gl-approve-sha` получает целевую ветку под своим управлением.
- Фикстура — 30 строк. У ветки клетки строка 03 удалена, строка 05 изменена, после строки 24 добавлены две. Смена head — новый коммит тем же API: меняется строка 27 во втором блоке diff, первый блок не затронут.
- Коммиты идут через Contents API GitHub (base64, при изменении — `sha` текущего blob из `GET …/contents/…?ref=`) и Commits API GitLab (`actions` с `create` или `update`), без `git push`. Ревьюер GitLab назначается в `reviewer_ids` при создании MR. Его ID взят из `GET /user` токена ревьюера.
- Журнал созданного `live-objects.jsonl` лежит в каталоге процесса, одна строка JSON на объект, каждая запись сбрасывается на диск до следующего запроса. Имя ветки пишется до запроса создания, номер PR/MR — сразу после ответа. Оборванная последняя строка при чтении пропускается.
- Уборка выполняется после успеха, после ошибки открытия, после ошибки тела и после паники сценария (`catch_unwind`). Порядок: поиск открытых PR/MR по исходным веткам журнала (ответ на создание мог потеряться), удаление черновиков ревьюера в каждом PR/MR, закрытие PR/MR, удаление ветки клетки, затем цели. `PENDING` review и `draft_notes` видит только их автор, поэтому черновики убирает транспорт ревьюера. Неудачный шаг не останавливает следующие. Ответы 404 и 422 на удаление ветки значат, что её нет.
- Подтверждение — чтение каждого объекта журнала: PR/MR закрыт, черновиков ревьюера нет, ветки нет. Затем поиск открытых PR/MR повторяется по каждой ветке журнала: ответ на создание мог потеряться, а первый поиск отказать, и тогда PR/MR не попал ни в один цикл уборки (MR GitLab остаётся открытым и после удаления исходной ветки). Найденный повторным поиском PR/MR, которого не было среди убранных, и отказ повторного поиска попадают в `leftovers`. Не подтверждённое попадает в `leftovers`. `resume_cleanup` продолжает уборку по журналу из другого процесса, например после `SIGKILL`, который не исполняет trap.
- Формы запросов refs, contents, pulls, reviews, branches, commits, merge requests и draft notes взяты из документации REST. `forge-fake` их не реализует, поэтому до первой живой клетки (задача 13) они проверены только встроенным транспортом.

### Общее для живых клеток (задача 13)

- Роли клетки строятся одним сторожем на роль. Репозиторий жизненного цикла и адаптер ревью берут адреса API из цели этого сторожа (`GuardTarget::github_endpoints`, `gitlab_endpoints`): сторож сравнивает адрес GraphQL точным равенством, и тот же адрес в другом виде, например с `/` в конце, он не пропустил бы.
- До записей клетки токены обеих ролей читают `GET /user`. Логин и отображаемое имя профиля (`name`, если задано) регистрируются в очистителе под меткой роли: имя профиля — те же персональные данные, что логин. У GitLab CE имена ролей известны из настройки, а адрес, который хост сам сообщает в `web_url` проекта (без `external_url` — имя контейнера), записывается в описание хоста и заменяется меткой `<gitlab-ce>` вместе с `127.0.0.1:<порт>`.
- Затем идёт уборка по журналам прежних процессов того же столбца: `<прогон>/<сценарий>-<столбец>/live-objects.jsonl` без отметки `live-objects.swept`, кроме своего каталога. Журнал начинается записью цели сторожа (адрес REST и путь репозитория), и убирается только журнал той же цели: номер PR/MR другого репозитория указал бы на чужой объект. Журнал без цели или другой цели попадает в `leftovers` текущей клетки. Журнал, уборка которого прошла без ошибок и без не убранного, получает отметку и больше не читается; ту же отметку ставит своя уборка клетки. Журналы `gitlab_ce` не перечитываются: контейнер прежнего подъёма удалён вместе с объектами, а номера MR нового подъёма начинаются заново и указали бы на чужие MR. Не убранное по прежнему журналу попадает в `leftovers` текущей клетки с источником `<прогон>/<процесс>`.
- В `result.json` итог уборки, её ошибки, `leftovers`, причина итога и текст ошибки исполнения попадают только через очиститель.
- Отказ сторожа и непустой `refused_writes` — ошибка исполнения клетки. Исключение — решение исполнителя: ответ 401, 403 или 404 на чтение репозитория сторожем (`GuardError::Denied`) и 401 или 403 на `GET /user` — нарушение предусловия, клетка получает `not_run` «токен без прав…»: приватный репозиторий, недоступный токену, GitHub отдаёт кодом 404, и отличить его от отсутствующей песочницы нельзя.
- Явный отказ по лимиту в итоге действия — `not_run` «лимит» без повтора. Неподтверждённое чтение итога записи с отказом транспорта или 5xx — ошибка исполнения, а не `fail`.
- Итог по отказу хоста собирает одна функция на действие. `approve` GitLab: отказ по правам (401, 403, роль ниже нужной) или с признаком тарифа в тексте — `absent`, 409 — наблюдение оракула ветви, отказ транспорта и 5xx — ошибка исполнения. `mergeRequestRequestChanges`: нет в схеме или признак тарифа или лицензии в тексте ответа — `absent`, другой отказ — `fail` с текстом ответа. `absent` без версии хоста в клетке — ошибка исполнения.

### Настройка

- Режим `probe-review --gitlab-ce-provision --url <корень> --out <каталог подъёма>`, код на Rust через API GitLab. Каждый адрес проверяется на `127.0.0.1` до запроса: записи настройки идут мимо сторожа `Guarded`, проекта до настройки нет, и его проверка отказала бы навсегда.
- Токен root — OAuth password grant (`POST /oauth/token`, `grant_type=password`, `scope=api`). Ответ 400 или 401 — код 5: `run.sh` создаёт личный токен root выражением `gitlab-rails runner` (`personal_access_tokens.create!` со сроком два дня, токен генерирует GitLab и печатает строкой `probe-token:…`) и повторяет настройку с `PROBE_REVIEW_GITLAB_ROOT_TOKEN`. Какой путь сработал, пишется в `gitlab-ce.json` (`root_token`) и в заметки клетки.
- Root: `GET /user` (`is_admin`), `GET /metadata` (версия должна совпасть с тегом закрепления), `POST /users` автора `probe-author` и ревьюера `probe-reviewer` (`force_random_password`, `skip_confirmation`), `POST /users/:id/personal_access_tokens` со `scopes: ["api"]` (User tokens API, только self-managed).
- Автор: `POST /projects` — приватный `shellio-review-sandbox` с README в своём пространстве имён, `POST /projects/:id/members` — ревьюер с ролью Developer. Ревьюер: `GET /projects/:id` должен показать `project_access` 30.
- Решение исполнителя: автор — отдельный пользователь, а не root. Root — администратор, его права скрывали бы ограничения роли, а в облачных песочницах автор — обычный владелец проекта. Root нужен только настройке. Участие ревьюера в проекте план не перечислял: без него приватный проект ревьюеру не виден.
- Описание хоста без секретов — `gitlab-ce.json` каталога подъёма (адрес, образ, версия, проект, ветка по умолчанию, ID и логины ролей). Токены ролей — одна строка JSON в stdout режима: `run.sh` держит их в переменной и передаёт процессам `gitlab_ce` окружением `PROBE_REVIEW_GITLAB_CE_TOKENS`, в аргументы процессов и файлы они не попадают.
- Очиститель клетки получает токены, адрес `127.0.0.1:<порт>`, путь проекта, логины и отображаемые имена ролей.

## Передачи

Передачи в P4.1 `forge-accounts` записываются по мере выводов.

- GitHub Enterprise Server — `not_run` «нет инсталляции».
- Introspection `__type(name: "Mutation")` на GitLab CE 19.6.1 в обеих проверенных формах (аргумент через `variables` и литерал, обе — анонимные операции) возвращает полную схему `data.__schema` около 8,8 МБ на вызов. Короткий ответ `__type` не получен; форма с именованной операцией и `operationName` не проверялась и остаётся открытой. Адаптер P4.1 разбирает обе формы и учитывает эту стоимость при чтении возможностей.
- Операции, создающие объект (сводка GitLab, Create review и создание `PENDING` GitHub), с потерянным ответом сверкой не подтверждаются и не опровергаются: элемент остаётся `unknown` с кандидатом или без, и проба не планирует такую же запись, пока он не сверен. Продукту нужен явный выбор пользователя (задача 9).
- Публикация `draft_note` GitLab с потерянным ответом сверкой не подтверждается (ответ 204 без тела, связи заметки с черновиком API не показывает). Если черновик исчез, элемент остаётся `unknown` навсегда, а его черновик — на ревизии отправки: продукту нужен явный выбор пользователя «считать опубликованным» или «отказаться», которого проба не делает (задача 9).
- Стойкость журнала к сбою питания не наблюдалась. Журнал пробы фиксирует каждый переход в WAL с `synchronous = FULL`; на macOS обычный `fsync` не сбрасывает кэш накопителя, для этого нужен `PRAGMA fullfsync` (задача 3).
