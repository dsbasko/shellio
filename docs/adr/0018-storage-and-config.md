# ADR-0018: Хранение состояния и конфигурация

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

Состояние включает воркспейсы, раскладки, черновики ревью и сообщения. Настройки должен читать и редактировать человек.

## Решение

| Что | Где | Формат |
| --- | --- | --- |
| Воркспейсы, проекты, раскладки, сообщения, черновики, состояние панелей | `~/Library/Application Support/shellio/state.db` | SQLite в режиме WAL |
| Настройки, keymap, профили агентов | `~/.config/shellio/settings.toml`, `keymap.toml` | TOML, горячая перезагрузка |
| Шаблоны | `~/.config/shellio/prompts/` | Markdown |
| Конфигурация терминала | `~/.config/shellio/ghostty.conf` | Формат Ghostty |
| Токены GitHub и GitLab | macOS Keychain | Подпись приложения постоянна (ADR-0019) |
| Runtime хостов | `~/Library/Application Support/shellio/runtime/<version>/` | Бинарники |

Правила:

- Запись структурных изменений немедленная, но частые события вроде смены cwd копятся и пишутся пакетами.
- Миграции схемы версионированы и перед применением создают резервную копию.
- Состояние плагина хранится с `state_version`, плагин отвечает за миграцию.
- Отсутствующий плагин или повреждённая запись не мешают запуску остальных панелей.
- Настройки: некорректный файл оставляет последнюю исправную версию и показывает ошибку.
- `SHELLIO_STATE_DIR` перенаправляет всё состояние и конфигурацию для тестов.

## Отвергнутые варианты

- JSON на каждую сущность: нет транзакций для журнала ревью и сообщений.
- Настройки в SQLite: неудобно редактировать и хранить в dotfiles.

## Последствия

Новая версия может мигрировать базу так, что откат станет возможен только из резервной копии. Откат документирован в плане P5.2.

## Основания

`agterm/ARCHITECTURE.md` (стратегия записи), `detached/docs/THEMES.md` (сохранение последней исправной версии).

## Уточнено в P1.1

Решение плана P1.1 `core-domain`, принятое при планировании 2026-11-21. Таблица размещения не меняется. Схема v1 записана в [ADR-0025](0025-workspaces-and-project-catalog.md), «Уточнено в P1.1».

- **Хранилище** — crate `shellio-store`, реализация порта `Persist` ядра ([ADR-0004](0004-process-model.md)). Его открывает один процесс: в продукте после блокировки единственного экземпляра P1.2.
- **Профиль.**
  - Без `SHELLIO_STATE_DIR` состояние — `$HOME/Library/Application Support/shellio`, конфигурация — `$HOME/.config/shellio` буквально: `XDG_CONFIG_HOME` не читается. Нет, пустой или относительный `HOME` — ошибка: относительный сделал бы каталог состояния зависимым от текущего каталога процесса.
  - С `SHELLIO_STATE_DIR=<d>` состояние — `<d>`, конфигурация — `<d>/config`. Пустое или относительное значение — ошибка, а не тихий переход на настоящий каталог. Переменная проверяется первой: при верном значении `HOME` не читается.
  - Окружение профиль получает параметром. Окружение процесса читает только `Profile::from_process_env`, тесты получают каталог через `Profile::isolated` и окружение процесса не меняют.
  - В каталоге состояния лежат `state.db` и `backups/`. Каталог создаётся с правами `0700` при открытии хранилища, недостающие родители — тоже с `0700`. Права существующего каталога и родителей не меняются, путь, занятый файлом, — ошибка. Каталог конфигурации в P1.1 не создаётся.
- **Прагмы:** `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=5000`.
- **Миграции.** Версия схемы — `PRAGMA user_version`, миграции — нумерованный список SQL внутри crate. Порядок открытия:
  1. Файл не база или повреждён — `Corrupt`, файл не трогается. Отрицательная `user_version` — тоже `Corrupt`: ни один бинарь shellio её не пишет.
  2. `user_version` больше последней известной — `NewerSchema`, ни одной записи. До конца проверок 1 и 2 закрытие соединения не переносит в файл кадры `-wal`, оставленные сбоем другой версии.
  3. Версия 0 и пустая схема — миграции без резервной копии.
  4. Версия ниже последней при непустой схеме — резервная копия backup API SQLite в `backups/state.db.v<версия>.<unix_ms>.bak`, затем открытие копии и проверка её `user_version`. Неудача копии — отказ, миграция не начинается.
  5. Каждая миграция — своя транзакция `IMMEDIATE` вместе с установкой `user_version`. Сбой откатывает её, база остаётся на последней исправной версии.

  Переход в WAL переписывает заголовок файла, поэтому он идёт после проверок 1 и 2 и копии. Копия переводится в режим журнала `DELETE` и получается самодостаточным файлом с правами `0600`, каталог `backups/` создаётся с `0700`. Занятое имя копии не перезаписывается: это отказ копии, недоделанная копия удаляется. Резервные копии автоматически не удаляются. Уборка копий и откат схемы — P5.2, путь восстановления при `Corrupt` и `NewerSchema` — P5.6.
- **Запись.** Структурное изменение пишется до ответа одной транзакцией `IMMEDIATE`: проверка `meta.revision` против базовой ревизии ядра, SQL каждого изменения, `meta.revision` +1. Ревизия поэтому монотонна через перезапуски. Любой отказ откатывает транзакцию целиком, состояние ядра не меняется.
  - `storage_conflict` — в базу писали в обход ядра: чужая ревизия, нарушение `UNIQUE`, первичного или внешнего ключа, а также изменение записи, которое затронуло не ровно одну строку. Иначе «успешная» запись разошлась бы с перезагрузкой.
  - `storage_unavailable` с признаком повтора — прочие ошибки SQLite.
  - Состояние окна пишется вставкой с обновлением при совпадении ключа, поэтому строка `window_state`, удалённая снаружи, восстанавливается следующей записью.
- **Построчная загрузка.** Одна читающая транзакция, каждое поле проверяется отдельно, каждая находка попадает в диагностику `{table, rowid, reason}`. Загрузка строки не удаляет и не исправляет, байты базы не меняются. Стабильные причины:
  - пропуск строки: `invalid_id` (идентификатор не из 16 байт), `title_empty`, `title_too_long`, `title_control_char`, `position_out_of_range` (позиция вне `u32`), `unknown_kind`, `owner_missing` (ссылка владения не на загруженную запись), `invalid_value` (тип значения не тот). Зависимые записи пропущенной строки пропускаются со своей диагностикой;
  - строка загружена, значение в памяти сброшено: `title_trimmed` (имя с пробелами по краям загружается обрезанным), `last_workbench_missing`, `last_workbench_foreign`, `active_workspace_missing`, `route_workbench_missing`, `route_workbench_foreign`, `row_missing` (нет строки `window_state`). Мягкая ссылка сбрасывается не только висячей, но и чужой: последняя рабочая область другого воркспейса, маршрут на область не активного воркспейса;
  - только диагностика: `position_taken` и `name_taken` (совпадение позиций внутри родителя и имён без учёта регистра в области уникальности). Диагностику получают все совпавшие строки, кроме строки с наименьшим `rowid`.

  Нет строки `meta.revision` или ревизия отрицательна — `Corrupt`, загрузка отказывает целиком: без ревизии запись не может проверить базовую.

  Так правило «повреждённая запись не мешает запуску остальных» выполняется для данных ядра.
- **Итог P1.1.** Подтверждено тестами `shellio-store`: SQLite в режиме WAL с прагмами выше, версионированные миграции с резервной копией, отказ на схеме новее бинаря без записи, построчная загрузка с диагностикой, перенаправление состояния `SHELLIO_STATE_DIR`, ревизия через перезапуски и равенство состояния до закрытия и после повторного открытия базы. Не подтверждено, поэтому статус остаётся `Proposed`:
  - TOML, горячая перезагрузка и последняя исправная версия настроек — P1.6 (`keymap.toml`) и P1.8 (`settings.toml`);
  - `state_version` состояния плагинов — P1.5;
  - пакетная запись частых событий вроде смены cwd — P2.2.

## Уточнено в P1.4 (планирование)

Решение плана P1.4 `layout-zones` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-23. Таблица размещения не меняется, статус остаётся `Proposed`. Модель раскладки записана в [ADR-0009](0009-layout-and-zones.md), команды и причины отказа — в [ADR-0007](0007-control-api.md), разделы «Уточнено в P1.4 (планирование)».

- **Миграция `0002_layout.sql`** (схема v2):
  - `panels(id BLOB PRIMARY KEY, workbench BLOB NOT NULL REFERENCES workbenches, plugin TEXT NOT NULL, title TEXT NOT NULL, created_at INTEGER NOT NULL)`;
  - `workbench_layouts(workbench BLOB PRIMARY KEY REFERENCES workbenches, layout TEXT NOT NULL)` — JSON модели `Layout<PanelId>` с полем версии формата.

  База v1 мигрирует по общему порядку раздела «Уточнено в P1.1», с резервной копией.
- **Запись.** Дельты `PanelAdd`, `PanelRemove` и `LayoutSet` пишутся той же транзакцией, что и остальные изменения команды. Команда, которая создаёт или закрывает панель, пишет строку панели и раскладку одной записью. Раскладка пишется целиком, вставкой с обновлением при совпадении ключа, как состояние окна.
- **Загрузка остаётся только чтением.** Строки `panels` проверяются так же, как остальные таблицы: `invalid_id`, `title_empty`, `title_too_long`, `title_control_char`, `owner_missing` (рабочей области нет или её строка пропущена) и `invalid_value` (plugin id не по правилу ADR-0007 или значение не того типа). Строка `workbench_layouts` разбирается и проверяется `Layout::validate` против живых панелей своей рабочей области. Строка раскладки без загруженной рабочей области — `owner_missing`. Новые стабильные причины находок:
  - `layout_unreadable` — JSON не разбирается или версия формата неизвестна;
  - `layout_invalid` — разобранная раскладка не проходит `validate`: выпавшая или лишняя панель, `active` или `last_active` вне диапазона, неверные доли, невидимый фокус;
  - `layout_missing` — у рабочей области есть живые панели, но нет строки раскладки. Находка адресует строку `workbenches` этой рабочей области.

  Раскладка с находкой в память не попадает, и рабочая область загружается без раскладки. Байты базы при загрузке не меняются.
- **Рабочие области без раскладки.** База v1 может уже содержать открытую рабочую область (`window_state.route_workbench_id`) и `last_workbench_id` воркспейса, которые открываются без `workbench.open`. Поэтому запуск ядра (`startup`) дописывает каждую загруженную рабочую область без раскладки одной записью до публикации сокета:
  - без панелей — раскладка по умолчанию ADR-0009 с новыми панелями `navigator` и `terminal`; это обычное состояние базы после миграции v1, а не находка;
  - с живыми панелями — раскладка, восстановленная из них (правило ниже).

  Повторный запуск находит раскладку и ничего не пишет, `PanelId` остаются прежними.
- **Восстановление испорченной раскладки** из панелей своей рабочей области. Первая по порядку панель `navigator` встаёт в колонку навигатора, остальные панели (в том числе другие `navigator`) — в центр одной частью. Порядок — `created_at`, затем `PanelId`. Фокус — первая панель центра, иначе навигатор. Размеры и скрытие — по умолчанию. Исправленную раскладку пишет та же запись запуска, которую `startup` уже делает при находках загрузки ([ADR-0007](0007-control-api.md), правило ревизии в разделе «Уточнено в P1.1»). Команды после такого запуска работают с исправленной раскладкой и не падают.

## Уточнено в P1.4

Вывод плана P1.4 [`layout-zones`](../plans/completed/20261123-layout-zones.md) по `make check` и приёмочному проходу исполнителя 2026-11-23. Таблица размещения не меняется. Статус остаётся `Proposed`: TOML и горячая перезагрузка — P1.6 и P1.8, `state_version` плагинов — P1.5, пакетная запись частых событий — P2.2.

**Подтверждено тестами** (`crates/shellio-store/tests/{load,recovery}.rs`, тесты запуска `crates/shellio-core`):

- миграция v1 → v2 с резервной копией на образце базы v1 с открытой рабочей областью: раскладка есть сразу после запуска без команд, второй запуск ничего не пишет и сохраняет `PanelId`;
- испорченный JSON, `active` и `last_active` вне диапазона, выпавшая и лишняя панель, ноль и два `navigator`, одинаковый `created_at` — находка и однозначное восстановление; первое изменение после восстановления и повторная загрузка;
- перезапуск ядра на том же `state.db` сохраняет раскладку, перезапуск без команд ничего не пишет; снимок и события дают то же состояние с раскладкой.

Наблюдение — пункты `restore-cold` и `restore-legacy` копии `layout.sh`, второй — на фикстуре `scripts/e2e/layout-fixtures/v1-open-workbench.sql` ([ADR-0021](0021-testing.md), «Уточнено в P1.4»).

**Форма, которую раздел планирования не задавал:**

- Версия формата — конверт `{"version":1,"layout":{…}}` только в `workbench_layouts.layout` (`crates/shellio-store/src/layout_json.rs`). В провод и в `Layout` она не попадает.
- Строка `panels` с названием, обрезанным по краям, загружается с находкой `title_trimmed`, как строки остальных таблиц. Значение `layout` не того типа — `invalid_value`. `layout_missing` возникает, только когда строки раскладки нет совсем, испорченная строка даёт свою находку. `PanelRemove`, затронувший не ровно одну строку, — `storage_conflict`.
- Plugin id — тип `PluginId` по правилу ADR-0007, он же проверяет строку при разборе снимка.
- Раскладку при запуске получает каждая загруженная рабочая область, в том числе рабочая область убранного проекта и удалённого воркспейса. Порядок — `WorkbenchId`. В рабочей области сначала идут `PanelAdd` навигатора и терминала, затем `LayoutSet`, дельты окна стоят перед ними в той же записи. Новые панели называются «Навигатор» и «Терминал», `created_at` — время запуска ядра. Пустой итог записи не порождает.
- Восстановление — `recovered_layout` в `crates/shellio-core/src/panel.rs`. Инварианты `State` получили нарушения `PanelOwnerMissing`, `LayoutOwnerMissing` и `LayoutInvalid`. Рабочая область без раскладки инвариант не нарушает.
- Эталон свежей схемы — `crates/shellio-store/tests/schema_v2.sql`. `schema_v1.sql` и образец v1 не менялись и сверяют копию до миграции.

## Уточнено в P1.5 (планирование)

Решение плана P1.5 `plugin-host` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-24. Таблица размещения не меняется, статус остаётся `Proposed`. Раздел выполняет правила «Состояние плагина хранится с `state_version`, плагин отвечает за миграцию» и «Отсутствующий плагин или повреждённая запись не мешают запуску остальных панелей». Контракт плагина и статус панели записаны в [ADR-0008](0008-plugin-system.md), команды и события — в [ADR-0007](0007-control-api.md), разделы «Уточнено в P1.5 (планирование)».

- **Миграция `0003_panel_state.sql`** (схема v3):
  - `panel_states(panel BLOB PRIMARY KEY REFERENCES panels ON DELETE CASCADE, version INTEGER NOT NULL, data TEXT NOT NULL)` — данные панели и их `state_version`;
  - столбец `panels.opened_from BLOB NULL` — вызывающая панель `PerApp`;
  - `plugin_registry(id INTEGER PRIMARY KEY CHECK (id = 1), fingerprint TEXT NOT NULL) STRICT` — отпечаток реестра. Отдельная таблица нужна потому, что у `meta.value` тип `INTEGER`.

  База v2 мигрирует по общему порядку раздела «Уточнено в P1.1», с резервной копией. Эталон свежей схемы — `crates/shellio-store/tests/schema_v3.sql`.
- **Исходный текст данных.** Загрузка кладёт `data` в модель исходным текстом, не разбирая. Ядро хранит данные панели в трёх видах:
  - `Missing` — строки нет;
  - `Text { version, raw }` — исходный текст, `"null"` — данные `null`;
  - `Unreadable` — строка есть, но `version` вне `1..=u32::MAX`, тип столбца не `TEXT` или байты не UTF-8.

  Загрузка нечитаемое не отбрасывает и в отсутствие не превращает. Строка `Unreadable` даёт находку `{table: "panel_states", rowid, reason}` в `query.status` с причиной `invalid_value`, панель получает статус `state_corrupt`, строка в базе не меняется, `init` её не перезаписывает. Причина находки выбрана исполнителем при записи этого раздела по правилу плана: ближайшая существующая, «значение не того типа».
- **Сохранение байтов.** Панель не в `ready` (отсутствующий плагин, данные новее поддерживаемой версии, нечитаемые данные, отказ `init` или миграции, дубликат singleton) сохраняет строку `panel_states` побайтно через перенос, `zoom`, запись других панелей, `app quit` и новый запуск. Запись пишет только строки данных, изменённые командой.
- **Запись.** Дельты данных панели, `opened_from`, переезда панели в другую рабочую область и статуса пишутся той же транзакцией, что и остальные изменения команды. Статус в базу не пишется: это производное значение. Каждый путь создания панели пишет `init` её данных в той же записи, что строку панели (у плагина без данных — текст `null`), поэтому повторный запуск ничего не дописывает.
- **Запуск с `init` и `migrate`.** Запуск ядра вычисляет статус каждой панели по строкам и реестру (порядок — ADR-0008). Каноническая панель известного плагина без строки данных получает `init(None)`, с меньшей версией — `migrate`, обе записи идут в записи запуска. Отказ или результат больше 65 536 байт даёт статус `init_failed` или `migrate_failed`, исходные байты сохраняются, запуск продолжается. Дубликаты не инициализируются и не мигрируют. Статусы заполняются до публикации первого снимка, без дельт.
- **Отпечаток реестра и запись запуска.** Отпечаток — отсортированный список `plugin:state_version:cardinality` и номер правил статуса хоста (`STATUS_RULES`). Загрузка отдаёт сохранённый отпечаток вместе с состоянием. Запись запуска получает новый отпечаток отдельным параметром внутренней записи, а не доменной дельтой, и пишет его в той же транзакции, что дельты и ревизию.
  - Если отпечаток отличается от сохранённого, запуск пишет одну запись (`init`, `migrate`, новый отпечаток) и не кладёт её в буфер событий, как запись с находками P1.4. Тогда клиент с курсором прежнего владельца получает снимок, даже если строки панелей не менялись.
  - Без находок, без смены отпечатка и без дельт запуск записи не порождает.
- **Откат.** Отказ посреди записи запуска или переезда панели откатывает транзакцию целиком: после повторного открытия база и отпечаток прежние. Это проверяют тесты `shellio-store` на настоящем SQLite с внедрённым отказом фиксации.
- **Версии.** Версия схемы базы (`user_version`), версия протокола и `state_version` плагина — разные числа.
