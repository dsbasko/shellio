# ADR-0018: Хранение состояния и конфигурация

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

Состояние включает воркспейсы, раскладки, черновики ревью и сообщения. Настройки должен читать и редактировать человек.

## Решение

| Что | Где | Формат |
| --- | --- | --- |
| Воркспейсы, проекты, раскладки, сообщения, черновики, состояние панелей | `~/Library/Application Support/shellio/state.db` | SQLite в режиме WAL |
| Настройки, keymap, профили агентов | `~/.config/shellio/settings.toml`, `keymap.toml` | TOML, горячая перезагрузка |
| Шаблоны | `~/.config/shellio/prompts/` | Markdown |
| Конфигурация терминала | `~/.config/shellio/ghostty.conf` | Формат Ghostty |
| Токены GitHub и GitLab | macOS Keychain | Подпись приложения постоянна (ADR-0019) |
| Runtime хостов | `~/Library/Application Support/shellio/runtime/<version>/` | Бинарники |

Правила:

- Запись структурных изменений немедленная, но частые события вроде смены cwd копятся и пишутся пакетами.
- Миграции схемы версионированы и перед применением создают резервную копию.
- Состояние плагина хранится с `state_version`, плагин отвечает за миграцию.
- Отсутствующий плагин или повреждённая запись не мешают запуску остальных панелей.
- Настройки: некорректный файл оставляет последнюю исправную версию и показывает ошибку.
- `SHELLIO_STATE_DIR` перенаправляет всё состояние и конфигурацию для тестов.

## Отвергнутые варианты

- JSON на каждую сущность: нет транзакций для журнала ревью и сообщений.
- Настройки в SQLite: неудобно редактировать и хранить в dotfiles.

## Последствия

Новая версия может мигрировать базу так, что откат станет возможен только из резервной копии. Откат документирован в плане P5.2.

## Основания

`agterm/ARCHITECTURE.md` (стратегия записи), `detached/docs/THEMES.md` (сохранение последней исправной версии).

## Уточнено в P1.1

Решение плана P1.1 `core-domain`, принятое при планировании 2026-11-21. Таблица размещения не меняется. Схема v1 записана в [ADR-0025](0025-workspaces-and-project-catalog.md), «Уточнено в P1.1».

- **Хранилище** — crate `shellio-store`, реализация порта `Persist` ядра ([ADR-0004](0004-process-model.md)). Его открывает один процесс: в продукте после блокировки единственного экземпляра P1.2.
- **Профиль.**
  - Без `SHELLIO_STATE_DIR` состояние — `$HOME/Library/Application Support/shellio`, конфигурация — `$HOME/.config/shellio` буквально: `XDG_CONFIG_HOME` не читается. Нет или пустой `HOME` — ошибка.
  - С `SHELLIO_STATE_DIR=<d>` состояние — `<d>`, конфигурация — `<d>/config`. Пустое или относительное значение — ошибка, а не тихий переход на настоящий каталог.
  - Окружение профиль получает параметром. Окружение процесса читает только `Profile::from_process_env`, тесты получают каталог через `Profile::isolated` и окружение процесса не меняют.
  - В каталоге состояния лежат `state.db` и `backups/`. Каталог создаётся с правами `0700` при открытии хранилища, каталог конфигурации в P1.1 не создаётся.
- **Прагмы:** `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON`, `busy_timeout=5000`.
- **Миграции.** Версия схемы — `PRAGMA user_version`, миграции — нумерованный список SQL внутри crate. Порядок открытия:
  1. Файл не база или повреждён — `Corrupt`, файл не трогается.
  2. `user_version` больше последней известной — `NewerSchema`, ни одной записи.
  3. Версия 0 и пустая схема — миграции без резервной копии.
  4. Версия ниже последней при непустой схеме — резервная копия backup API SQLite в `backups/state.db.v<версия>.<unix_ms>.bak`, затем открытие копии и проверка её `user_version`. Неудача копии — отказ, миграция не начинается.
  5. Каждая миграция — своя транзакция вместе с установкой `user_version`. Сбой откатывает её, база остаётся на последней исправной версии.

  Резервные копии автоматически не удаляются. Уборка копий и откат схемы — P5.2, путь восстановления при `Corrupt` и `NewerSchema` — P5.6.
- **Запись.** Структурное изменение пишется до ответа одной транзакцией: проверка `meta.revision` против базовой ревизии ядра, SQL каждого изменения, `meta.revision` +1. Ревизия поэтому монотонна через перезапуски. Чужая ревизия, нарушение `UNIQUE` или внешнего ключа — `storage_conflict`, состояние ядра не меняется.
- **Построчная загрузка.** Каждая находка попадает в диагностику `{table, rowid, reason}`. Загрузка строки не удаляет и не исправляет.
  - Пропуск строки: неверная длина идентификатора, пустое или слишком длинное имя, неизвестный вид корня, висячая ссылка владения. Зависимые записи пропущенной строки пропускаются со своей диагностикой.
  - Сброс с диагностикой, строка остаётся: висячая мягкая ссылка (последняя рабочая область воркспейса, маршрут, активный воркспейс).
  - Только диагностика: совпадение позиций внутри родителя.

  Так правило «повреждённая запись не мешает запуску остальных» выполняется для данных ядра.
