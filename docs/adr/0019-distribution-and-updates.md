# ADR-0019: Подпись, автообновление, Homebrew

- Статус: Accepted (владелец не использует Apple Developer ID), механизм проверен в P0.5: не подтверждено из-за Keychain, раздел «Уточнено в P0.5»
- Дата: 2026-11-09

## Контекст

Нужны установка через Homebrew и автоматическое обновление. Платной учётной записи Apple Developer не будет, поэтому нотаризации нет. Подпись должна быть постоянной: ad-hoc подпись меняет требование к коду при каждой сборке, и доступ к Keychain и разрешения слетают.

## Решение

**Подпись.** Постоянная самоподписанная идентичность `Shellio Dev`, сертификат и закрытый ключ хранятся в секретах CI. Bundle ID и designated requirement стабильны. Сохранение разрешений TCC для GUI и хостов старого поколения не считается автоматическим и проверяется в P0.5.

**Установка.** Собственный tap с cask: `depends_on arch: :arm64`, `auto_updates true`, `binary` для `shellioctl`, снятие карантина в `preflight_steps` со staged-копии. Сборка только под arm64. Ошибка снятия карантина приводит к понятному сообщению при установке, так как без нотаризации приложение иначе не запустится.

**Обновление.** Собственный механизм:

1. При запуске и раз в сутки читается `latest.json` из последнего релиза.
2. Файл и архив проверяются подписью minisign с вшитым публичным ключом.
3. Загрузчик приложения не ставит атрибут карантина (`LSFileQuarantineEnabled` не включён). Проверяется полученный артефакт.
4. Кодовая подпись новой версии проверяется по сертификату и требованию, а не по отображаемому имени.
5. Новая версия подготовлена на той же файловой системе, UI показывает готовность в статус-баре.
6. Замена бандла идёт по протоколу, который выбирает P0.5.
7. Новый GUI подключается к тем же сессиям.

Требования к протоколу замены:

- Обычный `rename` не заменяет непустой каталог, а два `rename` подряд неатомарны.
- Кандидаты: `renamex_np` с `RENAME_SWAP` на APFS либо журналируемая последовательность с восстановлением из любой промежуточной точки. Выполняет короткоживущий помощник после выхода GUI.
- Старая версия сохраняется до подтверждения работоспособности новой.
- P0.5 проверяет убийство помощника и нового GUI на каждой границе, нехватку места, отсутствие прав, передачу `flock` и сокета.

Живые хосты не запускаются из бандла. Активная версия `shellio-host` копируется в `runtime/<version>/`. Старые поколения удаляются, когда их не использует ни одна сессия.

Версия протокола хоста и версия схемы хранения независимы. Если новая версия не совместима с работающими хостами, активация откладывается с явным сообщением. Агенты молча не перезапускаются.

Перед миграцией схемы делается согласованная резервная копия средствами SQLite. Автоматический откат без потери новых данных не обещается, если миграция необратима.

## Отвергнутые варианты

- Sparkle: технически работает с EdDSA и без Developer ID. Принята стоимость своего установщика и восстановления ради полностью Rust-кода и управления связкой GUI, хостов и runtime.
- Curl-установщик как основной путь: требование — Homebrew.

## Последствия

- Браузерная загрузка блокируется Gatekeeper, поддерживаемые пути — Homebrew и встроенное обновление.
- Приватный ключ minisign и сертификат — самое ценное в проекте, их потеря означает ручную переустановку.
- Релизы должны быть доступны без авторизации. Для приватного репозитория нужен отдельный публичный источник.

## Основания

- `detached/README.md`: самоподписанная идентичность и minisign. `detached/crates/app/src/update.rs:174–192`: два `rename`, что показывает, чего избегать. `detached/PLAN-EXTENSIBLE.md`: карантинный бинарник завершается при запуске, без карантина работает.
- `agterm/packaging/agterm.rb`: техника снятия карантина. Само это приложение нотаризовано, поэтому работу без нотаризации подтверждает только P0.5.
- `agterm/CLAUDE.md:180`: перезапись `zmx` и session host под живыми демонами вызывает `SIGKILL (Code Signature Invalid)`.
- [Homebrew Cask Cookbook](https://docs.brew.sh/Cask-Cookbook), [Sparkle](https://sparkle-project.org/documentation/), `man 2 rename`.

## Условие пересмотра

Ужесточение Gatekeeper в новой macOS или появление Developer ID.

## Уточнено в P0.1

План [toolchain-bootstrap](../plans/completed/20261111-toolchain-bootstrap.md) конкретизирует подпись. Решение не меняется.

- Bundle ID — `io.github.dsbasko.shellio`.
- Designated requirement задаётся явно и хранится в `scripts/signing/requirement.txt`: `designated => identifier "io.github.dsbasko.shellio" and certificate leaf = H"<SHA-1 сертификата>"`. Сравнивается каноническая форма из `codesign -d -r-`, а не исходный текст. Хэш сертификата публичен, закрытый ключ в репозиторий не попадает.
- Подпись выполняется по SHA-1 сертификата, а не по отображаемому имени. Без идентичности сборка бандла завершается ошибкой, ad-hoc подпись не подставляется.
- Доверие к сертификату не требуется. Самоподписанный сертификат OpenSSL с назначением Code Signing подписывает бинарь с явным requirement и проходит `codesign --verify --strict` на macOS 27.0.1 без доверия. Это проверено во временных keychain и в login keychain владельца: подпись из него идёт без запросов Keychain, две чистые сборки дают одинаковый requirement.
- Hardened runtime в P0.1 не нужен. Сохранение разрешений TCC по-прежнему проверяет P0.5.

## Уточнено в P0.5 (планирование)

План пробы P0.5 `probe-update-lifecycle` [дорожной карты](../roadmap.md) уточняет, что значит «передача `flock` и сокета» среди проверок протокола замены. Решение не меняется. Вывод пробы записывается отдельным разделом «Уточнено в P0.5» после прогона.

- Этот ADR перечисляет передачу блокировки и сокета среди проверок, а [ADR-0006](0006-single-instance.md) запрещает наследование их дескрипторов любым порождаемым процессом.
- Проба трактует передачу как смену владельца обычным взятием блокировки. Прежний владелец отпускает `flock` закрытием или выходом, следующий процесс берёт его сам. Дескрипторы не наследуются (`O_CLOEXEC`, `POSIX_SPAWN_CLOEXEC_DEFAULT`), брокера, который держит блокировку или сокет за другие процессы, нет.
- Сокет публикует только текущий владелец блокировки. В промежутке между владельцами управляющий API недоступен.
- Временный отказ CLI в этом промежутке допустим. Контракт доступности [ADR-0004](0004-process-model.md) непрерывной доступности не требует: при недоступном приложении CLI возвращает явную ошибку с признаком повторной попытки. ADR-0006 различает отказы «владелец запускается или перезапускается» и «недоступен».
- Если при такой трактовке оракулы владения пробы не проходят, это отрицательный вывод с передачей. Наследование дескрипторов или брокер стенд ради результата не вводит.

## Уточнено в P0.5

Вывод [отчёта P0.5](../probes/p0.5-update-lifecycle.md) по последнему полному прогону `make probe-update` 2026-11-18 (`20261118-202351-3355`, коммит `9451413`, 19 процессов без ошибок исполнения). Проба моделирует процессный контракт на macOS 27.0.1 собственным минимальным GUI, помощником, хостом и нагрузкой, подписанными `Shellio Dev`. Продуктовый загрузчик P5.2 пишет заново по выводам отчёта. Решение этого ADR не меняется.

**Итог — «не подтверждено: F/next-read».** Обязательные клетки протокола замены, восстановления, владения, рантаймов и несовместимости прошли все. Наблюдённый `fail` дало наблюдение Keychain: обновлённая версия молча не читает секрет прежней. TCC не наблюдалось (`not_run`), карантин через brew подтверждён. Отрицательный вывод передаётся новым ADR при планировании P4.1 или P5.2, раздел «Keychain» ниже.

Протокол замены (шаг 6):

- Выбран `renamex_np(RENAME_SWAP)` на одном томе APFS с журналом намерения `<state>/update/journal.json` и восстановлением из любой промежуточной точки. Журналируемая пара `rename` не понадобилась: убийства и гонки в 37 частях, настоящие ENOSPC и EACCES и инъекции EIO оставили восстановимое состояние, `ENOTSUP` не встретился.
- Состояния журнала: `idle`, `staged-deferred`, `staged`, `intent`, `swapped`, `launched`, `committed`, `cleaning`, `aborting`, `rollback-intent`, `rolled-back`, `retired`. Журнал пишет только владелец `shellio.lock`, перечитав его и сверив номер попытки и состояние-предусловие. Каждая мутация диска идёт после записанного решения, а при отказе записи журнала следующей мутации нет.
- Восстановление выполняет любой взявший блокировку при журнале не в `idle` и не в `staged-deferred`. Повторное восстановление ничего не меняет. Незнакомая раскладка, поколение, не прошедшее проверку, или повреждённый журнал дают явную ошибку без перестановок.
- Поколение на диске определяет `codesign --verify --strict --deep -R=<требование>` вместе с CDHash. Процесс опознаётся по CDHash из ядра, а не по пути.
- `EXDEV` при кандидате на другом томе прерывает попытку (`aborting`), остаётся N. Поэтому шаг 5 «на той же файловой системе» проверяется явно до `staged`.
- Обмен занимает около 73 мс от старта помощника, `launched` — около 327 мс.

Проверка кандидата (шаг 4): кандидат с изменённым после подписи файлом, кандидат с тем же CN и другим сертификатом и кандидат с другим идентификатором отвергнуты до `intent`. Установка, журнал и живая сессия при этом не тронуты.

Подтверждение работоспособности. Старая версия хранится в каталоге попытки и проходит `codesign` до `committed`. N+1 подтверждается только при выполнении всех условий:

- исполняемый файл и CDHash процесса ожидаемые;
- N+1 — единственный владелец блокировки, его сокет отвечает своим поколением;
- каждая живая сессия найдена, attach согласовал версию, хвост без пропуска, квитанция ввода;
- процессы хостов и нагрузок прежние.

Срок задаётся один раз при `intent` (60 с в пробе) и проверяется под блокировкой перед записью. Сторож помощника снимает ровно процесс с ключом владельца, а подтверждение до срока побеждает. Откат после необратимой миграции схемы проба не проверяла.

Новый GUI и сессии (шаг 7), `runtime/<version>/` и несовместимость:

- GUI N+1, запущенный через LaunchServices, подключается к хостам, живущим из `runtime/1/`, по протоколу 1 без пропуска, а новая сессия идёт из `runtime/2/`.
- Прерванная подготовка `runtime/<N>/` восстанавливается, готовый каталог не перезаписывается. `runtime/1/` становится кандидатом на уборку только после остановки последнего своего хоста. Саму уборку делает P5.2.
- Несовместимый с живыми хостами кандидат откладывается: `staged-deferred` под заморозкой создания сессий, причина у клиента, хосты не перезапускаются, лидерство и размер сессии прежние. После остановки несовместимой сессии тот же кандидат активируется.

Передача `flock` и сокета по разделу «Уточнено в P0.5 (планирование)» подтверждена: двух владельцев нет, inode блокировки прежний, дескрипторы не наследуются, второй запуск получает квитанцию или явный временный отказ без ложного успеха. Порядок владения записан в [ADR-0006](0006-single-instance.md), раздел «Уточнено в P0.5».

TCC:

- Не наблюдалось. Все 48 частей обоих графов (разрешённый бандл и контроль `.denied`) и обоих вариантов запуска хоста — `not_run` с причиной «выдача владельца не выполнена или устарела: нет tcc-grant.json». Шаг выдачи `make probe-update-tcc-grant` не выполнялся.
- Сохранение разрешений TCC для GUI и для хостов старого поколения по-прежнему не считается автоматическим. Других категорий, кроме `SystemPolicyDocumentsFolder`, проба не проверяла.
- По правилу плана `responsibility_spawnattrs_setdisclaim` не выбран и автоматически не включается. Передача: решение по disclaim и TCC хостов — P2.1 ([ADR-0004](0004-process-model.md), «Уточнено в P0.5»), сохранение разрешений GUI N+1 после обновления — P5.2. GUI-часть передана в P5.2 решением исполнителя по [ADR-0036](0036-autonomous-execution.md), основание — в отчёте, раздел «Передачи».

Keychain:

- Отрицательный вывод. Item, созданный версией N через Security API с доступом только для собственного кода, получает partition ID `cdhash:<CDHash N>`. Версия N+1 с тем же designated requirement и другим CDHash при запрещённом взаимодействии получает `errSecAuthFailed` без окна. Кандидат с чужим сертификатом тоже получает отказ, item не меняется.
- Постоянная подпись сохраняет требование к коду, но для самоподписанного кода доступ к Keychain при обновлении не сохраняет. CDHash меняется с каждым релизом, в пробе — даже при неизменных исходниках, из-за вшитого коммита.
- Пределы вывода:
  - наблюдалась временная файловая keychain, механизм legacy keychain, как у login;
  - Data Protection keychain не проверялась, ей нужен entitlement с provisioning profile;
  - что отказ дал partition ID, выведено, а не трассировано;
  - чтение с разрешённым взаимодействием, где по исходникам Apple ожидается запрос пароля keychain, не проверялось.
- Передача: решение о хранении секретов при обновлении принимается новым ADR при планировании P4.1 или P5.2. ACL и partition list под результат не подгонялись.

Карантин:

- Подтверждено через изолированный Homebrew 7.0.14. Cask с `preflight_steps`, снимающими `com.apple.quarantine` со staged-копии, даёт установленный самоподписанный бандл без карантина, и `open` запускает его без окна Gatekeeper.
- Тот же бандл без снятия карантина Gatekeeper не запускает. Его окно по умолчанию предлагает «Переместить в Корзину», и Escape или Return выбирают именно её.
- `spctl --assess` отвергает оба бандла, запуску без карантина это не мешает.
- Передача в P5.3: понятное сообщение при ошибке снятия карантина учитывает это окно. Публичный tap и чистая установка на другой машине — тоже P5.3.

Не проверялось: `latest.json`, minisign и публикация релиза (P5.1), загрузка и сетевые ошибки (P5.2, P5.3), резервная копия и миграция SQLite.
