# ADR-0021: Стратегия проверки

- Статус: Proposed
- Дата: 2026-11-09
- Дополнено [ADR-0034](0034-probe-code.md): GUI-проба проверяется своей целью `make probe-<имя>` и ручной приёмкой, `make e2e` относится к продукту. Решение не меняется.
- Изменено [ADR-0036](0036-autonomous-execution.md): уровень «Ручная приёмка» и правило о пунктах ручной приёмки заменены приёмочным проходом исполнителя, владелец участвует только в планировании.

## Контекст

Планы выполняются автономно, а проверить AppKit-интерфейс без дисплея нельзя. Заявлять готовность UI по `cargo test` нельзя.

## Решение

| Уровень | Что проверяет | Как |
| --- | --- | --- |
| Чистые crate | Модель, раскладка, keymap, парсеры, журнал ревью, сообщения | `cargo test` без окна |
| Контракт плагинов | Модель панели во всех зонах и размерах, кардинальность, снимки и восстановление | Фикстуры `Geometry`, без AppKit |
| Интеграция | Реальные `git` во временных репозиториях, `forge-fake`, поддельный агент, реальные хосты | `cargo test` |
| E2E | Реальное приложение с изолированным `SHELLIO_STATE_DIR`, команды и чтение результата через `shellioctl`, снимки экрана | `make e2e`, нужен сеанс GUI |
| Ручная приёмка | Внешний вид, темы, IME, VoiceOver, ощущения | Чек-лист владельца в плане |

Общий рубеж `make check`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. `make e2e` запускается отдельно.

Правила:

- Тесты не касаются настоящего каталога состояния и не содержат `sleep` для синхронизации.
- Сеть в тестах только к локальному `forge-fake`, запись на настоящие сервисы только в приватные песочницы вручную.
- План, содержащий UI-результат, перечисляет пункты ручной приёмки, и ralphex не закрывает их автоматически.
- Обновление libghostty проходит регрессионный набор (ADR-0003).
- Производительность: измеряется набор сценариев, бюджеты из `docs/architecture.md`. Рост сверх бюджета — дефект.

## Отвергнутые варианты

- Только юнит-тесты: UI остаётся без проверки.
- XCUITest: требует Swift-таргета в проекте на Rust.

## Последствия

Управляющий API становится ещё и тестовым интерфейсом, поэтому чтение результата для каждой команды обязательно.

## Основания

`agterm/CLAUDE.md` (Toolchain and gates), `detached/CLAUDE.md` (Tests).

## Условие пересмотра

Если E2E окажутся нестабильными на runner CI, они останутся локальным рубежом.

## Уточнено в P0.1

План [toolchain-bootstrap](../plans/completed/20261111-toolchain-bootstrap.md) конкретизирует рубеж. Решение не меняется.

- `make check` сначала сверяет набор ghostty (`scripts/ghostty/vendor.sh --verify`), затем выполняет `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings` и `cargo test --locked`. Всё это идёт под блокировкой набора, без опубликованного `vendor/ghostty/` рубеж не проходит.
- Вне `make check`: `make test-scripts` (публикация набора на поддельном наборе и идентичность подписи на временных keychain), `make bindings-check`, `make link-audit` и `make check-bundle`. Все они выполняются в CI, `make check-bundle` — при заданных секретах подписи.
- Целям `make test-bundle` и `make run` нужны настоящая идентичность и запуск через `open`. Они входят в приёмку, но не в CI.

## Уточнено в P1.3 (планирование)

Решение плана P1.3 `appkit-foundation` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-22. Решение не меняется, статус остаётся `Proposed`. Ручную приёмку заменяет приёмочный проход исполнителя ([ADR-0036](0036-autonomous-execution.md)), чтения `ui.*` записаны в [ADR-0007](0007-control-api.md), раздел «Уточнено в P1.3 (планирование)».

**Два сценария `make e2e`.** Цель внутри блокировки `vendor/ghostty.lock` собирает и проверяет бандл скриптами, затем запускает по очереди `single-instance.sh` P1.2 без изменений и новый `scripts/e2e/appkit.sh`. Каталоги прогонов — `target/e2e/single-instance/<время>-<pid>/` и `target/e2e/appkit/<время>-<pid>/`. Код цели — наибольший из кодов сценариев по порядку 1 > 3 > 0. Второй сценарий запускается и после кода 3 первого, после кода 1 — нет. `appkit.sh` устроен как `single-instance.sh`: временные профили `/tmp/shellio-e2e.*`, PID только из `hello`, сверенный с бинарём бандла, `result.json` с теми же полями, коды 0/1/3, уборка по сверенным PID. В `check` и CI цель не входит.

**Оракул участков.** Снимок — `screencapture -x -o -l <windowNumber>` по номеру окна из `ui.window` этого владельца. Сравнивает его чистый crate `shellio-e2e` (бинарь `shellio-e2e-oracle`):

- ожидания независимы от приложения: оракул сам разбирает `prototype/css/tokens.css` и таблицу [ADR-0027](0027-focused-panel-contrast.md) и вычисляет цвет слота с вуалью и тоном. От `shellio-theme`, которым рисует приложение, он не зависит. Файл ожиданий называет компонент, участок внутри его кадра и слот;
- участок — медиана пикселей прямоугольника с отступом не меньше 4 точек от краёв компонента, текста и линий. Линии тоньше 8 точек мерятся только поперечной серией пикселей;
- PNG всегда один раз переводится в sRGB по профилю файла. Допуск — не больше 3 единиц на канал. Допуск и участки фиксируются до первого прогона и после результата не меняются;
- кадры `ui.inspect` переводятся в строки PNG умножением на `backingScaleFactor` и отражением по высоте содержимого, размер PNG сверяется с кадром окна до сравнения;
- доказательство отрисовки берётся из самого PNG: маркер 8×8 ячеек в углу галереи кодирует 64-битное поколение. Остальные участки сравниваются только на снимке с совпавшим маркером, не дождались его за 3 с — `fail` пункта;
- перед первым пунктом снимков оракул проверяет себя заведомо неверным ожиданием. Принял его — ошибка исполнения «оракул не различает цвета», код 1;
- сравнение снимка целиком, байтовое равенство PNG и «непустой файл» критериями не являются. Совпадение на встроенном дисплее подтверждает результат только для него.

**Предусловия `make e2e`.** К условиям P1.2 добавляются разрешения Screen Recording и Accessibility у терминала-предка, латинская раскладка и выключенные оконные менеджеры (AeroSpace). Частота экрана — условие только пунктов задержки. Проба предусловий идёт до первого пункта по окну владельца служебного профиля и на пиксели продукта не смотрит:

- Screen Recording — `CGPreflightScreenCaptureAccess`, захват окна владельца без ошибки и размер PNG, равный кадру окна из `ui.window`, умноженному на `backingScaleFactor`;
- Accessibility и Automation для System Events — чтение имени процесса с PID владельца прогона без отказа доступа и `-1743`.

Отсутствие любого условия — ошибка исполнения «предусловие: …», код 1, до первого пункта, а не `fail` и не `pass`.

**Ошибка предусловия и дефект вида не смешиваются.** При подтверждённом доступе неверный цвет или пустое содержимое окна — `fail` пункта. Неверный номер окна или отказ захвата посреди прогона — ошибка исполнения с диагностикой. Участки вне допуска при годном маркере остаются `fail` с числами и профилем PNG, допуск не меняется. То, чего автоматика не наблюдает (речь VoiceOver, системное переключение оформления, холодные кэши без `sudo purge`), получает `not_run` с причиной.

**Замеры.** Бюджеты — из `docs/architecture.md`, рост сверх бюджета — `fail` пункта. Три исхода замера не смешиваются: режим недоступен — `not_run` по правилу плана, годная серия сверх бюджета — `fail`, сбой измерителя — ошибка исполнения.

## Уточнено в P1.3

Вывод плана P1.3 [`appkit-foundation`](../plans/completed/20261122-appkit-foundation.md) по `make check` и приёмочному проходу исполнителя 2026-11-22. Решение не меняется, статус остаётся `Proposed`.

**Рубеж `appkit.sh` не снят.** Цель `make e2e` запускает `single-instance.sh`, затем `appkit.sh`, код цели — наибольший по порядку 1 > 3 > 0. Рецепт исполнялся в каждом настоящем прогоне задач 10–14, `single-instance.sh` в них — код 0. Настоящий `appkit.sh` во всех прогонах вышел ошибкой «предусловие: запущен оконный менеджер AeroSpace» до первого пункта: AeroSpace запустил владелец, а исполнитель приложения владельца не закрывает ([ADR-0036](0036-autonomous-execution.md)). Итоговый прогон — `target/e2e/appkit/20261122-194156-33832/`. Поэтому каждый пункт `appkit.sh` подтверждён только наблюдением — копией сценария без AeroSpace в списке оконных менеджеров, рубежом она не считается. Итоговая копия `target/e2e/appkit/20261122-194158-35050/` вышла с кодом 3: все обязательные пункты `pass`, кроме `key-latency-120` (`fail` по правилу плана, [ADR-0002](0002-ui-stack-appkit.md), «Уточнено в P1.3»). `system-appearance`, `voiceover` и `startup-cold` — `not_run` по правилу, `key-latency-60` — `not_run` «нет экрана 60 Гц».

**Оракул подтверждён тестами** (`crates/shellio-e2e`, интеграционные тесты на синтетических PNG и модульные тесты; цвета ожиданий в них посчитаны вручную, без палитры оракула):

- Смешение вуали и тона идёт в кодированных значениях sRGB, как `rgba()` в CSS, с одним округлением в конце. Модель проверена на настоящих снимках галереи до выбора участков: смешение в линейном свете дало бы у подложки под вуалью в тёмной ячейке (38, 36, 33) вместо ожидаемых (28, 26, 24), снимок показал (29, 26, 23).
- sRGB признаётся по приоритету PNG третьей редакции: `cICP`, затем любой `iCCP` — отказ с именем профиля, затем чанк `sRGB`, затем пара `gAMA` и `cHRM` со значениями sRGB. Эту пару без чанка `sRGB` пишет `sips --matchTo` файлу, который уже был в sRGB. Сырой снимок `screencapture` несёт профиль Display P3 и отвергается, сценарий переводит его в копию.
- Бинарь `shellio-e2e-oracle`: подкоманды `compare`, `marker` и `underline` (поперечная серия через линию под вкладкой), коды 0 — все участки в допуске, 1 — ошибка исполнения, 2 — неверный вызов, 3 — маркер совпал, но участок вне допуска, 4 — отрисовка ожидаемого поколения не наблюдалась.
- Самопроверка заведомо неверным слотом (`chrome` → `text`) обязана дать код 3.

**Ограничение участков.** В тёмной ячейке и обеих ячейках Increase Contrast фон `chrome` и `panel` под вуалью расходятся не больше чем на 3 единицы: вуаль по [ADR-0027](0027-focused-panel-contrast.md) сдвигает фон к тону окна. Там участок подложки без фокуса не отличает её отсутствие от фона окна, это различает только светлая ячейка (10 единиц). Отсутствие вуали, тона и перестановку слоёв участки различают во всех ячейках.

**Находки сценария**, продукт не менялся:

- System Events разрешает каждую ссылку на строку `AXTable` от корня и заново берёт все `AXRows`. У таблицы на 10 000 строк одно чтение текста ячейки занимало секунды, а обход в глубину с заходом в таблицу не укладывался в минуты. Обход `ax` читает только сверяемые строки по индексу, поиск других элементов в `AXTable` и `AXOutline` не заходит.
- Щелчок `CGEvent` через `ObjC.bindFunction` со структурой `CGPoint` не доставлялся. Работает мост JXA `ObjC.import('CoreGraphics')` того же `osascript -l JavaScript`, нового инструмента не нужно.
- `awk` BSD с кириллическими ключами отдавал одно значение на все ключи, ключи разбора — ASCII.
- `hello` отвечает раньше, чем владелец дописывает строку готовности: сценарий ждёт строку с режимом окна со сроком.
- Сразу после запуска владельца цикл главного потока часто просыпается ([ADR-0020](0020-concurrency.md), «Уточнено в P1.3»), поэтому `idle` начинается после затишья: прирост не больше двух пробуждений за секунду, срок 30 с.

**Не подтверждено:** защита обработчика сигналов сценария от повторного сигнала. Прерывание одним сигналом наблюдалось: владельцы остановлены, `result.json` записан.

**Передача:** формальный рубеж `appkit.sh` при выключенном AeroSpace — в следующем плане шага P1.3 (Post-Completion плана).

## Уточнено в P1.3: закрытие шага

Решение владельца 2026-11-22, принятое до судящего прогона. Решение не меняется, статус остаётся `Proposed`. Бюджет 16 мс прежний ([ADR-0002](0002-ui-stack-appkit.md), «Уточнено в P1.3: закрытие шага»).

**Протокол замера задержки клавиш списка.** Пункты `key-latency-120` и `key-latency-60` идут блоками A B B A на одном владельце галереи. Каждый блок — `gallery.reset`, режим тактов, фокус списку, 10 прогревочных и 100 учитываемых нажатий Down, каждое после отметки отрисовки предыдущего:

- A — с тактами `CADisplayLink` всю серию, как в плане `appkit-foundation`;
- B — без display link: `gallery.list.ticks` выключен, список его не заводит.

Бюджет судят оба блока B: p95 «событие → первая отрисовка списка с новым выбором» не больше 16 мс в каждом. Отложенная системой отрисовка входит в замер, показ композитором после неё — нет. Частота — штатный режим экрана с `maximumFramesPerSecond`, равным частоте пункта (встроенный ProMotion для `key-latency-120`); принудительной частоты замер не задаёт. Блоки A — диагностика влияния display link, бюджет они не судят. Сбой измерителя в любом блоке — ошибка исполнения, превышение в годном блоке B — `fail` пункта и вопрос владельцу с рядами.

**Почему A не судит.** Display link будит главный цикл каждый кадр, и при нём пробуждения цикла собраны у такта. Пять серий плана `appkit-foundation` с тактами дали p95 17,79–18,04 мс. Прогон `target/e2e/appkit/20261122-233400-27480/` по прежнему протоколу дал 17,97 мс, а пилотная серия без тактов на его дереве — 12,30 мс (`target/e2e/appkit/20261122-233740-41210/`). Замер с тактами меняет то, что мерит.

**Опрос готовности не меняется.** После каждого нажатия стенд по-прежнему читает `ui.stats`, а каждое чтение ставит в очередь пустое событие приложения. Опрос одинаков в A и B, поэтому их сравнение проверяет только display link. Помеха опроса может лишь добавить задержку: B судится с ней.

**Внешняя помеха `make e2e`.** Сценарий запускается из терминала-предка, и тот может выйти вперёд сам, например при обновлении своего окна. Первый прогон без AeroSpace (`target/e2e/appkit/20261122-233400-27480/`) потерял передний план посреди `ax`: вперёд вышел терминал-предок. В том же прогоне `idle` насчитал 32 пробуждения при пороге 20, причина не установлена. Следующий прогон (`target/e2e/appkit/20261122-233740-41210/`, пилотная сборка, отличалась только отключёнными тактами списка) прошёл оба пункта, итоговые — тоже. Пока идёт прогон, терминал-предок не должен получать вывод и фокус.

**Итог прогонов 2026-11-22 и 2026-11-23**, AeroSpace выключен, весь `make e2e`:

- `target/e2e/appkit/20261122-233400-27480/`, прежний протокол, вариант 2 активации — код 3: `ax` и `idle` — `fail` (внешняя помеха выше), `key-latency-120` — 17,97 мс, остальные обязательные пункты `pass`.
- `target/e2e/appkit/20261122-233740-41210/`, пилот без тактов — код 1: прежний разбор требовал тактов и дал сбой измерителя, p95 серии — 12,30 мс; остальные обязательные пункты `pass`.
- `target/e2e/appkit/20261122-234713-63364/`, вариант 1 — код 1 до первого пункта: самопроверка оракула, участок строки списка за кадром (ниже).
- Вариант 1 правила «Первый передний план» ([ADR-0006](0006-single-instance.md), «Уточнено в P1.3: закрытие шага»), `target/e2e/appkit/20261122-234830-67993/`: `key-latency-120` — B 14,34 и 14,18 мс, A 18,19 и 18,08 мс.
- Итоговое дерево, два прогона подряд, итог `make e2e` 0, все обязательные пункты обоих сценариев `pass`:
  - `target/e2e/single-instance/20261122-235338-90135/` и `target/e2e/appkit/20261122-235350-92384/`: B 12,74 и 12,67 мс, A 20,25 и 20,11 мс;
  - `target/e2e/single-instance/20261122-235659-5828/` и `target/e2e/appkit/20261122-235711-8134/`: B 11,99 и 12,30 мс, A 19,87 и 17,98 мс.
- Разложение по p95 итоговых блоков: у B доставка до `keyDown:` 3,8–4,9 мс, свой код 1,2–1,4, отрисовка 7,5–7,9; у A доставка 9,0–11,5 мс при тех же своём коде и отрисовке, пробуждения цикла собраны у такта. Разница между A и B лежит в участке доставки события. Это воспроизводимый эффект включённого на главном цикле display link в этой конфигурации; механизм задержки не установлен.
- `idle` — 3 пробуждения за 10 с, CPU до 0,1 %. `startup-warm` — максимум 240,3 и 255,5 мс при бюджете 500. `system-appearance`, `voiceover`, `startup-cold` — `not_run` по правилу, `key-latency-60` — `not_run` «нет экрана 60 Гц».

**Участок строки списка сдвинут из-за раскладки.** При постоянных полосах прокрутки, которые система включает в режиме «автоматически», например при подключённой мыши, строка списка уже на 17 точек: 243 вместо 260. Участки `list.row` и `list.selected` выходили за кадр строки, и самопроверка оракула давала ошибку исполнения (`target/e2e/appkit/20261122-234713-63364/`). Их начало перенесено с x 160 на 140 во всех четырёх ячейках, до сравнения цвета. Отступ от подписи механически не проверяется, конец подписи «Строка 00003 · 0» оценён по её длине примерно в 110 точек.

## Уточнено в P1.4 (планирование)

Решение плана P1.4 `layout-zones` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-23. Решение не меняется, статус остаётся `Proposed`. Модель раскладки и чтение `query.layout` записаны в [ADR-0009](0009-layout-and-zones.md) и [ADR-0007](0007-control-api.md), разделы «Уточнено в P1.4 (планирование)».

**Три сценария `make e2e`.** После `single-instance.sh` и `appkit.sh` третьим идёт `scripts/e2e/layout.sh`: раскладка в обычном окне по матрице приёмки плана P1.4. Каждый следующий сценарий запускается после кода 0 или 3 предыдущего и не запускается после кода 1. Ошибка исполнения обычно означает несостоятельное предусловие, общее для всех трёх сценариев. Правило для третьего сценария выбрал исполнитель как ближайшее к правилу раздела «Уточнено в P1.3 (планирование)». Код цели — наибольший из кодов запущенных сценариев по порядку 1 > 3 > 0.

**`layout.sh` устроен как `appkit.sh`.** Сценарий работает на подписанном бандле во временном профиле `/tmp/shellio-e2e.*` в обычном режиме окна. PID берётся только из `hello` и сверяется с бинарём бандла. `result.json` имеет те же поля, коды те же (0, 1, 3), уборка идёт по сверенным PID. Предусловия — как у `appkit.sh`, новых нет.

- Выход — `target/e2e/layout/<время>-<pid>/`: `result.json` и сырые выводы пунктов (JSON `query.layout` и `ui.*`, AX, PNG).
- Подготовка идёт штатным CLI: `workspace new`, `project add` на временный каталог, `workbench new`, `workbench open`.
- Каждый пункт сверяет чтение `query.layout` и независимо от него кадры, роли и значки по `ui.inspect` и AX окна (System Events). Кадры совпадают в пределах 1 точки, допуск не расширяется.
- Пункт `restore-legacy` начинает с профиля из фикстуры SQL схемы v1 (`scripts/e2e/layout-fixtures/`). Ожидания снимков лежат в `scripts/e2e/layout-expect/*.json`.
- **Условие пункта.** Пункты отказа и заглушки перед действием читают `query.layout` и проверяют своё условие: ширину целевой части и `min_size` в ответе. Если условие не выполнено, это ошибка исполнения «условие пункта», а не `fail`.

**Режим оракула без маркера.** Маркер поколения рисует только галерея, в обычном окне его нет. Поэтому подкоманды `compare` и `underline` получают режим без маркера. Снимок принимается, когда на двух снимках подряд после квитанции действия медианы каждого проверяемого участка совпадают в пределах допуска сравнения (3 единицы на канал), а поколение отрисовки из `ui.window` между снимками не изменилось. Устойчивость участков заменяет доказательство отрисовки маркером и критерием пункта не является. Снимок целиком и байты PNG по-прежнему не сравниваются, участки затем судятся по ожиданиям, как в P1.3. Срок ожидания совпадения — 3 с, как у маркера. Если совпадения нет, оракул выходит с кодом 4 «отрисовка поколения не наблюдалась», и пункт получает `fail`. Остальные правила оракула P1.3 не меняются: самопроверка, перевод в sRGB, допуск и участки, зафиксированные до первого прогона. Режим проверяют тесты на синтетических PNG: совпадение двух снимков, расхождение и истёкший срок.

## Уточнено в P1.4

Вывод плана P1.4 [`layout-zones`](../plans/completed/20261123-layout-zones.md) по `make check` и приёмочному проходу исполнителя 2026-11-23. Решение не меняется, статус остаётся `Proposed`.

**Рубеж `layout.sh` формально не пройден.** Итоговый `make e2e` на коде плана: `single-instance.sh` — код 0, все обязательные пункты `pass` (`target/e2e/single-instance/20261123-164922-76517/`). `appkit.sh` — код 1 «предусловие: запущен оконный менеджер AeroSpace» до первого пункта (`target/e2e/appkit/20261123-164936-79009/`). `layout.sh` не запускался, итог цели — 1. В окружении исполнителя, кроме того, источник ввода `RussianWin` и единственный экран — внешний, 60 Гц, без встроенного. Поэтому пункты `appkit.sh` и `layout.sh` подтверждены только наблюдением — копиями сценариев без проверок AeroSpace и источника ввода, рубежом они не считаются. Формальный прогон передан владельцу (Post-Completion плана).

**Наблюдение `layout.sh`** (`target/e2e/layout/20261123-165339-97795/`, код 3): все обязательные пункты матрицы `pass`, кроме `layout-snapshot`. У него светлая тема и линии под активной вкладкой в обеих темах в допуске, а тёмная тема на этом экране не судится (условие экрана ниже). `voiceover-speech` и `system-contrast` — `not_run` с причиной.

**Наблюдение `appkit.sh`** на итоговом коде (`target/e2e/appkit/20261123-164941-80251/`, код 3): регрессии P1.4 нет, не `pass` только пункты окружения:

- `snapshot-dark`, `contrast-cells` (ячейка `dark-ic`) и `appearance-live` (тёмная ячейка) — экран, как у `layout-snapshot`;
- `tabstrip-regimes` — меню «…» полосы половины открывается через 4,8–4,9 с после запуска `osascript` при сроке пункта 3 с. Один вызов AX здесь стоит около 16 мс на элемент у любого процесса, у Finder столько же: это свойство машины в этом окружении, а не приложения;
- `window-cycle` — ключевое окно при запущенном AeroSpace, в прогоне до последней правки кода тот же пункт — `pass`;
- `key-latency-120` — `not_run`: экран 60 Гц;
- `key-latency-60` — `fail`: p95 блоков B 19,4–21,8 мс в двух прогонах. Это первый замер на экране 60 Гц, в P1.3 такого экрана не было, сравнить не с чем. Замер шёл при запущенном AeroSpace, вердикт даёт формальный прогон.

**Условие экрана для снимков.** Пункты снимков — `snapshot-*`, `contrast-cells` и `appearance-live` у `appkit.sh`, `layout-snapshot` у `layout.sh` — судятся на экране, где эталон P1.3 в допуске, например на встроенном дисплее Display P3. На внешнем экране Redmi 27 NU тон фокуса тёмной темы выходит за допуск у галереи и у плитки одинаково: `#111415` при ожидаемом `#101011`, расхождение 4. В прогоне P1.3 на встроенном экране те же участки галереи дали расхождение 0 (`target/e2e/appkit/20261122-235711-8134/`). Сырой PNG до `sips` уже несёт это значение, и сдвинулись участки без слоёв (`chrome.background` на 1–2), чего слой плитки дать не может. Это условие прогона, как частота экрана у пунктов задержки. Допуск не меняется, ворота по эталону в сценарии не заводятся: они переименовали бы `fail` в `not_run` при том же коде 3.

**Оракул без маркера** (`crates/shellio-e2e`, раздел «режим без маркера» в `tests/oracle.rs`). У `compare` и `underline` флаги `--previous-window`, `--previous-png` и `--elapsed-ms` идут вместе и без `--generation`. Срок решает библиотека оракула (`SETTLE_MS` = 3000): пока снимки не совпали и срок не истёк — код 4 и `"retry": true`, после срока — код 4 и `"retry": false`. Сценарий повторяет снимок только при `retry: true`. Пара совпала, когда медианы каждого участка в допуске, у `underline` — каждый пиксель столбца, а поколения `ui.window` и `ui.inspect` обоих снимков равны. Предыдущий снимок другого размера или кадра окна — ошибка исполнения.

**Коды цели** считает `scripts/e2e/codes.sh` (`combine`, `next`, `result`, `check`), его проверяет `crates/shellio-e2e/tests/codes.rs`. Рецепт `make e2e` вызывает его и сам коды не считает.

**Условия пунктов места** судятся числом 200×120 (`MIN_W` и `MIN_H` в `layout.sh`): `query.layout` не отдаёт `min_size` панели, а до P1.5 оно у всех панелей одно. Это уточняет «ширину целевой части и `min_size` в ответе» раздела планирования.

**Находки сценария**, продукт не менялся:

- System Events разрешает элементы окна по имени процесса. При двух живых владельцах одного бандла он читал чужое окно, поэтому основной владелец выходит до `restore-legacy`, а AX опрашивается со сроком.
- Кнопки строки вкладок лежат внутри `AXTabGroup` с описанием строки («Вкладки центра, часть 2», у развёрнутой — «Вкладки развёрнутой панели»), их находит обход дерева AX по описанию.
- bash 3.2 принимал байт не-ASCII символа сразу после имени переменной за часть имени, поэтому такие переменные записаны как `${…}`. Пустой массив под `set -u` в bash 3.2 роняет сценарий.
- Тест `instance::leftover_sockets_are_replaced_by_new_owner_only` (`crates/shellio-control/tests/instance.rs`) один раз упал в `make check` и прошёл повтором. Вероятная причина — давняя гонка: соседний тест того же бинаря порождает процесс, и между `fork` и `exec` потомок держит копию дескриптора слушающего сокета. Если повторится — отдельная правка теста.
