# ADR-0021: Стратегия проверки

- Статус: Proposed
- Дата: 2026-11-09
- Дополнено [ADR-0034](0034-probe-code.md): GUI-проба проверяется своей целью `make probe-<имя>` и ручной приёмкой, `make e2e` относится к продукту. Решение не меняется.
- Изменено [ADR-0036](0036-autonomous-execution.md): уровень «Ручная приёмка» и правило о пунктах ручной приёмки заменены приёмочным проходом исполнителя, владелец участвует только в планировании.

## Контекст

Планы выполняются автономно, а проверить AppKit-интерфейс без дисплея нельзя. Заявлять готовность UI по `cargo test` нельзя.

## Решение

| Уровень | Что проверяет | Как |
| --- | --- | --- |
| Чистые crate | Модель, раскладка, keymap, парсеры, журнал ревью, сообщения | `cargo test` без окна |
| Контракт плагинов | Модель панели во всех зонах и размерах, кардинальность, снимки и восстановление | Фикстуры `Geometry`, без AppKit |
| Интеграция | Реальные `git` во временных репозиториях, `forge-fake`, поддельный агент, реальные хосты | `cargo test` |
| E2E | Реальное приложение с изолированным `SHELLIO_STATE_DIR`, команды и чтение результата через `shellioctl`, снимки экрана | `make e2e`, нужен сеанс GUI |
| Ручная приёмка | Внешний вид, темы, IME, VoiceOver, ощущения | Чек-лист владельца в плане |

Общий рубеж `make check`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`. `make e2e` запускается отдельно.

Правила:

- Тесты не касаются настоящего каталога состояния и не содержат `sleep` для синхронизации.
- Сеть в тестах только к локальному `forge-fake`, запись на настоящие сервисы только в приватные песочницы вручную.
- План, содержащий UI-результат, перечисляет пункты ручной приёмки, и ralphex не закрывает их автоматически.
- Обновление libghostty проходит регрессионный набор (ADR-0003).
- Производительность: измеряется набор сценариев, бюджеты из `docs/architecture.md`. Рост сверх бюджета — дефект.

## Отвергнутые варианты

- Только юнит-тесты: UI остаётся без проверки.
- XCUITest: требует Swift-таргета в проекте на Rust.

## Последствия

Управляющий API становится ещё и тестовым интерфейсом, поэтому чтение результата для каждой команды обязательно.

## Основания

`agterm/CLAUDE.md` (Toolchain and gates), `detached/CLAUDE.md` (Tests).

## Условие пересмотра

Если E2E окажутся нестабильными на runner CI, они останутся локальным рубежом.

## Уточнено в P0.1

План [toolchain-bootstrap](../plans/completed/20261111-toolchain-bootstrap.md) конкретизирует рубеж. Решение не меняется.

- `make check` сначала сверяет набор ghostty (`scripts/ghostty/vendor.sh --verify`), затем выполняет `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings` и `cargo test --locked`. Всё это идёт под блокировкой набора, без опубликованного `vendor/ghostty/` рубеж не проходит.
- Вне `make check`: `make test-scripts` (публикация набора на поддельном наборе и идентичность подписи на временных keychain), `make bindings-check`, `make link-audit` и `make check-bundle`. Все они выполняются в CI, `make check-bundle` — при заданных секретах подписи.
- Целям `make test-bundle` и `make run` нужны настоящая идентичность и запуск через `open`. Они входят в приёмку, но не в CI.

## Уточнено в P1.3 (планирование)

Решение плана P1.3 `appkit-foundation` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-22. Решение не меняется, статус остаётся `Proposed`. Ручную приёмку заменяет приёмочный проход исполнителя ([ADR-0036](0036-autonomous-execution.md)), чтения `ui.*` записаны в [ADR-0007](0007-control-api.md), раздел «Уточнено в P1.3 (планирование)».

**Два сценария `make e2e`.** Цель внутри блокировки `vendor/ghostty.lock` собирает и проверяет бандл скриптами, затем запускает по очереди `single-instance.sh` P1.2 без изменений и новый `scripts/e2e/appkit.sh`. Каталоги прогонов — `target/e2e/single-instance/<время>-<pid>/` и `target/e2e/appkit/<время>-<pid>/`. Код цели — наибольший из кодов сценариев по порядку 1 > 3 > 0. Второй сценарий запускается и после кода 3 первого, после кода 1 — нет. `appkit.sh` устроен как `single-instance.sh`: временные профили `/tmp/shellio-e2e.*`, PID только из `hello`, сверенный с бинарём бандла, `result.json` с теми же полями, коды 0/1/3, уборка по сверенным PID. В `check` и CI цель не входит.

**Оракул участков.** Снимок — `screencapture -x -o -l <windowNumber>` по номеру окна из `ui.window` этого владельца. Сравнивает его чистый crate `shellio-e2e` (бинарь `shellio-e2e-oracle`):

- ожидания независимы от приложения: оракул сам разбирает `prototype/css/tokens.css` и таблицу [ADR-0027](0027-focused-panel-contrast.md) и вычисляет цвет слота с вуалью и тоном. От `shellio-theme`, которым рисует приложение, он не зависит. Файл ожиданий называет компонент, участок внутри его кадра и слот;
- участок — медиана пикселей прямоугольника с отступом не меньше 4 точек от краёв компонента, текста и линий. Линии тоньше 8 точек мерятся только поперечной серией пикселей;
- PNG всегда один раз переводится в sRGB по профилю файла. Допуск — не больше 3 единиц на канал. Допуск и участки фиксируются до первого прогона и после результата не меняются;
- кадры `ui.inspect` переводятся в строки PNG умножением на `backingScaleFactor` и отражением по высоте содержимого, размер PNG сверяется с кадром окна до сравнения;
- доказательство отрисовки берётся из самого PNG: маркер 8×8 ячеек в углу галереи кодирует 64-битное поколение. Остальные участки сравниваются только на снимке с совпавшим маркером, не дождались его за 3 с — `fail` пункта;
- перед первым пунктом снимков оракул проверяет себя заведомо неверным ожиданием. Принял его — ошибка исполнения «оракул не различает цвета», код 1;
- сравнение снимка целиком, байтовое равенство PNG и «непустой файл» критериями не являются. Совпадение на встроенном дисплее подтверждает результат только для него.

**Предусловия `make e2e`.** К условиям P1.2 добавляются разрешения Screen Recording и Accessibility у терминала-предка, латинская раскладка и выключенные оконные менеджеры (AeroSpace). Частота экрана — условие только пунктов задержки. Проба предусловий идёт до первого пункта по окну владельца служебного профиля и на пиксели продукта не смотрит:

- Screen Recording — `CGPreflightScreenCaptureAccess`, захват окна владельца без ошибки и размер PNG, равный кадру окна из `ui.window`, умноженному на `backingScaleFactor`;
- Accessibility и Automation для System Events — чтение имени процесса с PID владельца прогона без отказа доступа и `-1743`.

Отсутствие любого условия — ошибка исполнения «предусловие: …», код 1, до первого пункта, а не `fail` и не `pass`.

**Ошибка предусловия и дефект вида не смешиваются.** При подтверждённом доступе неверный цвет или пустое содержимое окна — `fail` пункта. Неверный номер окна или отказ захвата посреди прогона — ошибка исполнения с диагностикой. Участки вне допуска при годном маркере остаются `fail` с числами и профилем PNG, допуск не меняется. То, чего автоматика не наблюдает (речь VoiceOver, системное переключение оформления, холодные кэши без `sudo purge`), получает `not_run` с причиной.

**Замеры.** Бюджеты — из `docs/architecture.md`, рост сверх бюджета — `fail` пункта. Три исхода замера не смешиваются: режим недоступен — `not_run` по правилу плана, годная серия сверх бюджета — `fail`, сбой измерителя — ошибка исполнения.
