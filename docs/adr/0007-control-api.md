# ADR-0007: Управляющий API и CLI

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

Терминал и всё приложение должны полностью управляться внешними вызовами, чтобы фоновые задачи и агенты могли работать с ними.

## Решение

Единый слой команд: действие из меню, по клавише, из палитры и из CLI вызывает один и тот же типизированный `Command` с одним обработчиком. Новое действие считается законченным, когда у него есть команда, CLI, чтение результата и тесты.

Транспорт: Unix-сокет с правами `0600` и проверкой UID собеседника, JSON построчно, лимит 1 МиБ на запрос. Первая команда клиента — `hello` с версией протокола. Ошибки структурированы и имеют стабильные коды. Путь сокета короче 104 байт.

CLI `shellioctl` (названия уточняются в P1.2):

- `tree`, `status`, `version`
- `workspace|project|workbench list|new|open|focus|rename|close`
- `panel list|open|focus|move|hide|close-view|remove`
- `pane text|type|paste|run|search|resize|copy`
- `session list|start|stop|attach`
- `agent list|start|status|ask|task|cancel`
- `msg send|read|ack`
- `events --since <cursor>`, `metrics`, `keymap reload`, `config reload`

Цель всегда задаётся явно (`--target`) либо берётся из окружения `SHELLIO_SESSION_ID`, `SHELLIO_PANEL_ID`, `SHELLIO_SOCKET`. Команда с явной целью не зависит от текущего фокуса.

Вывод — JSON с `--json`, иначе человекочитаемый. Каждая команда, меняющая состояние, видна в `tree` или в собственном чтении.

События: журнал с монотонным курсором. Клиент, потерявший поток, получает снимок и ревизию. Команды, которым нужен UI при закрытом окне, возвращают явный результат `no-ui`.

Сокет защищает от других пользователей, но не изолирует процессы одного пользователя.

Потоковая трансляция вывода терминала в протокол не входит. Чтение экрана — разовая команда.

## Отвергнутые варианты

- Отдельный API для CLI: логика разойдётся с интерфейсом.
- gRPC и HTTP: лишний вес для локального канала.

## Последствия

Плагин, добавляющий действие, обязан объявить его как команду. Ручное действие без команды — дефект.

`agterm/.claude/rules/control-api.md`, `agterm/CLAUDE.md` (Cross-surface contracts), `agterm/plugins/agterm/skills/agterm/reference.md`.

## Уточнено в P1.1

Решение плана P1.1 `core-domain`, принятое при планировании 2026-11-21. Слой команд и транспорт не меняются.

- **Команды P1.1:** `workspace.create`, `workspace.rename`, `project.add`, `workbench.create`, `workbench.rename`, `workbench.open`, `window.focus_workspace`. **Чтения:** `query.tree` с явной областью `Workspace(id)` или `All` ([ADR-0025](0025-workspaces-and-project-catalog.md): внешний CLI без контекста сессии задаёт область сам) и `query.status`.
- **Формат JSON.**
  - `Command` — внутренний тег `cmd` с именем команды, поля в `snake_case`: `{"cmd":"workspace.create","title":"Работа"}`. Имена в команде — строки как есть: пустое или неверное имя отвергает обработчик кодом `invalid_argument`, а не разбор.
  - `Query` — `{"query":"tree","scope":{"workspace":"…"}}`, `{"query":"tree","scope":"all"}` или `{"query":"status"}`.
  - `Reply` — `{"revision":12,"value":{…}}`. Значение без тега: дерево, состояние хранилища или значение команды — `{"workspace":…}`, `{"project":…,"root":…}`, `{"workbench":…}` или `null`. Варианты различаются набором полей, поэтому разбор однозначен.
  - `Event` — `{"revision":12,"changes":[{"change":"workspace_renamed",…}]}`.
  - `Snapshot` — `{"revision":12,"state":{…}}`, `EventsSince` — `{"events":[…]}` или `{"reset":снимок}`.
  - `CoreError` — `{"code":"root_taken","message":"…","retryable":false,"details":{…}}`. `retryable` следует из кода: повтор только у `storage_unavailable` и `busy`. Разбор `CoreError` с `retryable`, не совпадающим с кодом, отказывает.
  - Лишнее поле и неизвестный вариант отвергаются у всех типов границы, входящих и исходящих, включая записи модели в снимке. Порядок ключей объекта в контракт не входит: эталоны сравниваются как значения JSON.
- **Стабильные коды ошибок:** `invalid_argument`, `not_found`, `name_taken`, `root_taken`, `storage_unavailable`, `storage_conflict`, `busy`, `shutting_down`. Имена команд, чтений, изменений и коды закреплены эталонными JSON в `crates/shellio-core/tests/wire/`. После P1.1 они не переименовываются: новый смысл получает новый вариант.
- **Детали отказа:**
  - `invalid_argument` — `field` и `reason`, у пути ещё `path`;
  - `not_found` — `entity` и `id`;
  - `name_taken` — `entity`, `name` и `existing`;
  - `root_taken` — `project` и `workspace` владельца корня.
- **Стабильные причины `invalid_argument`:**
  - имя: `title_empty`, `title_too_long`, `title_control_char`, `title_required` (у канонического пути корня нет последнего компонента в UTF-8, имя по умолчанию не вычисляется);
  - путь корня: `path_not_absolute`, `path_not_found`, `not_a_directory`, `path_unreadable`, `path_not_utf8`, `git_link_invalid` ([ADR-0025](0025-workspaces-and-project-catalog.md), «Уточнено в P1.1»);
  - позиция: `position_exhausted` с деталью `scope` (`workspaces`, `project_list`, `workbenches`) — после наибольшей позиции родителя места нет;
  - курсор: `cursor_ahead` — курсор событий больше текущей ревизии.
- **Скрытые записи.** Удалённый воркспейс, убранный проект, проект удалённого воркспейса и рабочие области таких проектов для команд — `not_found`, удалённый или несуществующий воркспейс в области `query.tree` — тоже: дерево их не показывает.
- **`query.status`** сообщает ревизию, версию схемы, путь `state.db` и диагностику загрузки `{table, rowid, reason}` со стабильными причинами ([ADR-0018](0018-storage-and-config.md), «Уточнено в P1.1»).
- **Ревизия.** Ревизия хранится в `state.db` и растёт в той же транзакции, что и изменение, поэтому монотонна через перезапуски. Курсор событий — ревизия. Журнал событий живёт в памяти: курсор старше буфера или из прошлого запуска получает снимок и ревизию. Загрузка с находками значит, что базу правили в обход ядра: запуск тогда пишет одну запись, пусть и без дельт, и не кладёт её в журнал, поэтому снимок получает и курсор, равный ревизии загрузки, а курсор этого запуска — пустой список. Команда, не меняющая состояние, отвечает без новой ревизии и без события: переименование в то же имя, фокус активного воркспейса, открытие уже открытой рабочей области. Переименование, меняющее только регистр, — изменение.
- Внутренние команды запуска ядра (первый воркспейс, когда нет ни одного неудалённого, фокус, когда активный воркспейс пуст или удалён, и маршрут активного воркспейса, когда окно ведёт в скрытую рабочую область) в `Command` не входят и в JSON не сериализуются. Их изменения идут обычными событиями.
- **Законченное действие в P1.1 — частично:** команда, обработчик, чтение результата и тесты.
  - CLI каждой команды и чтения P1.1 — обязательная часть P1.2: `workspace new|rename|focus`, `project add`, `workbench new|rename|open`, `tree`, `status`. Вместе с ними P1.2 вводит конверт запроса с номером, `hello` с версией протокола, `events --since` и проверку области по ADR-0025.
  - Имя в keymap и UI этих действий — P1.7.

## Уточнено в P1.2 (планирование)

Решение плана P1.2 `single-instance-control`, принятое при планировании 2026-11-21. Слой команд и транспорт не меняются, статус остаётся `Proposed` до P2.3. Владение сокетом записано в [ADR-0006](0006-single-instance.md), проверка области — в [ADR-0025](0025-workspaces-and-project-catalog.md), разделы «Уточнено в P1.2 (планирование)».

**Протокол v1** (`shellio-control::wire`): JSON построчно, конверт с номером запроса, `hello` первым, лимит входящей строки 1 МиБ. Команды, чтения, ответы, события и `CoreError` — типы P1.1 как есть. Ошибки транспорта — отдельный тип `ControlError` со своими стабильными кодами. Одно соединение обслуживает запросы по одному, подписка делает соединение потоковым до закрытия.

| Направление | Форма |
| --- | --- |
| запрос `hello` | `{"id":1,"hello":{"protocol":1,"client":"shellioctl 0.1.0"}}` |
| ответ `hello` | `{"id":1,"ok":{"hello":{"protocol":1,"server":"0.1.0","pid":123,"owner":"ready"}}}` |
| команда | `{"id":2,"command":{"cmd":"workspace.rename",…},"scope":{"workspace":"…"}}` |
| чтение | `{"id":3,"query":{"query":"tree","scope":"all"}}` |
| события по курсору | `{"id":4,"events_since":{"cursor":12},"scope":"all"}` |
| подписка | `{"id":5,"subscribe":{},"scope":"all"}` |
| аргументы запуска | `{"id":6,"launch":{"args":["/abs/path"],"cwd":"/abs"}}` |
| ответ | `{"id":2,"ok":<Reply P1.1>}`, `{"id":4,"ok":<EventsSince P1.1>}`, `{"id":6,"ok":{"launch":{"activation":"requested","refused":[{"arg":"/abs/path","reason":"folder_open_unsupported"}]}}}` |
| отказ ядра | `{"id":2,"core_error":<CoreError P1.1>}` |
| отказ транспорта | `{"id":2,"error":<ControlError>}`, `id` равен `null`, если номер не разобран |
| поток подписки | `{"id":5,"snapshot":<Snapshot>}`, затем `{"id":5,"event":<Event>}`…, при отставании `{"id":5,"reset":<Snapshot>}` |

- `scope` — форма `TreeScope` P1.1: `"all"` или `{"workspace":"<id>"}`. У `hello`, `query` и `launch` поля `scope` нет: лишнее поле — `malformed_request`.
- `owner` в `hello` — `ready` или `leaving`. Состояние `starting` по сокету не наблюдается: сокет публикуется после готовности. Повторный `hello` на том же соединении разрешён и отвечается так же.
- `activation` — `requested` (вызов на главном потоке выполнен) или `no_ui` (UI нет, только у тестового владельца `shellio-owner-fixture`).
- Причины отказа аргумента запуска: `folder_open_unsupported`, `not_a_directory`, `path_not_found`, `unknown_argument` от владельца и локальная `arg_not_utf8` второго запуска ([ADR-0006](0006-single-instance.md)). Квитанция с отказами — успех передачи.
- Поток подписки кончается кадром `owner_leaving` при завершении владельца или обрывом без него.
- Лишнее поле и неизвестный вариант отвергаются во всех кадрах (`deny_unknown_fields`), как у типов P1.1.
- Сервер ограничивает только входящие строки. Ответ (дерево, снимок) лимитом не ограничен, клиент принимает строки до 64 МиБ.
- Собеседник проверяется на принятом соединении: UID из `peer_cred` против UID процесса, чужое соединение закрывается без ответа.

**Коды `ControlError`.** `retryable` следует из кода, как у `CoreError`. Коды закрепляются эталонами в `crates/shellio-control/tests/wire/` и после P1.2 не переименовываются.

| Код | Повтор | Когда |
| --- | --- | --- |
| `hello_required` | нет | первый запрос не `hello` |
| `protocol_mismatch` | нет | версия клиента не поддерживается; `details.supported` |
| `malformed_request` | нет | строка не разбирается как кадр; соединение остаётся |
| `request_too_large` | нет | строка длиннее 1 МиБ до перевода строки; соединение закрывается |
| `scope_required` | нет | у команды, `events_since` или `subscribe` нет `scope` |
| `scope_unsupported` | нет | `events_since` и `subscribe` с областью воркспейса |
| `owner_leaving` | да | владелец завершает работу |
| `not_running` | да | только клиент: блокировка свободна или нет файла |
| `owner_starting` | да | только клиент: блокировка занята, сокета нет до срока |
| `unavailable` | да | только клиент: подключение или ответ не уложились в срок при занятой блокировке |
| `outcome_unknown` | нет | только клиент: после полной отправки мутации или `launch` истёк срок, оборвалось соединение или пришёл негодный ответ |

**Новая причина `invalid_argument`:** `scope_requires_all` с полем `scope` — `workspace.create` с областью воркспейса. Она дополняет список стабильных причин раздела «Уточнено в P1.1».

**Правило `outcome_unknown`.** У вызова клиента один абсолютный срок на подключение, `hello`, запись запроса и чтение ответа, и он прерывает каждую из этих операций. До полной отправки запроса и для чтений исход срока повторяемый. После полной отправки мутации или `launch` срок, обрыв или негодный ответ — `outcome_unknown`, такой запрос не повторяется. Строка ответа длиннее 64 МиБ — код 1 у чтения и `outcome_unknown` у мутации и `launch`.

**`launch`** — служебный вход повторного запуска, а не действие пользователя: его вызывает только второй процесс `shellio`. В `shellioctl` и keymap его нет, правило законченного действия на него не распространяется.

**CLI `shellioctl`** — тонкая оболочка над клиентом `shellio-control::client`: разбор аргументов вручную, вызов, вывод JSON или текста, код выхода. Названия P1.2:

| Вызов | Запрос |
| --- | --- |
| `version` | `hello` |
| `status` | `query.status` |
| `tree (--workspace <id> \| --all)` | `query.tree` |
| `workspace new <title> --all` | `workspace.create` |
| `workspace rename [--target <id>] <title> (--workspace <id> \| --all)` | `workspace.rename` |
| `workspace focus [--target <id>] (--workspace <id> \| --all)` | `window.focus_workspace` |
| `project add <path> [--title <t>] [--target <id>] (--workspace <id> \| --all)` | `project.add` |
| `workbench new --target <project> <title> (--workspace <id> \| --all)` | `workbench.create` |
| `workbench rename --target <id> <title> (--workspace <id> \| --all)` | `workbench.rename` |
| `workbench open --target <id> (--workspace <id> \| --all)` | `workbench.open` |
| `events --since <cursor> --all` | `events_since` |
| `events --follow --all` | `subscribe` |

- Внешний `shellioctl` без контекста сессии всегда задаёт область явно. У команд с целью-воркспейсом `--target` по умолчанию равен `--workspace`, с `--all` он обязателен. Цель из `SHELLIO_SESSION_ID` и `SHELLIO_PANEL_ID` — P2.x.
- `--workspace` и `--all` у `status` и `version` — ошибка использования до отправки.
- `project add` делает путь абсолютным через `std::path::absolute` от рабочего каталога CLI, без канонизации: канонизирует ядро.
- `events --since` читает журнал по курсору, `events --follow` подписывается: первый кадр — снимок, затем события, при отставании — `reset` с новым снимком. У `--follow` срок действует только до первого кадра. `--since` и `--follow` вместе — ошибка использования.
- `--timeout <мс>` у любого вызова задаёт срок клиента, по умолчанию 5000. Тестового флага сроков в продукте нет.
- Адрес: `--socket <path>`, иначе `SHELLIO_SOCKET`, иначе `<state>/shellio.sock` профиля. С явным адресом проба `flock` не делается, недоступность — `unavailable` по сроку.
- `--json` печатает ответ кадра как есть, построчно для `events --follow`, иначе — человекочитаемый текст. Ошибка — в stderr, при `--json` — JSON ошибки в stdout.
- Остальные вызовы списка решения (`list`, `close`, `panel`, `pane`, `session`, `agent`, `msg`, `metrics`, `keymap reload`, `config reload`) появляются в своих шагах, `pane` и `session` — в P2.3.

| Код выхода | Когда |
| --- | --- |
| 0 | успех |
| 1 | отказ ядра или неповторяемый отказ транспорта |
| 2 | ошибка использования |
| 69 | `not_running` |
| 74 | `outcome_unknown` |
| 75 | повторяемый отказ: `owner_starting`, `owner_leaving`, `unavailable`, `busy`, `storage_unavailable` |

Поток `events --follow` кончается кодом 75: по кадру `owner_leaving` или по обрыву без него (`unavailable`).

**Сроки:** повтор через 50 мс, срок 5 с у CLI (меняет `--timeout`), 10 с у второго запуска, 1 с у шагов отмены и отправки при завершении владельца. Сроки идут через внедряемый порт часов, тесты в процессе управляют ими вручную.

**Исключение из заморозки формата P1.1.** Решение владельца при планировании 2026-11-21: до публикации протокола v1 `TreeView.route` становится `Option<Route>`, а `active_workspace` и `route` в дереве равны `null`, если активный воркспейс вне области. Значение `Some` сериализуется как прежде, поэтому эталон `reply.tree` не меняется, а новый случай закрепляет эталон `reply.tree.scoped_inactive`. Исключение разовое: после публикации v1 через `hello` формат меняется только новыми вариантами.

## Уточнено в P1.2

Вывод плана P1.2 `single-instance-control`. Протокол v1, сервер, клиент и `shellioctl` реализованы по разделу «Уточнено в P1.2 (планирование)» в `crates/shellio-control` и `apps/shellioctl`, решение не меняется. Статус остаётся `Proposed` до P2.3: CLI терминала и сессий ещё нет. Владение сокетом и итог приёмки — в [ADR-0006](0006-single-instance.md), раздел «Уточнено в P1.2».

**Подтверждено тестами:** каждая команда и чтение P1.1 через сокет видны в `query.tree`; `hello_required`, `protocol_mismatch`, повторный `hello`, `request_too_large` закрывает соединение, `malformed_request` его оставляет; матрица области двух воркспейсов в обход CLI; `events_since` внутри буфера, `Reset` вне его и `cursor_ahead`; подписка — снимок, затем события подряд, при отставании `reset` с новым снимком; медленный подписчик не задерживает команды другого соединения; порядок завершения с `owner_leaving`; `outcome_unknown` у мутации после квитанции ядра и повторяемый исход у чтения; `shellioctl` отдельным процессом — каждая команда и чтение с `--json` и текстом, `events --since`, `events --follow` до ухода владельца (код 75), состояния `not_running`, `owner_starting` и `unavailable` с кодами выхода. Коды `ControlError` и все кадры закреплены эталонами в `crates/shellio-control/tests/wire/`.

**Форма, которую раздел планирования не задавал** (закреплена эталонами и тестами `crates/shellio-control/tests/{wire,server,client}.rs`, `apps/shellioctl`):

- Пустая строка — строка: разбор даёт `malformed_request` с `id: null`. У `protocol_mismatch` деталь `supported` — массив чисел (`[1]`), у `request_too_large` — `limit` в байтах, у остальных кодов `details` пуст.
- `arg_not_utf8` входит в перечень причин отказа аргумента с пометкой «только локально»: квитанцию второй запуск печатает одним типом.
- `scope_required` и `scope_unsupported` выдаёт сам разбор кадра. Порядок отказов: строгий разбор (`malformed_request` с номером, если номер читается без остального кадра), затем ровно один вид запроса, затем область.
- До `hello`: негодная строка остаётся `malformed_request`, `scope_required` и `scope_unsupported` отвечаются `hello_required`, разобранный запрос не `hello` — `hello_required`. `protocol_mismatch` оставляет соединение без приветствия.
- Ключ `id` обязателен в каждом кадре ответа, `null` допустим только у кадра `error`. `null` на месте вида или области — `malformed_request`, а не отсутствие поля.
- Производный `Deserialize` из serde принимает структуру и в виде массива, как у типов P1.1: `{"id":1,"hello":[1,"x"]}` разбирается как `hello`. Это не лишнее поле и не неизвестный вариант, запрет потребовал бы ручного разбора всех кадров и типов P1.1.
- При уходе владельца прочитанная строка всегда получает ответ (`owner_leaving`, у `hello` — `ok` с `owner: "leaving"`), после него соединение закрывается. Недочитанная строка не отвечается, бездействующее соединение закрывается без кадра. Срок 1 с ограничивает только записи, ожидание ответа ядра им не ограничено.
- Подписку обслуживает задача её соединения: ввод клиента в потоке не отвечается, конец ввода закрывает соединение, отказ ядра при подписке — кадр `core_error`.

**CLI:**

- `--json` печатает кадр сервера целиком, построчно у `events --follow`. Отказ клиента со своим кодом печатается в stdout кадром `{"id":null,"error":<ControlError>}` той же формы, что отказ транспорта сервера, stderr при этом пуст. Ошибка использования (код 2) идёт текстом в stderr в обоих режимах.
- Негодный ответ у чтения (не разобран, длиннее 64 МиБ, не относится к запросу) и неудачная проба блокировки (например, нет прав на `shellio.lock`) дают код 1 без кода протокола: таблица `ControlError` не расширяется. Такие сбои, как и сбой профиля и записи вывода, идут текстом в stderr и при `--json`. У мутации и `launch` негодный ответ — `outcome_unknown`.
- `--workspace` у `workspace new` и `events` — ошибка использования до отправки: таблица задаёт им только `--all`. Явный `--target` под `--workspace` уходит как есть, область проверяет сервер.
- `hello` с `owner: leaving` у команды, чтения и подписки даёт `owner_leaving` без отправки запроса и без повтора внутри клиента, код 75. `version` печатает ответ `hello` как есть, в том числе с `leaving`, код 0.
- Срок подключения при занятой блокировке: последний отказ `ENOENT` или `ECONNREFUSED` — `owner_starting`, иначе и при сроке внутри самого подключения — `unavailable`. С явным адресом срок всегда даёт `unavailable`.
- `shutting_down` в список кода 75 не входит и даёт 1: допущенный запрос сервер доводит до ответа раньше остановки ядра.
- Флаги и операнды в любом порядке, `--флаг=значение`, `--` кончает флаги, `-h` и `--help` печатают справку с кодом 0. Нет ни `HOME`, ни `SHELLIO_STATE_DIR` при отсутствии явного адреса — код 1.

**Передача:** цель из `SHELLIO_SESSION_ID` и область по сессии — P2.x, `pane` и `session` — P2.3, `open-or-focus` из CLI — P1.5, `shellioctl` в бандле и ссылка Homebrew — P5.1 и P5.3.

## Уточнено в P1.3 (планирование)

Решение плана P1.3 `appkit-foundation` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-22. Слой команд и транспорт не меняются, статус остаётся `Proposed` до P2.3. Протокол v1 расширяется только новыми вариантами, эталоны P1.1 и P1.2 не меняются. Окно владельца и режим галереи записаны в [ADR-0006](0006-single-instance.md), раздел «Уточнено в P1.3 (планирование)».

**`UiCommand` в едином слое команд.** Действия интерфейса, которые не меняют состояния ядра, — варианты типизированного `UiCommand` (`crates/shellio-core/src/ui_command.rs`, чистый тип без обработчика) с одним обработчиком на главном потоке в `apps/shellio`. Меню, CLI, а с P1.6 клавиша и палитра вызывают этот обработчик. Актор ядра их не видит, поэтому `UiCommand` не входит в `Command` P1.1. Пользовательские действия P1.3:

| Действие | Команда | Имена в keymap |
| --- | --- | --- |
| закрыть окно | `window.close` | `window.close` |
| выйти | `app.quit` | `app.quit` |
| оформление | `ui.appearance.set` со значением `light`, `dark` или `system` | `ui.appearance.light`, `ui.appearance.dark`, `ui.appearance.system` |

У каждого действия есть команда, обработчик, CLI в `shellioctl`, чтение результата (`ui.window`) и тесты. Главное меню AppKit («shellio → Выйти», «Окно → Закрыть», «Вид → Оформление») вызывает тот же обработчик. Имена в keymap закрепляются здесь, их привязку в `keymap.toml` делает P1.6. Выбор оформления действует до выхода процесса, сохранение — P1.8.

**Запрос `ui`.** Новый вариант `RequestBody::Ui(UiRequest)`. Сервер передаёт его порту `UiHandler`, который реализует владелец через порт UI. Каждый запрос выполняется на главном потоке через `MainThread::exec` с ответом по каналу и сроком 2 с, главный поток не блокируется.

- Замыкание, не начатое к сроку, не выполняется, ответ — повторяемый `ui_timeout`.
- У начатого изменяющего запроса (`UiCommand`, `gallery.*`) срок не прерывает выполнения: срок истёк после начала — `outcome_unknown` P1.2, без повтора.
- `app.quit` отвечает `accepted` после постановки `terminate:` в очередь и до порядка завершения, ответ уходит до закрытия сервера.
- До готовности UI и у тестового владельца `shellio-owner-fixture` ответ — `no_ui`.
- `gallery.*` вне режима галереи — `gallery_only`.

Новые коды — `no_ui`, `ui_timeout`, `gallery_only`. Форма кадров `ui`, признак повтора `no_ui` и `gallery_only` и место кодов среди отказов закрепляются эталонами в `crates/shellio-control/tests/wire/` при реализации. Коды выхода `shellioctl` — по таблице P1.2.

**Запросы:**

- `ui.window` — PID, `windowNumber`, кадр в точках, `backingScaleFactor`, видимость, key, `colorSpace`, системный заголовок, ячейка и движение (эффективные и источник: система или переопределение), режим (`normal` или `gallery`), `maximumFramesPerSecond` экрана окна и список экранов с их частотой, ревизия зеркала, поколение отрисовки;
- `ui.inspect` — дерево компонентов окна, ограниченное видимой частью: у списков и деревьев только видимые строки и счётчики, кадр ответа меньше лимита строки протокола 1 МиБ. У компонента: идентификатор, класс компонента, кадр в точках окна, AX-роль, AX-имя, `accessibilityHelp`, выбор, раскрытие, first responder, видимость, число ключей анимаций у его слоёв, найденные классы материала с видимостью и состояние компонента;
- `ui.stats` — журнал анимаций по поколениям, счётчики созданных и живых экземпляров по классам `define_class!`, слабые ссылки на виды прежних деревьев галереи, созданные виды строк по каждому списку и дереву, `late_callbacks`, проходы отображения, занятость итераций цикла (число, максимум, p95 за окно), ряд задержек клавиш и старт процесса (`launchDate` → первая отрисовка окна key, содержащая первый снимок зеркала);
- `UiCommand` — `window.close`, `app.quit`, `ui.appearance.set`;
- `gallery.*` только в режиме галереи: `gallery.cell`, `gallery.motion`, `gallery.tabs.select`, `gallery.list.replace`, `gallery.list.scroll`, `gallery.tree.mutate`, `gallery.focus`, `gallery.menu.open`, `gallery.rebuild`, `gallery.window.recreate`, `gallery.place`, `gallery.reset`. Ответ — поколение состояния галереи. Каждый вариант входит в протокол вместе с наполнением галереи, промежуточного кода «не реализовано» нет.

**Служебные входы.** `ui.inspect`, `ui.stats` и `gallery.*` — входы тестов, как `launch` в P1.2: имён в keymap у них нет.

**Причина отказа аргумента запуска** `gallery_not_at_start` — `--gallery`, пересланный вторым запуском живому владельцу ([ADR-0006](0006-single-instance.md)). Это новый вариант закрытого перечня причин рядом с `folder_open_unsupported`, а не код ошибки. Квитанция с ним, как с прочими отказами, — успех передачи.

**CLI `shellioctl`:**

| Вызов | Запрос |
| --- | --- |
| `ui window` | `ui.window` |
| `ui inspect` | `ui.inspect` |
| `ui stats` | `ui.stats` |
| `ui appearance <light\|dark\|system>` | `ui.appearance.set` |
| `window close` | `window.close` |
| `app quit` | `app.quit` |
| `gallery <…>` | `gallery.*` |

`--json`, вывод ошибок и коды выхода — по правилам P1.2.

## Уточнено в P1.3

Вывод плана P1.3 [`appkit-foundation`](../plans/completed/20261122-appkit-foundation.md) по `make check` и приёмочному проходу исполнителя 2026-11-22. Слой команд и транспорт не меняются, статус остаётся `Proposed` до P2.3.

**Подтверждено тестами** (`crates/shellio-control/tests/{wire,ui,server}.rs`, `crates/shellio-core/src/ui_command.rs`, `apps/shellioctl/tests/cli.rs`, `apps/shellio/tests/owner.rs`):

- Отметка начала `UiGate` общая для сервера и главного потока. Работа, не начатая к сроку 2 с, отменяется и не выполняется: `ui_timeout`, повторяемый, код выхода 75. Начатый изменяющий запрос после срока — `outcome_unknown`, 74, начатое чтение — `ui_timeout`. Отказы порта `no_ui` и `gallery_only` — код 1. Тестовый владелец отвечает `no_ui`.
- `UiCommand` с именами команд и именами keymap закреплён эталоном имён. Главное меню, кнопка оформления и CLI вызывают один обработчик на главном потоке, id пунктов главного меню — имена keymap.
- `gallery_not_at_start` входит в закрытый перечень причин отказа с эталоном `response.ok.launch.gallery_not_at_start`.
- `shellioctl ui window|inspect|stats|appearance`, `window close`, `app quit` и `gallery …` с `--json` и кодами P1.2.

Вид ответов против настоящего владельца проверен только наблюдением: настоящий `appkit.sh` в прогонах плана не прошёл предусловие ([ADR-0021](0021-testing.md), «Уточнено в P1.3»).

**Форма, которую раздел планирования не задавал:**

- `Response` и `OkValue` теперь только `PartialEq`, без `Eq`: в ответе `ui` есть `f64` (кадры в точках, масштаб, миллисекунды). Формат кадров P1.1 и P1.2 не изменился.
- Ответ `gallery.*` — квитанция `accepted` с поколением, отдельного вида ответа нет. У `gallery.cell { appearance?, contrast? }` пропущенная ось снимает переопределение галереи. `gallery.focus` принимает `field`, `window`, `tabs`, `list`, `tree`. `gallery.place` с номером несуществующего экрана оставляет окно на месте, пишет строку в stderr и отвечает квитанцией, экран подтверждает `ui.window`.
- Состояние галереи в `ui.inspect` — необязательный ключ `gallery`: вне галереи ключа нет, поэтому прежние эталоны `ui.inspect` не изменились. `ui.stats` получил прежние деревья галереи с живыми объектами по классам, созданные виды строк по каждому списку и дереву, журнал анимаций с поколением публикации и ряд задержек клавиш `key_latency`.
- `app.quit` отвечает `accepted` с PID владельца и ставит `terminate:` таймером цикла после ответа ([ADR-0006](0006-single-instance.md), «Уточнено в P1.3»).
- Служебное чтение `ui.stats` после ответа ставит в очередь пустое событие приложения, которое сливает пул автоосвобождения `-[NSApplication run]`, поэтому следующее чтение видит отложенные освобождения ([ADR-0002](0002-ui-stack-appkit.md), «Уточнено в P1.3»). Цена — одно пробуждение цикла главного потока на каждое чтение `ui.stats`. Порог простоя это учитывает: в наблюдении 3–5 пробуждений за 10 с при пороге 20.

**Передачи:** привязка имён `window.close`, `app.quit`, `ui.appearance.*` в `keymap.toml` и подсказки кнопок с действующими клавишами — P1.6; сохранение выбора оформления — P1.8; `open-or-focus` из CLI — P1.5.

## Уточнено в P1.4 (планирование)

Решение плана P1.4 `layout-zones` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-23. Слой команд и транспорт не меняются, статус остаётся `Proposed` до P2.3. Модель раскладки и её правила записаны в [ADR-0009](0009-layout-and-zones.md), хранение — в [ADR-0018](0018-storage-and-config.md), разделы «Уточнено в P1.4 (планирование)».

**Команды раскладки и панелей** — варианты `Command` ядра. Они меняют состояние и идут через актор. Кнопки, меню «…», главное меню и CLI, а с P1.6 клавиши и палитра вызывают одну и ту же команду.

| Команда | CLI `shellioctl` | Имена в keymap |
| --- | --- | --- |
| `layout.split {panel, open?}` | `layout split <panel> [--open <plugin>]` | `layout.split` |
| `panel.focus {panel}` или `{workbench?, direction}` | `panel focus <panel>` или `panel focus --dir h\|j\|k\|l` | `panel.focus.left`, `panel.focus.down`, `panel.focus.up`, `panel.focus.right` |
| `panel.select {panel}` | `panel select <panel>` | `panel.select` |
| `panel.move {panel, zone}` | `panel move <panel> --zone left\|right\|center\|bottom` | `panel.move.left`, `panel.move.down`, `panel.move.up`, `panel.move.right` |
| `panel.move_part {panel, anchor, edge?}` | `panel move-part <panel> --to <anchor-panel> [--edge before\|after]` | `panel.move_part.next`, `panel.move_part.prev` |
| `panel.close {panel}` | `panel close <panel>` | `panel.close` |
| `layout.resize {workbench?, zone, part_of?, size}` | `layout resize --zone <z> [--part-of <panel>] <size>` | `layout.grow`, `layout.shrink`, `layout.wider`, `layout.narrower` |
| `layout.equal {workbench?, zone}` | `layout equal --zone <z>` | `layout.equal` |
| `layout.zoom {panel}` или `{workbench?, off}` | `layout zoom <panel>` или `layout zoom --off` | `layout.zoom` |
| `layout.only {workbench?}` | `layout only` | `layout.only` |
| `layout.visibility {workbench?, target, visible}` | `layout show\|hide navigator\|plate\|right\|bottom` | `layout.toggle.navigator`, `layout.toggle.plate`, `layout.toggle.right`, `layout.toggle.bottom` |

- Имя команды на проводе пишется в `snake_case` после точки, как `window.focus_workspace`. `panel.move-part` из [ADR-0031](0031-zone-splits.md) — то же действие: дефис остаётся написанием CLI (`panel move-part`), а команда называется `panel.move_part`.
- `direction` принимает `left`, `down`, `up` и `right` (в CLI `h`, `j`, `k`, `l`), `zone` — `left`, `right`, `center` и `bottom`. Имена `panel.move.*` (`Ctrl-w H/J/K/L`) переносят панель в левую, нижнюю, центральную и правую зону. Имена `panel.move_part.next` и `panel.move_part.prev` берут якорем активную вкладку соседней части вдоль оси зоны.
- У `layout.resize` без `part_of` значение `size` — размер зоны в точках, с `part_of` — доля части этой панели в тысячных. Имена `layout.grow`, `layout.shrink`, `layout.wider` и `layout.narrower` (`Ctrl-w + - > <`) означают относительные шаги, шаг и пересчёт в `size` задаёт P1.6.
- `layout.only` и имена `layout.toggle.*` переключают состояние, а CLI задаёт видимость явно (`show`, `hide`). Центр не скрывается и в цели `layout.visibility` не входит.
- `off` у `layout.zoom` — `true`: снять разворот рабочей области.
- Значение ответа — `null`, у `layout.split` с `open` — новая панель `{"panel":…}`. Новое значение отличается набором полей от значений P1.1, поэтому разбор `Reply` остаётся однозначным. Команда, которая раскладку не меняет (фокус уже на этой панели, вкладка уже активна), отвечает без новой ревизии и без события, как в P1.1.

**Рабочая область команды.** Команда с панелью берёт рабочую область этой панели. Команда без панели берёт `workbench`, а без него — открытую рабочую область окна (`Route::Workbench`). Если открытой нет, команда отказывает `no_open_workbench`. Во всех вызовах CLI `--workbench <id>` задаёт рабочую область явно. Область запроса задаётся так же, как у остальных команд P1.2: `--workspace <id>` или `--all`.

**Область доступа** ([ADR-0025](0025-workspaces-and-project-catalog.md)). Цель команды — `Target::Workbench` её рабочей области. Панель или рабочая область вне области доступа отвечает `not_found` так же, как несуществующая. Открытая рабочая область вне области доступа при запросе без `workbench` тоже даёт `not_found`, но её идентификатор не раскрывается: детали `entity: "workbench"` и `id: null`.

**Чтение `query.layout {scope, workbench?}`.** Область задаётся внутри чтения, как у `query.tree`, рабочая область выбирается по тому же правилу, что у команд. Ответ — раскладка, панели рабочей области и `Frames` по текущему размеру окна, без размера — `frames: null`: `{"workbench":"…","layout":{…},"panels":[…],"frames":{…}}`. CLI — `shellioctl layout get [--workbench <id>]`, вывод — JSON.

**Внутренний вход размера окна.** `CoreHandle::set_viewport` вызывает главный поток. Как и внутренних команд запуска P1.1, этого входа нет ни в протоколе, ни в `Command`. Вход не меняет ревизию и не порождает событий: кадры адаптер считает той же чистой функцией из зеркала и своего размера. Без размера (процесс без UI, `shellio-owner-fixture`) команды, которым нужно место (`layout.split` и `layout.resize`), отказывают `no_ui`, остальные выполняются. Тестовая поддержка задаёт размер явно.

**Отказы.**

- Новый код `CoreError` — `no_ui`, без повтора: команде нужно место, а размера окна у ядра нет. Имя и смысл совпадают с кодом транспорта `no_ui` из P1.3, но приходит он в кадре `core_error`. Код выхода `shellioctl` — 1.
- В деталях `not_found` появляется новый вид записи — `panel`.
- Новые причины `invalid_argument`. По образцу `position_exhausted` это отказы по состоянию с собственными деталями:

| Причина | `field` | Детали | Когда |
| --- | --- | --- | --- |
| `split_needs_panel` | `open` | `panel` | деление одиночной вкладки без `open` |
| `split_no_room` | `panel` | `parts: [{panel, need, have}]`, где `need` и `have` — `{width, height}` в точках | затронутая часть станет меньше `min_size` активной панели |
| `navigator_not_splittable` | `panel` | — | деление панели в колонке навигатора |
| `no_open_workbench` | `workbench` | — | нет ни `workbench`, ни открытой рабочей области |
| `zone_empty` | `zone` или `target` | — | `layout.resize` и `layout.equal` для зоны без частей, `layout.visibility` для зоны без частей или пустой колонки навигатора |
| `resize_out_of_range` | `size` | `min`, `max` в единицах запроса | размер вне границ правила «Размеры» ADR-0009 |
| `plugin_invalid` | `open` | — | plugin id пустой, длиннее 64 символов или содержит символы вне `[a-z0-9-]` |
| `zone_not_resizable` | `zone` | `zone` | `layout.resize` центра без `part_of`: размер центра — остаток |
| `panel_not_in_zone` | `part_of` | `panel`, `zone` | `layout.resize` с `part_of` панели другой зоны |
| `navigator_column` | `anchor` или `part_of` | `panel` | якорь `panel.move_part` или `part_of` в колонке навигатора |
| `arguments_conflict` | лишнее или недостающее поле | — | `panel.focus` без `panel` и `direction` или с обоими, `layout.zoom` без `panel` и `off`, с обоими или с `off: false`, `workbench` рядом с `panel` |

Выбор кодов (`no_ui` как код ядра, отказы раскладки как причины `invalid_argument`, `zone_empty` для видимости, `plugin_invalid`) сделан исполнителем при записи этого раздела по правилу плана: ближайший к существующему контракту и самый дешёвый вариант.

Четыре последние строки таблицы добавлены при исполнении команд ядра по тому же правилу: это отказы модели, которых не было при планировании. У `zone_empty` деталь с именем поля (`zone` или `target`) называет пустую цель. Сочетание полей проверяется до актора, без снимка состояния. Повторно выданный `PanelId` новой панели — внутренняя ошибка `storage_conflict`, а не причина провода: идентификаторы выдаёт само ядро. `no_ui` проверяется после выбора рабочей области и разбора аргументов (`plugin_invalid`, `zone_not_resizable`), но до операции модели, поэтому без окна деление одиночной вкладки без `open` отвечает `no_ui`, а не `split_needs_panel`.

**События.** Новые варианты `Change`: `panel_add`, `panel_remove` и `layout_set`. Последний несёт раскладку рабочей области целиком. В снимок входят поля `panels` и `layouts`.

**Протокол v2** (решение владельца 2026-11-23). Раскладка входит в `State`, поэтому меняется форма снимка и `reset`, а события получают новые варианты. `hello` P1.2 сверяет только число версии. `shellioctl` прежней сборки прошёл бы `hello` у нового владельца и потом отверг бы снимок или событие. Поэтому `PROTOCOL` становится 2: клиент и владелец разных версий расходятся на `hello` кодом `protocol_mismatch` до первой команды. Смешанные версии не поддерживаются. Это отменяет обещание раздела «Уточнено в P1.3 (планирование)», что v1 расширяется только новыми вариантами и прежние эталоны не меняются. По решению владельца эталоны `hello` и снимка обновляются, новые кадры получают новые эталоны. Внутри v2 формат дальше меняется только новыми вариантами.

**Законченное действие.** У каждого действия таблицы есть команда, обработчик, CLI, чтение результата (`query.layout`), имя в keymap и тесты.

**Передачи:** привязки `Ctrl-w` в `keymap.toml` и шаги относительного размера — P1.6; `open-or-focus` через `panel.*` — P1.5.

## Уточнено в P1.4

Вывод плана P1.4 [`layout-zones`](../plans/completed/20261123-layout-zones.md) по `make check` и приёмочному проходу исполнителя 2026-11-23. Слой команд и транспорт не меняются, статус остаётся `Proposed` до P2.3. Ответы против настоящего владельца проверены только наблюдением: формальный `make e2e` в окружении исполнителя не прошёл предусловия ([ADR-0021](0021-testing.md), «Уточнено в P1.4»).

**Подтверждено тестами** (тесты обработчика `crates/shellio-core`, `crates/shellio-control/tests/{wire,server}.rs`, `apps/shellioctl/tests/cli.rs`):

- каждая команда таблицы раздела планирования на успех и на каждую причину отказа; деление и `zoom` с явной целью в части без фокуса — одна ревизия; `no_ui` без размера окна;
- матрица области двух воркспейсов: чужой `PanelId` в своей рабочей области и чужая открытая рабочая область без `workbench` отвечают как несуществующие, в том числе у `query.layout` через сырой сокет;
- протокол v2: `hello` v1 к новому владельцу и `hello` v2 к владельцу v1 (подделка сервера) получают `protocol_mismatch` до команды; клиент после `reset` видит полную раскладку;
- эталоны: протокол v2 изменил `request.hello`, `response.ok.hello` и `error.protocol_mismatch` (образец — запрос версии 1 у владельца v2), в снимках `response.snapshot`, `response.reset` и `response.ok.events_since.reset` появились поля `panels` и `layouts`, `events_since.reset` ядра несёт непустые панели и раскладку; новые — по одному на команду (`request.command.layout_*`, `request.command.panel_*`), `request.query.layout`, `response.ok.layout`, изменения `change.panel_add`, `change.panel_remove`, `change.layout_set`, ядро — `reply.layout`, `reply.panel`, `error.no_ui`; строгость разбора — лишнее поле, неизвестные `zone`, `edge` и цель видимости, размер окна в `query.layout`, чтение без области;
- `shellioctl layout …` и `panel …` отдельным процессом: каждая команда, ошибка использования, отказ ядра с кодом.

**Форма, которую раздел планирования не задавал:**

- Команды — варианты `Command` ядра с внутренним тегом `cmd`, как у P1.1, поэтому `shellio-control` их принимает без новых кадров. Двойные формы `panel.focus` и `layout.zoom` — один вариант с необязательными полями: serde не сочетает `flatten` с `deny_unknown_fields`. Сочетание полей проверяется до актора, отказ — `arguments_conflict`. Поле `open` — строка: иначе неверный plugin id ронял бы разбор кадра вместо `plugin_invalid`.
- У `Target` ядра появились `Panel` и `OpenWorkbench`. Якорь `panel.move_part` и `part_of` вне раскладки рабочей области получают `not_found` от модели, поэтому панель другой рабочей области неотличима от несуществующей. Явный `workbench` рядом с `part_of` чужой ему панели — `not_found` этой панели.
- `CoreHandle::set_viewport` пишет значение в `watch`, актор читает его на каждом запросе. Очередь актора не участвует, поэтому вход не блокирует главный поток, не получает `busy` и упорядочен с командами.
- Название панели из `open` — «Навигатор» и «Терминал» у известных плагинов, у остальных сам plugin id. `min_size` каждой панели до P1.5 — 200×120. Закрытие пишет `LayoutSet`, затем `PanelRemove`, деление с `open` — `PanelAdd`, затем `LayoutSet`: раскладка в событии не ссылается на отсутствующую панель.
- `ReplyValue::Layout` несёт кадры `f64`, поэтому `Reply` и `ReplyValue` сравниваются только `PartialEq`.
- **CLI.** Каждый вызов `layout` и `panel` требует области `--workspace <id>` или `--all`. Фраза раздела планирования «Во всех вызовах CLI `--workbench <id>` задаёт рабочую область явно» уточнена: `--workbench` принимают только формы без панели-операнда (`layout get|resize|equal|only|show|hide`, `layout zoom --off`, `panel focus --dir`). У остальных рабочую область задаёт панель, и флаг — ошибка использования с кодом 2, а не отказ ядра `arguments_conflict`. `--dir` принимает только `h`, `j`, `k`, `l`, `--open` уходит строкой, plugin id проверяет ядро. `layout get` печатает JSON раскладки и в текстовом режиме.
- Тесты `shellioctl` идут против владельца в процессе теста (`Owner::start_sized`): тот же сервер над ядром в памяти под настоящей блокировкой, размер окна задаётся до первого вызова. Путь бинаря `shellio-owner-fixture` из пакета `apps/shellio` тестам `apps/shellioctl` недоступен.
- **`ui.inspect` раскладки.** Узлы `layout`, `layout.split.{root,column,left,right,center,bottom}`, `layout.navigator`, `layout.part.<зона>.<номер>` (состояние `part`: зона, номер, вкладки, активная, показана, фокус, развёрнута) и его строка вкладок `….tabs`, `layout.zoom`, `layout.panel.<PanelId>` (состояние `panel`: `PanelId`, `ComponentId` вида, plugin id, название, показан, зона и класс размера тела), `layout.note`, `layout.picker` (меню выбора «Открыть в новой части», только пока оно открыто), заглушки `<место>.stub` и `<место>.stub.expand`, строка статуса `status` и `status.message`. Варианты `ComponentState::Part` и `ComponentState::Panel` добавлены в провод с эталоном `response.ok.ui.inspect.layout`.
- Подсказка кнопок строки вкладок: формат P1.3 «Развернуть панель. Клавиша не назначена» заменён на «Развернуть панель  Клавиша не назначена» с двумя пробелами, как подсказка с клавишей [ADR-0032](0032-split-and-zoom-buttons.md). Изменены значения `hint` в эталоне `response.ok.ui.inspect.tab_strip`, форма провода прежняя. Других изменений прежних эталонов `ui.*` нет.
- Узлы кнопок зон `chrome.zone.*` факта `selected` не несут: по проводу он означает выбор, а нажатие кнопки зон — значение AX-переключателя (подроль `AXToggle`, значение 1 или 0).
- Пункты меню «…» строки вкладок имеют id — имена keymap: `panel.move_part.prev|next`, `panel.move.left|right|down|up`, `panel.close`.
- Отказ команды, поданной из интерфейса, показывается текстом в строке статуса, отказ CLI — только вызывающему. Отказ `split_needs_panel` из интерфейса открывает выбор «Открыть в новой части» вместо сообщения.

**Отрицательный вывод.** Пункты зон главного меню «Вид» получили id `layout.visibility.navigator`, `layout.visibility.bottom` и `layout.visibility.side`, а не имена keymap `layout.toggle.*`, хотя правило раздела «Уточнено в P1.3» «id пунктов главного меню — имена keymap» действует. У третьего пункта цель меняется вместе с раскладкой (правая зона или плитка левой), одного имени keymap у него нет. Передача P1.6: при привязке клавиш id пунктов — имена keymap, третьему — имя по текущей цели или новое имя действия боковой зоны.

**Передачи:** привязки `Ctrl-w` в `keymap.toml`, шаги относительного размера и id пунктов «Вид» — P1.6; `open-or-focus` через `panel.*` — P1.5.
