# ADR-0003: Терминал на полном libghostty

- Статус: Accepted (решение владельца). P0.3: автоматическая часть интеграции проверена, ручная приёмка и запись Instruments не проведены, вердикт по composition не вынесен
- Дата: 2026-11-09

## Контекст

Владелец требует libghostty. Он существует в двух видах: полный embedder API в `ghostty.h` с рендером на Metal и `NSView`, и публичная библиотека `libghostty-vt` без рендера.

## Решение

Каждая терминальная панель — поверхность полного libghostty в собственном подклассе `NSView`, написанном на Rust через `define_class!`. Подкласс реализует `NSTextInputClient` для IME.

Структура:

- `shellio-sys-ghostty` — привязки, сгенерированные `bindgen` из закреплённого `ghostty.h`.
- `shellio-ghostty` — единственный владелец инвариантов времени жизни и потоков. Типы и колбэки Ghostty не выходят в API плагинов и доменную модель.
- Сборка: статическая библиотека, собранная Zig. Вместе закреплены ревизия, дайджест патчей `scripts/ghostty-patches/`, версия Zig, настройки SDK, ресурсы и `terminfo`. Штамп сборки покрывает весь набор.

Правила, перенесённые из опыта agterm:

- Поверхность создаётся только при ненулевом размере и освобождается в одном месте.
- Колбэки C не трогают главное состояние напрямую: строки копируются, затем переход на главный поток.
- Буферы C-строк живут до уничтожения поверхности.
- `terminfo` лежит рядом с `Contents/Resources/ghostty`.
- Скрытая поверхность сообщает окклюзию и отпускает swap chain. При открытии рисует синхронно.
- Создание поверхности повторяется после пробуждения дисплея.

Обновление ревизии — всегда отдельный план:

1. Разбор изменений исходников и заголовка, повторная генерация привязок.
2. Компилируемая C-проба размеров, выравнивания и смещений используемых структур. Совпадение сигнатур не проверяет смысл колбэков.
3. Патчи применяются к чистой ревизии. Для каждого проверяется, не исправлено ли это выше, и обновляется условие его удаления.
4. Регрессионный набор: уничтожение и создание при активном выводе, поток заголовков при закрытии одной из нескольких поверхностей, запуск с `MallocScribble`, скрытие, показ, ресайз и смена родителя, перезагрузка темы с сохранением команды и окружения, спящий дисплей, IME, вставка и буфер обмена, фокус и перетаскивание, scrollback и поиск, подключение к хосту старого поколения.
5. Подписанная сборка и ручная приёмка на целевой macOS.

При провале проект остаётся на старой ревизии. Выход новой версии Ghostty сам по себе обновления не требует.

Конфигурация терминала — отдельный `~/.config/shellio/ghostty.conf`. Светлая и тёмная темы задаются условной записью Ghostty.

## Отвергнутые варианты

- `libghostty-vt` со своим рендером: публичный API, в котором есть выделение, поиск и кодирование ввода, но рендер, шрифты, интеграцию IME и доступность пришлось бы делать и сопровождать самим.
- `alacritty_terminal`: не удовлетворяет требованию владельца.

## Последствия

- `ghostty.h` прямо называет себя внутренним API. Любое обновление может сломать слой привязок, поэтому ревизия закреплена.
- Сборка требует Zig нужной версии и Metal toolchain из Xcode.
- Поверхности — отдельные `NSView` поверх остального. Перекрыть их может только AppKit-вид с большим z-порядком или отдельное окно.

## Основания

- `ghostty.h`: «The only consumer of this API is the macOS app… External embedders should instead use libghostty-vt».
- `agterm/agterm/Ghostty/GhosttySurfaceView.swift:605–658`, `agterm/ARCHITECTURE.md` (Load-bearing fragile points), `agterm/.claude/rules/libghostty.md`.
- `agterm/scripts/setup.sh`: закреплённая ревизия и патчи.

## Условие пересмотра

libghostty получает публичный стабильный API для встраивания поверхности, либо P0.3 показывает неустранимую проблему с composition.

## Уточнено в P0.1

План [toolchain-bootstrap](../plans/completed/20261111-toolchain-bootstrap.md) конкретизирует сборку. Решение не меняется. Пути и флаги выведены из исходников закреплённой ревизии и подтверждаются сборкой и линковкой в задачах 2 и 4 плана.

Набор сборки:

- Ревизия `83fb95624b0439ee660c2679b43b38c8b63769cd` (v1.4.0) с патчем `0001-drain-mailbox-during-surface-teardown.patch` из agterm. Только эта связка подтверждена на macOS 27.
- Флаги: `-Doptimize=ReleaseFast -Demit-xcframework=true -Dxcframework-target=native -Demit-macos-app=false -Dsentry=false -Dversion-string=1.4.0`.
- Без Sentry. На macOS он включён по умолчанию, и `ghostty_init` создаёт базу Sentry в каталогах Ghostty, которых `SHELLIO_STATE_DIR` не касается.
- Версия задаётся явно. В `ghostty.h` её нет, она приходит только полями `version` и `version_len` результата `ghostty_info`, а без `-Dversion-string` выводится из git и у неглубокой копии может получить суффикс.
- Линкуется архив `libghostty-internal.a` из `macos/GhosttyKit.xcframework/macos-arm64/`, в который уже объединены зависимости. Флага, который ставит эту библиотеку на macOS без xcframework, нет.
- Zig ставится не из Homebrew, а архивом точной версии 0.17.1 с закреплённым SHA-256. Ревизия допускает 0.17.x (`minimum_zig_version = "0.17.0"`), но собирается и принимается только 0.17.1, поэтому в штампе та версия, которая собирала.
- Минимумы macOS разные: приложение и тесты — 27.0 через `.cargo/config.toml` корня workspace, libghostty — собственный минимум upstream 13.0 (`genericMacOSTarget`, `osVersionMin`). Цель сборки ghostty его не меняет, а смена минимума приложения не пересобирает ghostty.

Штамп описывает входы сборки строками `ключ=значение`: ревизия, значения закрепления и флаги сборки; дайджест имён и содержимого патчей и дайджест рецепта сборки; SHA-256 Zig и архитектура; путь Xcode и `xcodebuild -version`; версия и сборка SDK, версия Metal toolchain. Всё это известно до загрузки исходников, поэтому ожидаемый штамп вычисляется без сети и до сборки. Публикация записывает штамп, снятый до сборки, и отказывает, если за время сборки входы изменились. Первая строка `stamp_format` — номер формата: его поднимают, когда меняется смысл сверки без изменения входов, и тогда старые наборы перестают приниматься.

Манифест перечисляет относительный путь и SHA-256 каждого файла набора, включая ресурсы и `terminfo`. Файлы `manifest` и `stamp` в него не входят и остаются единственными допустимыми файлами вне него. Набор принимается, только если штамп совпадает с ожидаемым, каждый файл манифеста на месте с тем же хэшем и лишних файлов нет. Набор без штампа не линкуется.

Исходные данные для P0.3. P0.1 не вызывает `ghostty_init`, а `ghostty_info` возвращает статические сведения о сборке без инициализации. Контракт запуска определяет P0.3 с учётом того, что `ghostty_init` влияет на весь процесс:

- ставит обработчики сигналов процесса;
- меняет locale;
- сохраняет указатели `argv`, не копируя их, поэтому переданные буферы должны оставаться живыми и после вызова;
- при пустом `LANG` вызывает `NSLocale currentLocale`, который поднимает число потоков с 1 до 3, и только потом делает `setenv("LANG")` и `setenv("LANGUAGE")`. Проверка одного потока на входе контракт не доказывает;
- в `ReleaseFast` берёт каталог ресурсов сначала из `GHOSTTY_RESOURCES_DIR`, и только без неё ищет `Contents/Resources/terminfo/78/xterm-ghostty` вверх от исполняемого файла. Родительский терминал Ghostty или agterm эту переменную задаёт.

`zig build` сам скачивает зависимости из `build.zig.zon`, часть из `deps.files.ghostty.org`. Сеть нужна только сборке набора, проверка готового набора в сеть не ходит.

## Уточнено в P0.3

Вывод [отчёта P0.3](../probes/p0.3-ghostty-surface.md) по полному автоматическому прогону 2026-11-15 (commit `6b91e3f56492`, 89 процессов, 479 `pass`, 0 `fail`). Решение не меняется. Ручной проход владельца и запись Instruments не проведены, поэтому у каждого правила ниже указано, чем оно подтверждено.

Composition:

- Вердикт по условию пересмотра не вынесен. Автоматика неустранимой проблемы не нашла: перенос между зонами сменой родителя того же `NSView`, нулевые bounds и живой ресайз сохраняют поверхность и процесс, палитра на дочерней непрозрачной `NSPanel` забирает ввод и возвращает режим, слой поверхности обрезается скруглением плитки по иерархии слоёв.
- Не проведены пиксельные проверки палитры и углов на настоящем кадре (снимки показали щит блокировки экрана владельца), клетки видимости «перекрыто» и «убрано», запись Instruments и ручной проход. До них условие пересмотра остаётся открытым, статус «интеграция проверена» не ставится.

Контракт запуска `ghostty_init` (подтверждено сценариями):

- Один вызов до `NSApplication`, рабочих потоков и журналирования из потоков. `argv` — отдельный минимальный массив из имени программы, строки и массив живут до конца процесса.
- Процесс запускается с окружением по белому списку: унаследованные `GHOSTTY_*`, `TERM*`, `TERMINFO`, `LC_*` не передаются, иначе `GHOSTTY_RESOURCES_DIR` родительского терминала в `ReleaseFast` важнее ресурсов бандла.
- Без `LANG` (маршрут LaunchServices) libghostty идёт путём Cocoa: после вызова `LANG=en_US.UTF-8`, `LANGUAGE` из предпочтений пользователя, все категории locale `en_US.UTF-8`. Число потоков на входе под LaunchServices уже 3–4 и вызовом не меняется. Недопустимый `LANG` заменяется на `en_US.UTF-8`.

Ресурсы и маршруты запуска (подтверждено сценариями):

- `Contents/Resources/ghostty` и `Contents/Resources/terminfo` рядом в бандле: у ребёнка `TERM=xterm-ghostty` и `TERMINFO` из бандла, `TERMINFO` libghostty выводит сам. Прямой запуск и `open` через LaunchServices проходят одинаково. Маршрут LaunchServices стенд запускает без переменных языка (`open` сам их не убирает, окружение наследуется от вызывающего), рабочий каталог процесса — `/`.
- Команда поверхности на macOS идёт через `/usr/bin/login` и `bash -c "exec -l …"`, а не через `/bin/sh -c`. Непустая команда сама включает `wait-after-command`: выход ребёнка поверхность не закрывает.
- `ghostty_app_set_color_scheme` без `ghostty_app_update_config` теряет команду и окружение у новых поверхностей. Живая смена темы — `ghostty_surface_set_color_scheme` и `ghostty_surface_update_config` у каждой поверхности.

Ввод и буфер обмена (автоматическая часть подтверждена, кириллица, dead keys и настоящая composition вручную не проверены):

- Клавиша и текст, накопленный `insertText` за `interpretKeyEvents`, уходят одним `ghostty_input_key_s` в `ghostty_surface_key`. Коммит IME вне `keyDown` — текстовое событие клавиши через тот же вызов.
- `ghostty_surface_text` — это вставка: bracketed paste и замена переводов строк. Он используется только для явной вставки, обычная буква через него не идёт.
- `ghostty_surface_ime_point` отдаёт пиксели подложки, а не точки, их делят на scale.
- Поддержан только текст в обычном буфере (`supports_selection_clipboard = false`). Каждое подтверждение (OSC 52, kitty, небезопасная вставка) пока отклоняется, поэтому `clipboard-paste-protection = false`. Токен запроса живёт в реестре, пока библиотека его не вернула или не завершила; при закрытии ожидающие запросы отклоняются на живой поверхности ровно один раз.

Видимость (подтверждено диагностикой под щитом, вердикт по записи Instruments не вынесен):

- Параметр `ghostty_surface_set_occlusion` означает `visible`. Видимость подаётся только на фронте модели сцены, частично перекрывающая палитра поверхность не скрывает.
- Скрытая поверхность не опрашивает: 0 пробуждений в секунду, после установления скрытия новых кадров нет. Освобождение swap chain при скрытии видно в исходниках (`src/renderer/generic.zig:1220–1256`), а сводный `phys_footprint` процесса падает на 18–20 МиБ на прогретую поверхность; ресурсам поверхности это не приписано.
- Из трёх проверенных обходов наблюдаемое меняют два: снятие `needsDisplayOnBoundsChange` у скрытого слоя убирает перерисовку скрытого вида при ресайзе, синхронный `ghostty_surface_draw` при показе даёт свежий кадр на первом проходе отображения вместо старого. Отложенное скрытие до первого кадра в матрице пользы не показало. Правило «скрытая поверхность сообщает окклюзию и отпускает swap chain, при открытии рисует синхронно» диагностика не опровергла. Снятие `needsDisplayOnBoundsChange` — кандидат для P2.2, окончательно правила видимости определяет запись Instruments.

Закрытие и пробуждение дисплея:

- Закрытие подтверждено сценариями, в том числе под `MallocScribble=1`: одно освобождение в одном месте, никогда со стека `ghostty_surface_key` или `tick`, соседи с выводом живут, ожидающих запросов буфера обмена 0. Патч `0001-drain-mailbox-during-surface-teardown` испытан на двух закрытиях до следующего `tick`.
- `ghostty_surface_free` синхронно ждёт рабочие потоки и держит главный поток около 14 мс, `ghostty_surface_new` — около 3,5 мс.
- Повтор создания после пробуждения дисплея проверен только на имитации: сбой при спящем дисплее повторяется ограниченно по пробуждению экранов и пути раскладки, неповторяемый не повторяется, после пробуждения поверхность одна. Настоящий сон дисплея не проверялся.
