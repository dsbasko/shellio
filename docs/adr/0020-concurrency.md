# ADR-0020: Потоки и асинхронность

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

AppKit работает только в главном потоке. Git, сеть, сокеты и таймеры не должны его блокировать, а интерфейс должен оставаться отзывчивым при большом числе панелей.

## Решение

Три области исполнения:

- **Главный поток**: только AppKit. Получает готовые снимки состояния и применяет разницу.
- **Актор состояния**: одна задача `tokio` владеет доменным состоянием. Команды приходят по каналу, события выходят с монотонной ревизией.
- **Рабочие потоки**: `spawn_blocking` для git и файловых операций, I/O на небольшом runtime `tokio` с ограниченным числом потоков.

Правила:

- Главный поток не вызывает блокирующие операции. Нарушение ловится проверкой времени кадра в сборке для разработки.
- Длинная операция получает идентификатор и токен отмены. Закрытие вида отменяет только работу, привязанную к виду. Сессия и начатая запись во внешний сервис живут по своим правилам.
- Потоки данных (строки лога, результаты blame) приходят пакетами на кадр.
- Результат устаревшего запроса отбрасывается по ревизии или идентификатору.
- Работа плагина выполняется с тегом `PanelId` для учёта ресурсов.

## Отвергнутые варианты

- Только блокирующий код на потоках, как в detached: много сокетов и отмен, сетевая отмена неудобна.
- Глобальные мьютексы над состоянием: дедлоки и лишние блокировки главного потока.

## Последствия

Состояние читается только по снимкам. Плагины пишутся асинхронно.
