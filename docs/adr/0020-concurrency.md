# ADR-0020: Потоки и асинхронность

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

AppKit работает только в главном потоке.
Git, сеть, сокеты и таймеры не должны его блокировать, а интерфейс должен оставаться отзывчивым при большом числе панелей.

## Решение

Три области исполнения:

- Главный поток: только AppKit. Получает готовые снимки состояния и применяет разницу.
- Актор состояния: одна задача `tokio` владеет доменным состоянием. Команды приходят по каналу, события выходят с монотонной ревизией.
- Рабочие потоки: `spawn_blocking` для git и файловых операций, I/O на небольшом runtime `tokio` с ограниченным числом потоков.

Правила:

- Главный поток не вызывает блокирующие операции. Нарушение ловится проверкой времени кадра в сборке для разработки.
- Длинная операция получает идентификатор и токен отмены. Закрытие вида отменяет только работу, привязанную к виду. Сессия и начатая запись во внешний сервис живут по своим правилам.
- Потоки данных (строки лога, результаты blame) приходят пакетами на кадр.
- Результат устаревшего запроса отбрасывается по ревизии или идентификатору.
- Работа плагина выполняется с тегом `PanelId` для учёта ресурсов.

## Отвергнутые варианты

- Только блокирующий код на потоках, как в detached: много сокетов и отмен, сетевая отмена неудобна.
- Глобальные мьютексы над состоянием: дедлоки и лишние блокировки главного потока.

## Последствия

Состояние читается только по снимкам.
Плагины пишутся асинхронно.

## Основания

`detached/PLAN-NATIVE.md` (Threads), `agterm/ARCHITECTURE.md` (Concurrency contract at the C boundary).

## Уточнено в P1.1

Решение плана P1.1 `core-domain`, принятое при планировании 2026-11-21.
Три области исполнения не меняются.
Транспортная граница ядра записана в [ADR-0004](0004-process-model.md), «Уточнено в P1.1».

- Состояние. Актор: одна задача `tokio`, владеющая `State` в `Arc`. Изменение идёт через `Arc::make_mut`, снимок: клон `Arc`.
- Чистые обработчики. Обработчик команды по снимку состояния возвращает ответ и список `Change` без файлового ввода-вывода, времени и случайности. Время и идентификаторы приходят через внедряемые `Clock` и `IdGen`. Ввод-вывод, нужный команде, выполняется до актора: корень проекта для `project.add` разрешается в `spawn_blocking`, актор получает готовый результат.
- Одна дельта. Тот же список `Change` пишет хранилище, применяет к памяти `State::apply` и несёт событие. Главный поток с P1.3 держит зеркало состояния и применяет те же `Change`.
- Поток хранения. Порт `Persist` блокирующий. Актор владеет отдельным потоком `std::thread` с экземпляром `Persist` и общается с ним каналом и квитанциями. Блокирующий SQLite не занимает потоки `tokio`, записи идут строго по порядку. Потерянная квитанция: `storage_unavailable`.
- Запуск. `Core::start` синхронный и работает как вне runtime, так и внутри него. Он загружает состояние на потоке хранения, выполняет внутренние команды запуска и ждёт квитанции их записи, и только после этого запускает цикл актора. Ошибка загрузки возвращается как есть. Отказ записи запуска: `StartError::Startup`; в обоих случаях поток хранения закрывается и присоединяется. Без записи запуска инвариант «активный воркспейс есть» не держится.
- Порядок команды.
  1. Проверка и вычисление `Change` чистым обработчиком.
  2. Пустой список: ответ без новой ревизии и без события.
  3. Иначе запись на потоке хранения, актор ждёт квитанцию.
  4. Успех: `State::apply`, ревизия +1, событие в буфер и подписчикам, ответ с ревизией.
  5. Отказ: состояние и ревизия не меняются, ответ `storage_unavailable` с признаком повтора или `storage_conflict` без него, если в базу писали в обход ядра ([ADR-0018](0018-storage-and-config.md), «Уточнено в P1.1»).

  Ответ приходит только после записи.
- Очередь и главный поток. Очередь команд: ограниченный `tokio::sync::mpsc` ёмкостью 256. Через неё строго по одному идут все запросы: команды, чтения, подписка и `events_since`. Поэтому снимок, ревизия и приёмник событий согласованы. Чтения в поток хранения не ходят.
  - `CoreHandle::try_request` не ждёт: при полной очереди сразу возвращает `busy` с признаком повтора, ответ приходит квитанцией. Для `project.add` подготовка корня идёт отдельной задачей на runtime, поэтому `try_request` сразу отдаёт квитанцию, и любой отказ, включая `busy`, приходит через неё.
  - `CoreHandle` хранит `runtime::Handle` и запускает задачи только через него: `try_request` вызывается с главного потока, где нет контекста runtime.
  - `request`: асинхронный вариант для фоновых задач и будущего сервера сокета, он ждёт места в очереди.
- Атомарная подписка. `subscribe` выполняется внутри актора и возвращает снимок с ревизией вместе с приёмником событий начиная со следующей ревизии, без разрыва. Канал подписчиков: `broadcast` ёмкостью 256. Отставший получает `Lagged` и запрашивает снимок.
- Буфер событий. Последние 1024 события лежат в кольцевом буфере в памяти. `events_since(cursor)` возвращает события после курсора или `Reset(Snapshot)`, если курсор старше буфера или из прошлого запуска. После загрузки с находками запуск пишет запись без события, поэтому `Reset` получает и курсор, равный ревизии загрузки. Курсор больше текущей ревизии: `invalid_argument` с причиной `cursor_ahead`.
- Отмена и завершение. Брошенная квитанция команду не отменяет: принятая команда атомарна и выполняется. `shutdown` отвечает новым запросам `shutting_down`, доводит принятые до ответа, закрывает канал событий, закрывает и присоединяет поток хранения. Признак завершения ставится в момент вызова, а не при первом опросе future, поэтому запрос после вызова получает `shutting_down` детерминированно. `subscribe` поэтому возвращает `Result`: после `shutdown` ему тоже нужен отказ.
- Итог P1.1. Подтверждено тестами `shellio-core` и `shellio-store`: актор состояния с отдельным потоком хранения, ответ после записи, отказ записи без изменения состояния и ревизии, `busy` при полной очереди, атомарная подписка без разрыва, снимки, буфер событий с `Reset(Snapshot)` и монотонная ревизия через перезапуски. Не подтверждено, поэтому статус остаётся `Proposed`:
  - проверка времени кадра главного потока в сборке для разработки: P1.3;
  - идентификатор и токен отмены длинных операций: P3.1.

## Уточнено в P1.3 (планирование)

Решение плана P1.3 `appkit-foundation` [дорожной карты](../roadmap.md), принятое при планировании 2026-11-22.
Три области исполнения не меняются, статус остаётся `Proposed`.
Чтения `ui.*` записаны в [ADR-0007](0007-control-api.md), раздел «Уточнено в P1.3 (планирование)».

### Зеркало состояния на главном потоке

- `Mirror` в `shellio-core` строится поверх `Snapshot` и `State::apply_all` P1.1: `Mirror::from_snapshot` и `Mirror::apply(event)` с исходом `Applied` или `NeedSnapshot`. Событие с ревизией через одну и `Reset` дают `NeedSnapshot`, повтор прежней ревизии игнорируется.
- Задача владельца подписывается на ядро (`subscribe`: атомарный снимок и приёмник) и передаёт снимок и дальнейшие события на главный поток через `MainThread::exec`. Там `Mirror` применяет `Change` в порядке ревизий, а по `NeedSnapshot` берётся новый снимок.
- Главный поток не ждёт ядро и не читает файлы.
- Потребители P1.3: кнопка воркспейса `ChromeBar` и системный заголовок окна. Они читают чистые проекции зеркала: имя активного воркспейса и строку заголовка по [ADR-0026](0026-titlebar-workspace-only.md).

### Монитор цикла главного потока

Проверка, переданная итогом P1.1, называет метрики тем, что они меряют:

- «занятость итерации цикла»: наблюдатели `CFRunLoop` `AfterWaiting` и `BeforeWaiting`;
- «проходы отображения»: наблюдатель с порядком после фиксации Core Animation;
- «отрисовка поколения N»: отметка, которую компонент ставит в `drawRect:` или `updateLayer` с номером поколения состояния, а не концом прохода цикла (P0.2, ограничение 4; P0.6).

Метрика кадра на экране в P1.3 не заводится.
В сборке `debug_assertions` итерация дольше 16 мс печатается строкой в stderr с меткой.
Счётчики идут в `ui.stats` в любой сборке.
Задержка клавиши мерится от `NSEvent.timestamp` события до отметки отрисовки поколения, в котором выбор уже сдвинут этим нажатием.
Часы обеих отметок: время с загрузки одного процесса, межпроцессного сравнения часов нет.

Вывод плана P1.3 [`appkit-foundation`](../plans/completed/20261122-appkit-foundation.md) по `make check` и приёмочному проходу исполнителя 2026-11-22.
Три области исполнения не меняются.
Статус остаётся `Proposed`: идентификатор и токен отмены длинных операций (P3.1).
«Наблюдение» ниже это копия `appkit.sh` без AeroSpace в списке оконных менеджеров, рубежом она не считается ([ADR-0021](0021-testing.md), «Уточнено в P1.3»).

Зеркало состояния подтверждено тестами (`crates/shellio-core/tests/mirror.rs`, тест владельца `mirror_follows_core_and_takes_new_snapshot_after_gap`):

- снимок плюс события равны состоянию актора на пяти зёрнах по 160 случайных команд с подписками и повторами прошлых событий между ними;
- потерянное событие и `Lagged` настоящей подписки дают новую подписку со снимком, закрытое ядро завершает задачу зеркала;
- первый снимок доставляется на главный поток до строки готовности и до активации собственного `launch` владельца.

Наблюдение.
Пункт `mirror`: `pass`.
После `shellioctl workspace rename` в пределах 2 с `ui.window` показывает ревизию ответа, новые имя кнопки воркспейса и системный заголовок, а `workspace new` неактивного воркспейса заголовок не меняет.

Отклонения от раздела «Уточнено в P1.3 (планирование)»:

- Вход `Mirror::apply`: `Delivery { Event, Reset, Snapshot }`, исход: `MirrorStep { Applied, Ignored, NeedSnapshot }`. `Ignored` отделяет повтор прежней ревизии, который велено игнорировать, от применённого события: перерисовка не нужна. Новый снимок после `NeedSnapshot` идёт той же доставкой. Снимок старее зеркала: `Ignored`. Той же ревизии и новее: замена состояния.
- Проекции `workspace_name` и `window_title` возвращают `Option`: без активного воркспейса текст по умолчанию выбирает окно («shellio» в системном заголовке, «Нет воркспейса» на кнопке). Убранный проект открытой области остаётся в заголовке по [ADR-0026](0026-titlebar-workspace-only.md).
- Приёмник зеркала: супертрейт порта UI, тестовый владелец без UI ведёт то же зеркало.

### Монитор цикла главного потока

Проверка времени главного потока, переданная итогом P1.1, реализована: в сборке `debug_assertions` итерация дольше 16 мс печатается строкой в stderr, счётчики идут в `ui.stats` в любой сборке.
Учёт итераций, вложенного цикла, непарных событий и перцентиля закреплён тестами `shellio-appkit`.

- Порядок событий цикла записан по трассе настоящего окна. В простое пробуждений нет вовсе. Нажатие клавиши даёт `AfterWaiting`, `Exit`, `keyDown:` вне цикла, `Entry`, отрисовку, `Exit`, `Entry`, `BeforeWaiting`. AppKit выходит из цикла и входит снова на каждое событие, поэтому итерация длится от пробуждения до засыпания, а `Exit` только считает проход отображения. У пробуждения с событием проходов два и больше, поэтому простой судится по счётчику пробуждений, а не проходов.
- Наблюдатель пробуждения стоит с самым ранним порядком, наблюдатель засыпания с порядком 2 100 000, после фиксации Core Animation. Засыпание вложенного цикла отслеживания меню закрывает итерацию, а его `Exit` только считает проход: внешний цикл продолжает ту же итерацию до своего засыпания.
- Отметка отрисовки ставится в `updateLayer` или `drawRect:` с поколением и временем `CACurrentMediaTime` (те же часы, что у `NSEvent.timestamp`). Нажатие получает поколение в два шага: состояние с его выбором применено, затем окно публикует поколение.
- Наблюдение: в простое галереи за 10 с отрисовок 0, пробуждений 3-5, CPU до 0,1 %. Сразу после запуска владельца галереи цикл просыпался около 196 раз за первые 10 с, затем раз за 10 с. Что его будит, не установлено. Замер простоя начинается после затишья цикла, пороги не менялись.
- Наблюдение: в серии задержки с тактами `CADisplayLink` пробуждения цикла собраны у такта (межквартильный размах фазы не больше четверти периода), то есть доставка события выровнена по кадру. В дымовой серии медиана «событие → пробуждение»: 6,9 мс с тактами и 1,8 без них ([ADR-0002](0002-ui-stack-appkit.md), «Уточнено в P1.3»).
