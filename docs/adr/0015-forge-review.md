# ADR-0015: GitHub/GitLab, ревью и черновики

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

В рабочей области открывается merge или pull request, изучаются изменения, пишутся комментарии как черновики и затем отправляются. Модели GitHub и GitLab различаются, а общей транзакции для комментариев и итога у GitLab нет.

## Решение

Общая доменная модель `ReviewTarget`, `Revision`, `Thread`, `DraftComment`, `ReviewSession` и адаптеры провайдеров с объявленными возможностями и сохранёнными нативными ID. ID провайдера — непрозрачная строка.

**Локальный журнал черновиков обязателен.** Черновик пишется в `state.db` немедленно. `ReviewSession` привязан к аккаунту, хосту, репозиторию и конкретной ревизии (`base_sha`, `start_sha`, `head_sha`). Смешивать свежие refs с ранее полученным `head_sha` запрещено. Локальные черновики принадлежат проекту и не видны из другого воркспейса, сам MR на сервере общий по природе сервиса ([ADR-0025](0025-workspaces-and-project-catalog.md)).

Шаги отправки разделены:

1. Загрузить свежую ревизию и сопоставить якоря.
2. Показать конкретный список и итог.
3. Опубликовать способом провайдера, записывая состояния `planned → in_flight → confirmed|unknown`.
4. Сохранить удалённые ID.
5. Показать полностью или частично отправленное.

Состояние `unknown` после таймаута сверяется с провайдером. Слепого повтора нет.

Различия провайдеров:

| | GitHub | GitLab |
| --- | --- | --- |
| Черновик на сервере | `PENDING` review, создаётся без `event` | Отдельные `draft_notes` |
| Отправка | Две ветви, см. ниже | Публикация каждого известного `draft_note`, сводка отдельным шагом |
| Итог | `COMMENT`, `APPROVE`, `REQUEST_CHANGES` | `approve` с проверкой `sha`, запрос изменений через GraphQL `mergeRequestRequestChanges` |
| Якорь | `commit_id`, `path`, `line`, `side`, `start_line`, `start_side` | `base_sha`, `start_sha`, `head_sha`, пути и строки, `line_range` |
| Просмотренные файлы | `markFileAsViewed` на сервере | Локально |

Ветви GitHub:

- Только локальные черновики: один запрос Create review с `comments[]` и итоговым `event`.
- Серверный `PENDING` review: создание и обновление комментариев с сохранением ID, затем Submit именно этого review. Запрос Submit не принимает `comments[]`.

Существующий `PENDING` review на GitHub не перезаписывается. Перед принятием в работу показывается весь его состав.

Запрещено использовать GitLab `bulk_publish`: он публикует все ожидающие черновики пользователя, включая написанные в браузере. Поэтому его `reviewer_state` недоступен. Запрос изменений выполняется только при наличии возможности `mergeRequestRequestChanges` и прав. Без неё действие недоступно, обычным комментарием оно не имитируется. «Просмотрено» и формальное одобрение — разные состояния.

При смене head показывается предупреждение: остаться на ревизии, перейти или перепривязать устаревшие якоря. Номер строки молча не подбирается.

Основной цикл (обязательно): список и URL, описание, коммиты, файлы, навигация по diff, комментарии к старой и новой стороне и диапазонам, suggestions, треды, ответы, resolve, просмотренные файлы, версии и «изменения с прошлого ревью», черновики, итог, повторы, статус проверок. Затем: approve, request changes, merge, squash, auto-merge, draft/ready, close/reopen, reviewers, assignees, labels, создание MR/PR, checkout ветки. Остальное открывается в браузере.

Ревью без checkout: файлы читаются по закреплённым SHA.

Агент может предлагать черновики через `shellioctl`, они попадают в тот же журнал и видны отдельной пометкой.

## Отвергнутые варианты

- Общий метод `post_comment`: неявно публикует сразу и не переживает смену ревизии.
- Только серверные черновики: нет работы офлайн, единого поведения у обоих провайдеров и данных для сверки, а несинхронизированные правки теряются.

## Последствия

Нужны тестовые приватные PR и MR и fake-сервер для тестов (`forge-fake`). Self-hosted версии могут уметь меньше, поэтому возможности проверяются.

## Основания

- [GitHub: Pull request reviews](https://docs.github.com/en/rest/pulls/reviews), [GraphQL reference](https://docs.github.com/en/graphql/reference/pulls).
- [GitLab: Draft Notes API](https://docs.gitlab.com/api/draft_notes/), [Discussions API](https://docs.gitlab.com/api/discussions/), [Approvals](https://docs.gitlab.com/api/merge_request_approvals/), [GraphQL `mergeRequestRequestChanges`](https://docs.gitlab.com/api/graphql/reference/mutations/#mergerequestrequestchanges).

## Уточнено в P0.7

Вывод [отчёта P0.7](../probes/p0.7-review-api.md) по полному прогону серии `t15-20261121` от 2026-11-21 (код `10cff16`, одна сборка на все вызовы, ошибок исполнения нет). Проба проверяла решение в двух местах: на собственном `forge-fake` (оракул пробы по документации) и на локальном GitLab CE 19.6.1 (образ `19.6.1-ce.0`, тариф `free`). Песочниц github.com и gitlab.com не было, поэтому их клетки — `not_run` «нет sandbox.toml». GitHub Enterprise Server — `not_run` «нет инсталляции», создание черновика в браузере не наблюдалось. Условие пересмотра выполнено только для self-hosted GitLab CE, облачные аккаунты переданы P4.1. Решение не меняется ([ADR-0036](0036-autonomous-execution.md)).

Подтверждено:

- На `forge-fake` — все 18 утверждений матрицы: две ветви GitHub, существующий `PENDING`, якоря GitHub, `markFileAsViewed`, поштучная публикация, `approve` с `sha`, `mergeRequestRequestChanges` с раздельными итогами, смена head, журнал, сверка, частичная отправка, возможности чтением. Это проверка клиента против контракта, записанного по документации, а не наблюдение хоста.
- На GitLab CE 19.6.1 — 11 из 12 клеток:
  - поштучная публикация трогает только известные черновики, черновик того же пользователя от другого клиента остаётся черновиком, `bulk_publish` не вызывается;
  - `approve` с актуальным `sha` проходит, с прежним даёт 409;
  - `mergeRequestRequestChanges` есть в схеме CE Free и переводит ревьюера в `REQUESTED_CHANGES`;
  - позиция строится с тройкой `diff_refs`, старая и новая сторона и `line_range` работают;
  - журнал переживает сбой до запроса и после принятой записи;
  - сверка не повторяет запись;
  - частичная отправка видна в журнале и в итоге.

`absent`: таких клеток нет. На CE Free есть и `approve` с `sha`, и `mergeRequestRequestChanges`.

Отрицательный вывод:

- GitLab CE 19.6.1 принимает `draft_note` с позицией прежней ревизии (`head_sha` не текущий) ответом 201, но записывает позицию с тройкой текущих `diff_refs`. Значит, путь «остаться на ревизии» для черновиков GitLab через Draft Notes API на наблюдённом случае не выполняется.
- Наблюдён только случай с той же базой и неизменённой строкой. Изменённая строка, смена базы и gitlab.com не наблюдались.
- Предупреждение, классификация якорей, явная перепривязка и запрет смешивать тройки на том же хосте выполнились.
- P4.1 сверяет тройку в ответе на каждое создание черновика. При расхождении черновик не публикуется, а пользователю предлагается перейти на новую ревизию. Черновик с подменённой тройкой к этому моменту уже создан на сервере: P4.1 сохраняет его ID из ответа в журнале и по выбору пользователя обновляет или удаляет его по этому ID. Адаптер пробы при расхождении ID отбрасывает, элемент остаётся `unknown`, и сверка по тройке сессии его не находит.

Метод серверного `PENDING` GitHub выбран по документации, на github.com он не наблюдался:

- создание — REST Create review без `event`;
- добавление — GraphQL `addPullRequestReviewThread` с `pullRequestReviewId`;
- изменение — GraphQL `updatePullRequestReviewComment` по node ID, ID комментария сохраняется;
- Submit — REST `POST …/reviews/{id}/events` без `comments[]`.

У REST нет добавления комментария в существующий `PENDING`. `addPullRequestReviewComment` документация выводит из употребления, а `databaseId` комментария устарел, поэтому используются node ID и `fullDatabaseId`. Существующий `PENDING` проверяется до первой записи: список reviews и весь его состав читаются по всем страницам.

Правило сверки `unknown`:

- `confirmed` ставится только при связи с нашей операцией: это удалённый ID из ответа на неё или ожидаемый итог известного объекта, прочитанного по ID. ID, полученный при создании `PENDING`, Submit не подтверждает.
- Совпадение по автору, якорю и тексту без такой связи даёт кандидата, и элемент остаётся `unknown`. Несколько совпадений дают «неоднозначно».
- `failed` по сверке ставится только операции над известным ID, который всё ещё в исходном состоянии. 404 и отсутствие в списке ничего не доказывают, а сбой чтения даёт «не выяснено».
- Слепого повтора нет. Такая же операция не планируется, пока элемент не сверен.
- Явный отказ по лимиту значит, что запись не принята: элемент получает `failed`. Потерянный ответ даёт `unknown`.
- Следствие: однозначный итог сверка может дать только операциям над известным объектом (изменение, Submit, `approve`, запрос изменений). Это правило таблицы сверки отчёта. Юнит-тесты против `forge-fake` проверяют его для Submit (`confirmed` и `failed`) и для `failed` публикации `draft_note`, а в прогонах серии такая сверка не встретилась.
- Создающие операции и публикация `draft_note` с потерянным ответом остаются `unknown`. Ответ публикации — 204 без тела, связи заметки с черновиком API не показывает, а исчезнуть черновик может и от удаления другим клиентом (наблюдено на CE). Продукту нужен явный выбор пользователя.

Уточнения к различиям провайдеров, наблюдённые на CE 19.6.1:

- Отсутствие `mergeRequestRequestChanges` определяется чтением схемы. На `__type(name: "Mutation")` CE 19.6.1 возвращает полную схему, около 8,8 МБ на вызов.
- Пользователь, не назначенный ревьюером, получает HTTP 200 и `payload.errors` `Reviewer not found`, поэтому итог читается из тела. Роль ниже Developer, отсутствие доступа и несуществующий MR, по предположению оракула пробы, дают один ответ «does not exist or you don't have permission» без точной причины. На CE этот случай не возникал.
- `diff_refs` и версии MR обновляются асинхронно, поэтому снимок ревизии ждёт готовности.
- Тариф CE виден в `GET /metadata`, а не в пространстве имён.

Не наблюдались и переданы P4.1:

- обе ветви GitHub и существующий `PENDING` на github.com, `markFileAsViewed`;
- gitlab.com целиком, в том числе тариф и лимит создания заметок;
- GitHub Enterprise Server;
- черновик, созданный в браузере;
- стойкость журнала к сбою питания.

## Условие пересмотра

Результаты P0.7 на реальных аккаунтах и self-hosted инсталляциях.
