# ADR-0015: GitHub/GitLab, ревью и черновики

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

В рабочей области открывается merge или pull request, изучаются изменения, пишутся комментарии как черновики и затем отправляются. Модели GitHub и GitLab различаются, а общей транзакции для комментариев и итога у GitLab нет.

## Решение

Общая доменная модель `ReviewTarget`, `Revision`, `Thread`, `DraftComment`, `ReviewSession` и адаптеры провайдеров с объявленными возможностями и сохранёнными нативными ID. ID провайдера — непрозрачная строка.

**Локальный журнал черновиков обязателен.** Черновик пишется в `state.db` немедленно. `ReviewSession` привязан к аккаунту, хосту, репозиторию и конкретной ревизии (`base_sha`, `start_sha`, `head_sha`). Смешивать свежие refs с ранее полученным `head_sha` запрещено. Локальные черновики принадлежат проекту и не видны из другого воркспейса, сам MR на сервере общий по природе сервиса ([ADR-0025](0025-workspaces-and-project-catalog.md)).

Шаги отправки разделены:

1. Загрузить свежую ревизию и сопоставить якоря.
2. Показать конкретный список и итог.
3. Опубликовать способом провайдера, записывая состояния `planned → in_flight → confirmed|unknown`.
4. Сохранить удалённые ID.
5. Показать полностью или частично отправленное.

Состояние `unknown` после таймаута сверяется с провайдером. Слепого повтора нет.

Различия провайдеров:

| | GitHub | GitLab |
| --- | --- | --- |
| Черновик на сервере | `PENDING` review, создаётся без `event` | Отдельные `draft_notes` |
| Отправка | Две ветви, см. ниже | Публикация каждого известного `draft_note`, сводка отдельным шагом |
| Итог | `COMMENT`, `APPROVE`, `REQUEST_CHANGES` | `approve` с проверкой `sha`, запрос изменений через GraphQL `mergeRequestRequestChanges` |
| Якорь | `commit_id`, `path`, `line`, `side`, `start_line`, `start_side` | `base_sha`, `start_sha`, `head_sha`, пути и строки, `line_range` |
| Просмотренные файлы | `markFileAsViewed` на сервере | Локально |

Ветви GitHub:

- Только локальные черновики: один запрос Create review с `comments[]` и итоговым `event`.
- Серверный `PENDING` review: создание и обновление комментариев с сохранением ID, затем Submit именно этого review. Запрос Submit не принимает `comments[]`.

Существующий `PENDING` review на GitHub не перезаписывается. Перед принятием в работу показывается весь его состав.

Запрещено использовать GitLab `bulk_publish`: он публикует все ожидающие черновики пользователя, включая написанные в браузере. Поэтому его `reviewer_state` недоступен. Запрос изменений выполняется только при наличии возможности `mergeRequestRequestChanges` и прав. Без неё действие недоступно, обычным комментарием оно не имитируется. «Просмотрено» и формальное одобрение — разные состояния.

При смене head показывается предупреждение: остаться на ревизии, перейти или перепривязать устаревшие якоря. Номер строки молча не подбирается.

Основной цикл (обязательно): список и URL, описание, коммиты, файлы, навигация по diff, комментарии к старой и новой стороне и диапазонам, suggestions, треды, ответы, resolve, просмотренные файлы, версии и «изменения с прошлого ревью», черновики, итог, повторы, статус проверок. Затем: approve, request changes, merge, squash, auto-merge, draft/ready, close/reopen, reviewers, assignees, labels, создание MR/PR, checkout ветки. Остальное открывается в браузере.

Ревью без checkout: файлы читаются по закреплённым SHA.

Агент может предлагать черновики через `shellioctl`, они попадают в тот же журнал и видны отдельной пометкой.

## Отвергнутые варианты

- Общий метод `post_comment`: неявно публикует сразу и не переживает смену ревизии.
- Только серверные черновики: нет работы офлайн, единого поведения у обоих провайдеров и данных для сверки, а несинхронизированные правки теряются.

## Последствия

Нужны тестовые приватные PR и MR и fake-сервер для тестов (`forge-fake`). Self-hosted версии могут уметь меньше, поэтому возможности проверяются.
