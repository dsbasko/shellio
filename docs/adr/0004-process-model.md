# ADR-0004: Модель процессов и время жизни сессий

- Статус: Proposed
- Дата: 2026-11-09

## Контекст

Главная ценность приложения — долгие терминальные и агентские сессии. Автообновление и падение интерфейса не должны их убивать. При этом полный libghostty сам запускает команду поверхности и не принимает внешний PTY.

## Решение

Процессы:

| Процесс | Владеет | Живёт |
| --- | --- | --- |
| `shellio` (GUI) | `NSWindow`, поверхности libghostty, ядро команд, плагины, управляющий сокет, сообщения, сэмплер | Пока приложение запущено |
| `shellio-host`, по одному на сессию | PTY master, дочерний процесс, состояние экрана, snapshot | Независимо от GUI, пока жива сессия |
| Attach-клиент | Мост между поверхностью libghostty и хостом | Расходуемый, живёт вместе с поверхностью |
| Процессы пользователя | shell, агенты, nvim, git | Внутри сессии |

Схема с двумя PTY. Поверхность libghostty запускает attach-клиент в своём PTY. Настоящие shell и агент работают во втором PTY, которым владеет хост, запущенный в отдельной сессии (`setsid`). Перезапуск GUI уничтожает только клиента. Повторное подключение никогда не запускает нагрузку заново.

Создание сессии идёт отдельно от поверхности, через атомарное `create-or-attach` по стабильному `SessionId`. Запуск нагрузки не ждёт создания поверхности, что также закрывает случай спящего дисплея.

Ядро команд — UI-free crate, работающий внутри процесса GUI на своём потоке, за транспортной границей. Отдельный брокер в первой версии не вводится.

Контракт доступности первой версии:

- Управляющий API и доставка сообщений работают, пока запущено приложение.
- При недоступном приложении CLI возвращает явную ошибку с признаком повторной попытки. Очередь не теряется, доставка возобновляется при следующем запуске.
- Закрытие окна приложение не завершает, поэтому обычный уход от компьютера контракт не нарушает.
- `shellioctl` и адаптеры не пишут в `state.db` напрямую. Единственный писатель — ядро.

Триггер выделения брокера: появление обязательных операций CLI или сообщений при отсутствующем GUI. Тогда ядро переносится в свой процесс как единственный писатель, а GUI становится проекцией его состояния.

Контракт времени жизни:

| Событие | Панель | Процессы сессии |
| --- | --- | --- |
| Скрыть или перенести панель | Состояние сохраняется | Живут |
| Закрыть панель с простаивающим shell | Закрывается | Завершаются |
| Закрыть панель с работающей программой или агентом | Выбор в одну клавишу: закрыть вид или остановить | При закрытии вида живут и доступны в навигаторе, при остановке завершаются |
| Закрыть окно macOS | Приложение остаётся в Dock | Живут |
| `Cmd-Q` | Подтверждение, только если работают агенты | Живут по умолчанию, вариант «Завершить всё» |
| Падение GUI | Восстановление при следующем запуске | Живут |
| Обновление | Перезапуск GUI, те же сессии | Живут на старом runtime |
| Потеря хоста | Состояние «хост потерян», контекст сохранён, проверка процессов по PID и времени старта | Могут продолжать работать. Показываются найденные процессы и действия «Остановить оставшиеся» и «Запустить новую» |
| Выход из системы, перезагрузка | Раскладка восстанавливается | Завершены, новая сессия запускается по запросу |

Команды разделены: `panel.hide` скрывает, `panel.close_view` закрывает вид и оставляет сессию, `session.stop` останавливает процессы, `panel.remove` убирает панель из раскладки. `×` и `Ctrl-w q` выполняют закрытие по таблице выше. Успех `session.stop` проверяется по процессам, а не по исчезновению сокета.

Транскрипт никогда не показывается как живой терминал. Второй экземпляр агента автоматически не запускается. Гарантии не распространяются на программы, которые сами стали демонами и покинули дерево сессии.

Живая сессия — это три свойства: процесс жив, вывод читается, состояние корректно показывается при повторном подключении. Проба P0.4 проверяет все три.

## Отвергнутые варианты

- PTY внутри GUI: простое решение, но каждое обновление завершает всех агентов.
- Демон-брокер `shelliod` сразу: добавляет IPC проекций, регистрацию службы и согласование версий. Его цена оправдана, только если работа агентов должна продолжаться без GUI.
- Один общий демон на все PTY: его падение убивает все сессии.

## Последствия

- Если GUI упал и не запущен снова, живые агенты продолжают работать, но поручения между ними стоят до следующего запуска приложения.
- Хосты могут остаться незаметно работающими после выхода. Вариант «Завершить всё» и панель Resources делают их видимыми.
- Атрибуция TCC для хостов, переживших обновление, проверяется в P0.5. В agterm для этого используется приватный `responsibility_spawnattrs_setdisclaim`. Его применение решается по результатам пробы и не считается бесплатной предпосылкой.

## Уточнено в P0.4

Вывод [отчёта P0.4](../probes/p0.4-session-survival.md) по полному прогону 2026-11-17 (`make probe-session` — `20261117-205948-31291`, `make probe-session-surface` — `20261117-211051-46612`, коммит `7ad4bee`, без ошибок исполнения). Схема с двумя PTY проверена на двух хостах: закреплённом zmx с патчами и минимальном Rust-хосте на `libghostty-vt`. Решение не меняется. Хост выбран в [ADR-0005](0005-session-backend.md): Rust-хост.

Три свойства живой сессии:

- **Процесс жив.** Подтверждено на обоих хостах. PID и время старта нагрузки не меняются после `SIGKILL` attach-клиента, обрыва PTY GUI и настоящего `SIGKILL` процесса GUI с поверхностью libghostty. Повторный attach нагрузку не запускает. Восемь одновременных `create-or-attach` одного `SessionId` дают одну нагрузку и один сокет. Замена подписанного бандла при живом хосте PTY не завершает, если хост запущен из копии рантайма вне бандла. Job control и группа переднего плана работают на обеих границах PTY.
- **Вывод читается.** Подтверждено на обоих хостах. Хост читает PTY без клиентов, и у нагрузки нет блокировки записи. Простой без клиентов не стоит CPU и не даёт собственных пробуждений хоста.
- **Состояние корректно показывается при повторном подключении.** Подтверждено только у Rust-хоста: основной и alternate screen, история с мягкими переносами, сохранённый курсор, стек Kitty, режимы ввода, начатая последовательность и шов «восстановление → живой поток» без пропуска и повтора, в том числе в новой поверхности после `SIGKILL` GUI. У zmx это свойство не выполняется: первый attach после работы без клиентов снимка не получает, снимок теряет переносы, сохранённый курсор, стек Kitty и начатую последовательность, у клиента пропадает экран строк истории. Именно это свойство решило выбор хоста.

Остальной контракт:

- **Потеря хоста.** Подтверждено на обоих хостах. После `SIGKILL` хоста при shell, агенте и фоновой задаче, игнорирующей HUP, состояние — «хост потерян», оставшиеся процессы находятся по сохранённым PID и времени старта после перехода к `launchd`. Для этого при создании сессии записываются PID и время старта нагрузки, группа и сессия: у Rust-хоста запись в каталоге состояния пишет сам хост, у zmx её вёл адаптер стенда по `ensure`. Нагрузка с потерей PTY выходит, процессы, игнорирующие HUP, остаются и показываются.
- **Остановка.** `stop` подтверждается гибелью хоста, нагрузки и её потомков по ключам процессов, а не исчезновением сокета. Подтверждено на обоих хостах.
- **Закрыть вид и остановить процесс — разные действия.** Гибель вида, клиента и всего процесса GUI нагрузку не трогает.
- Проверено на фикстурах, на nvim и в настоящей поверхности libghostty. Агент в A6 — фикстура. Настоящие Claude Code и Codex — исследование рубежа F ADR-0005, итоги и передача в P2.5 записаны там.
- Не проверялось и передано P0.5: протокол замены бандла продукта, `runtime/<version>/` продукта, TCC и `responsibility_spawnattrs_setdisclaim`, Keychain, карантин и гонка второго запуска. Выход из системы и перезагрузка не проверялись.

## Уточнено в P0.5

Вывод [отчёта P0.5](../probes/p0.5-update-lifecycle.md) по рубежному полному прогону `make probe-update` 2026-11-18 (`20261118-202351-3355`, коммит `9451413`, без ошибок исполнения). Контрольный полный прогон `20261118-205252-48346` (коммит `ce691e7`) дал те же статусы всех частей. Проба моделирует процессы собственным минимальным GUI, помощником, хостом и нагрузкой. Решение не меняется. Протокол замены и итог по контракту обновления записаны в [ADR-0019](0019-distribution-and-updates.md), «Уточнено в P0.5».

- **Строка «Обновление» контракта времени жизни** подтверждена моделью пробы.
  - GUI N и N+1 запущены через LaunchServices, и N+1 открывает те же сессии.
  - Хосты и нагрузки, запущенные из `runtime/1/`, сохраняют PID и время старта. N+1 подключается к ним по протоколу 1, хвост без пропуска, ввод с квитанцией. Новая сессия идёт из `runtime/2/`.
  - Повторное подключение нагрузку не запускает.
- **Несовместимость.** Кандидат, несовместимый с живыми хостами, откладывается без перезапуска агентов. Совместимость проверяется под заморозкой создания сессий соединением без лидерства и ресайза с диапазоном версий кандидата. Хост отвечает `Refused` до любого изменения сессии.
- **Контракт доступности.** В промежутках смены владельца при обновлении управляющий API недоступен. Клиент получает явный временный отказ с признаком повтора или ждёт сокет и получает квитанцию, ложного успеха нет. Непрерывной доступности контракт не требует, брокер не понадобился.
- **TCC хостов и `responsibility_spawnattrs_setdisclaim` не наблюдались.** Все части клетки TCC — `not_run`, шаг выдачи владельца не выполнялся. По правилу плана итог — «выбор не подтверждён». Приватный API автоматически не включается: хосты пробы по умолчанию запускаются обычным `posix_spawn`, disclaim — только вариант сценария. Пункт «Последствий» об атрибуции TCC остаётся в силе.
- **Передача в P2.1:**
  - решение по disclaim и TCC хостов, переживших обновление, по собственному наблюдению после шага выдачи владельца;
  - hello с диапазоном версий и `Refused` до изменения сессии;
  - запись PID и времени старта хоста и нагрузки;
  - запуск хоста из копии `runtime/<version>/`, потомки через `posix_spawn` с `POSIX_SPAWN_CLOEXEC_DEFAULT`.

## Уточнено в P1.1

Решение плана P1.1 `core-domain`, принятое при планировании 2026-11-21. Модель процессов не меняется. Устройство актора записано в [ADR-0020](0020-concurrency.md), «Уточнено в P1.1».

- Ядро команд — crate `shellio-core` без зависимостей от AppKit, objc2 и SQLite. Хранение объявлено в ядре портом `Persist`, его реализует crate `shellio-store` на SQLite. Соединяет их `apps/shellio` в P1.2 в порядке «блокировка единственного экземпляра → хранилище → ядро».
- Транспортная граница: всё, что проходит через `CoreHandle`, сериализуемо в JSON — `Command`, `Query`, `Reply`, `CoreError`, `Event`, `Snapshot`. В сообщениях нет `Arc`, каналов и ссылок. Перенос ядра в отдельный процесс по триггеру брокера меняет транспорт, а не сообщения.
- Равенство прямого вызова и вызова через границу проверяет тест JSON-петли: сценарий идёт через обёртку, которая сериализует и разбирает каждый запрос, ответ и событие, и сравнивается с тем же сценарием напрямую.
- Единственный писатель `state.db` — актор ядра. Ответ на команду, меняющую состояние, приходит только после записи.
- Конверт запроса с номером, `hello` и версия протокола — P1.2.

## Условие пересмотра

Требование продолжать доставку поручений и работу CLI без запущенного GUI.
