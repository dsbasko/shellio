# Фаза 5. Поставка и зрелость

Обзор фазы: что в ней реализуется, что система даёт по её итогу и что входит в каждый шаг. Состав и порядок шагов задаёт [дорожная карта](roadmap.md), решения — [ADR](adr/README.md), поведение — [ux.md](ux.md). Статусы приведены на 2026-11-24, актуальный статус шага — колонка «Готов» дорожной карты.

Детальных планов шагов фазы ещё нет. Состав ниже собран из дорожной карты, ADR, `ux.md`, отчёта пробы P0.5 и передач выполненных шагов. Он уточняется при планировании каждого шага ([ADR-0036](adr/0036-autonomous-execution.md)).

## Цель фазы

Фаза состоит из двух частей.

**Поставка** — P5.1–P5.3. Приложение собирается в проверяемый релиз, устанавливается через Homebrew и обновляет само себя, не завершая работающие сессии. Платной учётной записи Apple Developer нет, поэтому нотаризации не будет: подпись — постоянная самоподписанная идентичность, целостность релиза — minisign, поддерживаемые пути установки — Homebrew и встроенное обновление ([ADR-0019](adr/0019-distribution-and-updates.md)).

**Зрелость** — P5.4–P5.6. Готовое приложение проходит три сквозные проверки: бюджеты производительности на больших данных, доступность и восстановление после сбоев. P5.7 — необязательный шаг про внешние плагины.

P5.1–P5.3 не зависят от фаз 3 и 4. Их можно выполнить сразу после фазы 2, если автообновление понадобится раньше.

Отдельного критерия выхода у фазы в дорожной карте нет: она закрыта, когда закрыты её шаги.

## Что получаем по итогу фазы

### Для пользователя

- **Установка одной командой** из собственного Homebrew tap. Cask снимает карантин со staged-копии, ставит `shellioctl` в `PATH` и умеет удалять приложение.
- **Автообновление.** Проверка при запуске и раз в сутки. Готовое обновление показано в статус-баре, `Space u` или клик открывает поповер, из которого оно активируется. Сессии продолжают работать: после перезапуска те же рабочие области и сессии, короткое состояние «подключение» (поток 11).
- **Несовместимое обновление не убивает агентов.** Если новая версия не совместима с работающими хостами, активация откладывается с явным сообщением и списком сессий. Агенты молча не перезапускаются.
- **Откат.** Старая версия сохраняется до подтверждения работоспособности новой.
- **Предсказуемость.** Бюджеты [архитектуры](architecture.md) выполняются на больших репозиториях, при многих панелях и в долгих сессиях. Превышение бюджета считается дефектом.
- **Доступность.** VoiceOver, Increase Contrast, Reduce Motion и полная работа с клавиатуры проверены на всём приложении.
- **Путь восстановления** для повреждённых данных, отказа сети, недействительных токенов, падения плагина и несовместимого обновления.

- Автоматического отката без потери новых данных, если миграция схемы необратима ([ADR-0019](adr/0019-distribution-and-updates.md)).
- Внешних плагинов, если владелец не примет решение о P5.7.

## P5.1 `release-pipeline` — релизный конвейер

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P0.5 |
| Готово, когда | Тег создаёт проверяемый релиз |
| Решения | [ADR-0019](adr/0019-distribution-and-updates.md), [ADR-0022](adr/0022-licensing-and-borrowing.md) |

### Зачем этот шаг

До этого шага приложение существует только как локальная сборка `make bundle`. Обновлению и Homebrew нужен источник: опубликованный артефакт, который можно проверить, не доверяя каналу доставки.

### Что входит

- **Сборка и подпись в CI.** Бандл подписывается постоянной идентичностью `Shellio Dev` по SHA-1 сертификата с явным designated requirement. Сертификат и закрытый ключ хранятся в секретах CI. Сборка только под arm64.
- **`latest.json`** последнего релиза, по которому приложение узнаёт о новой версии.
- **minisign.** Файл и архив подписываются, публичный ключ вшит в приложение.
- **Публикация.** Релизы должны быть доступны без авторизации; для приватного репозитория нужен отдельный публичный источник.
- **Уведомления о лицензиях.** Сторонние уведомления собираются в `THIRD_PARTY_NOTICES`: libghostty (MIT) статически линкуется, и его уведомление входит в поставку; код agterm и zmx (MIT) можно переносить только с сохранением уведомления об авторстве.
- **`shellioctl` в бандле** — основание для ссылки Homebrew в P5.3 ([ADR-0007](adr/0007-control-api.md), «Уточнено в P1.2»). Для управляемого nvim его кладёт в бандл P3.6, если этот шаг ещё не выполнен ([ADR-0038](adr/0038-shipped-nvim-config.md)).
- **Комплект nvim в релизе.** Конфигурация, плагины, парсеры и инструменты языков входят в бандл и в `THIRD_PARTY_NOTICES` по инвентаризации P3.7–P3.9 ([ADR-0038](adr/0038-shipped-nvim-config.md)).

### Что получаем в результате

- Тег в репозитории даёт релиз, у которого проверяются подпись кода, подпись minisign и состав.
- Есть артефакт, от которого работают P5.2 и P5.3.

### Что шаг наследует

- **Схема подписи частей бандла.** Проба P0.5 подписывала каждую часть своим идентификатором со стабильным designated requirement на закреплённый лист и проверяла кандидата по требованию каждой части. Это был выбор стенда: схему подписи частей продукта выбирает этот шаг ([отчёт P0.5](probes/p0.5-update-lifecycle.md), «Передачи»).
- **CDHash меняется с каждым релизом,** поэтому секрет Keychain с partition ID прежнего релиза следующему недоступен. Решение — отдельным ADR (см. P5.2).
- **CI проверен только статически.** В P0.1 workflow прошёл `actionlint`, но первый прогон на раннере в документах не записан: метка раннера, путь Xcode, загрузка Metal toolchain и размеры кэшей не подтверждены.
- **Ценность ключей.** Приватный ключ minisign и сертификат — самое ценное в проекте: их потеря означает ручную переустановку у всех пользователей.
- Проба P0.5 `latest.json`, minisign, публикации, CI и секретов не касалась.

### Границы

- Загрузка и установка обновления — P5.2. Cask — P5.3.
- Sparkle отвергнут ради полностью Rust-кода и управления связкой GUI, хостов и runtime.

## P5.2 `auto-update` — автообновление

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P5.1, P2.1, P2.5 |
| Готово, когда | Обновление при живых агентах проверено приёмочным проходом исполнителя |
| Решения | [ADR-0019](adr/0019-distribution-and-updates.md), [ADR-0006](adr/0006-single-instance.md), [ADR-0004](adr/0004-process-model.md), [ADR-0018](adr/0018-storage-and-config.md) |

### Зачем этот шаг

Главная ценность приложения — долгие сессии агентов. Обновление, которое их завершает, обесценивает и то, и другое. Шаг делает обновление событием интерфейса: GUI перезапускается, сессии живут на прежнем runtime.

### Что входит

- **Проверка.** При запуске и раз в сутки читается `latest.json`. Файл и архив проверяются подписью minisign с вшитым публичным ключом.
- **Загрузка.** Загрузчик не ставит атрибут карантина. Кодовая подпись новой версии проверяется по сертификату и требованию, а не по отображаемому имени. Кандидат с изменённым после подписи файлом, с тем же именем и другим сертификатом или с другим идентификатором отвергается до начала замены.
- **Подготовка** на той же файловой системе, что и установленный бандл. Готовность показана в статус-баре.
- **Протокол замены,** выбранный пробой: `renamex_np(RENAME_SWAP)` на одном томе APFS с журналом намерения `<state>/update/journal.json`. Состояния журнала: `idle`, `staged-deferred`, `staged`, `intent`, `swapped`, `launched`, `committed`, `cleaning`, `aborting`, `rollback-intent`, `rolled-back`, `retired`. Журнал пишет только владелец `shellio.lock`; каждая мутация диска идёт после записанного решения.
- **Восстановление.** Любой процесс, взявший блокировку при незавершённой попытке, сначала доводит её по журналу до известного состояния и только потом публикует сокет. Место этого разбора — между взятием блокировки и открытием `state.db` — оставлено в P1.2 ([ADR-0006](adr/0006-single-instance.md)).
- **Подтверждение работоспособности.** Новая версия подтверждается, когда: исполняемый файл и CDHash процесса ожидаемые; она единственный владелец блокировки и её сокет отвечает своим поколением; каждая живая сессия найдена и подключена без пропуска вывода; процессы хостов и нагрузок прежние. Срок задаётся один раз, сторож снимает неподтверждённую версию.
- **Откат** на сохранённую прежнюю версию.
- **Runtime.** Активная версия `shellio-host` копируется в `runtime/<version>/`. Старое поколение удаляется, когда его не использует ни одна сессия.
- **Отложенная активация.** Несовместимый с живыми хостами кандидат остаётся в `staged-deferred`: в статус-баре «обновление ждёт завершения сессий» и их список, можно завершить сессии или отложить.
- **Миграция схемы.** Перед миграцией делается согласованная резервная копия средствами SQLite.
- **Интерфейс** (поток 11): обновление в статус-баре, `Space u` или клик открывает поповер.

### Что получаем в результате

- Поток 11: активация обновления перезапускает GUI, новый GUI подключается к тем же сессиям.
- Требование «Автообновление» из [requirements.md](requirements.md) закрыто.
- Риск «обновление завершает сессии» снимается на продукте: проба P0.5 сняла его только на своей модели.

### Что шаг наследует

Загрузчик пишется заново по таблицам переходов и восстановления, правилу подтверждения, сторожу, заморозке и отсрочке [отчёта P0.5](probes/p0.5-update-lifecycle.md). Вместе с ними приходят:

- **Keychain.** Отрицательный вывод P0.5: версия N+1 с тем же designated requirement и другим CDHash молча не читает секрет, созданный версией N. Решение о хранении секретов при обновлении принимается новым ADR при планировании P4.1 или этого шага. Пределы вывода: наблюдалась временная файловая keychain, Data Protection keychain не проверялась, чтение с разрешённым взаимодействием не проверялось.
- **TCC.** Сохранение разрешений GUI после обновления в пробе не наблюдалось: все 48 частей — `not_run`, шаг выдачи не выполнялся. GUI-часть передана сюда, хосты — P2.1.
- **Сторож.** Правка после закрытия пробы: время для решения о сигнале берётся до чтения журнала. Обе ветки сторожа — модель, стенд их чередование не воспроизводил.
- **Уборка:** `runtime/<N>/` без живых хостов, каталоги неудачных попыток, оставшийся каталог подготовки без журнала, резервные копии базы ([ADR-0018](adr/0018-storage-and-config.md), «Уточнено в P1.1»).
- **Отмена и устойчивость отложенного кандидата,** новая попытка при журнале не в `idle`.
- **Повторное открытие во время передачи владения.** Обычный `open` при живом экземпляре нового процесса не создаёт и аргументы не доставляет.
- **Зависший владелец.** Клиент не отличает зависшую новую версию от запускающейся: это ограничение протокола.
- **Откат после необратимой миграции схемы** проба не проверяла. Откат документируется в плане шага ([ADR-0018](adr/0018-storage-and-config.md)).
- **Живой nvim.** Ресурсы редактора удерживаются по поколениям, как runtime хостов ([ADR-0038](adr/0038-shipped-nvim-config.md)). Сценарий N → N+1 с несохранённым буфером: старый nvim впервые открывает файл другого типа и вызывает команду нового GUI, новый nvim в другой области получает новое поколение, старые ресурсы удаляются после последнего потребителя. Его проверяет тот из шагов P3.7 и P5.2, который выполняется позже.
- **Кандидат на другом томе** прерывает попытку, поэтому условие «на той же файловой системе» проверяется явно до подготовки.

### Границы

- Установка и обновление через brew — P5.3.
- Сессии не переживают выход из системы и перезагрузку.
- Приёмка — приёмочный проход исполнителя: то, чего автоматика не наблюдает, получает `not_run` с причиной.

## P5.3 `homebrew-cask` — установка через Homebrew

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P5.1, P1.2 |
| Готово, когда | Чистая установка и обновление на другой машине |
| Решения | [ADR-0019](adr/0019-distribution-and-updates.md) |

### Зачем этот шаг

Без нотаризации приложение, скачанное браузером, Gatekeeper не запустит. Homebrew — основной поддерживаемый путь установки: cask снимает карантин до первого запуска.

### Что входит

- **Собственный tap с cask:** `depends_on arch: :arm64`, `auto_updates true`, `binary` для `shellioctl`.
- **Снятие карантина** в `preflight_steps` со staged-копии.
- **`shellioctl`** в `PATH` ссылкой из бандла.
- **Удаление** через cask.
- **Понятное сообщение при ошибке снятия карантина:** без него приложение не запустится.

### Что получаем в результате

- На чистой машине одна команда ставит приложение, оно запускается без окна Gatekeeper, `shellioctl` доступен из терминала.
- Cask объявляет `auto_updates true`: новые версии ставит собственный механизм обновления приложения.
- Требование «Установка через Homebrew» из [requirements.md](requirements.md) закрыто.

### Что шаг наследует

Проба P0.5 подтвердила механизм на изолированном Homebrew 7.0.14 и macOS 27.0.1 ([ADR-0019](adr/0019-distribution-and-updates.md), «Карантин»):

- Cask со снятием карантина даёт установленный самоподписанный бандл, который `open` запускает без окна Gatekeeper.
- Тот же бандл с карантином не запускается. Окно Gatekeeper по умолчанию предлагает «Переместить в Корзину», и Escape или Return выбирают именно её. Сообщение об ошибке снятия карантина должно это учитывать.
- `spctl --assess` отвергает оба бандла, запуску без карантина это не мешает.

Не проверялось пробой и остаётся шагу: публичный tap, чистая установка на другой машине, сетевые ошибки загрузки.

### Границы

- Curl-установщик как основной путь отвергнут.
- Условие пересмотра ADR-0019 — ужесточение Gatekeeper в новой macOS или появление Developer ID.

## P5.4 `performance-pass` — проход по производительности

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | Фазы 2–4 |
| Готово, когда | Бюджеты выполняются |
| Решения | [ADR-0021](adr/0021-testing.md), [ADR-0002](adr/0002-ui-stack-appkit.md), [ADR-0011](adr/0011-resource-accounting.md) |

### Зачем этот шаг

Каждый шаг проверяет свои бюджеты на своих данных. Этот шаг проверяет приложение целиком на том, что встречается в ежедневной работе: большие репозитории, много панелей, долгие сессии.

### Что входит

- **Сценарии:** большие репозитории, много панелей, длинные сессии.
- **Бюджеты** [архитектуры](architecture.md):

  | Показатель | Цель |
  | --- | --- |
  | Запуск до интерактивного окна | до 500 мс |
  | Реакция на клавишу в `Navigation` | до 16 мс |
  | CPU GUI в простое при видимых панелях | до 1% |
  | Скрытые поверхности | без рендера и swap chain |
  | Память GUI без терминалов | до 150 МБ |
  | Открытие diff на 100 тыс. строк, первый экран | до 200 мс |
  | Прокрутка diff | без потери кадров при 120 Гц |
  | Стоимость сэмплера | до 0,5% CPU |

- **Правило:** измеряется набор сценариев, рост сверх бюджета — дефект ([ADR-0021](adr/0021-testing.md)).

### Что получаем в результате

- Подтверждённые или уточнённые бюджеты: значения архитектуры по её же тексту уточняются по замерам P0.8 и этого шага.
- Требование «Rust, быстрота, экономия CPU и памяти» из [requirements.md](requirements.md) получает итоговую проверку.

### Что шаг наследует

- **Холодный старт и навигация на 60 Гц** — передача из P1.3. Навигация на 120 Гц там в бюджете, на 60 Гц вердикта нет, холодный старт не замерялся ([ADR-0002](adr/0002-ui-stack-appkit.md), «Уточнено в P1.3»).
- **Граф истории на больших репозиториях:** после проверки на 100 тыс. коммитов в P3.5 — ещё раз здесь ([ADR-0033](adr/0033-git-history-panel.md)).
- **Бюджеты, не подтверждённые пробами:** открытие и память `DiffView` (P0.6, отрицательный вывод) и стоимость сэмплера (P0.8, не измерена). Их закрывают P3.2 и P2.4, здесь — повторная проверка на больших данных.
- **Цена Rust-хоста** из P0.4 — attach, CPU на объём вывода, память после attach — получает бюджеты в P2.1 и проверяется здесь на долгих сессиях.
- **Условия замера.** Замеры P0.8 сорвала фоновая нагрузка машины, замеры задержки чувствительны к частоте экрана и способу замера. Условия записываются до первого прогона.

### Границы

- Шаг проверяет и чинит, новых возможностей не добавляет.

## P5.5 `accessibility-polish` — доступность

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | Фазы 2–4 |
| Готово, когда | Приёмочный проход исполнителя пройден |
| Решения | [ADR-0002](adr/0002-ui-stack-appkit.md), [ADR-0023](adr/0023-opaque-window-and-shell.md), [ADR-0027](adr/0027-focused-panel-contrast.md), [ADR-0036](adr/0036-autonomous-execution.md) |

### Зачем этот шаг

Собственные компоненты — `DiffView`, вид терминала, граф истории — реализуют протоколы доступности сами: AppKit даёт их только стандартным контролам. Требования к темам и клавиатуре действуют с первого шага, но проверялись по частям. Шаг проверяет их на готовом приложении.

### Что входит

- **VoiceOver** на всех панелях, включая собственные компоненты.
- **Контраст:** светлая и тёмная темы и обе ячейки Increase Contrast. Панель с фокусом контрастнее остальных, панели без фокуса покрыты вуалью ([ADR-0027](adr/0027-focused-panel-contrast.md)).
- **Reduce Motion:** анимация короткая и отключается.
- **Регрессия клавиатуры:** каждое действие панели доступно с клавиатуры в любой зоне, в компактном виде — через раскрытие вглубь или `zoom` ([AGENTS.md](../AGENTS.md), «Адаптация к зонам»). Всё, что есть мышью, есть с клавиатуры, и наоборот (принцип 4 [ux.md](ux.md)).
- **Смысл не только цветом:** значок типа и точка статуса рядом, ветки и теги графа доступны текстом.

### Что получаем в результате

- Приёмочный проход по доступности всего приложения с записанными исходами.
- Требование «обязательны светлая и тёмная темы, Increase Contrast и Reduce Motion» проверено на всех панелях, а не только на галерее компонентов.

### Что шаг наследует

Проверки доступности, которые в пробах получили `not_run`, переданы шагам, строящим соответствующие виды:

- VoiceOver и доступность терминала со scrollback, Increase Contrast и Reduce Motion в поверхности — P2.2 (из P0.3).
- VoiceOver и системный Increase Contrast в открытом окне для `DiffView`, ключ элемента доступности строки — P3.2 (из P0.6).

Приёмка — приёмочный проход исполнителя: наблюдаемое записывается `pass` с сырым артефактом, ненаблюдаемое автоматикой — `not_run` с причиной, а не `pass` ([ADR-0036](adr/0036-autonomous-execution.md)).

### Границы

- Прозрачные материалы и размытие не используются и не добавляются ([ADR-0023](adr/0023-opaque-window-and-shell.md)).

## P5.6 `recovery-acceptance` — восстановление после сбоев

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | Фазы 2–4 |
| Готово, когда | Каждый сценарий показывает путь восстановления |
| Решения | [ADR-0018](adr/0018-storage-and-config.md), [ADR-0008](adr/0008-plugin-system.md), [ADR-0004](adr/0004-process-model.md), [ADR-0015](adr/0015-forge-review.md), [ADR-0019](adr/0019-distribution-and-updates.md) |

### Зачем этот шаг

Принцип 10 [ux.md](ux.md): ошибка показывается рядом с действием и содержит следующий шаг. Шаг проверяет его на сбоях, которые в обычной работе редки, а потому легко остаются без пути выхода.

### Что входит

Сценарии дорожной карты и то, что о них уже решено:

- **Повреждённые данные.** База, которая не открывается, даёт `Corrupt`, файл не трогается. Схема новее бинаря даёт `NewerSchema` без единой записи. Путь восстановления для обоих состояний передан этому шагу из P1.1 ([ADR-0018](adr/0018-storage-and-config.md)). Повреждённая строка или запись панели не мешает запуску остальных панелей.
- **Сеть.** Отказ сети при ревью и пайплайнах: черновики сохранены локально, состояние `unknown` сверяется, слепого повтора нет ([ADR-0015](adr/0015-forge-review.md)).
- **Токены.** Образец поведения уже записан для воркспейса без аккаунта сервиса: внешние записи приглушены, рядом причина, следующий шаг — подключить аккаунт в настройках ([ux.md](ux.md), «Пограничные пути»).
- **Падение плагина.** Отсутствующий плагин или нечитаемые данные панели оставляют заглушку с причиной и сохраняют запись ([ADR-0008](adr/0008-plugin-system.md)).
- **Несовместимое обновление.** Активация откладывается, сессии живут (P5.2). База со схемой новее бинаря отвергается без записи.

### Что получаем в результате

- Для каждого сценария известно, что видит пользователь и что он может сделать. Новое поведение отражается в [ux.md](ux.md).
- Приложение не остаётся в состоянии, из которого нет действия.

### Что шаг наследует

- Резервные копии базы создаются перед миграцией и автоматически не удаляются; их уборку и откат схемы делает P5.2.
- Потеря хоста при живых процессах и без них уже имеет пути восстановления с P2.1.
- Некорректный файл настроек оставляет последнюю исправную версию и показывает ошибку, некорректная привязка клавиш отключается с сообщением ([ADR-0018](adr/0018-storage-and-config.md), [ADR-0010](adr/0010-input-and-navigation.md)).

### Границы

- Автоматический откат без потери новых данных после необратимой миграции не обещается.

## P5.7 `external-plugins` — внешние плагины

| | |
| --- | --- |
| Статус | ⬜ не начат, необязательный |
| Зависит от | P1.5 |
| Готово, когда | Пример плагина подключается без пересборки |
| Решения | [ADR-0008](adr/0008-plugin-system.md) |

### Зачем этот шаг

Плагины первой версии собираются вместе с приложением: у Rust нет стабильного ABI, а внешних авторов пока нет. Шаг существует на случай, если они появятся. План создаётся только по решению владельца.

### Что входит

По [ADR-0008](adr/0008-plugin-system.md) внешний плагин — исполняемый процесс с протоколом поверх управляющего API, декларативными панелями и терминальными вкладками.

### Что получаем в результате

- Пример плагина подключается к собранному приложению без пересборки.
- Ограниченный набор `placements` допускается только для таких внешних типов: встроенные плагины объявляют все четыре зоны.

### Что шаг наследует

- Контракт плагина P1.5: манифест, кардинальность, команды шины, область доступа.
- Сокет управляющего API защищает от других пользователей, но не изолирует процессы одного пользователя ([ADR-0007](adr/0007-control-api.md)).

### Границы

- `dylib` с `abi_stable` и WASM отвергнуты: хрупкая граница и невозможность передать нативный `NSView`.
- Протокол внешних плагинов ещё не спроектирован: это предмет плана и нового решения.
