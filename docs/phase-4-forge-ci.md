# Фаза 4. GitHub, GitLab, CI

Обзор фазы: что в ней реализуется, что система даёт по её итогу и что входит в каждый шаг. Состав и порядок шагов задаёт [дорожная карта](roadmap.md), решения — [ADR](adr/README.md), поведение — [ux.md](ux.md). Статусы приведены на 2026-11-24, актуальный статус шага — колонка «Готов» дорожной карты.

Детальных планов шагов фазы ещё нет. Состав ниже собран из дорожной карты, ADR, `ux.md`, отчёта пробы P0.7 и передач выполненных шагов. Он уточняется при планировании каждого шага ([ADR-0036](adr/0036-autonomous-execution.md)).

## Цель фазы

Основной цикл работы с merge и pull request и с пайплайнами без браузера: открыть MR, изучить изменения, написать комментарии черновиками, отправить их с итогом, слить. Работа идёт с GitHub, GitHub Enterprise, GitLab и self-hosted GitLab через общую модель с адаптерами. Главное свойство фазы — черновик не теряется: он записан локально раньше любого сетевого запроса, а отправка переживает таймаут, сбой и смену ревизии без слепого повтора ([ADR-0015](adr/0015-forge-review.md)).

Отдельного критерия выхода у фазы в дорожной карте нет: она закрыта, когда закрыты её шесть шагов. Критерий последнего шага — «основной цикл закрыт без браузера».

## Что получаем по итогу фазы

### Для пользователя

- **Аккаунты по воркспейсам.** GitHub, GitHub Enterprise, GitLab и self-hosted GitLab подключаются в настройках. Аккаунты и их списки ограничены воркспейсом, секреты лежат в Keychain ([ADR-0025](adr/0025-workspaces-and-project-catalog.md), [ADR-0018](adr/0018-storage-and-config.md)).
- **Ревью без checkout.** `Space r o` и ссылка либо выбор из списка открывают MR или PR. Описание, коммиты, файлы, diff, треды, версии и «изменения с прошлого ревью» читаются по закреплённым SHA, рабочая копия не меняется.
- **Черновики.** `c` на строке или диапазоне создаёт черновик, который сразу записан в `state.db`. Счётчик черновиков всегда виден. Suggestions, ответы в тредах, отметка просмотренных файлов.
- **Отправка в два шага.** Экран отправки показывает полный список и итог — Comment, Approve или Request changes — и называет репозиторий и ветки. После отправки виден итог: отправлено полностью или частично.
- **Честное «неизвестно».** Таймаут даёт состояние «неизвестно», которое сверяется с сервером, а не повторяется. Смена head показывает баннер с выбором: остаться, перейти, перепривязать.
- **Действия над MR.** Merge, squash, auto-merge, draft/ready, close/reopen, reviewers, assignees, labels, создание MR и checkout ветки.
- **Пайплайны.** Статус проекта в статус-баре, список запусков по репозиториям, jobs, лог, retry, cancel и ручной шаг. Упавший job передаётся агенту с закреплённым логом ([ADR-0016](adr/0016-pipelines.md)).

### Потоки `ux.md`, которые начинают работать

### Управление из CLI

Каждое действие ревью и пайплайнов получает команду шины и CLI по правилу [ADR-0007](adr/0007-control-api.md). Имена групп определяют планы шагов. Из решений известно одно требование к составу: агент предлагает черновики ревью через `shellioctl`, они попадают в тот же журнал и видны отдельной пометкой ([ADR-0015](adr/0015-forge-review.md)).

### Что появляется в репозитории

По [архитектуре](architecture.md): crate `shellio-forge` (общая модель, адаптеры GitHub и GitLab, журнал ревью), `forge-fake` (локальный GitLab и GitHub для тестов), плагины `review` и `pipelines`.

### Чего после фазы ещё нет

- Автообновление и поставка — фаза 5.

## P4.1 `forge-accounts` — аккаунты и клиент сервисов

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P0.7, Фаза 1 |
| Готово, когда | Подключаются GitHub, GitHub Enterprise, GitLab и self-hosted |
| Решения | [ADR-0015](adr/0015-forge-review.md), [ADR-0018](adr/0018-storage-and-config.md), [ADR-0025](adr/0025-workspaces-and-project-catalog.md), [ADR-0019](adr/0019-distribution-and-updates.md) |

### Зачем этот шаг

Ревью и пайплайны нуждаются в общем основании: кто пользователь на каком хосте, какой репозиторий проекта какому remote соответствует, что умеет конкретная инсталляция. Шаг даёт это основание и тестовый сервер, на котором проверяются все остальные шаги фазы.

### Что входит

- **Аккаунты.** Токены GitHub и GitLab хранятся в macOS Keychain. Аккаунт привязан к воркспейсу: данные и списки ограничены им, секреты физически лежат в одном Keychain.
- **Соответствие remotes.** Проект содержит несколько репозиториев с remotes, каждый remote сопоставляется с хостом и аккаунтом ([ADR-0001](adr/0001-vocabulary.md)).
- **HTTP-клиент** вне главного потока с учётом лимитов хоста.
- **Возможности.** Адаптер объявляет возможности инсталляции и проверяет их чтением: self-hosted версии могут уметь меньше. ID провайдера — непрозрачная строка.
- **Общая модель** `ReviewTarget`, `Revision`, `Thread`, `DraftComment`, `ReviewSession` в `shellio-forge` с адаптерами провайдеров.
- **`forge-fake`** — локальный GitLab и GitHub для тестов. Тесты в настоящую сеть не ходят ([ADR-0021](adr/0021-testing.md)).
- **Подключение аккаунта** в настройках.

### Что получаем в результате

- Четыре вида инсталляций подключаются и отвечают на чтение возможностей.
- Пограничный путь «В воркспейсе нет аккаунта сервиса»: отправка ревью и перезапуск приглушены, рядом причина и переход к настройкам.
- При переносе проекта в другой воркспейс выбирается допустимый аккаунт, иначе операции с GitHub и GitLab приостанавливаются ([ADR-0025](adr/0025-workspaces-and-project-catalog.md)).
- Остальные шаги фазы пишутся против `forge-fake`.

### Что шаг наследует

Проба P0.7 подтвердила журнал, якоря и сверку на `forge-fake` (все 18 строк матрицы `pass`) и на GitLab CE 19.6.1 (11 из 12 клеток `pass`). Остальное передано сюда ([отчёт P0.7](probes/p0.7-review-api.md), раздел «Передачи»; [ADR-0015](adr/0015-forge-review.md), «Уточнено в P0.7»):

- **Не наблюдались вовсе:** github.com и gitlab.com (песочниц и токенов не было), GitHub Enterprise Server (нет инсталляции), черновик, созданный в браузере. Первым живым прогоном подтверждаются обе ветви GitHub, существующий `PENDING`, `markFileAsViewed`, тариф и лимиты gitlab.com.
- **Гипотезы GitHub без опоры на наблюдение:** второй `PENDING` того же пользователя — 422; Submit с `comments[]` — отказ; обязательность `body`; поля входов нескольких мутаций; вид ошибки лимита GraphQL.
- **Отрицательный вывод по GitLab.** CE 19.6.1 принимает `draft_note` с позицией прежнего head ответом 201, но записывает её под текущие `diff_refs`. Адаптер сверяет тройку SHA в ответе на каждое создание черновика; при расхождении черновик не публикуется, пользователю предлагается перейти на новую ревизию, а ID созданного объекта сохраняется для обновления или удаления.
- **Асинхронность GitLab.** `diff_refs` и версии MR обновляются не сразу: адаптер опрашивает MR до готовности тройки.
- **Чтение возможностей.** Introspection на CE возвращает полную схему, около 8,8 МБ на вызов; адаптер учитывает эту стоимость.
- **Лимиты.** На gitlab.com 60 запросов в минуту на создание заметок, на self-managed по умолчанию 300. Входит ли в счёт публикация `draft_note`, не наблюдалось. Состояние лимита показывается, только если хост прислал заголовки.
- **`forge-fake` продукта** моделирует то, чего не было у оракула пробы: асинхронное обновление MR, системные заметки в тредах, ответы без заголовков лимитов, `user_can_approve: true` у автора.
- **Секреты в ответах.** Ответ `GET /projects/:id` владельцу содержит действующий `runners_token`. Такие ответы не пишутся в журналы и диагностику без правила очистки ключей `*_token`, `*_secret`, `*_password`.
- **Журнал:** хранить вид отказа записи и ID из ответа, чтобы отличать обрыв транспорта от отвергнутого ответа. Стойкость к сбою питания не наблюдалась: на macOS для сброса кэша накопителя нужен `PRAGMA fullfsync`.

Открытый вопрос из P0.5: обновлённая версия приложения молча не читает секрет Keychain, созданный прежней. Без Team ID partition ID секрета — CDHash, а он меняется с каждым релизом. Решение о хранении секретов при обновлении принимается новым ADR при планировании этого шага или P5.2 ([ADR-0019](adr/0019-distribution-and-updates.md), «Keychain»).

### Границы

- Чтение MR — P4.3, пайплайны — P4.2.
- Запись на настоящие сервисы в тестах — только в приватные песочницы.

## P4.2 `pipelines` — пайплайны

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P4.1, P2.7 |
| Готово, когда | Поток 9 на нескольких репозиториях |
| Решения | [ADR-0016](adr/0016-pipelines.md) |

### Зачем этот шаг

Проект состоит из нескольких репозиториев на разных сервисах, а иерархии у них разные: у GitLab pipeline, stages и jobs, у GitHub workflow, run, jobs и отдельные checks. Шаг показывает их в одном месте, не искажая ни одну модель, и сокращает путь от упавшего job до агента, который его чинит.

### Что входит

- **Плагин `pipelines`, `PerWorkbench`.** Агрегирует явно выбранные репозитории и remotes проекта.
- **Идентичность запуска:** хост, проект, запуск, попытка, ref, SHA. Нормализуется только общий статус, детали провайдера сохраняются. Сторонние check runs GitHub показываются отдельно.
- **Опрос:** ETag, адаптивный интервал и backoff; активный при видимой панели или идущем запуске, редкий в фоне, без опроса при отключённой сети. Устаревший запуск не выглядит как проверка текущего коммита.
- **Интерфейс:** статус проекта в статус-баре, список с группировкой по репозиторию, jobs, лог, ссылка.
- **Действия:** retry, cancel и ручной шаг при наличии возможности. Retry и Cancel показывают конкретный запуск и попытку.
- **Уведомления.** Завершение следимого запуска даёт системное уведомление.
- **Передача агенту.** Упавший job отдаётся агенту с закреплёнными репозиторием, ref и логом — через composer «спросить» из P2.7.
- **Адаптация к зонам:** сбоку — компактные статусы; в центре — граф, job и лог; внизу — запуски ветки и граф выбранного запуска, лог на месте графа.

### Что получаем в результате

- Поток 9: статус в статус-баре, `Space p` — список, `Enter` — job, `L` — лог, `Space q` — вопрос агенту с закреплённым логом. 4 действия.
- Переход от строки лога к файлу в nvim (P3.6).
- Требование «Пайплайны, в том числе несколько» из [requirements.md](requirements.md) закрыто.

### Что шаг наследует

- Child и downstream pipelines GitLab требуют отдельной проверки на настоящем API ([ADR-0016](adr/0016-pipelines.md), «Последствия»).
- Скрытая панель не опрашивает сеть бесконечно ([ADR-0008](adr/0008-plugin-system.md)).

### Границы

- Постоянный опрос всех проектов отвергнут: расход и лимиты API.
- Общая иерархия stages и jobs для обоих провайдеров отвергнута.

## P4.3 `review-reader` — чтение MR и PR

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P4.1, P3.2 |
| Готово, когда | Большой MR читается без изменения worktree |
| Решения | [ADR-0015](adr/0015-forge-review.md) |

### Зачем этот шаг

Прежде чем комментировать, MR нужно прочитать. Шаг даёт панель ревью в режиме чтения и закладывает привязку ко ревизии, на которой держатся черновики и отправка следующих шагов.

### Что входит

- **Плагин `review`.** `Space r o` и вставленная ссылка либо выбор из списка.
- **Снимок ревизии.** `ReviewSession` привязан к аккаунту, хосту, репозиторию и конкретной ревизии: `base_sha`, `start_sha`, `head_sha`. Смешивать свежие refs с ранее полученным `head_sha` запрещено.
- **Ревью без checkout:** файлы читаются по закреплённым SHA, рабочая копия не меняется.
- **Содержимое:** описание, коммиты, файлы, diff тем же `DiffView`, существующие треды, статус проверок.
- **Версии** и «изменения с прошлого ревью».
- **Навигация:** `n/N` — следующий непросмотренный файл, `]c/[c` — изменения.
- **Разделы «Обзор», «Файлы» и «Треды»** сохраняют смысл при любой ширине: меняются колонки и переход в глубину, а не назначение вкладки.
- **Цель вне панели** определяется по рабочей области: открытая панель ревью или MR/PR текущей ветки. При нескольких целях или их отсутствии открывается список, чужая цель не подставляется.
- **Адаптация к зонам:** сбоку — файлы и треды; в центре — описание, файлы, diff, треды; внизу — статус, черновики, следующее действие.

### Что получаем в результате

- Начало потока 8: MR открывается в 2 действия и читается целиком.
- Большой MR не трогает worktree и не мешает работающим в нём агентам.
- Тексты комментариев и код копируются обычным `Cmd-C` (принцип 14 [ux.md](ux.md)).

### Что шаг наследует

- Снимок ревизии GitLab ждёт готовности `diff_refs` и версий: они обновляются асинхронно ([ADR-0015](adr/0015-forge-review.md), «Уточнено в P0.7»).
- Локальные данные ревью принадлежат проекту и не видны из другого воркспейса, сам MR на сервере общий ([ADR-0025](adr/0025-workspaces-and-project-catalog.md)).
- Бюджеты `DiffView` из P3.2 действуют и здесь.

### Границы

- Черновики и комментарии — P4.4, отправка — P4.5, merge и остальные действия — P4.6.

## P4.4 `review-drafts` — черновики ревью

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P4.3 |
| Готово, когда | Черновики восстанавливаются после сбоя |
| Решения | [ADR-0015](adr/0015-forge-review.md), [ADR-0018](adr/0018-storage-and-config.md) |

### Зачем этот шаг

Комментарий, написанный за полчаса вдумчивого чтения, не должен пропасть из-за сети, сбоя или новой ревизии. Поэтому черновик — локальная запись, а не объект на сервере.

### Что входит

- **Локальный журнал черновиков** в `state.db`. Черновик пишется немедленно, раньше сетевого запроса (принцип 7 [ux.md](ux.md)).
- **Якоря:** строка старой или новой стороны и диапазон. У GitHub — `commit_id`, `path`, `line`, `side`, `start_line`, `start_side`; у GitLab — тройка SHA, пути и строки, `line_range`.
- **Создание:** `c` на строке или диапазоне, `Cmd-Enter` — сохранить. Клик по половине diff в режиме «Рядом» задаёт и строку, и сторону комментария.
- **Suggestions** и **ответы в существующих тредах.**
- **Устаревшие якоря.** При смене head показывается предупреждение с выбором: остаться на ревизии, перейти или перепривязать. Номер строки молча не подбирается.
- **Просмотренные файлы:** `v`. У GitHub отметка хранится на сервере (`markFileAsViewed`), у GitLab — локально. «Просмотрено» и формальное одобрение — разные состояния.
- **Счётчик черновиков** всегда виден.

### Что получаем в результате

- Середина потока 8: черновики пишутся и правятся, переживают закрытие панели, перезапуск и сбой приложения.
- Работа офлайн: черновики создаются без сети.
- Черновики одного проекта не видны из другого воркспейса.

### Что шаг наследует

- **Существующий серверный черновик.** `PENDING` review на GitHub не перезаписывается: перед принятием в работу показывается весь его состав. Черновик, созданный в браузере, на живых сервисах не наблюдался — это проверяет P4.1.
- **GitLab и «остаться на ревизии».** Черновик GitLab с позицией прежнего head сервер записывает под текущую ревизию, поэтому путь «остаться на ревизии» для серверных `draft_note` этим API не выполняется. Расхождение обнаруживается сверкой тройки SHA в ответе на создание черновика, которую вводит P4.1.
- **Диапазон через стороны diff** (`start_side`): у модели пробы P0.6 его нет, продуктовый `DiffView` получает его в P3.2.
- **Стойкость журнала** к сбою питания — открытый пункт P0.7.

### Границы

- Публикация и итог — P4.5.
- Черновики, предложенные агентом, — P4.6.

## P4.5 `review-submit` — отправка ревью

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P4.4 |
| Готово, когда | Поток 8 проходит на обоих провайдерах |
| Решения | [ADR-0015](adr/0015-forge-review.md) |

### Зачем этот шаг

Отправка — единственное место, где локальные черновики становятся записями на чужом сервере. У GitLab нет общей транзакции для комментариев и итога, ответы теряются, ревизия меняется посреди работы. Шаг делает отправку наблюдаемой и восстановимой.

### Что входит

- **Экран отправки** `Space r s` с полным списком и итогом: Comment, Approve, Request changes. Экран называет репозиторий и ветки.
- **Шаги отправки разделены:**
  1. загрузить свежую ревизию и сопоставить якоря;
  2. показать конкретный список и итог;
  3. опубликовать способом провайдера с записью состояний `planned → in_flight → confirmed | unknown`;
  4. сохранить удалённые ID;
  5. показать полностью или частично отправленное.
- **GitHub — две ветви.** Только локальные черновики: один запрос Create review с `comments[]` и итоговым `event`. Серверный `PENDING` review: создание и обновление комментариев с сохранением ID, затем Submit именно этого review.
- **GitLab.** Публикация каждого известного `draft_note` поштучно, сводка отдельным шагом. `approve` с проверкой `sha`. Запрос изменений — через GraphQL `mergeRequestRequestChanges` и только при наличии возможности и прав: без неё действие недоступно и обычным комментарием не имитируется. `bulk_publish` запрещён — он публикует все ожидающие черновики пользователя, включая написанные в браузере.
- **Resolve** тредов.
- **`unknown` и сверка.** После таймаута состояние сверяется с провайдером. `confirmed` ставится только при связи с нашей операцией: удалённый ID из ответа на неё или ожидаемый итог известного объекта. Совпадение по автору, якорю и тексту даёт кандидата, и элемент остаётся `unknown`. Слепого повтора нет: такая же операция не планируется, пока элемент не сверен.
- **Частичный успех.** Если комментарии опубликованы, а сервер отклонил итог, показывается список отправленного и причина отказа, повторить можно только итог.
- **Завершение.** После подтверждения всех шагов экран показывает итог и кнопку «Готово». Новое ревью начинается отдельным действием.

### Что получаем в результате

- Поток 8 целиком на GitHub и GitLab.
- Пограничные пути «Комментарии опубликованы, сервер отклонил итог» и «Таймаут публикации или итога».
- Журнал переживает сбой посреди отправки без повтора записи — это подтверждено пробой на `forge-fake` и GitLab CE.

### Что шаг наследует

Из [ADR-0015](adr/0015-forge-review.md), «Уточнено в P0.7», и [отчёта P0.7](probes/p0.7-review-api.md):

- **Операции, которые сверка не разрешает.** Создающие операции и публикация `draft_note` с потерянным ответом остаются `unknown`: ответ публикации — 204 без тела, связи заметки с черновиком API не показывает. Продукту нужен явный выбор пользователя «считать опубликованным» или «отказаться».
- **Лимит посреди отправки.** Явный отказ по лимиту значит, что запись не принята: элемент получает `failed`, отправка частичная, оставшееся повторяется по выбору пользователя. У GitHub после отказа на сервере остаётся невидимый другим `PENDING` с частью комментариев: продукт показывает это и даёт продолжить или удалить его.
- **Стоимость большого ревью.** На 200 черновиков ветвь локальных черновиков GitHub делает одну запись, серверный `PENDING` — 202, GitLab — 401, все последовательно. Ветвь локальных черновиков выбирается, когда серверный `PENDING` не нужен; длинная отправка GitLab показывает ход.
- **Метод серверного `PENDING`** выбран по документации и на github.com не наблюдался.
- **Запрос изменений GitLab:** пользователь, не назначенный ревьюером, получает HTTP 200 с ошибкой в теле, поэтому итог читается из тела ответа.
- Запрет автору одобрять собственный MR из роли не выводится.

### Границы

- Merge и остальные действия над MR — P4.6.
- Начатая запись во внешний сервис закрытием вида не отменяется: она живёт по своим правилам ([ADR-0020](adr/0020-concurrency.md)).

## P4.6 `review-actions` — действия над MR и PR

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P4.5, P2.6 |
| Готово, когда | Основной цикл закрыт без браузера |
| Решения | [ADR-0015](adr/0015-forge-review.md), [ADR-0013](adr/0013-agent-messaging.md) |

### Зачем этот шаг

После чтения, черновиков и отправки остаются действия, ради которых всё ещё приходится открывать браузер. Шаг закрывает основной цикл и подключает к ревью агентов.

### Что входит

- **Слияние:** merge, squash, auto-merge.
- **Состояние:** draft/ready, close/reopen.
- **Участники и метки:** reviewers, assignees, labels.
- **Создание MR или PR** и **checkout ветки.**
- **Черновики от агента.** Агент предлагает черновики через `shellioctl`; они попадают в тот же локальный журнал и видны отдельной пометкой.
- **Подтверждения по правилу `ux.md`:** подтверждение требуется только там, где действие необратимо или меняет общую ветку, например merge. Обратимые изменения, такие как Draft и Ready, применяются сразу.

### Что получаем в результате

- Основной цикл [ADR-0015](adr/0015-forge-review.md) закрыт без браузера: от списка MR до слияния.
- Агент участвует в ревью как коллега: его предложения попадают в тот же журнал черновиков с отдельной пометкой. Сообщение агента новых прав не даёт ([ADR-0013](adr/0013-agent-messaging.md)).
- Требование «MR/PR: изучение, черновики, отправка» из [requirements.md](requirements.md) закрыто полностью.

### Что шаг наследует

- Каждое действие — команда с обработчиком, CLI, чтением результата и тестами; меню, клавиша, палитра и CLI вызывают один обработчик.
- Возможности инсталляции проверяются: self-hosted версии могут уметь меньше ([ADR-0015](adr/0015-forge-review.md), «Последствия»).

### Границы

- Остальное, что не входит в список основного цикла, открывается в браузере.
