# Проба жизненного цикла обновления: второй запуск

## Overview

- Второй запуск шага P0.5 `probe-update-lifecycle` [дорожной карты](../roadmap.md). Первый запуск — план [20261118-probe-update-lifecycle.md](20261118-probe-update-lifecycle.md). Стенд, клетки, оракулы, правила выбора и статусы результатов заданы там, этот план их не повторяет и не меняет.
- Цели запуска:
  - клетки TCC (E) после шага выдачи владельца;
  - свежий полный прогон и приёмочный проход исполнителя;
  - итог отчёта `docs/probes/p0.5-update-lifecycle.md`, выбранные данные, разделы «Уточнено в P0.5» в ADR-0019, ADR-0004, ADR-0006 и ADR-0034.
- Запуски разведены двумя планами по решению владельца при планировании: один прогон не должен закрыть клетки TCC без шага выдачи.
- Исполнение автономное ([ADR-0036](../adr/0036-autonomous-execution.md)).

## Предусловия

Физические предусловия по ADR-0036. Владелец запускает этот план только после них:

- первый план выполнен и перенесён в `docs/plans/completed/`;
- владелец выполнил `make probe-update-tcc-grant` (раздел «Предусловия» первого плана);
- предусловия первого плана по сеансу GUI, идентичности подписи и разрешениям терминала исполнителя в силе.

Если проверка выдачи в задаче 1 не проходит, клетки E получают `not_run` с причиной «выдача владельца не выполнена или устарела», и исполнение продолжается.

## Development Approach

- **testing approach**: Regular.
- Каждая задача завершается до начала следующей. Рубеж — `make check` и, для задач со стендом, `make probe-update SCENARIOS="…"` без ошибок исполнения.
- Код бандлов пробы меняется только при ошибке исполнения стенда. Правка, меняющая designated requirement, делает выдачу устаревшей: E — `not_run` с этой причиной.
- Правила, статусы и итоги — по разделам «Правила выбора» и «Результаты» первого плана. Непредвиденный выбор — исполнителем с ⚠️ в плане и отчёте.

## Implementation Steps

### Task 1: TCC (E)

- [ ] проверка выдачи: `tcc-grant.json` есть, designated requirement совпадают, живая базовая проверка (разрешённый читает, контроль — `EPERM`); без выдачи — `not_run` клеток E с причиной и переход к задаче 2
- [ ] сценарий `tcc` на всех частях обоих графов и обоих вариантах запуска хоста; подрезультаты «чтение» и «атрибуция»
- [ ] применить правило `responsibility_spawnattrs_setdisclaim` и записать решение исполнителя по правилу плана
- [ ] журнал команд `tccutil` показывает отсутствие вызовов вне цели выдачи
- [ ] `make check` и `make probe-update SCENARIOS="tcc"` проходят

### Task 2: Полный прогон и приёмочный проход исполнителя

- [ ] свежий `make probe-update` без ошибок исполнения на одном коммите; обязательные клетки — по своим сценариям
- [ ] приёмочный проход в сеансе GUI. Пункты, критерий `pass` и сырой артефакт каждого:
  - окно N+1 после обновления показывает ту же сессию: квитанция окна и снимок окна, строки без пропуска по номерам;
  - ввод с клавиатуры в окно N+1 доходит до нагрузки: квитанция нагрузки;
  - обычный `open` во время обновления не создаёт второго владельца: журнал наблюдателя процессов и ответ клиента;
  - диалоги TCC и Gatekeeper, если появлялись: снимок и запись закрытия.

  Эти пункты — дополнительные наблюдения. Ненаблюдаемое получает `not_run` с причиной. Итоги обязательных клеток H и C1 берутся из их сценариев.
- [ ] сверка итогов с черновиком первого запуска по частям, расхождения записаны
