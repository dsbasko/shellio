# Проба учёта CPU и памяти

## Overview

- Шаг P0.8 `probe-resource-accounting` [дорожной карты](../roadmap.md). Зависит от P0.3, открывает P2.4 `resource-metrics`. Критерий шага: подтверждённые формулы и базовые бюджеты.
- [ADR-0011](../adr/0011-resource-accounting.md) (`Proposed`) задаёт две сводки: «Измерено: процессы» (`proc_pid_rusage`, `ri_phys_footprint`, дельта `user + system` к монотонному времени, 100% — одно логическое ядро, уникальное множество `(pid, время старта)`, частичный замер помечается) и «Оценка `≈`» (учтённые байты арен панели, CPU фактически исполняемых участков, общая работа Git в служебной группе). Один общий сэмплер, раз в 2 с при видимом индикаторе. Условие пересмотра: учёт исполняемых участков искажает значения или стоит больше 1% CPU.
- Бюджет [docs/architecture.md](../architecture.md): стоимость сэмплера до 0,5% CPU.
- Передачи из [отчёта P0.3](../probes/p0.3-ghostty-surface.md), таблица передач: `login` с setuid не читается; память на поверхность — сводный `phys_footprint` процесса без ресурсов GPU; необъяснённый остаток после циклов.
- Проба отвечает на вопросы:
  - верны ли формулы измеренной сводки, проверенные против независимых квитанций нагрузки;
  - находит ли атрибуция каждый процесс сессии ровно один раз при переподчинении, быстром выходе, повторном PID и нечитаемом процессе;
  - не начисляет ли учёт исполняемых участков ожидание и вложенную работу, и сколько он стоит;
  - укладывается ли сэмплер в 0,5% CPU на разных размерах множества PID и числе панелей.
- Охват (решения владельца при планировании):
  - проба headless, без AppKit и без поверхности libghostty, набор ghostty не читает;
  - настоящий `login` с setuid запускается напрямую, как его вызывает поверхность Ghostty (`/usr/bin/login -flp <user> /bin/bash --noprofile --norc -c "exec -l <команда>"`); запуск без pty проверен при планировании;
  - утверждение «обновление чисел не вызывает перерисовку терминала» и память на поверхность требуют настоящей поверхности: `not_run` с передачей P2.4;
  - замеры стоимости идут под машинной замерной блокировкой с проверкой фона.
- Итог:
  - проба `spikes/probe-resource-accounting`;
  - цель `make probe-resources`;
  - отчёт `docs/probes/p0.8-resource-accounting.md` с формулами, таблицами стоимости и выбранными сырыми данными;
  - раздел «Уточнено в P0.8» в ADR-0011 и ADR-0034, строка бюджета в `docs/architecture.md`.
- Исполнение автономное ([ADR-0036](../adr/0036-autonomous-execution.md)), параллельно с планом P0.7 по разделу «Параллельное исполнение с P0.7». UI у пробы нет, приёмочного прохода в сеансе GUI нет, его роль выполняет полный прогон (задача 13).

## Параллельное исполнение с P0.7

Этот план и план [20261120-probe-review-api.md](20261120-probe-review-api.md) исполняются одновременно, каждый в своём git worktree и своём рабочем пространстве agterm. Раздел одинаков в обоих планах.

### Запуск (предусловие, выполняется до исполнения)

`ralphex --worktree` запускается только из ветки по умолчанию (`main`), а она отстаёт от `toolchain-bootstrap` на 290 коммитов, и набор ghostty в созданном им worktree до старта не собрать. Поэтому worktree создаются вручную. Worktree создаются от коммита, в котором закоммичены оба плана. Его SHA записывается в файл вне git: переменная оболочки не переходит в другие рабочие пространства agterm, а пустой `--base-ref` вернул бы ralphex к `main`.

```bash
# в основной копии, после коммита обоих планов:
git rev-parse HEAD > ../shellio-p07-p08.base
base=$(cat ../shellio-p07-p08.base)
git worktree add ../shellio-p07 -b probe-review-api "$base"
git worktree add ../shellio-p08 -b probe-resource-accounting "$base"
(cd ../shellio-p07 && make ghostty)   # по очереди: кэш ~/.cache/shellio блокировкой не защищён
(cd ../shellio-p08 && make ghostty)
# в рабочем пространстве agterm P0.7:
cd ../shellio-p07 && base=$(cat ../shellio-p07-p08.base) && ralphex docs/plans/20261120-probe-review-api.md --base-ref "$base" --max-iterations 120
# в рабочем пространстве agterm P0.8:
cd ../shellio-p08 && base=$(cat ../shellio-p07-p08.base) && ralphex docs/plans/20261120-probe-resource-accounting.md --base-ref "$base" --max-iterations 120
```

- `--max-iterations 120`: задачи с длинными прогонами идут по шагу за итерацию (серия стоимости P0.8 — по точке, живые хосты P0.7 — по хосту), значения по умолчанию 50 не хватит.
- `vendor/` игнорируется git, поэтому у каждого worktree свой набор ghostty и своя блокировка `vendor/ghostty.lock`. Общий набор через `SHELLIO_GHOSTTY_VENDOR` не используется: `scripts/ghostty/lock.sh` строит путь блокировки от корня набора, и два worktree отказывали бы друг другу на каждом `make check`.
- У каждого worktree свой `target/`, временный `SHELLIO_STATE_DIR` и каталог прогона `target/probes/<slug>/`.

### Границы веток

- Каждая ветка трогает только свою пробу `spikes/<slug>/`, свой отчёт `docs/probes/<id>-<slug>.md`, свои данные `docs/probes/data/<id>-<slug>/`, свой ADR (ADR-0015 у P0.7, ADR-0011 у P0.8) и свой план.
- Общие файлы, которые трогают обе ветки: `Cargo.toml` (members), `Cargo.lock`, `Makefile` (переменная `PROBE_*`, строка `.PHONY`, цели), `AGENTS.md` (пункт «Сборка» и список целей вне CI), `docs/README.md` (ссылка на отчёт), `docs/roadmap.md` (строки 30 и 31 рядом), `docs/adr/0034-probe-code.md` (раздел «Уточнено в P0.x» в конце), `docs/architecture.md`.
- `.github/workflows/ci.yml` не меняется: CI вызывает `make check`, и чистые тесты новых членов workspace попадают туда сами.
- Общий скрипт или общий crate для обеих проб не заводится: файл, добавленный в обеих ветках, даёт конфликт add/add. Соглашения записаны здесь, каждая проба реализует свою часть сама.

### Замерная блокировка

Замеры P0.8 искажает любая фоновая нагрузка, в том числе сборки и прогоны P0.7 на той же машине.

- Файл блокировки: `${SHELLIO_CACHE_DIR:-$HOME/.cache/shellio}/measure.lock`, берётся встроенным `/usr/bin/lockf` в `run.sh` каждой пробы, без общего скрипта.
- Любое ожидание укладывается в итерацию ralphex: по `session_timeout = 30m` он снимает всю группу процессов итерации (SIGTERM, затем SIGKILL), и `not_run`, назначенный по сроку длиннее итерации, никогда бы не записался. Процесс, который не дождался блокировки или тишины, завершается кодом «не начат» (отдельно от ошибки исполнения) и повторяется в следующей итерации.
- P0.8: блокировку держит процесс одной точки замера (общий срок попытки 25 минут по плану P0.8), а не вся серия, поэтому между точками её может взять P0.7. Срок захвата — 5 минут (`lockf -k -t 300`), ожидание тишины под блокировкой — тоже до 5 минут (правило в плане P0.8). Итерация с точкой замера `make check` не запускает: код в ней не меняется.
- P0.7: `run.sh` целей `make probe-review` и `make probe-review-live` берёт ту же блокировку на весь рецепт, включая подъём и остановку контейнера GitLab, со сроком захвата 5 минут (`lockf -k -t 300`). Рубеж задач P0.7 исполнитель запускает как `/usr/bin/lockf -k -t 900 "${SHELLIO_CACHE_DIR:-$HOME/.cache/shellio}/measure.lock" make check`. Срок ограничивает только ожидание захвата: 15 минут ожидания оставляют `make check` около 15 минут до `session_timeout = 30m` ralphex. Не дождался — рубеж не пройден, исполнитель записывает ⚠️ «замерная блокировка занята» и повторяет рубеж в следующей итерации; это не провал задачи.
- Захват один и внешний. Цели проб P0.7 обёрткой `lockf` не оборачиваются: их `run.sh` берёт блокировку сам, а вложенный захват того же файла не проходит (проверено: внутренний `lockf -t 0` под внешним возвращает 75). `run.sh` выполняет рецепт под захватом отдельной внутренней командой, а не повторным вызовом публичной цели.
- Код 75 может вернуть и сама команда. Как в `scripts/ghostty/lock.sh`, команда под блокировкой сначала удаляет маркер старта: маркер на месте и код 75 — блокировка не взята, маркера нет — код принадлежит сценарию, и потерянный `result.json` — ошибка исполнения, а не `not_run`. Логику проверяет тест `run.sh` на временном файле блокировки.
- Остальную нагрузку (ревью ralphex, сборки вне рубежа, `make ghostty`) блокировка не покрывает. Её ловит проверка фона P0.8 на протяжении каждого замерного окна.
- Первое наполнение общего кэша и обе сборки `make ghostty` заканчиваются в разделе «Запуск» до старта исполнителей: при холодном кэше обе сборки пишут один `refs/shellio/pin` в `ghostty-src.git`. Исполнители `make ghostty` не запускают.

### Слияние

Итог каждого плана — подготовленная ветка: задачи завершены, план перенесён в `completed/`, `make check` проходит. Исполнители не видят состояние соседней ветки, поэтому слияние в задачи не входит. Его выполняет владелец после окончания обоих прогонов и их ревью.

1. Первая завершённая ветка вливается в `toolchain-bootstrap` из основной копии без конфликтов.
2. В worktree второй ветки вливается обновлённая `toolchain-bootstrap`, merge-коммит завершается там. Ожидаемые конфликты и их разрешение:
   - `Cargo.toml`: обе строки members в алфавитном порядке (`probe-resource-accounting`, затем `probe-review-api`);
   - `Makefile`: обе переменные `PROBE_*`, объединённая строка `.PHONY`, обе группы целей;
   - `AGENTS.md`: оба пункта «Сборка» в порядке P0.7, P0.8, список целей вне CI — объединение;
   - `docs/README.md`, `docs/architecture.md`: обе записи;
   - `docs/roadmap.md`: обе строки с ✅;
   - `docs/adr/0034-probe-code.md`: разделы «Уточнено в P0.7», затем «Уточнено в P0.8», перед «Условием пересмотра»;
   - `Cargo.lock`: основа — lock уже влитой ветки, затем `cargo metadata --format-version 1 >/dev/null` досчитывает вторую пробу по объединённым манифестам. Diff lock проверяется: меняются только пакеты второй пробы, посторонних обновлений нет. Выбор `ours`/`theirs` целиком не используется.
   - относительные ссылки перенесённых в `completed/` планов (ADR, дорожная карта, отчёт, соседний план) проверяются на объединённом HEAD.
3. `make check` на объединённом HEAD проходит, затем `toolchain-bootstrap` перематывается на него (fast-forward). Если `toolchain-bootstrap` за это время ушла вперёд, шаг 2 повторяется.

## Предусловия

Физические предусловия по ADR-0036. Отсутствующее предусловие обязательного сценария — ошибка исполнения, предусловие наблюдения — `not_run` с причиной.

- Worktree создан и набор ghostty в нём собран по разделу «Запуск» (нужен только для `make check`).
- Машина на питании от сети, режим энергопотребления записывается сценарием. Замеры идут в окна без сборок и прогонов P0.7: это обеспечивает замерная блокировка и проверка фона.
- `/usr/bin/login` запускается от текущего пользователя без пароля (`login -f` для себя). Отказ — сценарий `login` получает `not_run` «login не запустился».

## Development Approach

- **testing approach**: Regular. Код и его проверки входят в одну задачу.
- Каждая задача завершается до начала следующей и не опирается на код более поздней. Рубеж каждой задачи — `make check`, для задач со стендом также `make probe-resources SCENARIOS="<сценарии задачи>"` без ошибок исполнения.
- Граница пробы. Нет плагина Resources, статус-бара, шины команд и `shellio-metrics`. Есть источник процессов, снимок и формулы, атрибуция, сэмплер, учёт участков и арен, фикстуры и стенд. P2.4 пишет `shellio-metrics` заново по выводам отчёта.
- `unsafe` и системные C API (`proc_pid_rusage`, `proc_pidinfo`, `sysctl`, `mach_timebase_info`, `host_statistics`, `clock_gettime`, `thread_info`) — только в `spikes/probe-resource-accounting` (ADR-0034).
- Тесты:
  - чистая логика идёт в `make check` и CI: формулы снимка, дельты по идентичностям, повторный PID, пометки неполноты, объединение принадлежности, правило фона, статистика вердикта, учёт вложенных участков на подставных часах, модель результатов и агрегирование;
  - настоящие процессы, `login` и замеры стоимости идут в цели пробы.
- Синхронизация — квитанции фикстур, каналы и барьеры. `sleep` не используется. Окно замера — интервал по монотонным часам, а не синхронизация.
- Исполнитель не останавливается ради решения или приёмки владельца (ADR-0036). Предвидимый выбор делается по правилу раздела «Правила выбора». Непредвиденный выбор исполнитель делает сам и записывает с ⚠️ в план и отчёт. Не наблюдённое получает `not_run` с причиной, а не `pass`.
- Ожидания, допуски, число блоков и статистика вердикта записываются в раздел «Ожидания» отчёта до первого замерного прогона и после результатов не меняются. Превышение бюджета — отрицательный вывод с передачей, порог не сдвигается.
- Запуски только с изолированным `SHELLIO_STATE_DIR`.

## Solution Overview

- **Источник процессов** (`proc/`). Обёртки `proc_pid_rusage` (`RUSAGE_INFO_V4` или новее), `proc_pidinfo(PROC_PIDTBSDINFO)` для времени старта, родителя и группы, `getsid(pid)` для сессии (в `proc_bsdinfo` поля SID нет, группа его не заменяет), `sysctl(KERN_PROC_ALL)` для списка процессов одним вызовом. Отказ чтения различается: процесс вышел (`ESRCH`), нет прав (`EPERM`), прочее. Между перечислением и чтением PID может смениться: чтение `rusage` сверяется с идентичностью по `ri_proc_start_abstime`, несовпадение — пропуск, а не CPU и память чужой жизни PID.
- **Снимок и формулы** (`snapshot/`). Идентичность — `(pid, время старта)`. Снимок на монотонной границе `T` с отметками начала и конца сбора. Память — сумма `ri_phys_footprint` по уникальному множеству. CPU% — `100 × Σ Δ(ri_user_time + ri_system_time) / ΔT` в одних единицах, 100% — одно логическое ядро, значения выше 100% допустимы. Дельта считается только для идентичности, прочитанной на обеих границах. Свежий процесс без базы — память есть, дельта CPU неизвестна. Пропуск, выход и отказ чтения — пометка неполноты с причиной и долей покрытия. Повторный PID с другим временем старта — новая идентичность, дельта через него не протягивается.
- **Атрибуция** (`attrib/`). Три источника: запись владения от хоста (PID и время старта его программ), дерево потомков по родителю, члены сессии (`getsid` и группа). Итог панели — объединение по идентичности, каждый процесс один раз. Служебная группа «Git» получает дочерние `git` общей работы репозитория, а не первую запросившую панель. Процесс, найденный несколькими источниками, учитывается один раз; источник находки записывается.
- **Сэмплер** (`sampler/`). Один поток, один срок следующего прохода. Шаг 2 с при видимом индикаторе и фоновый шаг по правилу. Число панелей не меняет число пробуждений. Каждый проход записывает длительность, размер множества, число частичных чтений.
- **Учёт участков** (`spans/`). Обёртка `Accounted<F>` вокруг future: CPU потока замеряется на входе и выходе каждого `poll` и начисляется логическому владельцу. Ожидание между `poll` не начисляется. Стек владельцев на потоке вычитает время вложенного учтённого участка из внешнего. Та же обёртка для замыканий `spawn_blocking`.
- **Учёт арен** (`arena/`). Счётчик учтённых байт собственных кэшей и арен владельца: рост, переиспользование, освобождение. Показываются занятые байты, ёмкость записывается отдельно как диагностика.
- **Фикстуры** (`fixture/`). Режим того же исполняемого файла `--fixture <режим>`: заданная нагрузка CPU с фиксированным темпом работы, заданная память с касанием страниц, дерево детей и внуков, быстрый выход, уход из дерева двойным `fork`, хост с записью владения, `login`-ребёнок. У macOS `getrusage` есть только `RUSAGE_SELF` и `RUSAGE_CHILDREN`, потокового `RUSAGE_THREAD` нет, поэтому `getrusage(RUSAGE_SELF)` — независимая квитанция CPU всего процесса. Фикстура нагрузки однопоточная до 100% одного ядра; для значений выше 100% в одном PID она запускает два рабочих потока, квитанция остаётся процессной. Фикстура калибровки учёта участков всегда однопоточная. Каждая фикстура пишет квитанции: идентичность, родитель, CPU процесса (`getrusage(RUSAGE_SELF)`) и собственное чтение `ri_phys_footprint` на согласованных границах, выделенные байты.
- **Стенд** (`scenario/`). Процесс на сценарий, замерная блокировка, проверка фона, наблюдатель — отдельный процесс, который независимо читает CPU стенда для замеров стоимости.

### Сценарии атрибуции и формул

| Сценарий | Что строит | Что проверяет |
| --- | --- | --- |

| `formula-cpu` | фикстуры 10% и 50% одного ядра одним потоком, 150% одного ядра двумя потоками в одном PID | CPU% каждого PID, включая значение выше 100%, против квитанций |

| `eperm-inject` | подставной отказ чтения | пометка неполноты с причиной, итог не скрывает отказ |

Повторный PID проверяется детерминированным юнит-тестом на подставном источнике. Живой повтор PID не требуется.

Сценарий `login` записывает PID и время старта `login` и ребёнка, факт жизни обоих на момент чтения, результат `proc_pid_rusage` и `errno`. Живой `login` прочитался — записанное отличие окружения от P0.3, а не `fail`. `login` исчез до чтения — `not_run` «отказ доступа не наблюдался». Запуск идёт без pty (проверено при планировании); если `login` откажет без терминала — через `openpty`, с записью. Логику частичного снимка независимо проверяет `eperm-inject`.

### Стоимость

- Четыре состояния: сэмплер выключен или включён × учёт участков выключен или включён (`00`, `10`, `01`, `11`). Одинаковая полезная работа: 200 операций в секунду, каждая около 0,5 мс CPU и 4 учтённых `poll`; число завершённых операций записывается, отклонение больше 1% от заданного делает окно недействительным. Нагрузка, насыщающая ядро, не используется — её CPU уже около 100%, и добавка скрылась бы. Профиль сборки — `release`, записывается.
- Точки (ось — процесс на точку): множество PID 8, 32, 128 при 4 панелях и видимом шаге 2 с; 16 панелей при 32 PID; фоновый шаг при 32 PID; простой без работы при 32 PID (в простое CPU на операцию не определён, мерится только эффект сэмплера).
- Протокол точки: прогрев 10 с, затем 5 блоков; в блоке четыре окна по 30 с — по одному на состояние, порядок сбалансирован сдвигом от блока к блоку. Окна точки — 10 минут, с двумя повторами блоков — 14 минут; серия из шести точек идёт по одной точке за итерацию (правило «Длинный прогон»).
- Общий срок попытки точки — 25 минут от старта процесса: захват блокировки (до 5), ожидание тишины (до 5), прогрев, блоки и повторы. Новый блок не начинается, если до срока меньше 3 минут (блок и запись результата). На сроке точка выносит вердикт по уже чистым блокам при их числе не меньше трёх, иначе «не подтверждено» «шумно», и атомарно пишет `result.json`. Так `result.json` появляется раньше, чем ralphex снимет итерацию по `session_timeout = 30m`. В точке простоя операций нет: проверка числа завершённых операций к ней не применяется.
- Эффекты в процентных пунктах одного ядра по наблюдателю: сэмплер — `10 − 00` и `11 − 01`; учёт участков — `01 − 00` и `11 − 10`, плюс CPU процесса на одну операцию. Разница двух оценок одного эффекта — взаимодействие, записывается.
- Вердикт сначала выносится по каждой оценке отдельно: во всех чистых блоках не выше бюджета (граница «до» включает равенство) — `pass`; во всех выше — `fail`; иначе — «не подтверждено». Вердикт эффекта: хотя бы одна оценка `fail` — `fail` с указанием состояния (например, сэмплер укладывается при выключенном учёте и превышает при включённом); обе `pass` — `pass`; остальное — «не подтверждено». Бюджеты: сэмплер — 0,5 п. п. (`docs/architecture.md`). Учёт участков — две независимые причины отрицательного вывода по ADR-0011: стоимость выше 1 п. п. или искажение сверх допусков таблицы оракулов.
- Записываются: длительность прохода, пробуждения в минуту, размер множества, частичные чтения, footprint стенда. Это базовые точки для P2.4.

### Проверка фона

- Под замерной блокировкой сценарий меряет фон 10 с: CPU системы по `host_statistics(HOST_CPU_LOAD_INFO)` за вычетом всей группы стенда (стенд, фикстуры, наблюдатель) и самый занятый посторонний процесс по `proc_pid_rusage`. Постороннее чтение, которое отказало, не скрывается: записываются покрытие и системная дельта.
- Тихо: фон не выше 30% одного ядра и ни один посторонний процесс не выше 10% одного ядра. Шумно — следующее окно проверки. Тишины нет 5 минут — процесс завершается кодом «не начат» с записанным фоном и повторяется в следующей итерации (раздел «Замерная блокировка»). Третий подряд «не начат» одного сценария или точки — `not_run` «шумно» или «замерная блокировка занята».
- Замерные сценарии (берут блокировку и проверяют фон): `smoke`, `units`, `formula-cpu`, `span-busy`, `span-wait`, `span-migrate`, `span-nested`, `span-parallel`, `span-blocking`, `cost`. Остальные (`formula-mem`, `sessions`, `git-shared`, `reparent`, `churn`, `attach-move`, `login`, `eperm-inject`, `arena`) идут без блокировки: их оракулы точные или по памяти и от фона CPU не зависят.
- Фон меряется и на протяжении каждого замерного окна тем же способом и с вычетом той же группы (стенд, фикстуры, наблюдатель), что и до него, и записывается в `result.json` вместе с фоном до и после. Окно, где фон выше порога, делает загрязнённым весь блок из четырёх окон: блок не входит в вердикт и повторяется целиком, всего не больше двух повторов на точку. Вердикт точки требует не меньше трёх полных чистых блоков, иначе — «не подтверждено» «шумно».

### Правила выбора

- **Фоновый шаг сэмплера.** 10 с. Записывается в отчёт как предложение для P2.4, а не как решение ADR.
- **Часы потока.** `clock_gettime(CLOCK_THREAD_CPUTIME_ID)` и `thread_info(THREAD_BASIC_INFO)` сравниваются в задаче 7 микрозамером стоимости и точностью в однопоточном процессе против `getrusage(RUSAGE_SELF)` с допуском таблицы оракулов. Берётся более дешёвый из точных; при равенстве — `clock_gettime`.
- **Асинхронный рантайм.** `tokio` с функциями `rt-multi-thread`, `sync`, `time`, два рабочих потока: модель ADR-0020.
- **Список процессов.** `sysctl(KERN_PROC_ALL)` одним вызовом на проход. Если микрозамер задачи 6 покажет `proc_listallpids` + `proc_pidinfo` дешевле при том же наборе полей — он, с записью.
- **Нечитаемый процесс.** Не учитывается в сумме, учитывается в покрытии, итог помечен частичным. Попытки обойти отказ (привилегии, `task_for_pid`) не делаются.
- **Повторный прогон шумного сценария.** До трёх полных прогонов замерных сценариев в задаче 13. Все шумные — вердикт «не подтверждено» с ⚠️ и передачей P2.4, готовность плана это не блокирует.
- **Длинный прогон.** Сессия исполнителя ограничена `session_timeout = 30m`, а ralphex при отмене и при штатном выходе итерации шлёт всей группе процессов SIGTERM, затем SIGKILL (`pkg/executor/procgroup_unix.go`), поэтому отсоединённый `nohup` итерацию не переживает. Серия стоимости идёт по одной точке за вызов и одной точке за итерацию, без `make check` в той же итерации: `make probe-resources SCENARIOS=cost POINTS=<точка> RUN=<run-id>`. Общий срок попытки точки 25 минут (раздел «Стоимость») оставляет запас до 30 минут итерации. Точка записывает `result.json` атомарно (запись во временный файл и переименование) и отметку в `status`; run-id и пройденные точки записываются в план. Следующая итерация запускает первую незавершённую точку того же run-id. При продолжении `run.sh` сверяет хеш бинаря, профиль сборки и параметры протокола с сохранёнными в каталоге прогона: расхождение — новый run-id, результаты разных сборок под одним run-id не смешиваются. Точка, прерванная без `result.json`, повторяется целиком.

### Результаты

`result.json` на процесс: сценарий, точка осей, режим питания, фон, сырые счётчики с идентичностями и отметками времени, квитанции фикстур, сравнение с оракулом, итог (`pass`, `fail`, `not_run` с причиной, «не подтверждено»). `--aggregate` собирает `summary.json`, таблицы стоимости по числу PID и панелей и таблицы Markdown для отчёта. Ошибка исполнения роняет цель, отрицательный вывод — нет (ADR-0034).
