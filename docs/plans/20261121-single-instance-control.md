# Единственный экземпляр и управляющий сокет

## Overview

- Шаг P1.2 `single-instance-control` [дорожной карты](../roadmap.md). Зависит от P1.1, от него зависят P1.3 (каркас E2E на управляющем API), P1.5, P2.1 и P5.3.
- Соединяет ядро P1.1 в продуктовый процесс: блокировка единственного экземпляра → хранилище → ядро → управляющий сокет. Заводит `crates/shellio-control` (протокол v1, выбор владельца, сервер и клиент), `apps/shellioctl` (CLI) и минимальный `crates/shellio-appkit` (`NSApplication` без окна и активация).
- Решения: единственный экземпляр — [ADR-0006](../adr/0006-single-instance.md), управляющий API — [ADR-0007](../adr/0007-control-api.md), модель процессов — [ADR-0004](../adr/0004-process-model.md), область CLI — [ADR-0025](../adr/0025-workspaces-and-project-catalog.md), актор — [ADR-0020](../adr/0020-concurrency.md), хранение — [ADR-0018](../adr/0018-storage-and-config.md), тесты — [ADR-0021](../adr/0021-testing.md), автономное исполнение — [ADR-0036](../adr/0036-autonomous-execution.md).
- Готово, когда второй запуск активирует первый, а CLI читает дерево:
  - на один профиль владелец ровно один: два претендента дают одного владельца, после `SIGKILL` владельцем становится следующий, inode `shellio.lock` не меняется;
  - второй запуск через `open -n` и прямым запуском бинаря передаёт аргументы владельцу, владелец их обрабатывает, второй получает квитанцию и завершается, PID владельца не меняется, передний план переходит с другого PID на PID владельца;
  - путь папки во втором запуске доходит до владельца и получает явный отказ `folder_open_unsupported` в квитанции, текст квитанции прямо говорит, что папка не открыта;
  - `shellioctl` выполняет каждую команду и чтение P1.1, `version`, `events --since` и `events --follow`, результат каждой мутации виден в `tree`;
  - область проверяется на сервере: адресная команда по чужому воркспейсу под `--workspace` получает `not_found` и ничего не меняет, `tree --workspace` не раскрывает другой воркспейс;
  - CLI различает «не запущено», «владелец запускается», «владелец уходит» и «недоступен» стабильными кодами и кодами выхода;
  - дескрипторы блокировки и сокетов не наследуются порождёнными процессами;
  - сценарий `make e2e` и приёмочный проход исполнителя записывают `pass` по каждому обязательному пункту, ненаблюдаемое — `not_run` с причиной (матрица — раздел «Матрица приёмки»).

## Context (from discovery)

- `apps/shellio` — заглушка самопроверки P0.1 (`src/main.rs`, `src/self_check.rs`): печатает строку и выходит. Её запускают без аргументов три потребителя, и все проверяют, что каталог состояния остался пустым: `scripts/check-bundle.sh` (`check_self_check`, `check_open` через `open -W -n`), поддельный `open` в `scripts/test-bundle.sh` и `apps/shellio/tests/layout.rs` (`run_isolated`, в том числе через символическую ссылку). `make run` сейчас — `check-bundle.sh --open`.
- `make run`, `make bundle`, `make check-bundle` и `make test-bundle` держат `vendor/ghostty.lock` весь рецепт (`LOCKED_TARGETS`, `lockf -t 0`): вызов публичной цели из рецепта другой такой цели получает «набор ghostty занят». Внутри одной блокировки вызываются внутренние цели `locked-*` или сами скрипты.
- P1.1 оставил: `shellio_store::{Profile, Database, SqlitePersist}` (`Profile::from_process_env` — единственное чтение окружения, `ensure_state_dir` с `0700`), `shellio_core::{Core, CoreHandle}` с `request`, `try_request`, `query`, `subscribe` (атомарный снимок и приёмник), `events_since` (`Reset` вне буфера, `cursor_ahead` впереди), `shutdown`; кольцо событий 1024, `broadcast` 256, очередь 256. JSON-петля и `MemoryPersist`/`FaultyPersist` — за функцией `test-support`.
- Эталоны JSON P1.1 лежат в `crates/shellio-core/tests/wire/`, имена и коды заморожены. `TreeView::build` копирует глобальные `active_workspace` и `route` (`route: Route` обязательный), поэтому дерево одного воркспейса раскрывает активный другой.
- В `Cargo.lock` уже есть `objc2 0.6.5`, `objc2-app-kit 0.3.2`, `objc2-foundation 0.3.2`, `block2 0.6.2`, `dispatch2 0.3.0` (проба P0.2), `tokio 1.54.1`, `rustix 1.1.6`, `libc 0.2.191`. Toolchain `1.99.1`: `std::fs::File::try_lock` и `try_lock_shared` стабильны.
- P0.2: исполняемый файл без бандла, запущенный из терминала, кооперативным `activate()` не активируется (отказ 3 из 3), `activateIgnoringOtherApps(true)` в `applicationDidFinishLaunching` после `makeKeyAndOrderFront` сработал 20 из 20. Это старт приложения с окном; активацию уже работающего владельца без окна по запросу извне P0.2 не проверяла.
- P0.5 подтвердил на модели пробы: публикация сокета через временное имя и `rename`, удаление пути прежнего владельца только под блокировкой, клиенты чужой сокет не удаляют; уходящий владелец отвечает временным отказом с повтором; второй запуск в промежутке без сокета ждёт его ограниченное время. Обычный `open` при живом экземпляре, запущенном LaunchServices, нового процесса не создаёт и `--args` не доставляет. Замена поколений, журнал обновления и CDHash — P5.2.
- Цели `make e2e` и каркаса E2E нет. AGENTS.md и ADR-0021 требуют для продуктового UI `make e2e` и приёмочный проход исполнителя. Активация — продуктовый эффект GUI, поэтому план заводит `make e2e` с одним сценарием без галереи и снимков; P1.3 наращивает цель своим каркасом.

## Решения планирования

Ответы владельца при планировании 2026-11-21:

- **Активация** — минимальный `NSApplication` без окна в новом crate `shellio-appkit`: run loop на главном потоке и безопасная активация. Без окна приложение видно иконкой в Dock. P1.3 наращивает этот crate, а не создаёт его.
- **Папка во втором запуске** — путь доставляется владельцу абсолютным (от рабочего каталога отправителя), владелец активируется и отвечает квитанцией с отказом `folder_open_unsupported` по этому аргументу. P1.7 заменяет отказ действием «открыть папку».
- **Состояния для CLI** — проба `flock`: CLI открывает `shellio.lock` без создания, пробует неблокирующий разделяемый `flock` и сразу отпускает. Свободен — сразу `not_running`. Занят, а сокета нет — ожидание до срока, затем `owner_starting`. Претендент в владельцы повторяет взятие блокировки в цикле до срока, поэтому проба CLI в неудачный момент запуск не срывает.
- **Дерево одной области** — разовое исключение из заморозки формата P1.1 до публикации протокола v1: `TreeView.route` становится `Option<Route>`, и `active_workspace` и `route` равны `null`, если активный воркспейс вне области. Исключение записывается в ADR-0007. После публикации v1 через `hello` формат меняется только новыми вариантами.

## Предусловия

- Для `make check` нужен опубликованный набор ghostty (`scripts/ghostty/vendor.sh --verify`), иначе перед исполнением — `make ghostty`.
- Для `make e2e`: идентичность `Shellio Dev` в login keychain (как у `make bundle`), открытый сеанс GUI, разблокированный экран, клавиатуру и мышь во время прогона не трогают. Разрешения Accessibility и Screen Recording не нужны: передний план читается через `lsappinfo`.

## Development Approach

- **testing approach**: Regular. Код и его тесты входят в одну задачу.
- Каждая задача завершается до начала следующей и не опирается на код более поздней. Рубеж каждой задачи — `make check`. Для итераций внутри задачи допустим `cargo test -p <crate>`.
- Граница плана:
  - нет окна, компонентов, токенов темы и каркаса E2E — P1.3;
  - нет раскладки и панелей — P1.4, `open-or-focus` и кардинальности — P1.5, keymap и UI семи действий — P1.6 и P1.7, действия «открыть папку» — P1.7;
  - нет хостов сессий, `SessionId` в окружении и области по сессии — P2.1 и P2.x; `shellioctl` без контекста сессии всегда задаёт область явно;
  - нет журнала обновления, CDHash, помощника замены и повторного открытия во время передачи — P5.2; `shellioctl` в бандле и ссылка Homebrew — P5.1 и P5.3.
- Правило AGENTS.md о законченном действии: CLI каждой команды и чтения P1.1 входит сюда (передача из ADR-0007). Новых доменных действий план не вводит. `launch` — служебный вход повторного запуска, а не действие пользователя: его вызывает только второй процесс `shellio`, в `shellioctl` и keymap его нет. Запись — в ADR-0007 задачей 1.
- `unsafe` разрешён только в `shellio-appkit`. `shellio-control`, `apps/shellio` и `apps/shellioctl` используют безопасные API: `File::try_lock`, `tokio::net::UnixStream::peer_cred`, `rustix::process::getuid`, `tokio::signal`. Если безопасного API не хватает, выбор делается по разделу «Правила выбора».
- `NSApplication` не запускается ни одним тестом `make check`. Владелец собран над портом `Ui`: в продукте его реализует `shellio-appkit`, в тестах — записывающая подделка. Настоящая активация проверяется только приёмочным проходом.
- Тесты:
  - каталог состояния — только `Profile::isolated` во временном каталоге, окружение процесса тестов не читается и не меняется; порождённым процессам окружение передаётся явно через `Command::env_clear` и `env`;
  - синхронизация — квитанции, каналы, барьеры и вывод порождённых процессов; `sleep` и ожидание по времени не используются. Сроки в библиотеке идут через внедряемые часы (раздел «Сроки»), тесты в процессе управляют ими вручную. Отдельно запущенный `shellioctl` получает срок пользовательским флагом `--timeout`, тестового флага в продукте нет;
  - в сеть не ходят, сокеты только Unix в каталоге профиля.
- Тестовая поддержка стоит за функцией `test-support` своего crate и подключается dev-зависимостью на себя, как в P1.1. `required-features` у тестов запрещён.
- Исполнитель не останавливается ради решения или приёмки владельца (ADR-0036). Предвидимый выбор делается по разделу «Правила выбора». Непредвиденный — самим исполнителем: вариант, ближайший к принятым ADR и объёму плана, обратимый и самый дешёвый, с записью ⚠️ в плане. Решение ADR исполнитель не меняет: противоречие записывается отрицательным выводом с передачей.
- План коммитится вместе с изменениями каждой задачи (AGENTS.md).

## Testing Strategy

- **unit tests**: кадры протокола и эталоны, кодек строк с лимитом, разбор аргументов CLI и запуска, классификация состояний клиента, проверка области, проекция дерева, коды выхода.
- **integration tests**: выбор владельца на настоящих `flock` и сокетах во временном профиле, сервер над `CoreHandle` с прямыми JSON-запросами по сокету, `shellioctl` отдельным процессом, владелец `shellio-owner-fixture` отдельными процессами: два претендента, `SIGKILL`, наследование дескрипторов, передача аргументов, сохранность после перезапуска.
- **e2e tests**: `make e2e` с одним сценарием второго запуска на подписанном бандле (задача 9), вне `check` и CI; приёмочный проход исполнителя — его прогон с записью итога (задача 10). Каркас E2E — P1.3.

## Solution Overview

- **Порядок запуска владельца** (`apps/shellio`):
  1. разбор аргументов; `--self-check` выполняет самопроверку P0.1 и выходит, не трогая профиль, блокировку и хранилище;
  2. `Profile::from_process_env`, `ensure_state_dir`;
  3. выбор владельца (`shellio-control::instance`): неблокирующий эксклюзивный `flock` на `<state>/shellio.lock`; проигравший идёт путём второго запуска;
  4. `Database::open`, `SqlitePersist`, `Core::start` — синхронные, поэтому идут через `spawn_blocking` или отдельный поток, не на главном и не на рабочих потоках runtime.

  Шаги 2–4 выполняет фоновая задача: главный поток не делает файлового ввода-вывода и ничего не ждёт синхронно (AGENTS.md, ADR-0020). Главный поток создаёт runtime, отдаёт задаче профиль и сразу запускает `NSApplication` с политикой `.prohibited`: без иконки в Dock, меню и фокуса. Выбранную роль задача доставляет на главный поток через `dispatch2`: «владелец» — политика `.regular`, дальше шаг 5; «второй запуск» — его путь на фоновой задаче, затем закрытие ресурсов, сброс stdout и stderr и `std::process::exit` с кодом этого пути (0, 74 или 75): у `terminate:` кода выхода нет. Штатное завершение владельца идёт через AppKit. Так проигравший не появляется в Dock и не забирает фокус;
  5. готовность — встреча двух условий: ядро загружено и `Ui` сообщил о готовности главного потока (`applicationDidFinishLaunching`). Только после обоих — публикация сокета: удаление оставшегося `shellio.sock` и временных `.shellio.sock.*` прежних владельцев (только сокеты), `bind` во временное имя, `0600`, `rename` в `<state>/shellio.sock`;
  6. сервер управления принимает соединения; собственные аргументы запуска владельца обрабатываются тем же обработчиком, что и пересланные.

  Отказ старта на шагах 4–5: ядро останавливается, временный узел удаляется под блокировкой, блокировка отпускается, процесс выходит с кодом 1 и сообщением.
- **Второй запуск**: не получив блокировку, процесс остаётся с политикой `.prohibited` и фокус не забирает. В пределах срока он подключается к сокету. `ENOENT` и `ECONNREFUSED` — ждать и снова пробовать блокировку: освободилась — стать владельцем по шагу 4. Подключился — `hello`; владелец `leaving` — ждать и повторить; `ready` — отправить `launch` с аргументами и рабочим каталогом, напечатать квитанцию, выйти с кодом 0. Срок истёк до отправки — сообщение «владелец запускается или перезапускается» и код 75. После полной отправки `launch` срок, обрыв или негодный ответ — код 74 «исход неизвестен», без повтора.
- **Завершение владельца** (`SIGTERM`, `SIGINT`, завершение `NSApplication`), строго по порядку:
  1. состояние `leaving`: слушатель закрывается, допуск новых операций закрыт; запрос, уже читаемый с соединения, получает `owner_leaving` с повтором;
  2. бездействующие соединения, ожидание чтения, подписки и запись клиенту отменяются; подписка получает кадр `owner_leaving`, если запись укладывается в срок завершения (1 с), иначе соединение закрывается;
  3. уже допущенные команды доводятся до ответа ядра, ответ отправляется в пределах того же срока;
  4. `CoreHandle::shutdown` до завершения;
  5. свой сокет удаляется под блокировкой, блокировка отпускается последней, файл блокировки не удаляется.

  `applicationShouldTerminate` сразу отвечает `TerminateLater` и не блокирует главный поток: принятая активация, ждущая главного потока, выполняется. По готовности порядка главный поток вызывает `replyToApplicationShouldTerminate(true)`.
- **Протокол v1** (`shellio-control::wire`): JSON построчно, конверт с номером запроса, `hello` первым, лимит входящей строки 1 МиБ. Команды, чтения, ответы, события и `CoreError` — типы P1.1 как есть. Ошибки транспорта — отдельный тип `ControlError` со своими стабильными кодами. Одно соединение обслуживает запросы по одному; подписка делает соединение потоковым до закрытия.
- **Область** проверяется в акторе ядра (`shellio-core`), а не в разборе CLI: команда приходит с областью, проверка принадлежности цели и обработчик выполняются на одном снимке. Несовпадение — `not_found` по цели, без изменений и без чужих данных. У `project.add` прямой `workspace`, не совпадающий с областью воркспейса, отвергается `not_found` до подготовки корня (без файлового ввода-вывода), окончательная проверка всё равно идёт в акторе. Корень, занятый проектом другого воркспейса, остаётся `root_taken` с обоими id: так задумано в P1.1 и ADR-0025, это отдельный исход, а не утечка области.
- **Клиент** (`shellio-control::client`) классифицирует недоступность пробой `flock` и подключением, не создаёт файл блокировки, не удаляет сокет, не становится владельцем и не запускает приложение. У вызова один абсолютный срок на подключение, `hello`, запись запроса и чтение ответа, и он прерывает каждую из этих операций. До полной отправки запроса и для чтений исход срока повторяемый. После полной отправки мутации срок, обрыв или негодный ответ — `outcome_unknown`. У `events --follow` срок действует только до первого кадра. `shellioctl` — тонкая оболочка над клиентом: разбор аргументов, вызов, вывод JSON или текста, код выхода.
- **Активация** (`shellio-appkit`): `NSApplication` стартует с политикой `.prohibited` и переходит в `.regular` по роли владельца, `Ui::activate` выполняется на главном потоке через `dispatch2` и отвечает после вызова. Квитанция честно называет исход `requested`, а не «приложение активно»: факт выхода на передний план проверяет приёмочный проход.

## Technical Details

### Файлы профиля

- `<state>/shellio.lock` — постоянный, создаётся претендентом (`OpenOptions::create(true)`, `0600`), никогда не удаляется. CLI открывает его без создания: нет файла — `not_running`.
- `<state>/shellio.sock` — публикует только владелец. Временное имя — `<state>/.shellio.sock.<pid>`, оно длиннее конечного. Обе длины пути в байтах меньше 104 (`sun_path` Darwin): иначе владелец отказывает в запуске с сообщением и кодом 1, переход на другой путь не делается.
- Обычный файл или символическая ссылка на месте `shellio.sock` или временного имени — ошибка запуска владельца без удаления: удаляются только сокеты. Временный сокет, оставшийся после `SIGKILL` между `bind` и `rename`, удаляет следующий владелец под блокировкой, в том числе при совпадении PID.
- Все дескрипторы открываются с `CLOEXEC` (std и tokio делают это сами, тест задачи 4 проверяет).

### Протокол v1

| Направление | Форма |
| --- | --- |
| запрос `hello` | `{"id":1,"hello":{"protocol":1,"client":"shellioctl 0.1.0"}}` |
| ответ `hello` | `{"id":1,"ok":{"hello":{"protocol":1,"server":"0.1.0","pid":123,"owner":"ready"}}}` |
| команда | `{"id":2,"command":{"cmd":"workspace.rename",…},"scope":{"workspace":"…"}}` |
| чтение | `{"id":3,"query":{"query":"tree","scope":"all"}}` |
| события по курсору | `{"id":4,"events_since":{"cursor":12},"scope":"all"}` |
| подписка | `{"id":5,"subscribe":{},"scope":"all"}` |
| аргументы запуска | `{"id":6,"launch":{"args":["/abs/path"],"cwd":"/abs"}}` |
| ответ | `{"id":2,"ok":<Reply P1.1>}`, `{"id":4,"ok":<EventsSince P1.1>}`, `{"id":6,"ok":{"launch":{"activation":"requested","refused":[{"arg":"/abs/path","reason":"folder_open_unsupported"}]}}}` |
| отказ ядра | `{"id":2,"core_error":<CoreError P1.1>}` |
| отказ транспорта | `{"id":2,"error":<ControlError>}`, `id` равен `null`, если номер не разобран |
| поток подписки | `{"id":5,"snapshot":<Snapshot>}`, затем `{"id":5,"event":<Event>}`…, при отставании `{"id":5,"reset":<Snapshot>}` |

- `scope` — форма `TreeScope` P1.1: `"all"` или `{"workspace":"<id>"}`. У `hello`, `query` и `launch` поля `scope` нет: лишнее поле — `malformed_request`. CLI отвергает `--workspace` и `--all` у `status` и `version` ошибкой использования до отправки.
- `owner` в `hello` — `ready` или `leaving`. Состояние `starting` по сокету не наблюдается: сокет публикуется после готовности. Повторный `hello` на том же соединении разрешён и отвечается так же.
- `activation` — `requested` (вызов на главном потоке выполнен) или `no_ui` (UI нет: только у `shellio-owner-fixture`).
- Причины отказа аргумента владельцем: `folder_open_unsupported` (существующий каталог), `not_a_directory` (существующий не каталог), `path_not_found`, `unknown_argument` (флаг). Аргумент не в UTF-8 второй запуск не отправляет: квитанция печатает его отказ `arg_not_utf8` локально, остальные аргументы уходят владельцу.
- Квитанция с отказами — успех передачи, код 0; текст называет каждый отказанный аргумент, для папки — «папка не открыта: открытие папок пока не поддерживается».
- Поток подписки кончается кадром `owner_leaving` при завершении владельца (клиент — код 75) или обрывом без него (клиент — `unavailable`, код 75).
- Лишнее поле и неизвестный вариант отвергаются во всех кадрах (`deny_unknown_fields`), как у типов P1.1.

### Коды `ControlError`

| Код | Повтор | Когда |
| --- | --- | --- |
| `hello_required` | нет | первый запрос не `hello` |
| `protocol_mismatch` | нет | версия клиента не поддерживается; `details.supported` |
| `malformed_request` | нет | строка не разбирается как кадр; соединение остаётся |
| `request_too_large` | нет | строка длиннее 1 МиБ до перевода строки; соединение закрывается |
| `scope_required` | нет | у команды, `events_since` или `subscribe` нет `scope` |
| `scope_unsupported` | нет | `events_since` и `subscribe` с областью воркспейса |
| `owner_leaving` | да | владелец завершает работу |
| `not_running` | да | только клиент: блокировка свободна или нет файла |
| `owner_starting` | да | только клиент: блокировка занята, сокета нет до срока |
| `unavailable` | да | только клиент: подключение или ответ не уложились в срок при занятой блокировке |
| `outcome_unknown` | нет | только клиент: после полной отправки мутации или `launch` истёк срок, оборвалось соединение или пришёл негодный ответ |

`retryable` следует из кода, как у `CoreError`. Коды закреплены эталонами в `crates/shellio-control/tests/wire/`.

| Вызов | Запрос |
| --- | --- |
| `version` | `hello` |

| `tree (--workspace <id> \| --all)` | `query.tree` |

- `--json` печатает ответ кадра как есть, построчно для `events --follow`; иначе — человекочитаемый текст. Ошибка — в stderr, при `--json` — JSON ошибки в stdout.

| --- | --- |
| 0 | успех |
| 1 | отказ ядра или неповторяемый отказ транспорта |
| 2 | ошибка использования |
| 69 | `not_running` |
| 74 | `outcome_unknown` |

### Сроки

- Порт часов `Clock`: абсолютный срок вызова и ожидание «до следующей попытки или до срока, что раньше». Каждая операция ввода-вывода клиента (подключение, запись, чтение) идёт под `tokio::time::timeout_at` до того же срока через этот порт. В продукте — `tokio::time`, интервал повтора 50 мс, срок 5 с у CLI (меняет `--timeout`), 10 с у второго запуска, 1 с у шагов завершения владельца. В тестах в процессе — ручные часы `tokio::time::pause` и `advance` или собственная реализация с барьером: тест решает, когда попытка продолжается и когда срок истёк.
- Сервер ограничивает только входящие строки. Ответ (дерево, снимок) лимитом не ограничен; клиент принимает строки до 64 МиБ. Длиннее — для чтения код 1, для мутации и `launch` — `outcome_unknown`.

### Владелец и порты

```rust
pub trait Ui: Send + Sync + 'static {
    /// Готовность главного потока (`applicationDidFinishLaunching`).
    fn ready(&self) -> impl Future<Output = ()> + Send;
    /// Роль выбрана: владелец переводит приложение в `.regular`.
    fn become_owner(&self) -> impl Future<Output = ()> + Send;
    /// Выполняет активацию на главном потоке и возвращается после вызова.
    fn activate(&self) -> impl Future<Output = Activation> + Send;
    /// Запрос завершения от UI (`applicationShouldTerminate`); владелец отвечает квитанцией.
    fn terminate_requests(&self) -> TerminateRequests;
    /// Порядок завершения выполнен: UI отпускает приложение.
    fn finish_terminate(&self);
}
pub enum Activation { Requested, NoUi }
```

- Точная форма методов — выбор исполнителя; набор обязанностей порта — нет.
- `apps/shellio` — библиотека `shellio::owner` и два бинаря: `shellio` (`Ui` из `shellio-appkit`, главный поток в run loop `NSApplication`) и `shellio-owner-fixture` (`Ui` без AppKit: главный поток ждёт завершения runtime, `ready` готов сразу, `become_owner` ничего не делает, `activate` даёт `NoUi` и пишет строку в stdout, запросов завершения от UI нет — только сигналы). Бандл получает только `shellio`: `scripts/bundle.sh` копирует его по имени.
- Подписчик `subscribe` обслуживается своей задачей: медленный клиент не держит актор и другие соединения. При `Lagged` задача заново вызывает `CoreHandle::subscribe`, отправляет `reset` с новым снимком и читает только новый приёмник.
- Сервер за функцией `test-support` даёт три крючка: пауза чтения `broadcast` задачей подписки (для детерминированного `Lagged`), задержка ответа после квитанции ядра (для `outcome_unknown`) и барьер после разбора кадра до допуска к обработчику (для `owner_leaving`). Продуктовая сборка их не содержит.

### Матрица приёмки

Сценарий `make e2e` (задача 9) на подписанном бандле и временном профиле. Обязательные пункты должны получить `pass`; `not_run` допустим только с причиной, которую автоматика не может наблюдать.

| Пункт | Обязательный | Критерий `pass` |
| --- | --- | --- |
| `owner` | да | владелец запущен `open -n` с профилем прогона, `hello` по сокету прогона даёт PID, этот PID — процесс бандла прогона; `shellioctl status` и `tree --all` отвечают |
| `forward-open-n` | да | передний план сначала переведён на Finder и подтверждён (`lsappinfo front` → PID Finder); второй запуск `open -n` с тем же профилем: квитанция в его stdout, строка обработки аргументов в журнале владельца, PID владельца прежний, передний план — PID владельца не позже 3 с после квитанции (опрос `lsappinfo front`); позже — `fail` с записанным временем |
| `forward-direct` | да | то же для прямого запуска `Contents/MacOS/shellio` с `SHELLIO_STATE_DIR` прогона |
| `folder-refused` | да | второй запуск с существующим каталогом: квитанция с `folder_open_unsupported`, код 0, текст «папка не открыта» |
| `persist` | да | `shellioctl workspace new … --all`, `SIGTERM` PID владельца (сверенного по `hello` перед сигналом), сокет удалён, файл блокировки на месте; новый владелец — `tree --all` показывает воркспейс |
| `kill-recover` | да | `SIGKILL` сверенного PID, новый запуск `open -n` — новый владелец, сокет заменён, inode блокировки прежний |
| `two-profiles` | да | второй профиль запускает своего владельца рядом с первым, `hello` по двум сокетам даёт разные PID |
| `plain-open` | нет | обычный `open` бандла при живом владельце: PID владельца прежний; передний план записывается как наблюдение поведения LaunchServices. Пересылку этот способ не проверяет |
| `gui-quit` | нет | завершение через `applicationShouldTerminate`: `not_run`, причина — Apple Events адресуют идентификатор бандла, а не PID, и задели бы чужой экземпляр |

- `shellioctl` в сценарии получает `env -u SHELLIO_SOCKET` и `SHELLIO_STATE_DIR` прогона. stdout и stderr каждого запуска сохраняются в каталог прогона.
- Сигналы и уборка адресуют только PID, полученные через `hello` сокетов прогона и сверенные с путём бандла прогона.

### Правила выбора

- **Новые зависимости.** `tokio` в `shellio-control` и приложениях получает функции `net`, `io-util`, `time`, `signal`, `macros`, в `dev-dependencies` также `test-util` (ради `pause` и `advance`). `rustix` — функция `process` ради `getuid`. `objc2`, `objc2-app-kit`, `objc2-foundation`, `dispatch2` — версии из `Cargo.lock`, функции по необходимости. `clap`, `thiserror`, `anyhow` не добавляются: разбор аргументов и ошибки — вручную. Лицензия каждого нового пакета проверяется по списку P1.1 (MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib, Unicode-3.0 и их сочетания) и записывается в задачу 1; пакет вне списка — ⚠️ и замена ближайшим допустимым. `Cargo.lock` обновляется точечно, остальные версии не поднимаются.
- **Безопасный API не нашёлся** (например, для `flock` с нужным флагом или UID собеседника): берётся безопасная обёртка из пакета, уже стоящего в `Cargo.lock` (`rustix`, `tokio`); если нет и её — ближайший безопасный обход с записью ⚠️. Перенос системного вызова в `shellio-appkit` не допускается: этот crate только для AppKit. `unsafe` вне `shellio-appkit` не появляется.
- **Активация.** Варианты пробуются по порядку, пока `make e2e` не покажет переход переднего плана для `open -n` и прямого запуска; выбранный записывается в задачу 10 и ADR-0006:
  1. `activateIgnoringOtherApps(true)` у владельца (P0.2, но там — старт с окном) с узким `#[allow(deprecated)]` и комментарием-основанием;
  2. второй запуск (политика `.prohibited`) перед пересылкой вызывает `yieldActivationToApplication` для владельца через `shellio-appkit`, владелец — кооперативный `activate()`;
  3. оба вместе.

  Если ни один не даёт перехода хотя бы для одного из двух обязательных способов, функция не считается готовой: пункт получает `fail` с причиной, задача 10 записывает ⚠️-препятствие, ADR-0006 получает отрицательный вывод «Уточнено в P1.2» с передачей в P1.3, статус ADR-0006 остаётся `Proposed`, строка P1.2 в дорожной карте остаётся ⬜. Остальные задачи доводятся до конца, план закрывается и переносится в `completed/` как обычно, а в Post-Completion называется следующий план `single-instance-activation`, который доводит активацию; ✅ шага P1.2 ставит он (шаг из нескольких планов отмечает последний).
- **Конфликт эталона JSON** P1.1 с нуждами P1.2 решается новым вариантом. Единственное исключение — `TreeView.route` по решению владельца.
- **`Cargo.lock`** входит в изменённые файлы каждой задачи, которая добавляет член workspace или зависимость (задачи 3, 4, 6, 7, 8): `make check` идёт с `--locked`.
- **Длина пути сокета** у временного каталога тестов больше 103 байт: тест использует более короткий каталог через `tempfile::Builder::tempdir_in("/tmp")` и записывает это. Каталог профиля по умолчанию в `~/Library/Application Support/…` укладывается; проверка — тест.
- **Найденное противоречие ADR** — запись в «Уточнено в P1.2» соответствующего ADR как передача, без изменения решения.

  - `MainThread` (`Send + Sync + Copy`) — `exec(impl FnOnce(&App) + Send + 'static)` через `DispatchQueue::main().exec_async`. `exec_sync` и `run_on_main` не используются: они заблокировали бы рабочий поток runtime. Пока цикл не запущен, работа копится в главной очереди.
- Решения исполнителя по форме, которую план не задаёт (ближайшее к ADR-0006 и самое дешёвое):
  - у завершения два входа — запрос AppKit и порядок завершения владельца по сигналу, — и оба выходят через AppKit. Это чистый автомат `Termination` (`Running`, `Pending`, `Finished`) в главном потоке, закреплённый модульными тестами. Первый `applicationShouldTerminate` даёт `TerminateLater` и вызывает `terminate_requested`, повторный, пока первый ждёт, — `TerminateLater` без второго вызова. `App::finish_terminate` при ждущем запросе отвечает `replyToApplicationShouldTerminate(true)`, без запроса вызывает `terminate:`, и делегат отвечает `TerminateNow`, повторный вызов ничего не делает. Квитанция идёт через главную очередь, а не сразу: отданная из самого `terminate_requested`, она иначе пришла бы раньше ответа `TerminateLater`;
  - `#![deny(clippy::undocumented_unsafe_blocks)]` в crate: блок без `SAFETY` не проходит clippy (проверено удалением комментария). Части `define_class!` (`unsafe(super)`, `unsafe impl`, `unsafe(method)`) линт не видит, комментарии-основания у них стоят вручную.
