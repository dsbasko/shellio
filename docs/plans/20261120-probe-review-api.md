# Проба API ревью GitHub и GitLab

## Overview

- Шаг P0.7 `probe-review-api` [дорожной карты](../roadmap.md). Зависит от P0.1, открывает P4.1 `forge-accounts`. Критерий шага: матрица возможностей и обновлённый ADR-0015.
- [ADR-0015](../adr/0015-forge-review.md) (`Proposed`) задаёт локальный журнал черновиков, раздельные шаги отправки с состояниями `planned → in_flight → confirmed|unknown`, две ветви GitHub, поштучную публикацию `draft_notes` GitLab без `bulk_publish`, запрос изменений только через `mergeRequestRequestChanges`, запрет смешивать свежие refs с ранее полученным `head_sha`. Условие пересмотра: результаты P0.7 на реальных аккаунтах и self-hosted инсталляциях. Последствия: нужен `forge-fake`.
- Проба отвечает на вопросы:
  - выполнимы ли обе ветви GitHub и поведение с существующим `PENDING` review так, как записано в ADR-0015;
  - публикует ли поштучная публикация GitLab только известные черновики, не задевая черновики того же пользователя из другого клиента;
  - доступны ли `approve` с `sha` и `mergeRequestRequestChanges` на gitlab.com и self-hosted GitLab CE, и как отличить отсутствие возможности, отсутствие прав и ошибку;
  - переживает ли журнал сбой посреди отправки, и сводится ли `unknown` к однозначному итогу без слепого повтора;
  - как ведут себя якоря при смене head.
- Охват (решения владельца при планировании):
  - обязательный стенд — локальный `forge-fake` на loopback, цель `make probe-review`;
  - живые наблюдения — приватные песочницы на github.com и gitlab.com с отдельным аккаунтом-ревьюером и локальный GitLab CE в docker, цель `make probe-review-live`;
  - клетки живых хостов с `not_run` готовность плана не блокируют и записываются открытой передачей в P4.1;
  - GitHub Enterprise Server — `not_run` «нет инсталляции» с передачей в P4.1.
- Итог:
  - проба `spikes/probe-review-api`;
  - цели `make probe-review` и `make probe-review-live`;
  - отчёт `docs/probes/p0.7-review-api.md` с матрицей возможностей и выбранными сырыми данными;
  - раздел «Уточнено в P0.7» в ADR-0015, при необходимости в ADR-0034.
- Исполнение автономное ([ADR-0036](../adr/0036-autonomous-execution.md)), параллельно с планом P0.8 по разделу «Параллельное исполнение с P0.8». UI у пробы нет, приёмочного прохода в сеансе GUI нет, его роль выполняет полный прогон обеих целей (задача 15).

## Параллельное исполнение с P0.8

Этот план и план [20261120-probe-resource-accounting.md](20261120-probe-resource-accounting.md) исполняются одновременно, каждый в своём git worktree и своём рабочем пространстве agterm. Раздел одинаков в обоих планах.

### Запуск (предусловие, выполняется до исполнения)

`ralphex --worktree` запускается только из ветки по умолчанию (`main`), а она отстаёт от `toolchain-bootstrap` на 290 коммитов, и набор ghostty в созданном им worktree до старта не собрать. Поэтому worktree создаются вручную. Worktree создаются от коммита, в котором закоммичены оба плана. Его SHA записывается в файл вне git: переменная оболочки не переходит в другие рабочие пространства agterm, а пустой `--base-ref` вернул бы ralphex к `main`.

```bash
# в основной копии, после коммита обоих планов:
git rev-parse HEAD > ../shellio-p07-p08.base
base=$(cat ../shellio-p07-p08.base)
git worktree add ../shellio-p07 -b probe-review-api "$base"
git worktree add ../shellio-p08 -b probe-resource-accounting "$base"
(cd ../shellio-p07 && make ghostty)   # по очереди: кэш ~/.cache/shellio блокировкой не защищён
(cd ../shellio-p08 && make ghostty)
# в рабочем пространстве agterm P0.7:
cd ../shellio-p07 && base=$(cat ../shellio-p07-p08.base) && ralphex docs/plans/20261120-probe-review-api.md --base-ref "$base" --max-iterations 120
# в рабочем пространстве agterm P0.8:
cd ../shellio-p08 && base=$(cat ../shellio-p07-p08.base) && ralphex docs/plans/20261120-probe-resource-accounting.md --base-ref "$base" --max-iterations 120
```

- `--max-iterations 120`: задачи с длинными прогонами идут по шагу за итерацию (серия стоимости P0.8 — по точке, живые хосты P0.7 — по хосту), значения по умолчанию 50 не хватит.
- `vendor/` игнорируется git, поэтому у каждого worktree свой набор ghostty и своя блокировка `vendor/ghostty.lock`. Общий набор через `SHELLIO_GHOSTTY_VENDOR` не используется: `scripts/ghostty/lock.sh` строит путь блокировки от корня набора, и два worktree отказывали бы друг другу на каждом `make check`.
- У каждого worktree свой `target/`, временный `SHELLIO_STATE_DIR` и каталог прогона `target/probes/<slug>/`.

### Границы веток

- Каждая ветка трогает только свою пробу `spikes/<slug>/`, свой отчёт `docs/probes/<id>-<slug>.md`, свои данные `docs/probes/data/<id>-<slug>/`, свой ADR (ADR-0015 у P0.7, ADR-0011 у P0.8) и свой план.
- Общие файлы, которые трогают обе ветки: `Cargo.toml` (members), `Cargo.lock`, `Makefile` (переменная `PROBE_*`, строка `.PHONY`, цели), `AGENTS.md` (пункт «Сборка» и список целей вне CI), `docs/README.md` (ссылка на отчёт), `docs/roadmap.md` (строки 30 и 31 рядом), `docs/adr/0034-probe-code.md` (раздел «Уточнено в P0.x» в конце), `docs/architecture.md`.
- `.github/workflows/ci.yml` не меняется: CI вызывает `make check`, и чистые тесты новых членов workspace попадают туда сами.
- Общий скрипт или общий crate для обеих проб не заводится: файл, добавленный в обеих ветках, даёт конфликт add/add. Соглашения записаны здесь, каждая проба реализует свою часть сама.

### Замерная блокировка

Замеры P0.8 искажает любая фоновая нагрузка, в том числе сборки и прогоны P0.7 на той же машине.

- Файл блокировки: `${SHELLIO_CACHE_DIR:-$HOME/.cache/shellio}/measure.lock`, берётся встроенным `/usr/bin/lockf` в `run.sh` каждой пробы, без общего скрипта.
- Любое ожидание укладывается в итерацию ralphex: по `session_timeout = 30m` он снимает всю группу процессов итерации (SIGTERM, затем SIGKILL), и `not_run`, назначенный по сроку длиннее итерации, никогда бы не записался. Процесс, который не дождался блокировки или тишины, завершается кодом «не начат» (отдельно от ошибки исполнения) и повторяется в следующей итерации.
- P0.8: блокировку держит процесс одной точки замера (общий срок попытки 25 минут по плану P0.8), а не вся серия, поэтому между точками её может взять P0.7. Срок захвата — 5 минут (`lockf -k -t 300`), ожидание тишины под блокировкой — тоже до 5 минут (правило в плане P0.8). Итерация с точкой замера `make check` не запускает: код в ней не меняется.
- P0.7: `run.sh` целей `make probe-review` и `make probe-review-live` берёт ту же блокировку на весь рецепт, включая подъём и остановку контейнера GitLab, со сроком захвата 5 минут (`lockf -k -t 300`). Рубеж задач P0.7 исполнитель запускает как `/usr/bin/lockf -k -t 900 "${SHELLIO_CACHE_DIR:-$HOME/.cache/shellio}/measure.lock" make check`. Срок ограничивает только ожидание захвата: 15 минут ожидания оставляют `make check` около 15 минут до `session_timeout = 30m` ralphex. Не дождался — рубеж не пройден, исполнитель записывает ⚠️ «замерная блокировка занята» и повторяет рубеж в следующей итерации; это не провал задачи.
- Захват один и внешний. Цели проб P0.7 обёрткой `lockf` не оборачиваются: их `run.sh` берёт блокировку сам, а вложенный захват того же файла не проходит (проверено: внутренний `lockf -t 0` под внешним возвращает 75). `run.sh` выполняет рецепт под захватом отдельной внутренней командой, а не повторным вызовом публичной цели.
- Код 75 может вернуть и сама команда. Как в `scripts/ghostty/lock.sh`, команда под блокировкой сначала удаляет маркер старта: маркер на месте и код 75 — блокировка не взята, маркера нет — код принадлежит сценарию, и потерянный `result.json` — ошибка исполнения, а не `not_run`. Логику проверяет тест `run.sh` на временном файле блокировки.
- Остальную нагрузку (ревью ralphex, сборки вне рубежа, `make ghostty`) блокировка не покрывает. Её ловит проверка фона P0.8 на протяжении каждого замерного окна.
- Первое наполнение общего кэша и обе сборки `make ghostty` заканчиваются в разделе «Запуск» до старта исполнителей: при холодном кэше обе сборки пишут один `refs/shellio/pin` в `ghostty-src.git`. Исполнители `make ghostty` не запускают.

### Слияние

Итог каждого плана — подготовленная ветка: задачи завершены, план перенесён в `completed/`, `make check` проходит. Исполнители не видят состояние соседней ветки, поэтому слияние в задачи не входит. Его выполняет владелец после окончания обоих прогонов и их ревью.

1. Первая завершённая ветка вливается в `toolchain-bootstrap` из основной копии без конфликтов.
2. В worktree второй ветки вливается обновлённая `toolchain-bootstrap`, merge-коммит завершается там. Ожидаемые конфликты и их разрешение:
   - `Cargo.toml`: обе строки members в алфавитном порядке (`probe-resource-accounting`, затем `probe-review-api`);
   - `Makefile`: обе переменные `PROBE_*`, объединённая строка `.PHONY`, обе группы целей;
   - `AGENTS.md`: оба пункта «Сборка» в порядке P0.7, P0.8, список целей вне CI — объединение;
   - `docs/README.md`, `docs/architecture.md`: обе записи;
   - `docs/roadmap.md`: обе строки с ✅;
   - `docs/adr/0034-probe-code.md`: разделы «Уточнено в P0.7», затем «Уточнено в P0.8», перед «Условием пересмотра»;
   - `Cargo.lock`: основа — lock уже влитой ветки, затем `cargo metadata --format-version 1 >/dev/null` досчитывает вторую пробу по объединённым манифестам. Diff lock проверяется: меняются только пакеты второй пробы, посторонних обновлений нет. Выбор `ours`/`theirs` целиком не используется.
   - относительные ссылки перенесённых в `completed/` планов (ADR, дорожная карта, отчёт, соседний план) проверяются на объединённом HEAD.
3. `make check` на объединённом HEAD проходит, затем `toolchain-bootstrap` перематывается на него (fast-forward). Если `toolchain-bootstrap` за это время ушла вперёд, шаг 2 повторяется.

## Context (from discovery)

- **ADR-0015**: доменная модель `ReviewTarget`, `Revision`, `Thread`, `DraftComment`, `ReviewSession`, ID провайдера — непрозрачная строка. Якорь GitHub — `commit_id`, `path`, `line`, `side`, `start_line`, `start_side`. Якорь GitLab — `base_sha`, `start_sha`, `head_sha`, пути, строки, `line_range`. Просмотренные файлы: GitHub `markFileAsViewed`, GitLab локально.

- Образец стенда результатов — `spikes/probe-update-lifecycle` и `spikes/probe-session-survival`: `run.sh` с процессом на сценарий, временный `SHELLIO_STATE_DIR`, `result.json` на процесс, агрегирование. Нужный код копируется и упрощается с пометкой источника (ADR-0034), зависимости от соседней пробы нет.
- Окружение на момент планирования: docker 29.9.3 (aarch64, 12,5 ГБ памяти виртуальной машины), хост 18 ГБ, 11 ядер.
- У проекта нет файла лицензии. Допустимые лицензии зависимостей — MIT, Apache-2.0, BSD-2/3-Clause, ISC, Zlib, Unicode-3.0, их сочетания через `OR` или `AND`.

## Предусловия

Физические предусловия по ADR-0036. Отсутствующее предусловие обязательной цели `make probe-review` — ошибка исполнения. Отсутствующее предусловие живой клетки даёт её `not_run` с причиной.

- Worktree создан и набор ghostty в нём собран по разделу «Запуск».
- Песочница github.com: приватный репозиторий `shellio-review-sandbox` владельца с хотя бы одним коммитом в ветке по умолчанию (в пустом репозитории ref через API не создаётся); второй аккаунт-ревьюер — collaborator с правом записи.
- Песочница gitlab.com: приватный проект `shellio-review-sandbox` владельца с хотя бы одним коммитом в ветке по умолчанию; второй аккаунт-ревьюер с ролью Developer или выше.
- Токены в login keychain, сервис `shellio-probe-review`, аккаунты `github-author`, `github-reviewer`, `gitlab-author`, `gitlab-reviewer`. Элементы созданы с доверенным приложением `/usr/bin/security`, например `security add-generic-password -s shellio-probe-review -a github-author -T /usr/bin/security -w`. Проба читает их только через `/usr/bin/security find-generic-password -w`: пересобранный бинарь пробы меняет подпись и вызвал бы диалог ACL. Владелец один раз выполняет `security find-generic-password -s shellio-probe-review -a <аккаунт> -w >/dev/null` для каждого аккаунта из терминала, где запускается ralphex, и убеждается, что диалога нет. Проба вызывает `security` со сроком 10 с: истёк — клетки аккаунта получают `not_run` «Keychain ждёт диалога», процесс `security` снимается. Права токенов: GitHub автора — `repo` (classic) или fine-grained с Pull requests и Contents на чтение и запись; GitHub ревьюера — только classic `repo`: fine-grained PAT не работает у outside collaborator личного репозитория; GitLab — `api`. Ошибка доступа из-за токена — нарушение предусловия (`not_run` «токен без прав»), а не наблюдение возможностей API.
- Файл песочниц вне git: `~/.config/shellio-probe-review/sandbox.toml` с хостами, путями репозиториев и именами элементов Keychain. Только перечисленные в нём репозитории пригодны для записи.
- Для локального GitLab CE: docker daemon запущен (`docker info` проходит), свободно не меньше 6 ГБ памяти виртуальной машины docker.

## Development Approach

- **testing approach**: Regular. Код и его проверки входят в одну задачу.
- Каждая задача завершается до начала следующей и не опирается на код более поздней. Рубеж каждой задачи — `/usr/bin/lockf -k -t 900 "${SHELLIO_CACHE_DIR:-$HOME/.cache/shellio}/measure.lock" make check` по разделу «Замерная блокировка», для задач со стендом также `make probe-review SCENARIOS="<сценарии задачи>"` без ошибок исполнения.
- Граница пробы. Нет плагина, шины команд, `shellioctl`, продуктового `forge-accounts` и UI. Есть UI-free модель ревью, журнал, адаптеры двух провайдеров, `forge-fake` и стенд. P4.1 пишет адаптеры и `forge-fake` заново по выводам отчёта.
- `unsafe` не нужен. Если понадобится системный C API, он допустим только в `spikes/probe-review-api` (ADR-0034).
- Тесты:
  - чистая логика идёт в `make check` и CI: модель, якоря, классификация смены head, журнал на временном файле, сборка запросов, разбор ответов по образцам, адаптеры против встроенного транспорта со сценарием, `forge-fake` через loopback, очистка следа, модель результатов и агрегирование;
  - живые хосты и docker идут только в `make probe-review-live`.
- Тесты не ходят в настоящую сеть: только встроенный транспорт или `forge-fake` на `127.0.0.1` с портом 0.
- Синхронизация — квитанции, каналы и барьеры. `sleep` не используется. Ожидание готовности GitLab — опрос с крайним сроком в `run.sh`, а не в тестах.
- Исполнитель не останавливается ради решения или приёмки владельца (ADR-0036). Предвидимый выбор делается по правилу раздела «Правила выбора». Непредвиденный выбор исполнитель делает сам и записывает с ⚠️ в план и отчёт. Не наблюдённое получает `not_run` с причиной, а не `pass`.
- Ожидания каждого сценария записываются в раздел «Ожидания» отчёта до его первого прогона. Ожидания и оракулы после результатов не меняются.
- Запуски только с изолированным `SHELLIO_STATE_DIR`.

## Testing Strategy

- **unit tests**: в каждой задаче с кодом, в `make check` и CI.
- **цели пробы**: `make probe-review` (fake, обязательная) и `make probe-review-live` (живые хосты) идут отдельными процессами на сценарий и хост, у каждого `result.json`. В `make check` цели не входят (ADR-0034).
- **e2e**: `make e2e` к пробе не относится (ADR-0034).

## Progress Tracking

- Выполненные пункты отмечаются `[x]` сразу.
- Новые задачи — с префиксом ➕, блокеры и решения исполнителя вне правил — с ⚠️.
- Решения по правилу плана записываются как «решение исполнителя по правилу плана» с основаниями.
- План обновляется при изменении объёма и коммитится вместе с изменениями каждой задачи.

## Solution Overview

- **Модель** (`model/`, UI-free). `ReviewTarget { host, repo, number }`, `Revision { base_sha, start_sha, head_sha }`, `Anchor` в общей форме (сторона, строка, диапазон, путь старый и новый) с переводом в якорь GitHub и позицию GitLab, `Thread`, `DraftComment`, `ReviewSession` (аккаунт, хост, репозиторий, ревизия). Инвариант: якорь черновика и запрос отправки берут SHA только из ревизии сессии. Смена head классифицируется: остаться на ревизии, перейти, перепривязать устаревшие якоря. Номер строки молча не подбирается.
- **Журнал** (`journal/`). SQLite на временном `state.db` (системная `libsqlite3`). Черновик пишется сразу. У элемента отправки состояния `planned → in_flight → confirmed | unknown | failed`, сохранённые удалённые ID и отметка времени входа в `in_flight`. После переоткрытия журнал восстанавливает незавершённую отправку.
- **Транспорт** (`transport/`). Типаж `Transport` с запросом и ответом. Реализации: HTTP-клиент для живых хостов и `forge-fake`, встроенный транспорт со сценарием для юнит-тестов. Каждый вызов попадает в след: метод, путь, тело, код, заголовки лимитов. След очищается от токенов, логинов, адресов и путей репозиториев до записи на диск.
- **Адаптеры** (`github/`, `gitlab/`). Объявленные возможности (`Capabilities`), определённые на хосте чтением, а не по имени хоста.
  - GitHub. Только локальные черновики — один Create review с `comments[]`, `event` и верхнеуровневым `body` (обязателен для `COMMENT` и `REQUEST_CHANGES`). Серверный `PENDING` — создание review без `event`, добавление и обновление комментариев с сохранением ID (в GraphQL тред привязывается к review по node ID `pullRequestReviewId`, REST Submit берёт свой `review_id`), Submit именно этого review без `comments[]` — проверяется по исходящему JSON. Существующий `PENDING` того же аккаунта не перезаписывается: адаптер читает весь его состав по всем страницам (REST до 100 на страницу, GraphQL по курсорам) и принимает его в работу только явным действием. `markFileAsViewed` через GraphQL.
  - GitLab. Публикация каждого известного `draft_note` по его ID, сводка отдельной заметкой, `approve` с `sha` (несовпадение — документированный 409; 409 возможен и при том же head после изменения diff целевой ветки), запрос изменений через GraphQL `mergeRequestRequestChanges(projectPath, iid)` без SHA-предусловия. У мутации проверяются отдельно: наличие в схеме, права и тариф, наблюдаемый итог повторным чтением состояния ревьюера; читаются `errors` верхнего уровня и `payload.errors`. HTTP 200 бывает и при отказе. Одинаковый ответ «не существует или нет прав» точной причины не получает. `bulk_publish` не вызывается никогда.
- **Отправка** (`submit/`). Пять шагов ADR-0015: загрузить свежую ревизию и сопоставить якоря; построить конкретный список и итог; опубликовать с записью состояний; сохранить удалённые ID; показать полностью или частично отправленное. `unknown` после таймаута сверяется с провайдером. `confirmed` требует связи с нашей операцией и чтения именно ожидаемого итога: удалённый ID, полученный в ответе на эту операцию, или наблюдаемый ожидаемый итог известного объекта. Для Submit — известный `PENDING` review по его ID в ожидаемом отправленном состоянии; ID, полученный при создании `PENDING`, сам Submit не подтверждает. Для публикации `draft_note` — опубликованная заметка, связанная с известным черновиком; исчезновение известного ID из списка черновиков или 404 публикацию не доказывает: тот же черновик мог удалить второй клиент (удаление и публикация — раздельные операции API). Объект, совпавший по автору, якорю и тексту, но без такой связи, — кандидат, а не подтверждение: его мог создать другой клиент того же пользователя. Элемент с кандидатом остаётся `unknown` с записанным кандидатом. Слепого повтора нет.
- **`forge-fake`** (`fake/`). HTTP-сервер на loopback с состоянием, реализующий нужное подмножество REST и GraphQL обоих провайдеров по документации. Управляется сценарием: подложенные черновики другого клиента, смена head, отказ после принятой записи до ответа, 5xx, таймаут, ошибки GraphQL при HTTP 200, отсутствие возможности, отсутствие прав. Ведёт счётчики вызовов, в том числе `bulk_publish`. Сервер — не продуктовый `forge-fake`, а оракул пробы; его расхождения с живыми хостами фиксируются в отчёте как вход P4.1.
- **Живой контур** (`live/`). Чтение `sandbox.toml`, токенов через `/usr/bin/security`, сторож записи, жизненный цикл прогона (ветка и PR/MR на каждый прогон с уборкой), локальный GitLab CE.

### Матрица возможностей

Строка — утверждение ADR-0015, столбец — где оно наблюдалось. Значения клетки: `pass`, `fail` (отрицательный вывод), `absent` (у проверенной роли или редакции хоста возможности нет — наблюдавшееся ограничение, а не `not_run`), `not_run` с причиной (нет песочницы, токена или доступа для наблюдения). Сломанный стенд или потерянный обязательный артефакт (след, журнал, серверное состояние до и после) — ошибка исполнения.

Столбец `fake` проверяет инварианты нашего клиента против нашего же оракула. Его `fail` — ошибка в коде пробы, то есть ошибка исполнения: цель падает, задача не закрывается. Отрицательный вывод бывает только на живых столбцах, где опровергается внешняя гипотеза (ADR-0034).

«Браузерный черновик» в песочницах создаёт второй API-клиент отдельным процессом от имени ревьюера, чей токен ведёт черновики пробы. Черновик другого аккаунта не проверял бы ничего: его не тронул бы и ошибочный `bulk_publish`. Автор независимо читает, что стало видимым в PR/MR после отправки. Это тот же серверный объект, что создаёт веб-интерфейс (`PENDING` review у GitHub, `draft_note` у GitLab). Создание именно в браузере — `not_run` «браузер не наблюдался» отдельной клеткой каждой песочницы.

### Живой контур

- **Сторож записи.** Перед первой записью в прогоне адаптер читает репозиторий и проверяет: путь есть в `sandbox.toml`, репозиторий приватный (`private: true` у GitHub, `visibility: private` у GitLab). Иначе сценарий завершается ошибкой исполнения без единой записи. Юнит-тест проверяет отказ на публичном и на не перечисленном репозитории.
- **Жизненный цикл.** Каждая клетка создаёт ветку `probe/<run-id>-<клетка>` от ветки по умолчанию и PR/MR через API (коммиты через Contents API GitHub и Commits API GitLab, без `git push` и без токена в аргументах процесса). Фикстура — известный файл с удалёнными, изменёнными и добавленными строками. Смена head — новый коммит тем же API. ID созданных объектов пишутся в каталог прогона сразу после создания, чтобы уборку можно было продолжить после частичного сбоя. В конце клетки PR/MR закрывается, ветка удаляется, оставшиеся черновики клетки удаляются; уборка выполняется и после ошибки сценария и подтверждается чтением только созданных в клетке объектов. Не убранное записывается в `result.json`.
- **Аккаунты.** Роли закреплены на весь цикл. Автор создаёт ветку и PR/MR, меняет head и независимо читает опубликованное. Ревьюер создаёт, обновляет и отправляет своё review и черновики (у GitHub `PENDING` принадлежит создателю, у GitLab `draft_notes` видны только автору черновика), выполняет `APPROVE`, `REQUEST_CHANGES`, `approve`, `mergeRequestRequestChanges`. На GitLab ревьюер назначается reviewer у MR клетки. Без токена ревьюера клетки ревью — `not_run` «нет ревьюера», без токена автора — `not_run` «нет автора»; чтение песочницы после прогона требуется только от тех клеток, что запускались.
- **Очистка данных.** В `docs/probes/data/` попадают только очищенные `result.json`, `summary.json` и выдержки следа. Очиститель заменяет токены, логины аккаунтов, адреса электронной почты, адрес локального GitLab и пути репозиториев метками (`<author>`, `<reviewer>`, `<repo>`, `<gitlab-ce>`). Публичные `github.com` и `gitlab.com` не заменяются. Юнит-тест очистителя проверяет каждую категорию, а задача 16 проверяет каталог данных поиском исходных значений.
- **Лимиты.** Заголовки лимитов записываются на каждом вызове. Явный отказ «лимит исчерпан» означает, что запись не принята: элемент получает `failed`, а не `unknown`, клетка — `not_run` «лимит», повторов с ожиданием нет. Потерянный ответ после отправки — другой случай, он даёт `unknown`.

### Локальный GitLab CE

- Образ `gitlab/gitlab-ce` закрепляется по digest в `spikes/probe-review-api/gitlab/pin` (тег, digest, дата). Подъём — `docker run` с меткой `shellio.probe.run-id=<run-id>`, томами во временном каталоге прогона, `GITLAB_ROOT_PASSWORD` из случайного значения прогона, портом на `127.0.0.1`. В начале каждого вызова `run.sh` (любой цели пробы, сразу после захвата блокировки) проверяет доступность docker (`docker info` со сроком 10 с). Доступен — удаляет контейнеры с меткой `shellio.probe.run-id` от прежних прогонов и проверяет, что их не осталось. Недоступен — уборка записывается как «не наблюдалась», а fake и облачные клетки идут дальше; клетки `gitlab_ce` получают `not_run` «docker недоступен». Уборка нужна, потому что `SIGKILL` группы не исполняет trap, а освобождённая блокировка контейнер не останавливает, и забытый GitLab грузил бы машину в окна замеров P0.8.
- Готовность — опрос `/-/readiness` с крайним сроком 15 минут. Вместе с захватом блокировки (до 5 минут) это оставляет сценарию не меньше 10 минут итерации. Не дождался — клетки `gitlab_ce` получают `not_run` «GitLab не поднялся», журнал контейнера сохраняется в каталоге прогона.
- Настройка — кодом пробы на Rust через API GitLab (AGENTS.md: собственный код на Rust): токен root по паролю (OAuth password grant), затем административные API — пользователь-ревьюер, токены автора и ревьюера (User tokens API self-managed), приватный проект `shellio-review-sandbox`, инициализированный README. Если password grant выключен в выбранной версии, токен root создаётся одним выражением `gitlab-rails runner` из `run.sh`, решение записывается с ⚠️. Сторож записи для этого хоста проверяет адрес `127.0.0.1` вместо `sandbox.toml`.
- Контейнер и тома удаляются в конце рецепта и после ошибки.

### Правила выбора

- **HTTP-клиент.** Блокирующий клиент с TLS платформы (Security.framework), чтобы не тянуть `ring` или `aws-lc`. Порядок: `ureq` с `native-tls`, затем `reqwest` blocking с `native-tls`. Берётся первый, у которого все зависимости в допустимых лицензиях.
- **HTTP-сервер `forge-fake`.** `tiny_http`, затем собственный минимальный сервер на `std::net`. Берётся первый с допустимыми лицензиями.
- **SQLite.** `rusqlite` без функции `bundled`, системная `libsqlite3` из SDK macOS. Встроенный исходник SQLite (общественное достояние) не входит в список допустимых лицензий.
- **Метод серверного `PENDING` GitHub.** Добавление и обновление комментариев — документированный незаустаревший метод: сначала REST, если он умеет добавлять комментарий к существующему `PENDING`, иначе GraphQL `addPullRequestReviewThread` и `updatePullRequestReviewComment`. Выбранный метод и отвергнутые записываются в матрицу.
- **Тег GitLab CE.** Новейший стабильный `X.Y.Z-ce.0` с манифестом `linux/arm64` (`docker manifest inspect`). Нет такого — клетки `gitlab_ce` получают `not_run` «нет образа arm64», эмуляция amd64 не используется.
- **Сверка `unknown`.** `confirmed` — только при связи с нашей операцией (см. «Отправка»). Совпадение по содержимому даёт кандидата и оставляет `unknown`. Скрытые метки в тексте комментария не добавляются: это видимое пользователю изменение.
- **Расхождение с ADR-0015.** Живой результат, противоречащий ADR-0015, записывается отрицательным выводом с передачей P4.1. Решение ADR исполнитель не меняет (ADR-0036), раздел «Уточнено в P0.7» фиксирует наблюдение и передачу.

### Результаты

`result.json` на процесс: сценарий, столбец матрицы, версия и тариф хоста (тариф — если виден токену), итог клетки (`pass`, `fail`, `absent`, `not_run` с причиной), очищенный след вызовов, число вызовов по методам, серверное состояние до и после, журнал после переоткрытия, не убранные объекты. `--aggregate` собирает матрицу `summary.json` и таблицу Markdown для отчёта. Живые вызовы идут по хосту и по частям `SCENARIOS`, у каждого свой каталог прогона, поэтому вход агрегатора — явный список каталогов одной серии (общий идентификатор серии в каждом `result.json`) и одной сборки (хеш бинаря) и ожидаемые пары «столбец × сценарий». Каталог чужой серии или сборки, необъяснённый пропуск пары или её дубль — ошибка агрегатора. Пара прерванного куска, перезапущенного целиком, берётся из последнего завершённого каталога, замена записывается. Ошибка исполнения (сторож записи, падение стенда, нарушение предусловия обязательной цели) роняет цель, отрицательный вывод — нет (ADR-0034).
