# Проба виртуального diff на AppKit

## Overview

- Шаг P0.6 `probe-diff-view` [дорожной карты](../roadmap.md). Зависит от P0.2, открывает P3.2 `diff-view`. Критерий шага: кадры и память в бюджете, решение по ADR-0002.
- [ADR-0002](../adr/0002-ui-stack-appkit.md) поручает P0.6 проверить стоимость `DiffView` на `objc2`. Условие пересмотра: если `DiffView` не укладывается в бюджеты, вопрос о Swift-оболочке возвращается владельцу. Самостоятельного перехода нет. ADR-0002 «Последствия»: `DiffView` реализует протоколы доступности сам.
- Бюджеты [docs/architecture.md](../architecture.md):
  - открытие diff на 100 тыс. строк, первый экран, — до 200 мс;
  - прокрутка diff без потери кадров при 120 Гц;
  - память GUI без терминалов до 150 МБ;
  - реакция на клавишу в `Navigation` до 16 мс;
  - CPU GUI в простое при видимых панелях до 1%.
- Передачи из [отчёта P0.2](../probes/p0.2-appkit-shell.md), таблица «Гипотезы и остаток»:
  - кадры прокрутки diff на экране, а не ритм `displayLink`;
  - отметка конца прохода, которая не опережает `drawRect:`;
  - `DiffView` сам реализует протоколы доступности;
  - память с diff на 100 тыс. строк.
- Охват (решения владельца при планировании):
  - unified и side-by-side («Рядом») целиком, с переносом длинных строк, на обоих вариантах отрисовки;
  - подсветка синтаксиса, inline-треды, выделение строк;
  - доступность `DiffView` для внешнего клиента доступности;
  - адаптация к зонам: классы `Narrow`, `Regular`, `Wide`, `ShortBar`, смена unified и «Рядом» по ширине, заглушка ниже `min_size`.
- Сравниваются два варианта отрисовки (решение владельца при планировании):
  - **A** — собственный `NSView` в `NSScrollView`, строки рисуются Core Text, есть индекс высот;
  - **B** — view-based `NSTableView`, строка таблицы — строка diff или блок треда.

  Модель, подсветка и стенд у вариантов общие. Выбор варианта для P3.2 делается по правилу раздела «Правила выбора».
- Итог:
  - проба `spikes/probe-diff-view`;
  - цели `make probe-diff` и `make probe-diff-demo`;
  - отчёт `docs/probes/p0.6-diff-view.md` с выбранными сырыми данными;
  - раздел «Уточнено в P0.6» в ADR-0002, строка риска в `docs/architecture.md`.
- Исполнение автономное ([ADR-0036](../adr/0036-autonomous-execution.md)), одним запуском. Ручной приёмки нет, её заменяет приёмочный проход исполнителя (задача 18). Пункты `not_run` готовность плана не блокируют, включая кадры на 120 Гц и прогоны на 60 Гц (решение владельца при планировании). Они записываются открытой передачей.

## Context (from discovery)

- Решения, на которые опирается проба:

  - **ADR-0009** и **ADR-0031**: `Geometry { zone, size, width, height }`, `SizeClass`, `adapt` получает геометрию части зоны, ниже `min_size` показывается заглушка «Развернуть». Половина центра шириной 440 точек даёт `Narrow`. Числовых порогов классов в ADR нет.
  - **ADR-0010**: `j k gg G Ctrl-d Ctrl-u` двигают внутри diff. Из `docs/ux.md`: `]c/[c` — изменения, `v` — выделить строки, `c` на строке или диапазоне — черновик, `Cmd-Enter` — сохранить. Щелчок по половине diff в режиме «Рядом» задаёт строку и сторону комментария. Длинные строки в этом режиме переносятся, обе стороны остаются рядом. Режим включается, только если ширины самого diff хватает на обе стороны.

## Development Approach

- **testing approach**: Regular. Код и его проверки входят в одну задачу.
- Каждая задача завершается до начала следующей и не опирается на код более поздней. Рубеж каждой задачи — `make check`, для задач со стендом также `make probe-diff SCENARIOS="<сценарии задачи>"` без ошибок исполнения.
- Граница пробы. Нет плагина, шины команд, `shellioctl`, `RepositoryService`, адаптера раскладки и `shellio-appkit`. Есть UI-free модель diff, подсветка на worker, два варианта отрисовки и стенд. P3.2 пишет `DiffView` заново по выводам отчёта.
- `unsafe` Objective-C и системные C API — только в `spikes/probe-diff-view` (ADR-0034): AppKit, Core Text, Core Graphics, `proc_pid_rusage`, `clock_gettime`, Accessibility API внешнего клиента.
- Главный поток не блокируется. Разбор diff, подсветка и построение индексов идут на worker. На главный поток приходят готовые неизменяемые снимки с номером поколения. Работа отменяется при смене diff, режима или закрытии вида.
- Тесты:
  - чистая логика идёт в `make check` и CI: разбор unified diff, модель строк и адресов, пары «Рядом», индекс высот, перенос по заданной ширине символов, выделение, якоря тредов, подсветка по эталону, классы геометрии, генераторы фикстур, модель результатов и агрегирование;
  - GUI, Core Text, кадры, доступность и память идут в цели пробы.
- Синхронизация — квитанции, барьеры, наблюдатели цикла и уведомления. `sleep` не используется.
- Исполнитель не останавливается ради решения или приёмки владельца (ADR-0036). Предвидимый выбор делается по правилу раздела «Правила выбора». Непредвиденный выбор исполнитель делает сам и записывает с ⚠️ в план и отчёт. Не наблюдённое автоматикой получает `not_run` с причиной, а не `pass`.
- Ожидания каждого сценария записываются в раздел «Ожидания» отчёта до его первого прогона. Пороги и стимулы после результатов не меняются.
- Запуски только с изолированным `SHELLIO_STATE_DIR`.

## Solution Overview

- **Модель** (UI-free, `model/`). Вход — текст unified diff как у `git diff` и полные blob старой и новой стороны. Модель строит:
  - ханки и строки с адресом `LineAddr { side: Old | New, line }` — у контекстной строки два адреса;
  - строки показа двух раскладок: unified (строка diff) и «Рядом» (пара старой и новой строки, у вставки или удаления одна сторона пустая);
  - блоки тредов, привязанные к якорю ADR-0015 (`side`, `start_line`, `line`) и показанные после последней строки якоря;
  - индекс высот (дерево Фенвика по строкам показа): координата → строка и строка → координата, правка высоты за O(log n).

  Перенос считается по ширине в символах моноширинного шрифта, ширину символа даёт вид. Высота строки «Рядом» равна максимуму высот её сторон.
- **Подсветка** (`highlight/`). tree-sitter с грамматикой Rust. Один отменяемый worker разбирает старый и новый blob целиком и держит деревья. Запрос подсвечивает видимый диапазон байт каждой стороны через `QueryCursor::set_byte_range`. Если полный разбор не готов к первому экрану, worker даёт предварительную подсветку локальным разбором окна вокруг видимых строк, а после полного разбора — исправление. Стили берутся из токенов темы.
- **Вариант A** (`view_a/`). Один `NSView` — document view в `NSScrollView`. Рисуются только видимые строки, раскладка Core Text (`CTLine` или `CTFramesetter` на строку с переносом) хранится в ограниченном кэше на несколько экранов. Выделение, гуттер с номерами и блоки тредов рисует сам вид. Поле черновика — одно переиспользуемое `NSTextView`, оно ставится над блоком треда.
- **Вариант B** (`view_b/`). View-based `NSTableView` без заголовка, одна колонка. Строка таблицы — строка показа или блок треда. Высота задаётся `heightOfRow` из индекса высот модели, при изменении — `noteHeightOfRowsWithIndexesChanged`. В режиме «Рядом» одна таблица, и вид строки содержит обе половины. Две синхронизированные таблицы не используются: пара и якорь должны жить в одной строке. Виды ячеек переиспользуются по идентификатору. Полный `reloadData` вызывается только при замене diff (находка P0.2).
- **Общие для A и B**: состояние вида (прокрутка как якорь «адрес строки + смещение», выделение, раскрытые треды, режим) хранится в модели. Вид применяет разницу состояний. Клавиши и мышь вызывают одни обработчики модели.
- **Стенд** (`scenario/`). Копия стенда P0.2 с пометкой источника: синтетические события, readback, сторож, счётчики объектов, сэмплер, результаты, агрегирование. Добавлено:
  - отметка конца `drawRect:` с поколением содержимого: вид рисует номер поколения и диапазон строк, стенд ждёт отрисовки нужного поколения, а не конца прохода цикла;
  - запись кадров через `xctrace` с калибровкой, запасной путь ScreenCaptureKit;
  - внешний клиент доступности — отдельный процесс пробы `--ax-client`, он читает дерево AX окна через `AXUIElement`.

## Technical Details

### Фикстуры

Генераторы детерминированы (фиксированное зерно), их форма проверяется юнит-тестами. Текст — синтетический Rust, в котором есть многострочные и вложенные блочные комментарии, raw-строки `r#"…"#`, многострочные строковые литералы, макросы и длинные выражения.

| Фикстура | Старая сторона | Новая сторона | Строк показа unified | Назначение |
| --- | --- | --- | --- | --- |
| `added` | пусто | 100 000 строк | 100 000 | новый файл: максимум строк показа, открытие, кадры, память |
| `modified` | 100 000 строк | 100 000 строк, каждая 5-я изменена | около 120 000 (один сплошной ханк при `-U3`: между изменениями 4 строки) | плотные пары «Рядом», кадры, память |
| `sparse` | 100 000 строк | 100 000 строк, 50 ханков по 6 изменённых строк, последний ханк начинается на строке 99 900 | около 650 | холодное открытие сразу на последнем ханке: подсветке нужен контекст всего файла |
| `wrap` | 10 000 строк | 10 000 строк | около 12 000 | строки от 200 до 4 000 символов, перенос в обоих режимах |
| `threads` | `modified` | `modified` | `modified` и 500 тредов | треды по обеим сторонам и диапазонам, 1–20 комментариев, 10 тредов на диапазон через границу ханка |
| `real` | `d6893dcc4b97` | `cc81b21e03bb` | около 14 000 по 32 файлам | настоящий код: `git diff d6893dcc4b97 cc81b21e03bb -- spikes/probe-appkit-shell/src/`, проверка подсветки и разбора |

- В фикстуре `sparse` последний ханк начинается внутри многострочного комментария на старой стороне и внутри raw-строки на новой. Комментарий и raw-строка открываются больше чем за 200 строк до видимой области, то есть до начала окна локального разбора, поэтому локальный разбор эти контексты угадать не может.
- Фикстуры из нескольких файлов (`real`) дают модели список файлов и активный файл. Якорь треда включает `path`.
- Фикстуру `real` готовит `run.sh` до сценариев. Текст diff (`git diff -U3 --inter-hunk-context=0 --no-ext-diff --no-textconv --no-color`) и blob пар файлов он кладёт в `target/probes/diff-view/fixtures/real/`, читая их через `git` без сети. Синтетические фикстуры используют те же параметры: контекст 3, без слияния ханков сверх него. Проба в измеряемом процессе git не вызывает. Фикстура `real` в `make check` не входит: в неглубокой копии CI этих коммитов может не быть. Код этих коммитов принадлежит проекту.
- Эталон подсветки фикстуры — стили полного разбора tree-sitter, посчитанные вне измеряемого процесса командой `--reference` и сохранённые в `fixtures/<имя>/reference.json` по диапазонам строк, которые открывают сценарии.

### Интервалы и оракулы

Значения порогов записаны здесь и в отчёте до первого прогона и после результатов не меняются.

**Открытие, бюджет 200 мс.**

- Предусловие: текст diff и оба blob уже прочитаны в память процесса как `Arc<[u8]>`. Чтение из git и диска — работа P3.1, его время записывается для `real` отдельной строкой без вердикта.
- Начало — вызов `postEvent` клавиши открытия.
- Промежуточные отметки:
  - модель и индекс высот первого экрана готовы;
  - первый `drawRect:` с текстом видимых строк (поколение открытия);
  - первый проход, после которого все видимые строки обеих сторон отрисованы с эталонными стилями.
- Готовность экрана — барьер покрытия: вид сообщает поколение и диапазон каждой отрисованной строки или ячейки, стенд ждёт, пока текущим поколением покрыты все видимые строки обеих сторон. У B одного обратного вызова ячейки для этого мало. Конец `drawRect:` означает «экран отрисован приложением», время до показа композитором пишется отдельным наблюдением.
- С бюджетом сравнивается конец — последняя отметка: первый экран с правильной подсветкой. Если предварительная подсветка совпала с эталоном, засчитывается её кадр. Если нет, записываются время предварительного кадра и время исправления, а с бюджетом сравнивается исправление.
- Каждое открытие идёт в свежем процессе. На фикстуру, вариант и режим приходится 11 процессов, первый в агрегаты не входит и записывается отдельно. Остальные — свежие процессы с прогретыми системными кэшами. С бюджетом сравнивается максимум 10 остальных: p95 ближайшим рангом для 10 значений и так равен максимуму.
- Входные байты в памяти до начала допустимы только сырыми: разбор, индексы, деревья и раскладка до клавиши открытия не строятся.
- Обязательные комбинации: `added`, `modified`, `sparse` (открытие на последнем ханке), каждая в unified и «Рядом», на A и B. `wrap` и `real` идут наблюдением без вердикта.
- 20 повторных открытий в одном процессе пишутся рядом как «прогретое открытие» без вердикта.
- Под `xctrace` открытие не измеряется.

**Кадры, бюджет «без потери кадров при 120 Гц».**

- Частота подтверждена, если `displayLink` даёт ожидаемый интервал 8,33 мс и трасса показывает vsync с тем же периодом. Иначе вердикт по кадрам — `not_run` «120 Гц не подтверждены».
- Стимулы записаны заранее:
  - **S1, равномерная прокрутка, бюджетная.** Положение clip view — функция времени по независимой шкале: `y(t) = y0 ± 4800 точек/с × (targetTimestamp − t0)`. Вызов `displayLink` ставит положение для своего `targetTimestamp`, а не прибавляет шаг, поэтому пропущенный вызов виден как скачок, а не как замедление. Три отрезка по 10 с: от начала вниз, из середины вниз, от конца вверх.
  - **S2, бросок, проверка без вердикта.** Синтетические события колеса с фазами `began`, `changed`, `ended` и momentum по заранее заданной временной траектории (начальная дельта 200 точек, затухание 0,95 за событие до 1 точки, около 0,87 с). Журнал доставки записывает время каждого события. Проверяется обработка фаз и что вид следует траектории. Бюджет по S2 не выносится: бросок короче прогрева, а генератор событий на главном потоке сам теряет события при его зависании.
  - **S3, ресайз, наблюдение.** Ширина окна меняется на 8 точек за вызов `displayLink` в режиме «Рядом» с фикстурой `wrap`: перенос пересчитывается на каждом кадре.
- Первая секунда каждого отрезка S1 — прогрев, в окно замера она не входит. В окне замера должно быть не меньше 1 000 тактов vsync, иначе отрезок — ошибка исполнения, а не `pass`.
- Потерянный кадр — vsync в окне замера, после которого показанный кадр окна пробы не соответствует ожидаемому положению S1 на этом такте. Связь «окно — дисплей — показанный кадр — ожидаемый шаг» доказывает калибровка (задача 6). Если она не доказана, работает правило «Способ замера кадров».
- Вердикт `pass` — ноль потерянных кадров во всех обязательных отрезках. Обязательные: S1 на `added`, `modified` и `threads` с раскрытыми тредами, в обоих режимах. S2, S3 и все прогоны на 60 Гц — наблюдение без вердикта.
- Дополнительно пишется ритм `displayLink` и время `drawRect:` по кадрам, как в P0.2.

**Память, бюджет 150 МБ = 150 000 000 байт.**

- Сравнивается весь процесс GUI пробы: `ri_phys_footprint` из `proc_pid_rusage` по фазам и `ri_lifetime_max_phys_footprint` для пика между выборками. Сначала стенд сверяет, что поле `ri_lifetime_max_phys_footprint` в `rusage_info_v4` есть и растёт на контрольном выделении. Если сверка не прошла, пик между выборками — `not_run`, а сравнение идёт по максимуму выборок.
- Фазы в одном процессе: пустое окно → `added` unified → прокрутка до конца → «Рядом» → `threads` с раскрытыми тредами → ресайз S3 на `wrap` → закрытие diff. Каждая фаза снимается около 1 с с частотой около 200 выборок в секунду.
- Вердикт — максимум по фазам до закрытия не больше 150 000 000 байт.
- Оценка `≈` данных модели пишется отдельной строкой и с измеренным итогом не складывается: ёмкость буферов blob и текста diff, индекса высот, кэша раскладки и строк показа по фактической `capacity`. Память деревьев tree-sitter оценивается, только если есть способ её измерить, например подсчёт выделений распределителем пробы. `size_of::<Tree>()` за оценку дерева не выдаётся.

**Клавиши, бюджет 16 мс.** Как в P0.2: p95 «postEvent → конец `drawRect:` нужного поколения» по 100 событиям после 10 прогревочных. События: `j`, `k`, `Ctrl-d`, `]c`, `G`, `gg`. Вердикт на 120 Гц, на 60 Гц наблюдение.

**CPU в простое, бюджет 1%.** Как в P0.2: 10 с неподвижного видимого diff `modified` после окончания подсветки. Вердикт — не больше 1%.

### Контракт корректности

Обязательные проверки обоих вариантов в обоих режимах. Каждая — стимул, оракул и сырой артефакт.

- **Якорь.** Адрес строки под верхним краем и её смещение в пикселях сохраняются:
  - при смене ширины, когда меняется перенос;
  - при раскрытии и свёртке треда выше якоря;
  - при смене unified на «Рядом» и обратно, в пределах строки, которая есть в обоих режимах.

  `G`, `gg`, `]c` и `[c` меняют верхнюю строку по смыслу команды: проверяется, что достигнут ожидаемый адрес, а после возврата — прежний. Оракул — адрес и смещение из модели против прямоугольника строки, который вид отдал при отрисовке. Допуск — 0 строк и не больше 1 точки.
- **Выделение.** `v` с движением `j` и `k`, протяжка мышью и `Shift`-щелчок дают диапазон адресов одной стороны. В «Рядом» щелчок по половине задаёт сторону и строку. Выделение переживает перенос, раскрытие треда и уход строк за экран.
- **Треды.** `c` на строке или диапазоне открывает черновик в одном переиспользуемом поле. `Cmd-Enter` сохраняет его в модель. Блок треда стоит после последней строки якоря, у диапазона через границу ханка — после последней строки диапазона. Число созданных полей черновика за 100 циклов открытия и закрытия — 1.
- **Пары «Рядом».** У каждой строки показа старая и новая половины из одной пары модели. Номера строк в гуттере совпадают с адресами. Строка слева, перенесённая на 3 строки, и строка справа на 1 строку занимают одну высоту.
- **Доступность.** Внешний клиент читает видимые строки: роль, текст, номер старой и новой строки, признак добавления или удаления, выбранность. Проверяется после прокрутки за пределы первого экрана и после переиспользования видов (B) или кэша раскладки (A). Элемент строки не указывает на другую строку после прокрутки. Фокус доступности следует за выделением. Озвучивание VoiceOver автоматикой не наблюдается и получает `not_run` «VoiceOver не наблюдается».
- **Ограниченность работы.** Число видов строк (B) не больше `2 × видимых + 10`. Записей кэша раскладки (A) не больше чем на 3 экрана. Ни одна раскладка Core Text не строится для строки дальше 2 экранов от видимой области. Счётчики объектов после 10-го и 100-го цикла открытия и закрытия совпадают.

### Зоны и геометрия

У пробы нет плагина и адаптера раскладки. Адаптация проверяется функцией `adapt(Geometry) -> DiffLayout` модели и сценой с хостом заданного размера.

- Пороги пробы — параметры, а не решения. Они записываются в отчёт и передаются P1.4 и P3.2:
  - `ShortBar` — высота меньше 240 точек;
  - `Narrow` — ширина меньше 480 точек;
  - `Wide` — ширина от 1 100 точек;
  - `Regular` — остальное;
  - `min_size` — 200 × 120 точек. Боковая часть шириной 236 точек (ширина левой зоны по умолчанию в ADR-0024, нижняя граница боковых ширин в ADR-0031) остаётся выше порога и показывает unified diff, а не заглушку.
- «Рядом» включается, если ширины самого diff хватает на две стороны: `2 × (гуттер + 60 символов) + разделитель`. Иначе показывается unified, даже если запрошено «Рядом».
- Приоритет правил:
  1. ниже `min_size` — заглушка «Развернуть» без отрисовки строк;
  2. политика зоны: левая и правая зоны всегда unified (`AGENTS.md`, «Адаптация к зонам»), при любой ширине;
  3. центр и нижняя зона: «Рядом», если класс `Wide` или `Regular` и ширины хватает на две стороны, иначе unified;
  4. `ShortBar` — гуттер сокращён до одной колонки номеров, режим по пункту 3.
- Отдельные тесты: широкая боковая часть (unified, несмотря на ширину) и короткая широкая часть центра (`ShortBar` с «Рядом»).
- `adapt` разбирает `Zone` исчерпывающим `match` без `_`.
- Сценарий `zones` проходит фикстуры геометрии всех четырёх зон и классов и границу `min_size`. Он проверяет режим, заглушку, сохранение якоря при смене класса и доступность клавиш.

### Правила выбора

- **Вариант для P3.2.**
  1. Вариант проходит, если выполнены все обязательные бюджеты (открытие, кадры, память, клавиши, CPU) и весь контракт корректности в обоих режимах. Бюджет с вердиктом `not_run` вариант не роняет, но выбор с ним помечается «не подтверждено по <бюджету>».
  2. Если проходит один вариант, выбирается он.
  3. Если проходят оба, сначала предпочитается вариант с подтверждёнными кадрами перед вариантом с `not_run` по кадрам. Затем выбирается вариант с меньшим числом непустых строк модулей вида (`view_a` или `view_b`, по `cost.sh`). При точном равенстве — A. Блоки `unsafe` и обходы AppKit записываются отдельными фактами и в выбор не входят.
  4. Если ни один не проходит из-за измеренного превышения бюджета, итог по ADR-0002 — отрицательный вывод «`DiffView` на `objc2` не укладывается в бюджеты», вопрос о Swift-оболочке передаётся владельцу к следующему планированию. Если оба варианта проваливают бюджет в общей фазе (разбор, модель, подсветка — по промежуточным отметкам открытия), вывод это называет: смена языка UI эту причину сама не устраняет.
  5. Если ни один не проходит только по контракту корректности (например, доступности), вывод — «контракт <часть> не пройден» с передачей P3.2. Формулировка «превышен бюджет» и условие пересмотра ADR-0002 применяются только к измеренному превышению.
  6. Выбор и основания записываются в отчёт и ADR-0002 как «решение исполнителя по правилу плана».
- **Способ замера кадров.**
  1. По умолчанию — `xctrace` с шаблоном Animation Hitches, если калибровка проходит (задача 6). В `displayed-surfaces-interval` нет колонки PID, есть `surface-id` и `event-label`, а IOSurface переиспользуется, поэтому калибровка обязана доказать, какие строки выгрузки относятся к окну пробы.
  2. Если калибровка `xctrace` не прошла, используется ScreenCaptureKit: поток окна пробы с `SCStreamFrameInfo.displayTime`, вид рисует номер поколения маркером в углу, потеря — vsync без нового маркера при движущемся содержимом. Путь годится, если проходит ту же калибровку и наблюдатель сам не теряет кадры.
  3. Если не прошёл ни один, вердикт по кадрам — `not_run` с причиной. Итог по ADR-0002 — «не подтверждено по кадрам» с передачей P3.2.
- **Предварительная подсветка.** Окно локального разбора — 200 строк выше и 200 строк ниже видимой области. Размер окна записан до прогона и после результатов не меняется. Совпадение с эталоном проверяется по каждой видимой строке.
- **Сроки и размеры.** Сроки сторожа, ожиданий отрисовки и записи трассы записываются в отчёт до первого прогона. После результатов они не меняются, кроме ошибки исполнения стенда, которая записывается с ⚠️.
