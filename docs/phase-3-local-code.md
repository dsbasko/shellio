# Фаза 3. Код локально

Обзор фазы: что в ней реализуется, что система даёт по её итогу и что входит в каждый шаг. Состав и порядок шагов задаёт [дорожная карта](roadmap.md), решения — [ADR](adr/README.md), поведение — [ux.md](ux.md). Статусы приведены на 2026-11-24, актуальный статус шага — колонка «Готов» дорожной карты.

Детальных планов шагов фазы ещё нет. Состав ниже собран из дорожной карты, ADR, `ux.md`, отчёта пробы P0.6 и передач выполненных шагов. Он уточняется при планировании каждого шага ([ADR-0036](adr/0036-autonomous-execution.md)).

## Цель фазы

Работа с кодом без выхода из приложения и без сети: незакоммиченные изменения и их diff, выбор файлов, ханков и строк, commit с сообщением от агента, история коммитов в духе GitLens и управляемый nvim, в который ведут переходы из всех панелей. Агенты из фазы 2 меняют код, эта фаза позволяет увидеть и принять результат.

Отдельного критерия выхода у фазы в дорожной карте нет: она закрыта, когда закрыты её девять шагов.

## Что получаем по итогу фазы

### Для пользователя

- **«Изменения».** Весь index рабочей копии, включая добавленное агентом или из терминала, итоговый diff и сообщение коммита видны одновременно. Галочка на файле, ханке или строке сразу меняет настоящий index. Commit части файла забирает только выбранные строки ([ADR-0014](adr/0014-git.md)).
- **Сообщение коммита от агента.** `a` запускает одноразовую отменяемую задачу по diff index с настраиваемым prompt. Ручной текст не перезаписывается, при изменении index результат помечается устаревшим.
- **«История».** Граф коммитов рабочей области с ветками и тегами, сведения и файлы коммита, diff файла, история файла с учётом переименований, история строки или выделения, сравнение двух ревизий. Панель одна на рабочую область и только читает репозиторий ([ADR-0033](adr/0033-git-history-panel.md)).
- **Diff одного вида везде.** Один компонент `DiffView` в «Изменениях», «Истории» и позже в ревью: подсветка, unified и side-by-side, выделение строк мышью и клавиатурой, копирование без номеров строк.
- **nvim по необходимости.** `gf` на строке diff открывает файл в nvim рабочей области на нужной строке. Экземпляр один на область, запускается при первом переходе, вкладка называется `nvim` ([ADR-0029](adr/0029-single-nvim-per-workbench.md)).
- **Конфигурация nvim от shellio.** Управляемый nvim работает на поставляемой конфигурации: лидер `Space` и `Ctrl-w` продолжают схему shellio, действия приложения вызываются из Normal-режима без `Ctrl-\`. Для языков владельца настроены LSP, форматирование, линтеры, отладчик и запуск тестов, весь комплект приезжает вместе с приложением и работает без сети. `~/.config/nvim` не читается и не меняется ([ADR-0038](adr/0038-shipped-nvim-config.md)).
- **Рабочая область в новом worktree.** При создании области опция «в новом worktree» переключается одной клавишей, ветка берётся из имени (поток 3).

### Управление из CLI

Каждое действие панелей получает команду шины и CLI по правилу [ADR-0007](adr/0007-control-api.md). В решениях уже названы:

- `shellioctl history open [--file <путь>[:<начало>-<конец>]] [--rev <sha>]` и `shellioctl history read` — вид панели в JSON: режим, фильтр, выбранный коммит и файл ([ADR-0033](adr/0033-git-history-panel.md));
- `shellioctl editor open <файл>[:<строка>]` ([ADR-0029](adr/0029-single-nvim-per-workbench.md));
- `shellioctl panel focus --dir h|j|k|l`, которым Lua-плагин nvim переводит фокус на границе окна nvim, — команда уже есть с P1.4.

Имена команд «Изменений» и генерации сообщения определяют планы P3.3 и P3.4.

По [архитектуре](architecture.md): crate `shellio-git` (runner, парсеры, частичная индексация, раскладка графа), `shellio-nvim` (RPC), компонент `DiffView` и ячейка графа в `shellio-appkit`, плагины `changes`, `history` и `editor`. По [ADR-0038](adr/0038-shipped-nvim-config.md): Lua-конфигурация управляемого nvim, её каталог определяет план P3.7.

## P3.1 `repository-service` — служба репозиториев

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | Фаза 1 |
| Готово, когда | Две связанные worktree с независимыми HEAD и index работают одновременно |
| Решения | [ADR-0014](adr/0014-git.md), [ADR-0020](adr/0020-concurrency.md), [ADR-0001](adr/0001-vocabulary.md), [ADR-0011](adr/0011-resource-accounting.md) |

### Зачем этот шаг

Все панели фазы читают один и тот же репозиторий. Если каждая будет сама запускать `git` и следить за файлами, получатся лишние процессы, расхождения и блокировки главного потока. Шаг даёт одну службу, от которой панели получают данные и события.

### Что входит

- **Runner.** Git вызывается как внешняя команда `git` с таймаутами, отменой и лимитом вывода. Форматы машинные: `status --porcelain=v2`, `log` со своим форматом. Так работают хуки, credential helpers, конфигурация пользователя и нестандартные пути.
- **`RepositoryService`** общий, но статус, diff, кэш index и очередь его изменений имеют ключ `WorktreeId`. Подписки адресуют конкретный worktree. На уровне репозитория кэшируются только общие объекты и refs.
- **Watcher** следит за изменениями и сбрасывает кэш. Панели собственные опросы не запускают.
- **Отмена длинных операций.** Длинная операция получает идентификатор и токен отмены: закрытие вида отменяет только работу, привязанную к виду. Эта часть [ADR-0020](adr/0020-concurrency.md) отложена до P3.1 ещё в P1.1. Результат устаревшего запроса отбрасывается по ревизии или идентификатору.
- **Вне главного потока.** Git и файловые операции идут через `spawn_blocking`, данные приходят пакетами на кадр.
- **Рабочая область в новом worktree.** Создание области с опцией «в новом worktree», ветка берётся из имени.
- **Большие и бинарные файлы:** runner ограничивает объём вывода, состояние binary показывается явно ([ADR-0014](adr/0014-git.md)).
- **Учёт ресурсов.** Общая работа репозитория относится к служебной группе «Git», а не к первой запросившей панели. Дочерние `git`-процессы учитываются один раз ([ADR-0011](adr/0011-resource-accounting.md)).

### Что получаем в результате

- Две рабочие области на двух worktree одного репозитория видят разные `HEAD` и index и не мешают друг другу. Области одного каталога видят одно состояние.
- Git-операция всегда адресует конкретный репозиторий и worktree, рабочая область хранит активный из них ([ADR-0001](adr/0001-vocabulary.md)).
- Поток 3 получает опцию «в новом worktree».
- Панели фазы строятся на готовых событиях службы.

### Что шаг наследует

- **Чтение из git в бюджете открытия diff.** Проба P0.6 начинала открытие с сырых байт в памяти. Чтение diff и blob из git в её бюджет не входило: у фикстуры `real` оно заняло 450,0 мс на 51 вызов `git`. Цена чтения — работа этого шага ([отчёт P0.6](probes/p0.6-diff-view.md), раздел «Гипотезы и остаток»).
- Зависимость от установленного `git`. Для массовых операций нужна осторожность с числом процессов. Gitoxide допускается точечно для тяжёлого чтения по замерам ([ADR-0014](adr/0014-git.md)).
- Проверка идёт на настоящем `git` во временных репозиториях ([ADR-0021](adr/0021-testing.md)).

### Границы

- Интерфейса у шага нет: первые панели — P3.3 и P3.5.
- Изменение index и commit — P3.3.
- Запрещены `git commit -- <path>` и ручное удержание `index.lock`.

## P3.2 `diff-view` — компонент diff

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P0.6, P3.1 |
| Готово, когда | Бюджеты выполняются |
| Решения | [ADR-0002](adr/0002-ui-stack-appkit.md), [ADR-0014](adr/0014-git.md), [ADR-0015](adr/0015-forge-review.md) |

### Зачем этот шаг

`DiffView` — самый дорогой собственный компонент интерфейса и общая основа «Изменений», «Истории» и ревью. Проба P0.6 дала отрицательный вывод по бюджетам, поэтому шаг начинается не с кода, а с решения владельца.

### Что входит

- **Продуктовый `DiffView`** в `shellio-appkit`: виртуальная прокрутка, подсветка, режимы unified и side-by-side, выделение строк и диапазонов. Inline-треды и блок черновика проверены пробой и понадобятся ревью фазы 4.
- **Режим «Рядом»** включается только там, где ширины самого diff хватает на обе стороны, иначе показывается одна колонка. Длинные строки в нём переносятся, обе стороны остаются рядом.
- **Адаптация к зонам:** в боковой зоне unified, в центре side-by-side, внизу diff рядом со списком.
- **Копирование.** Код выделяется мышью и копируется обычным `Cmd-C` без номеров строк и элементов управления (принцип 14 [ux.md](ux.md)).
- **Собственная доступность:** элементы строк по адресу, как в пробе.
- **Контракт корректности пробы** — `ax`, `anchor`, `selection`, `threads`, `pairs`, `bounded` — переносится в проверки продукта.
- **Бюджеты** [архитектуры](architecture.md): первый экран diff на 100 тыс. строк до 200 мс, прокрутка без потери кадров при 120 Гц, память GUI.

### Что получаем в результате

- Один компонент diff, который переиспользуют три панели и ревью. Правило «один элемент управления переиспользуется, а не создаётся заново» выполняется для самого сложного вида.
- Измеренное соответствие бюджетам — или записанное решение об их изменении.

### Что шаг наследует

Итог [P0.6](probes/p0.6-diff-view.md) по [ADR-0002](adr/0002-ui-stack-appkit.md) отрицательный: `DiffView` на `objc2` в бюджеты не уложился ни в варианте A на собственном `NSView` с Core Text, ни в варианте B на `NSTableView`.

- **Открытие в глубине файла:** 231,1–245,3 мс на последнем ханке при пороге 200 мс. Экран ждёт полного разбора стороны.
- **Память:** пик 1,32–1,33 ГБ при бюджете 150 МБ, уже при открытии добавленного файла 296–406 МБ. Живые выделения деревьев tree-sitter — от ≈212 до ≈1 287 МБ.
- Оба превышения лежат в общей фазе подсветки tree-sitter, одинаковой у A и B. Части, зависящие от вида, укладываются: первый текст до 38,1 мс, реакция на клавишу p95 до 7,67 мс на 120 Гц, CPU в простое до 0,033%.
- **Кадры не подтверждены:** калибровка показанного кадра не прошла ни у `xctrace`, ни у ScreenCaptureKit.
- **Вариант по правилу плана не выбран.** Справочно: если решение ADR-0002 остаётся, шаг начинает с варианта A.

Вопрос владельцу по условию пересмотра ADR-0002 открыт до планирования шага. Варианты из отчёта:

1. ADR-0002 и бюджеты остаются. Шаг снижает цену подсветки: открытие в глубине файла без ожидания полного разбора и ограниченная память деревьев для больших файлов. Проба эти способы не проверяла.
2. Уточнить бюджеты: считать первым экраном кадр с предварительной подсветкой или записать, входит ли подсветка большого diff в 150 МБ GUI.
3. Вернуть вопрос о Swift-оболочке. Оба превышения лежат в разборе tree-sitter, который Swift-оболочка с Rust-ядром выполняла бы так же.

Остальные передачи пробы:

- Правило показа предварительного кадра и ожидания исправления подсветки; подсветка строк у края прокрутки без отставания на кадр.
- Способ наблюдать показанный кадр окна до вердикта по кадрам.
- Ключ элемента доступности — файл и адрес строки: в пробе удержанный элемент после смены файла становился строкой другого файла, а после смены раскладки менял индекс.
- Выделение через стороны diff (`start_side` из [ADR-0015](adr/0015-forge-review.md)), которого у модели пробы нет.
- Закрытие вида без ожидания рабочих потоков на главном потоке, освобождение деревьев вне него.
- Живой ресайз diff с переносом строк; разница памяти между вариантами в 110–134 МБ без найденной причины; возврат страниц после закрытия diff.
- Вариант на таблице держит точную прокрутку к якорю только через приватный API.
- Системные переключатели Increase Contrast в открытом окне и VoiceOver пробой не проверены.
- Пороги пробы: «Рядом» при ширине `2 × (гуттер + 60 символов) + разделитель`.

### Границы

- Чтение diff из git — P3.1. Изменение index — P3.3. Якоря и черновики ревью — P4.3 и P4.4.
- Код пробы не переносится как есть ([ADR-0034](adr/0034-probe-code.md)).

## P3.3 `changes-panel` — панель «Изменения»

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P3.2 |
| Готово, когда | Частичный commit проверен на реальном git |
| Решения | [ADR-0014](adr/0014-git.md) |

### Зачем этот шаг

Агенты и терминалы меняют рабочую копию и index. Панель показывает, что именно попадёт в коммит, и даёт собрать его с точностью до строки.

### Что входит

- **Плагин `changes`.** Открывается `Space g c`.
- **Выбор — это настоящий index.** Галочка на файле, ханке или строке меняет index немедленно. Частичная подготовка строит патч и применяет его через `git apply --cached`. Панель показывает весь index, включая то, что туда добавил агент или терминал.
- **Клавиши:** `j/k` — файлы, `x` — выбрать, `Enter` — diff, `v` — выделить строки, `x` — выбрать их, `A` — добавить в index все файлы, `U` — убрать все, `Cmd-Enter` — commit.
- **Последовательные изменения index.** Операции из приложения выполняются по очереди, короткими шагами. `index.lock` не удерживается.
- **Commit и amend** с ручным сообщением. Отдельные действия: выбрать → проверить итоговый diff → commit.
- **Ошибки хуков.** Сбой хука оставляет текст сообщения и выбор, вывод хука доступен.
- **Явные состояния:** «нет изменений», rename, binary, конфликт, detached HEAD.
- **Адаптация к зонам:** сбоку — список, diff раскрывается вглубь, unified; в центре — список и side-by-side; внизу — колонки с файлами и выбранным diff.

### Что получаем в результате

- Поток 6 без генерации сообщения: для всего файла — 4 действия. Index, итоговый diff и сообщение видны одновременно.
- Выбор файла держится за путь: постановка в index не переключает открытый diff.
- Commit части файла забирает только выбранные строки, остаток остаётся в рабочей копии.
- Области одного каталога worktree видят одно состояние, области разных каталогов — разное.

### Что шаг наследует

- **Граница гарантий.** Index общий с агентами и терминалом. Между проверкой и `git commit` кто-то может выполнить `git add`, и commit заберёт и это. Приложение снижает риск проверкой перед commit и сообщает о расхождении после него, но строгой гарантии не даёт и созданный commit не переписывает ([requirements.md](requirements.md), «Уточнения к требованиям»).
- Теневого index нет: агенты в том же worktree должны видеть тот же выбор.
- Проверка — на настоящем git во временных репозиториях.

### Границы

- Генерация сообщения — P3.4.
- Строка «Рабочая копия» над `HEAD` в «Истории» ведёт сюда, сама история — P3.5.
- Push, ветки и работа с remotes в состав шага дорожной картой не включены.

## P3.4 `ai-commit-message` — сообщение коммита от агента

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P3.3, P2.5 |
| Готово, когда | Поток 6 работает целиком, ручной текст не перезаписывается |
| Решения | [ADR-0014](adr/0014-git.md), [ADR-0012](adr/0012-agents.md) |

### Зачем этот шаг

Сообщение коммита — рутинная работа, которую удобно отдать агенту. При этом генерация не должна трогать идущие разговоры с агентами, менять index или затирать то, что пользователь написал сам.

### Что входит

- **Одноразовая отменяемая задача,** не касающаяся идущих диалогов: профиль с `claude -p`, `codex exec` или своей командой.
- **Настраиваемый prompt:** шаблон `~/.config/shellio/prompts/commit.md`. Вход — diff index.
- **Вывод потоком** в поле сообщения панели «Изменения». Клавиша — `a`.
- **Свежесть** определяется по репозиторию и worktree, `HEAD` и OID дерева index. При изменении дерева результат помечается устаревшим и предлагается повторить.
- **Ручной текст не перезаписывается.** Ручное изменение текста отменяет идущую генерацию, в коммит попадает показанный текст.
- **Генерация сама ничего не индексирует и не коммитит.** `index.lock` во время генерации не удерживается.

### Что получаем в результате

- Поток 6 целиком: выбрать, сгенерировать, закоммитить.
- Пограничный путь «Index изменился после генерации»: сообщение помечено устаревшим, показан новый diff, можно оставить текст или сгенерировать снова.
- Требование «AI commit message с настраиваемым prompt» из [requirements.md](requirements.md) закрыто.

### Что шаг наследует

- Профили команд берутся из настроек агентов P2.5: флаги по умолчанию задаются там же.
- Длинная операция отменяема и не блокирует главный поток: задача получает идентификатор и токен отмены из P3.1 ([ADR-0020](adr/0020-concurrency.md)).

### Границы

- Задача не отправляет сообщение работающему агенту и не использует канал сообщений P2.6.
- Автоматического коммита после генерации нет.

## P3.5 `git-history` — панель «История»

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P3.2 |
| Готово, когда | Поток 7 работает, второй экземпляр невозможен, граф из 100 тыс. коммитов укладывается в бюджет |
| Решения | [ADR-0033](adr/0033-git-history-panel.md), [ADR-0014](adr/0014-git.md), [ADR-0008](adr/0008-plugin-system.md) |

### Зачем этот шаг

Исходное требование называло git blame, но владелец уточнил, что имел в виду GitLens: историю коммитов, из которой открываются файлы коммита и их diff. Шаг даёт ответ на вопрос «почему эта строка такая» без выхода из рабочей области.

### Что входит

- **Плагин `history`, панель «История», `PerWorkbench`.** Повторное открытие переводит существующую панель на новый файл, строки или коммит, «Назад» возвращает прежний вид. Панель только читает репозиторий.
- **Граф коммитов:** линии ветвей и слияний, ветки, теги, `HEAD` и upstream текущей ветки. По умолчанию показаны все локальные ветки с их upstream, `b` оставляет только текущую.
- **Строка коммита:** линии графа, сообщение, ветки и теги, автор, относительная дата, короткий SHA.
- **«Рабочая копия»** над `HEAD` при незакоммиченных изменениях, `Enter` открывает «Изменения».
- **Поиск** `/` по сообщению, автору, SHA и пути. Совпадения идут списком без линий графа.
- **Коммит:** автор, дата, сообщение целиком, родители, ветки и теги; файлы со статусом A, M, D или R и числом строк; diff файла тем же `DiffView`. Diff слияния строится относительно первого родителя, корневой коммит сравнивается с пустым деревом.
- **История файла** с учётом переименований (`git log --follow`).
- **История строк** — коммиты, менявшие строку или диапазон, новые сверху (`git log -L`). Номера строк рабочей копии переводятся в номера `HEAD`. Строка, которой ещё нет в коммитах, показывает только «Рабочую копию» с пояснением.
- **Сравнение ревизий:** `c` на базе и `c` на цели. Сравниваются деревья базы и цели, а не изменения от общего предка.
- **Явные состояния:** пустой репозиторий, detached `HEAD`, неполная история после shallow clone, бинарный или слишком большой diff, отсутствующий объект.
- **Источник данных.** Граф — `git log` с `--topo-order` и `--parents`, ветки и теги — `git for-each-ref`. Коммиты приходят порциями по 500, следующая — при прокрутке. Раскладку линий считает чистая модель в `shellio-git` вне главного потока. Загрузка инкрементальная и отменяемая, кэш сбрасывает watcher P3.1.
- **Компонент графа.** Линии рисует ячейка `VirtualList` в `shellio-appkit` по готовой раскладке модели — новый элемент набора компонентов.
- **Команды и клавиши:** `history.open { path?, lines?, rev?, side? }`, `Space g l` — история области, `Space g h` — история файла, в панели `j/k`, `Enter` или `l`, `h` или `Ctrl-o`, `/`, `b`, `c`, `g f`.
- **CLI:** `shellioctl history open` и `shellioctl history read`.
- **Адаптация к зонам** по геометрии части: сбоку и в узкой части центра — граф в одну колонку, сведения и diff вглубь, unified; в широкой части центра — граф со всеми колонками и сведения справа; внизу — граф строками в ширину, файлы коммита рядом.

### Что получаем в результате

- Поток 7: `Space g l` — граф в 1 действие, diff файла выбранного коммита — ещё 2. История файла и сравнение ревизий.
- Выбор держится по SHA: после обновления refs и переноса панели курсор остаётся на том же коммите.
- Второй экземпляр панели в рабочей области открыть нельзя — это проверка кардинальности из P1.5 на продуктовой панели.
- Ветки, теги и родители доступны текстом: тон линий не единственный носитель смысла, VoiceOver читает строку целиком.

### Что шаг наследует

- **Бюджет графа.** Кадры и память проверяются на истории из 100 тыс. коммитов, большие репозитории ещё раз в P5.4.
- **Приёмка** идёт на настоящем git во временных репозиториях: слияние, корневой коммит, переименование и удаление, узкая часть и `ShortBar`, отмена загрузки, одна панель на рабочую область.
- Тексты нескольких ADR упоминают blame как прежний план. Действует ADR-0033.

### Границы

- `Space g L` берёт строку и выделение из nvim через RPC, поэтому история строк из nvim появляется в P3.6. До него она открывается из diff и командой `history.open` с `lines`.
- Открытие ревизии в nvim только для чтения — P3.6.
- Автор строки прямо в nvim и подписи над функциями владельцем отвергнуты.

## P3.6 `nvim-editor` — управляемый nvim

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P2.2, P3.2, P3.5 |
| Готово, когда | Потоки 7 и 10 работают из Normal- и Visual-режима nvim при запуске приложения из Finder, `~/.config/nvim` не читается |
| Решения | [ADR-0017](adr/0017-nvim.md), [ADR-0029](adr/0029-single-nvim-per-workbench.md), [ADR-0038](adr/0038-shipped-nvim-config.md), [ADR-0010](adr/0010-input-and-navigation.md), [ADR-0033](adr/0033-git-history-panel.md) |

### Зачем этот шаг

Редактор кода в shellio — это nvim, запущенный в терминальной панели на конфигурации shellio. Шаг связывает его с остальными панелями: из diff, истории, ревью и поиска можно перейти к файлу и вернуться обратно. Саму конфигурацию наполняют P3.7–P3.9.

### Что входит

- **Плагин `editor`** запускает `nvim --listen <socket>` в терминальной панели через ту же сессию, что и у терминала. nvim получает собственные каталоги конфигурации, данных, состояния и кэша: конфигурация пользователя не загружается, в каталоге конфигурации в этом шаге лежит только Lua-плагин интеграции ([ADR-0038](adr/0038-shipped-nvim-config.md)).
- **Каталоги nvim.** Шаг определяет механизм изоляции и раскладку: ресурсы только для чтения в бандле, записываемые данные, состояние и кэш, профиль теста. Обычный nvim, набранный в терминальной панели, по-прежнему читает свою конфигурацию.
- **`shellioctl` в бандле.** Lua-плагин вызывает его по абсолютному пути, от `PATH` вызов не зависит. Вызов не блокирует редактор. Команда в `PATH` и ссылка Homebrew остаются за P5.1 и P5.3.
- **Один управляемый nvim на рабочую область.** Он запускается в её worktree. nvim, набранный вручную в обычном терминале, не управляется и в лимит не входит. Вкладка называется `nvim`: файлы, буферы и вкладки показывает сам nvim.
- **Запуск по необходимости.** При открытии рабочей области nvim не запускается. Его запускают `Space e` (`editor.open`), переход к файлу из diff, истории, ревью, пайплайнов и поиска и `shellioctl editor open <файл>[:<строка>]`.
- **Владелец запуска.** Запуск принадлежит одному владельцу: он создаёт сессию или подключается к ней по стабильному `SessionId` рабочей области, в том числе после перезапуска GUI. Переходы, пришедшие во время запуска, ждут готовности RPC и второй процесс не создают.
- **`shellio-nvim`** — RPC по сокету: открыть файл на строке, получить текущую строку и выделение, число изменённых буферов.
- **Возврат к источнику:** привязка Lua-плагина из Normal-режима, клавишу выбирает план, либо `Ctrl-\`, затем `Ctrl-o`. Фокус и прокрутка возвращаются в исходную панель.
- **История файла, строки и выделения:** `Space g h` и `Space g L` из nvim без `Ctrl-\`. `Space g L` в Normal открывает историю текущей строки, в Visual — активного диапазона. Последнее выделение вместо текущей строки не подставляется.
- **Lua-плагин навигации.** Привязывает в Normal-режиме ровно действия потоков 7 и 10 через `shellioctl`: историю файла, историю строки и выделения, возврат к источнику. При достижении края окна nvim по `Ctrl-h/j/k/l` вызывает `shellioctl panel focus --dir …`, отчитывается о текущем файле. Клавиши — по умолчанию: остальную схему и следование `keymap.toml` добавляет P3.7.
- **Жизненный цикл:**
  - закрытие вкладки оставляет nvim и несохранённые буферы жить, сессия видна в «В фоне»;
  - выход из nvim с кодом 0 убирает вкладку, другой код оставляет состояние «Завершена» с действием «Запустить заново»;
  - остановка из shellio выполняет обычный выход nvim, который сам проверяет изменённые буферы; если nvim отказался выйти, остановка успешной не считается.
- **Нет связи с RPC при живом процессе:** «Нет связи с nvim, управление из shellio недоступно». Поверхность остаётся рабочей, действия — переподключиться, выйти в самом nvim, принудительно завершить с предупреждением. Второй экземпляр не запускается.
- **Историческая ревизия** открывается буфером только для чтения в том же nvim.
- **Нет `nvim`** — ошибка с действием, а не пустая панель.

### Что получаем в результате

- Поток 10: `gf` на строке diff открывает файл на нужной строке в 1 действие, обратно — 1 действие из Normal-режима nvim.
- Поток 7 из nvim: `Space g h` открывает историю текущего файла, `Space g L` — историю строки или выделения.
- В навигаторе и поиске рядом с сессией nvim может стоять текущий файл по отчёту Lua-плагина.
- Адаптация к зонам: полный nvim в центре и внизу при достаточной высоте, заглушка при малой ширине.

### Что шаг наследует

- В Insert-режиме и в `:terminal` клавиши принадлежат nvim, в Normal-режиме лидер `Space` и `Ctrl-w` продолжают схему shellio ([ADR-0038](adr/0038-shipped-nvim-config.md)). Аккорд выхода действует во всех режимах: `Ctrl-\` также префикс nvim, поэтому `<C-\><C-n>` набирается как `Ctrl-\ Ctrl-\ Ctrl-n` ([ADR-0010](adr/0010-input-and-navigation.md)). Под русской раскладкой этот аккорд в P0.3 дал `fail`, исправление передано P2.2.
- Под хостом пробы P0.4 nvim не включал протокол Kitty; порядок ответов на запросы терминала передан P2.1.
- shellio не меняет каталог живого nvim вслед за активным репозиторием области. Файл другого репозитория открывается по полному пути.
- Интеграция ограничена тем, что доступно по RPC.
- → из ADR-0038: приоритет клавиш между окнами nvim, клавишами редактора и shellio владелец обсуждает при планировании этого шага и P3.7. К обсуждению предложено: `Ctrl-w h/j/k/l` сразу меняет панель shellio, `Ctrl-h/j/k/l` сначала идёт в соседнее окно nvim и только на краю в shellio.
- → из ADR-0038: цель по задержке вызова shellio из nvim согласуется в плане до замера. Замер — от клавиши до видимой смены фокуса на подписанном приложении, отдельно первый вызов и p95 серии. `history.line` может в том же вызове запросить выделение обратно по RPC, поэтому синхронное ожидание в Lua недопустимо. Обратный канал RPC обсуждается только при измеренном превышении.
- → из ADR-0037: новые видимые состояния редактора сначала добавляются в прототип, `prototype/js/plugins/editor.js` Ctrl-сочетания пропускает и новой схемы не знает.
- Приёмка: запуск из Finder с минимальным `PATH`, два изолированных профиля, фактические `stdpath` и `runtimepath`, ловушка в подставной конфигурации пользователя; выделение нескольких строк снизу вверх открывает именно этот диапазон, после возврата история одной строки открывает одну строку.

### Границы

- `nvim --embed` со своей отрисовкой и собственный редактор отвергнуты.
- Переходы из ревью и пайплайнов начинают работать вместе со своими панелями в фазе 4.
- Схема клавиш сверх действий потоков 7 и 10, плагины, темы и языки — P3.7–P3.9.

## P3.7 `nvim-config` — поставляемая конфигурация nvim

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P1.6, P1.8, P3.6 |
| Готово, когда | Действия shellio из таблицы клавиш плана вызываются из Normal-режима nvim без `Ctrl-\`, переназначение в `keymap.toml` доходит до живого nvim, проверка конфигурации проходит без сети и без каталогов nvim пользователя |
| Решения | [ADR-0038](adr/0038-shipped-nvim-config.md), [ADR-0010](adr/0010-input-and-navigation.md), [ADR-0017](adr/0017-nvim.md), [ADR-0022](adr/0022-licensing-and-borrowing.md) |

### Зачем этот шаг

После P3.6 управляемый nvim запускается почти пустым: в его конфигурации только плагин интеграции. Шаг делает из него редактор для ежедневной работы и продолжает в нём схему клавиш shellio.

### Что входит

- **Плагины.** Закреплённые версии, плагины лежат в поставке приложения и не загружаются при первом запуске. Минимальная версия nvim проверяется при запуске редактора.
- **Схема клавиш.** Таблица клавиш Normal-режима: лидер-группы shellio через `shellioctl`, клавиши редактирования и навигации по коду вне этих групп, подсказка клавиш.
- **Следование keymap.** Схема nvim строится из действующего keymap shellio по разрешённой таблице P1.6 и меняется при правке `keymap.toml` без перезапуска nvim: старая привязка снимается, подсказка обновляется, при ошибке остаётся последняя исправная карта.
- **Темы.** Светлая и тёмная цветовые схемы, Increase Contrast, смена темы при живом nvim.
- **Путь ресурсов с версией.** Ресурсы редактора лежат по пути с версией, который на месте не изменяется: старый nvim после обновления догружает Lua своего поколения. Удержание поколения и его удаление — P5.2.
- **Проверка.** nvim без окна над изолированными каталогами, без сети.

### Что получаем в результате

- Одна схема клавиш в панелях shellio и в nvim: `Space` и `Ctrl-w` значат одно и то же.
- Конфигурация обновляется вместе с приложением.

### Что шаг наследует

- → из ADR-0038: приоритет клавиш между окнами nvim, клавишами редактора и shellio владелец обсуждает при планировании. Решить также, как темы nvim связаны с темой shellio, какой менеджер плагинов и какие плагины, что происходит при конфликте переназначенной клавиши с клавишей редактора или с сочетанием, которое терминал не различает.
- → из P3.6: каталоги nvim, `shellioctl` в бандле и привязки потоков 7 и 10 уже есть, шаг их не дублирует.
- → из ADR-0037: состояния поверхности редактора и подсказки клавиш добавляются в прототип до построения вида. Тест темы без окна цвета в поверхности libghostty не подтверждает.
- Сценарий обновления N → N+1 с несохранённым буфером и живым nvim проверяет тот из шагов P3.7 и P5.2, который выполняется позже.
- Каждый плагин — новая зависимость и проверяется по [ADR-0022](adr/0022-licensing-and-borrowing.md). Шаг ведёт инвентаризацию того, что попадает в поставку, для `THIRD_PARTY_NOTICES`.

### Границы

- Языки — P3.8, отладчик и тесты — P3.9.
- Переключателя на конфигурацию пользователя нет ([ADR-0038](adr/0038-shipped-nvim-config.md)).

## P3.8 `nvim-languages` — языки в nvim

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P3.7 |
| Готово, когда | Образец проекта каждого языка проходит все клетки своей строки матрицы возможностей плана на чистой установке без сети |
| Решения | [ADR-0038](adr/0038-shipped-nvim-config.md), [ADR-0022](adr/0022-licensing-and-borrowing.md) |

### Зачем этот шаг

Владелец назвал языки, с которыми работает. Редактор без их серверов и форматтеров остаётся просмотрщиком.

### Что входит

- **Языки:** Go, Rust, JavaScript, TypeScript, Python, HTML, CSS, Markdown, Makefile, YAML, TOML, Bash, C — подсветка и текстовые объекты tree-sitter, LSP, форматирование и линтеры. Swift и Objective-C владелец исключил.
- **Запросы PostgreSQL и MongoDB:** подсветка, автодополнение и форматирование в файлах, без подключений к базам. План фиксирует диалект или формат файла и содержательный пример дополнения без сети.
- **Матрица возможностей:** клетка на каждую обещанную возможность каждого языка — подсветка, текстовые объекты, диагностика, переход к определению, форматирование, линтер, для запросов автодополнение — с инструментом, ожидаемым эффектом и сырым свидетельством. Обязательная клетка с `fail` или `not_run` оставляет шаг открытым.
- **Парсеры tree-sitter:** закреплённые ревизии грамматик, совместимый ABI, запросы подсветки и текстовых объектов, собранные под arm64 парсеры в поставке.
- **Комплект инструментов в поставке.** Серверы LSP, форматтеры и линтеры с закреплёнными версиями приезжают при установке приложения, загрузки при первом запуске нет. Для каждого инструмента план называет источник, версию, проверку идентичности и поведение при отсутствии.
- **Образцы проектов** для проверки каждого языка.

### Что получаем в результате

- Файл любого из названных языков открывается с диагностикой, переходами и форматированием в пределах матрицы.

### Что шаг наследует

- → из ADR-0038: решить, что делать с инструментами, которым нужна внешняя среда исполнения — вложить её в комплект, выбрать инструмент без неё или потребовать от системы, — и какой размер бандла допустим.
- Проверка не ходит в сеть. Чистая установка с пустым кэшем и установка поверх наполненного кэша проверяются раздельно.
- Вложенные грамматики, запросы и бинарники входят в инвентаризацию лицензий по [ADR-0022](adr/0022-licensing-and-borrowing.md) и в `THIRD_PARTY_NOTICES`.
- Парсеры и инструменты лежат по тому же пути с версией, что и ресурсы P3.7: файл нового типа, впервые открытый в старом nvim после обновления, получает парсер и инструменты своего поколения. Удержание и удаление — P5.2.
- Первая задача шага проводит один язык до конца — вложен в бандл, подписан, работает без сети на чистой установке — и только потом состав тиражируется на остальные.
- → из ADR-0038: решить подпись сторонних исполняемых файлов внутри бандла и их проверку в `check-bundle.sh`, допустимость отдельного инструмента под GPL в поставке (спорный случай — владельцу), соответствие собранных парсеров версии nvim.

### Границы

- Клиента баз данных с подключениями нет ([ADR-0038](adr/0038-shipped-nvim-config.md)).
- Отладчик и запуск тестов — P3.9.

## P3.9 `nvim-debug-test` — отладка и тесты в nvim

| | |
| --- | --- |
| Статус | ⬜ не начат |
| Зависит от | P3.8 |
| Готово, когда | Образец проекта каждого языка проходит все клетки своей строки матрицы возможностей плана: отладка и тесты |
| Решения | [ADR-0038](adr/0038-shipped-nvim-config.md), [ADR-0022](adr/0022-licensing-and-borrowing.md) |

### Зачем этот шаг

Владелец выбрал глубину поддержки с отладчиком и запуском тестов из редактора.

### Что входит

- **Языки:** Go, Rust, JavaScript, TypeScript, Python, C.
- **Отладчик:** точки останова, шаги, стек, переменные. Какие отладчики приезжают в поставке, задаёт матрица плана: сначала проверяется, может ли вложенный и переподписанный отладчик подключаться к процессу на macOS без системных инструментов разработчика.
- **Тесты:** запуск ближайшего теста, файла и набора, результат в редакторе.
- **Матрица возможностей:** шесть строк по языкам, клетки — остановка, шаг, стек, значение переменной, запуск ближайшего теста, файла и набора, видимый результат успешного и упавшего теста. В образце несколько тестов, чтобы было видно, какой запуск состоялся.
- **Клавиши** отладки и тестов в схеме P3.7.

### Что получаем в результате

- Цикл «правка, тест, отладка» проходит в nvim без перехода в терминал.

### Что шаг наследует

- → из P3.8: образцы проектов и способ установки инструментов.

### Границы

- Отладка и тесты языков вне списка не входят.
