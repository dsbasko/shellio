# Архитектура shellio

shellio — нативный для macOS хаб разработчика на Rust: воркспейсы, проекты, рабочие области с терминалами, агентами, git, ревью и nvim. Решения и их причины описаны в [docs/adr](adr/README.md). Термины определены в [ADR-0001](adr/0001-vocabulary.md).

## Стек

| Часть | Выбор | ADR |
| --- | --- | --- |
| Язык собственного кода | Rust 2024 | 0002 |
| Интерфейс | AppKit через `objc2`, непрозрачные поверхности | 0002, 0023 |
| Терминал | Полный libghostty, закреплённая ревизия | 0003 |
| Постоянство сессий | Отдельный хост на сессию | 0004, 0005 |
| Асинхронность | Главный поток AppKit, актор состояния, runtime `tokio`, рабочий пул | 0020 |
| Хранение | SQLite, TOML, Keychain | 0018 |
| Git | Внешний `git` | 0014 |
| Редактор | Один `nvim --listen` на рабочую область, по необходимости, на поставляемой конфигурации shellio | 0017, 0029, 0038 |
| Поставка | Самоподписанная идентичность, minisign, Homebrew tap | 0019 |

Платформа: macOS 27, Apple Silicon.

## Единственный экземпляр

На профиль (`SHELLIO_STATE_DIR`) приходится ровно один владелец: процесс, взявший неблокирующий `flock` на `<state>/shellio.lock` ([ADR-0006](adr/0006-single-instance.md)). Главный поток сразу запускает `NSApplication` с политикой `.accessory` (бандл объявляет `LSUIElement`): без иконки в Dock, но с правом стать активным. Роль выбирает фоновая задача.

```text
запуск shellio
  ├─ flock взят → владелец: обработчики сигналов → .regular и окно → state.db → ядро → готовность главного потока
  │                → публикация <state>/shellio.sock → сервер управления → первый снимок зеркала
  │                → обработка своих аргументов: показ окна и активация
  └─ flock занят → второй запуск (.accessory, без Dock), срок 10 с:
       connect shellio.sock ─ нет сокета или отказ → ждать и снова пробовать flock
       hello ─ владелец уходит → ждать и повторить
       передача активации PID владельца, срок 1 с: служебное окно → передний план себе
         → нет своей активности за 500 мс → LaunchServices открывает бандл владельца
         → yieldActivationToApplication и activateFromApplication_options владельцу
       launch {args, cwd} → квитанция в stdout, выход 0
                           ↓
       владелец: разбор аргументов → активация на главном потоке → квитанция
```

Отказы аргументов приходят в квитанции: папка до P1.7 получает `folder_open_unsupported`. Срок до отправки `launch` даёт код 75, срок или обрыв после неё — 74 «исход неизвестен». Передний план второй запуск получает только для передачи владельцу: при `open -n` и прямом запуске из терминала он переходит на владельца ([план доводки активации](plans/completed/20261122-single-instance-activation.md)). Исход передачи второй запуск печатает строкой в stderr, истёкший срок передачи `launch` не отменяет. Без собственной активности за 500 мс второй запуск печатает об этом строку и просит LaunchServices открыть бандл владельца: LaunchServices адресует бандл, а не PID, и при нескольких профилях может вывести другого владельца ([ADR-0006](adr/0006-single-instance.md), «Ограничения»). Служебное окно второго запуска — без рамки, за пределами всех экранов — живёт до конца передачи. Заменить его окном владельца в P1.3 не удалось: без служебного окна второй запуск не становится активным, и `two-owners-front` дал `fail`. Окно сохранено до нового ADR ([ADR-0006](adr/0006-single-instance.md), «Уточнено в P1.3»).

`shellioctl` подключается к тому же сокету, а состояние без сокета различает пробой `flock`: файла нет или блокировка свободна — `not_running`, занята без сокета — `owner_starting`. Протокол и коды — в [ADR-0007](adr/0007-control-api.md).

Сейчас в репозитории есть `apps/shellio`, `apps/shellioctl`, `crates/shellio-core`, `shellio-store`, `shellio-control`, `shellio-layout`, `shellio-theme`, `shellio-plugin-api`, `shellio-plugin-view`, `shellio-appkit`, `shellio-e2e`, `shellio-conformance`, `shellio-sys-ghostty` и `shellio-ghostty`, а также плагины `plugins/navigator`, `plugins/terminal`, `plugins/demo-list` и `plugins/demo-native`. Остальные части появляются в своих шагах [дорожной карты](roadmap.md).

- `shellio-appkit` с P1.3 содержит `NSApplication`, активацию и завершение через AppKit, безопасный слой над objc2 и компоненты. Слой — это владелец вида, который отвязывает источник данных, делегат и цели до освобождения, слабые обратные вызовы со счётчиком поздних вызовов, подписки на уведомления и счётчики экземпляров каждого класса. На нём построены главное окно, главное меню, `ChromeBar`, примитив `Surface`, `TabStrip`, `VirtualList`, `TreeList`, `TextField`, `Menu`, наблюдатель ячейки оформления, маркер поколения галереи и монитор цикла главного потока. Типы objc2 из crate не выходят ([ADR-0002](adr/0002-ui-stack-appkit.md), «Уточнено в P1.3»).
- `shellio-layout` с P1.4 — чистая модель раскладки без зависимостей, кроме `serde`: зоны, части, операции, геометрия, классы размера, цель перетаскивания и обвязка контрактного теста геометрии. Модель обобщена по ключу панели, метрики получает своим типом `LayoutMetrics`, от `shellio-core` и `shellio-theme` не зависит. `shellio-core` хранит раскладку в `State` как `Layout<PanelId>` и с P1.4 зависит от `shellio-theme`: `LayoutMetrics` ядра и адаптера строит одна функция `shellio_core::layout_metrics()` ([ADR-0009](adr/0009-layout-and-zones.md)).
- `shellio-plugin-api` с P1.5 — чистый контракт плагинов: `PluginId`, манифест, кардинальность, представление, типаж модели `PanelModel` со стёртой обёрткой `DynModel`, реестр `Registry` с проверками и проверка представления поверх `shellio_layout::contract`. Он зависит только от `serde`, `serde_json` и `shellio-layout`. `shellio-core` зависит от него и получает реестр в `Core::start`: по нему ядро выполняет `panel.open` и `panel.command`, считает статус панели и берёт `min_size` ([ADR-0008](adr/0008-plugin-system.md), «Уточнено в P1.5»).
- `shellio-plugin-view` с P1.5 — контракт вида: фабрика `ViewFactory`, вид `PluginView`, отправитель запросов `PanelSink`, токены работы вида `ViewWork`, владелец тела `Body` и нейтральная карточка заполнителей. Он зависит от `shellio-plugin-api`, `shellio-appkit` и `shellio-theme`, от ядра и `shellio-control` не зависит. `shellio-appkit` о плагинах не знает.
- `plugins/<id>` — один crate на плагин (пакет `plugin-<id>`) с модулями `model` и `view`. `plugins/navigator` и `plugins/terminal` — заполнители с нейтральной карточкой до P1.7 и P2.2, `plugins/demo-list` и `plugins/demo-native` — демонстрационные плагины приёмки хоста. Список регистраций — `apps/shellio/src/plugins.rs`: из него строятся реестр ядра и таблица фабрик главного потока, ровно одна фабрика на id.
- `shellio-theme` — чистая тема `AppTheme` без AppKit: слоты цвета, метрики и ячейки (светлота, Increase Contrast, движение). Значения сверены тестом с `prototype/css/tokens.css` и таблицей [ADR-0027](adr/0027-focused-panel-contrast.md), метрики для `adapt` плагины берут отсюда.
- `shellio-e2e` — чистый оракул снимков `make e2e`: сам разбирает `tokens.css` и таблицу ADR-0027 и от `shellio-theme` не зависит, поэтому ожидания не берутся из токенов, которыми рисует приложение ([ADR-0021](adr/0021-testing.md), «Уточнено в P1.3»). Подкоманда `conform` сверяет паспорт прототипа с чтениями `ui.inspect`, `ui.window` и снимком окна.
- `shellio-conformance` — сверка с прототипом ([ADR-0037](adr/0037-prototype-conformance.md)): чистая библиотека паспорта и его годности, реестра состояний, сцен, рецептов, инвентаря прототипа, таблицы ключей и контракта полей, без браузера и AppKit, и бинарь `shellio-snap`, который снимает паспорта через закреплённый `chrome-headless-shell` по CDP. От неё зависит оракул `shellio-e2e`, от `shellio-theme` и `shellio-appkit` она не зависит. Данные сверки лежат в каталоге `conformance/`.

## Правила зависимостей

1. `shellio-core` и остальные чистые crate не зависят от AppKit.
2. Модель плагина зависит от `shellio-plugin-api` и сервисных crate. Фабрика вида выполняется на главном потоке и дополнительно использует `shellio-plugin-view` и безопасные компоненты `shellio-appkit` и `shellio-ghostty`. Модуль `model` плагина не импортирует `shellio_plugin_view`, `shellio_appkit` и `objc2*`. Плагин не зависит от другого плагина, от `shellio-core` и от `apps/*`.
3. Конкретные плагины знает только `apps/shellio`.
4. `unsafe` Objective-C находится в `shellio-appkit` и `shellio-ghostty`. Исключение — пробы в `spikes/` ([ADR-0034](adr/0034-probe-code.md)): в них допустим `unsafe` Objective-C и системных C API, а продуктовые crate, плагины и `apps/*` от `spikes/` не зависят.
5. Плагины взаимодействуют только через команды шины.
6. `shellio-plugin-api`, `shellio-layout`, `shellio-core`, `shellio-store`, `shellio-control` и `shellio-theme` транзитивно не зависят от `shellio-appkit`, `shellio-plugin-view`, `objc2*` и плагинов, в том числе через необязательные зависимости.

Правила 1, 2 и 6 проверяют тесты `make check`: граф зависимостей по `cargo metadata` (`apps/shellio/tests/dependency_graph.rs`) и текстовый тест модулей модели (`apps/shellio/tests/model_imports.rs`).

## Поток данных

```text
клавиша, меню, палитра, CLI → Command → актор → запись state.db → новое состояние + Event(ревизия)
                                                                    ├─ главный поток: снимок и применение разницы
                                                                    ├─ подписчики CLI: журнал с курсором
                                                                    └─ плагины: подписки
```

У каждого действия один обработчик. Интерфейс не изменяет домен напрямую. Действия интерфейса, которые не меняют домен (`window.close`, `app.quit`, `ui.appearance.set`), — варианты `UiCommand` с одним обработчиком на главном потоке: меню, кнопка и `shellioctl` вызывают его, актор ядра их не видит ([ADR-0007](adr/0007-control-api.md), «Уточнено в P1.3 (планирование)»).

Обработчик по снимку состояния вычисляет список изменений. Тот же список пишется в `state.db`, применяется к состоянию актора и уходит событием. Ответ на команду, меняющую состояние, приходит только после записи, а отказ записи не меняет ни состояние, ни ревизию. Ревизия хранится в базе и растёт в одной транзакции с изменением, поэтому монотонна через перезапуски. Журнал событий живёт в памяти: курсор старше буфера или из прошлого запуска получает `Reset(Snapshot)`, то есть снимок с ревизией, от которой подписчик продолжает по событиям ([ADR-0020](adr/0020-concurrency.md), «Уточнено в P1.1»).

Главный поток держит зеркало состояния ядра. Задача владельца подписывается на ядро и доставляет снимок и события на главный поток, там `Mirror` применяет те же изменения по ревизиям, а при пропуске ревизии или `Reset` берёт новый снимок. Главный поток ядро не ждёт и файлы не читает. С P1.3 из зеркала строятся кнопка воркспейса в заголовке и системный заголовок окна ([ADR-0020](adr/0020-concurrency.md), «Уточнено в P1.3»).


Окно владельца создаётся после выбора роли: 1180×720 точек с тем же минимумом, `colorSpace` sRGB, заголовок `ChromeBar` высотой 40 точек ([ADR-0024](adr/0024-main-screen-design.md)). Закрытие окна прячет его, а владелец, сокет и ядро продолжают работать. Обычный запуск бандла и второй запуск показывают то же окно и выводят владельца вперёд. Выход идёт через `applicationShouldTerminate` и порядок завершения владельца ([ADR-0006](adr/0006-single-instance.md), «Уточнено в P1.3»). Режим `--gallery` на отдельном профиле показывает в том же окне галерею компонентов для `make e2e`. С P1.4 обычное окно показывает раскладку открытой рабочей области: колонку навигатора, плитки частей четырёх зон со строками вкладок и строку статуса ([ADR-0009](adr/0009-layout-and-zones.md), «Уточнено в P1.4»). Кадры считает чистая модель `shellio-layout` по раскладке из зеркала и размеру области содержимого. Адаптер в `apps/shellio` (`scene.rs` — сцена и разница, `layout_ui.rs` — применение к AppKit) ставит виды по этим кадрам, а размер окна передаёт ядру внутренним входом до публикации сокета и при каждом изменении.

Все поверхности непрозрачны, глубина задаётся тоном, линией и тенью ([ADR-0023](adr/0023-opaque-window-and-shell.md)). Тулбар отвечает на вопрос «где я и куда перейти», статус-бар на вопрос «что происходит». Заголовок панели — вкладка. Палитра, подсказки и другие наложения — отдельные плавающие панели поверх поверхностей libghostty, так как те являются `NSView` со своим Metal-слоем.

## Плагины

Контракт описан в [ADR-0008](adr/0008-plugin-system.md), зоны и адаптация — в [ADR-0009](adr/0009-layout-and-zones.md), поведение в каждой зоне — в [docs/ux.md](ux.md).

С P1.5 каждая панель окна показывает тело своего плагина. Данные панели — сериализуемое состояние модели: они лежат в `State` ядра и в `state.db` и приходят в зеркало обычными событиями. Модель — чистые функции над ними (`init`, `reopen`, `apply`, `migrate`, `adapt`), сама команд не шлёт. Действие из меню, вида или CLI становится командой ядра `panel.open` или `panel.command`: актор находит канонический экземпляр по кардинальности, зовёт модель и пишет панель, раскладку, данные и статус одной записью.

На главном потоке хост (`apps/shellio/src/bodies.rs` — чистая часть, `layout_ui.rs` — применение к AppKit) держит один контейнер на `PanelId`. Фабрика плагина строит в нём тело один раз, пока панель готова. Перенос, разворот, смена вкладки, заглушка и переезд между рабочими областями переставляют или прячут контейнер и тело не пересоздают. Сцена считает представление чистой `adapt` модели по снимку зеркала и передаёт телу данные, представление, активность и фокус только при изменении. Панель, вид которой показать нельзя (плагина нет, состояние новее или не читается, дубликат), показывает заглушку с причиной, байты её записи сохраняются.

## Подсистемы

Терминал: `shellio-ghostty` и `plugins/terminal` создают поверхность, `shellio-session` управляет хостом. Каждый агент — своя терминальная панель с адаптером и статусами ([ADR-0030](adr/0030-agent-panel-per-agent.md)). Зоны делятся на части по одной оси ([ADR-0031](adr/0031-zone-splits.md)).

Агенты: профиль запуска → адаптер → статусы через хуки → сообщения через `state.db` и механизм доставки агента.

Git: `shellio-git` выполняет команды, кэширует статус по `WorktreeId` и отдаёт события. Одна служба обслуживает все панели. Панели не запускают свои опросы.

Forge: `shellio-forge` — общая модель с адаптерами, журнал черновиков в `state.db`.

Ресурсы: один сэмплер, измеренная сводка процессов и отдельная оценка данных внутри приложения.
