# Фаза 0. Пробы

Обзор фазы: что в ней сделано, что проект получил по её итогу и что входило в каждый шаг. Состав и порядок шагов задаёт [дорожная карта](roadmap.md), решения — [ADR](adr/README.md), подробности каждого шага — отчёты в [probes/](probes/) и планы в [plans/completed/](plans/completed/). Статусы приведены на 2026-11-24, актуальный статус шага — колонка «Готов» дорожной карты.

Фаза выполнена: все восемь шагов закрыты. Разделы шагов ниже описывают фактический итог, включая отрицательные выводы и то, что не наблюдалось.

## Цель фазы

Подтвердить или изменить рискованные решения до основной разработки. Каждое из них могло обесценить месяцы работы: интерфейс на AppKit через `objc2` без готового набора компонентов, терминал на внутреннем API libghostty, сессии, переживающие интерфейс и обновление, собственный механизм обновления без Apple Developer ID, виртуальный diff, API ревью двух сервисов и учёт ресурсов по панелям.

Итог пробы — записанные замеры и обновлённые ADR, а не код продукта. Код проб P0.2–P0.8 лежит в `spikes/` и в продукт не переносится ([ADR-0034](adr/0034-probe-code.md)). P0.1 не проба: он создаёт сборочную базу, которая остаётся в продукте.

Отрицательный вывод цель пробы не роняет, роняет только ошибка исполнения. Поэтому шаг отмечен выполненным и тогда, когда проба ответила «нет» или «не наблюдалось»: такой ответ записан и передан шагу, который с ним работает.

### Зачем этот шаг

Это первый код репозитория: до него были только документы и прототип. Шаг не проба. Он создаёт продуктовую сборочную базу, от которой зависят все остальные планы ([roadmap.md](roadmap.md), фаза 0). Он снимает три риска сразу: воспроизводимость сборки внутреннего API libghostty, постоянство подписи без Apple Developer ID и единый рубеж проверки.

### Что входит

**Workspace и рубеж.** `rust-toolchain.toml` закрепляет Rust 1.99.1 с `rustfmt`, `clippy` и целью `aarch64-apple-darwin`. Workspace: `resolver = "3"`, edition 2024, `[workspace.lints]` с запретом `clippy::unwrap_used` и `clippy::expect_used`. Минимум macOS приложения — 27.0 через `.cargo/config.toml` с `force = true`, у libghostty остаётся собственный минимум upstream 13.0. `make check` выполняет `vendor.sh --verify`, `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings` и `cargo test --locked` ([ADR-0021](adr/0021-testing.md), «Уточнено в P0.1»).

**Набор ghostty.** `scripts/ghostty/`:

- `pin` — ревизия `83fb95624b0439ee660c2679b43b38c8b63769cd` (v1.4.0), версия `1.4.0`, Zig 0.17.1 с SHA-256 архива;
- `tools.sh` — Zig архивом точной версии, Metal toolchain, `bindgen-cli` 0.73.2;
- `build.sh` — загрузка ревизии, патч `0001-drain-mailbox-during-surface-teardown.patch`, сборка с флагами `-Doptimize=ReleaseFast -Demit-xcframework=true -Dxcframework-target=native -Demit-macos-app=false -Dsentry=false -Dversion-string=1.4.0`;
- `vendor.sh` — `--print-stamp`, `--verify` и `publish`;
- `lock.sh` — блокировка `vendor/ghostty.lock` через `lockf -k -t 0`;
- `link-libs` — единственный список линковки: архив `ghostty`, одиннадцать системных фреймворков (включая `GameController` для Dear ImGui), `c++` и `objc`;
- `bindings.sh`, `link-audit.sh`, `test-publish.sh`.

Штамп описывает входы сборки и вычисляется без сети до сборки. Манифест перечисляет SHA-256 каждого файла набора. Набор принимается, только если совпал штамп, все файлы манифеста на месте и лишних нет ([ADR-0003](adr/0003-terminal-libghostty.md), «Уточнено в P0.1»). Сборка идёт без Sentry: иначе `ghostty_init` создаёт базу в каталогах Ghostty, которых `SHELLIO_STATE_DIR` не касается.

**Привязки.** `shellio-sys-ghostty` линкует `libghostty.a` как `static:-bundle` и хранит сгенерированный `bindings.rs` в репозитории. В P0.1 в allowlist только `ghostty_info`. `shellio-ghostty` даёт одну безопасную функцию `info()` с режимом сборки и версией. `ghostty_init` не вызывается.

**Заглушка приложения.** `apps/shellio` проверяет раскладку бандла от пути исполняемого файла, вызывает `info()` и печатает одну строку JSON с ключами `app_version`, `ghostty_version`, `ghostty_build_mode`, `ghostty_resources`, `terminfo`. Каталог состояния не читается и не пишется.

**Подпись и бандл.** `scripts/signing/create-identity.sh` создаёт идентичность в трёх режимах (`--export`, `--from-p12`, `--finish`): ключ RSA 3072, сертификат на 20 лет, `.p12` с AES-256-CBC. `sign.sh` подписывает по SHA-1 из `requirement.txt`. `scripts/bundle.sh` раскладывает `target/bundle/shellio.app` с ресурсами `ghostty/`, `terminfo/` и `licenses/ghostty.txt`, `scripts/check-bundle.sh` проверяет подпись, requirement, раскладку, минимум 27.0 и зависимости только из `/System` и `/usr/lib`. Bundle ID — `io.github.dsbasko.shellio` ([ADR-0019](adr/0019-distribution-and-updates.md), «Уточнено в P0.1»).

**CI.** Один job на раннере `xcode-27`: `make ghostty`, `check`, `test-scripts`, `bindings-check`, `link-audit`, при заданных секретах — `bundle` и `check-bundle` из временной keychain. Кэши: архив Zig, кэш пакетов Zig и набор по SHA-256 штампа.

### Что получаем в результате

- Одна команда `make setup ghostty check` приводит чистую машину к проходящему рубежу.
- Подписанный пустой бандл: `make bundle`, `make check-bundle`, `make run`.
- Изменение любого входа сборки ghostty (патч, флаги, Zig, SDK) останавливает линковку до `make ghostty`. Прямой `cargo build` получает отказ в `build.rs` с подсказкой.
- Потоки [ux.md](ux.md) не затрагиваются: окна ещё нет.

### Фактический итог

- Набор: 831 файл, 144 МБ. В архиве 225 объектов с минимумом 13.0, объектов Sentry нет. Первая публикация заняла 287 с, `--print-stamp` — около 1 с, `--verify` — около 6 с.
- rlib `shellio-sys-ghostty` весит 14 КБ: архив в 140 МБ не копируется в каждый профиль. Без `GameController` в `link-libs` линковка падает на `_OBJC_CLASS_$_GCController`.
- Проверка в копии рабочего дерева без `target/` и `vendor/`: вся цепочка `make setup ghostty check test-scripts bindings-check link-audit bundle check-bundle run` прошла за 197 с, набор собран за 138 с при прогретых кэшах. Повторный `make ghostty` за 1 с ответил «сборка ghostty не нужна». Строка, дописанная в патч, роняет `make check`, `make bundle` и `make link-audit` на сверке штампа.
- Подпись: после `cargo clean` вторая сборка дала тот же requirement и тот же CDHash, `Authority=Shellio Dev`, `flags=0x0(none)`. Подпись из login keychain идёт без запросов Keychain. Доверие к сертификату и hardened runtime не понадобились.
- Тесты скриптов: `test-publish.sh` — 63 проверки, `test-identity.sh` — 23, `test-bundle.sh` — 31.
- Находка `open -W`: заглушка выходит раньше, чем `open` подписывается на её завершение. В 1 запуске из 60 `open` вернул код 1 с «Unable to block on applications». `check-bundle.sh --open` судит по выводу и принимает код 1 только с этим сообщением, после правки прошли все 60 запусков.
- Нужен OpenSSL 3 или новее: `/usr/bin/openssl` — это LibreSSL 3.3.6, он шифрует `.p12` устаревшими алгоритмами.
- Отрицательное: CI проверен только статически (`actionlint`). На раннере не подтверждены метка `xcode-27`, путь Xcode, загрузка Metal toolchain без `sudo`, время сборки набора и размеры кэшей. Первый прогон CI, открытие бандла из Finder и резервная копия ключа оставлены владельцу в разделе Post-Completion плана, их итог в документах не записан.

### Зачем этот шаг

[ADR-0002](adr/0002-ui-stack-appkit.md) требует писать интерфейс на Rust через `objc2` без готового набора компонентов и называет это главным объёмом работы фазы 1. Проба отвечает на два вопроса до начала этой работы: укладываются ли базовые компоненты в бюджеты [architecture.md](architecture.md) и сколько стоит их написать. Заодно она закрывает открытый вопрос [ADR-0023](adr/0023-opaque-window-and-shell.md): навязывает ли `NSSplitViewItem` сайдбара или инспектора системный материал. От ответа зависели P0.3, P0.6 и состав P1.3.

### Что входит

**Правила проб.** Первой задачей плана принят [ADR-0034](adr/0034-probe-code.md): `unsafe` Objective-C и системных C API допустим в `spikes/`, GUI-проба проверяется целью `make probe-<имя>`, отчёт и выбранные данные лежат в `docs/probes/`.

**Сцена.** `spikes/probe-appkit-shell` — исполняемый файл без бандла и подписи. Окно 1180×720 точек: `ChromeBar` 40 точек, плоский навигатор 236 точек с `TreeList`, центральная и правая плитки с `TabStrip` и `VirtualList`, нижняя плитка-заглушка, палитра на дочерней `NSPanel`, меню, ячейки темы. Модули компонентов: `chrome`, `split`, `tiles`, `tabs`, `list`, `tree`, `palette`, `menu`, `theme`. Токены сверяются с `prototype/css/tokens.css`.

**Фикстуры.** Списки на 1 000, 10 000 и 100 000 строк, дерево на 10 000 узлов, 1, 8 и 30 вкладок, 2 000 команд палитры.

**Стенд.** Сценарий ведёт процесс изнутри синтетическими событиями `NSEvent` через `postEvent`, читает фактическое состояние AppKit и пишет `result.json`. Ожидания — предикаты с тайм-аутом, без `sleep`. Сторож в отдельном потоке завершает зависший сценарий. Событие, которого нет в таблице стенда, — ошибка исполнения «внешний ввод».

**Сценарии:** `startup` (по 21 запуску на вариант), `launch`, `native-menu`, `parent-click`, `key-delivery`, `readback-check`, `split`, `tabs`, `list`, `tree`, `palette`, `menu`, `theme`, `idle`, `frames`, `cycles`. Сплит сравнивается в двух вариантах: `sidebar` (режимы сайдбара и инспектора) и `plain` (обычные элементы).

**Цели.** `make probe-appkit [SCENARIOS="…"]` и `make probe-appkit-demo [ARGS="--split sidebar|plain --contrast normal|more --motion normal|reduced"]`. Набор ghostty они не читают и блокировку не берут.

**Стенд замеров.** Mac15,6 (Apple M3 Pro, 18 ГБ), macOS 27.0.1, встроенный дисплей 120 Гц, профиль `release`. Основной прогон 2026-11-13: 60 процессов, ошибок исполнения 0.

### Зачем этот шаг

[ADR-0003](adr/0003-terminal-libghostty.md) строит каждую терминальную панель как поверхность полного libghostty в собственном подклассе `NSView`. Заголовок `ghostty.h` называет этот API внутренним, а условие пересмотра решения — неустранимая проблема с composition. Проба выносит вердикт по композиции поверхности с окном, палитрой, скруглением, скрытием и переносом между зонами. От неё зависели P0.4 и P0.8, а её выводы — основа P2.2.

### Что входит

**Проба.** `spikes/probe-ghostty-surface` в собственном бандле `target/probes/ghostty-surface/bundle/probe-ghostty-surface.app`, подписанном `Shellio Dev` под идентификатором `io.github.dsbasko.shellio.probe.ghostty-surface`. Модули: `ghostty/` (`init`, `config`, `runtime`, `surface`, `clipboard` — весь `unsafe` вокруг libghostty), `view` (подкласс `NSView` с `NSTextInputClient`, мышью и доступностью), `router` (режимы `Input` и `Navigation`, аккорд выхода), `scene` (окно с четырьмя зонами), `palette`, `visibility`, `gpu`.

**Фикстура.** Режим `--fixture` того же файла — программа в PTY поверхности с квитанциями на каждый `SIGWINCH` и каждые прочитанные байты. Управление идёт по сокету Unix.

**Гипотезы H1–H14:** запуск API и ресурсы, маршрут ввода, `NSTextInputClient`, аккорд выхода, ресайз и перенос, палитра и скругление, скрытие без рендера (H7a) и без swap chain (H7b), закрытие, задержка, память, CPU в простое, nvim и агент, доступность, сон дисплея.

**Сценарии:** `startup`, `startup-ls`, `window`, `surface-env`, `zones`, `input`, `ime`, `chord`, `palette`, `gpu-calibration`, `visibility` (пять вариантов обходов: `base`, `bounds`, `defer`, `syncdraw`, `all`), `teardown` (в том числе под `MallocScribble=1`), `latency`, `memory`, `idle`, `nvim`, `a11y`, позже `accept`.

**Цели.** `make probe-ghostty [SCENARIOS="…"]` и `make probe-ghostty-demo [ARGS="…"]`. Обе читают набор ghostty и держат `vendor/ghostty.lock` весь рецепт ([ADR-0034](adr/0034-probe-code.md), «Уточнено в P0.3»).

**Два слоя результата.** Полный автоматический прогон 2026-11-15 шёл под полноэкранным окном-щитом владельца: WindowServer считал окно пробы перекрытым, и пиксельные проверки не выносились. **Проба.** `spikes/probe-session-survival`: `backend/` (трейт `Backend` и адаптеры `zmx` и `rust`), `pty/` и `observer` (настоящие PTY, `setsid`, процессы по PID и времени старта), `fixture/`, `oracle/`, `vt/` (обёртка над `libghostty-vt`), `host/` (Rust-хост), `proto/` (wire-формат с замороженным v1), `matrix/`, `measure/`, `surface/`.

**Наборы пробы** в `target/probes/session-survival/`, каждый со штампом, манифестом и `--verify`:

- `zmx` — v0.8.1 `8bab1f0` с патчами `0001`–`0004` и патчем formatter его ghostty 1.3.2-dev, Zig 0.16.0;
- `zmx-prev` — та же ревизия с патчами `0002` и `0003`, предыдущее поколение для рубежа G;
- `vt` — `libghostty-vt` 1.4.0 ревизии и патчей поверхности, Zig 0.17.1.

**Cargo-функции.** Код, которому нужен набор, стоит за функциями `vt` и `surface`. Одним вызовом cargo они не включаются: `libghostty-vt.a` и `libghostty.a` не попадают в одну линковку. `make check` собирает пробу без функций ([ADR-0035](adr/0035-probe-ffi-tests.md)).

**Цели.** `make probe-session [SCENARIOS="…"]` — headless-сценарии `smoke`, `capi`, `lifecycle`, `restore`, `queries`, `io`, `geometry`, `versions`, `measure`, `apps`. `make probe-session-surface [SCENARIOS="…"]` — `report-policy`, `bridge`, `update`, `apps-surface` в настоящей поверхности libghostty из подписанного бандла, под блокировкой `vendor/ghostty.lock`.

**Рубеж решения.** До написания хоста проверено, отдаёт ли публичный C API `libghostty-vt` нужное состояние. 2026-11-17 владелец решил «идём»: байтовый мост по B1–B9 и политика отчётов в минимальной поверхности прошли во всех частях.

**Правило выбора.** Кандидат годен без обязательных `fail`, `unsupported` и `not_run`. Исключение — `not_run` только по причинам `surface` или `stand`. Годны оба — выбирается Rust-хост, годен один — он, ни один — отрицательный вывод без принятых отклонений.

### Зачем этот шаг

Автообновление без Apple Developer ID заменяет бандл под работающими сессиями агентов. [ADR-0019](adr/0019-distribution-and-updates.md) оставил пробе выбор протокола замены и проверку трёх рисков самоподписанной версии: разрешения TCC, доступ к Keychain и карантин Gatekeeper. P0.4 показал только механику: хост из копии рантайма переживает атомарный обмен бандлов. Здесь проверяется весь контракт: журнал намерения, помощник после выхода GUI, подтверждение работоспособности с сохранением прежней версии, восстановление из каждой промежуточной точки, смена владельца блокировки и сокета, старые и новые рантаймы, отложенная активация несовместимого обновления. От итога зависят P5.1–P5.3 и часть P2.1.

### Что входит

- **Проба `spikes/probe-update-lifecycle`.** Бинари: раннер `probe-update`, роль GUI `probe-update-app`, помощник замены `probe-update-helper`, минимальный хост `probe-update-host`, клиент `probe-update-attach` и нагрузка `probe-update-fixture`. Модули: `journal`, `recover`, `health`, `watchdog`, `owner`, `runtime`, `compat`, `keychain`, `tcc`, `brew`, `volume`. Хост и attach-клиент — собственная минимальная модель процессного контракта Rust-хоста, а не код P0.4: нужное оттуда скопировано и упрощено.
- **Поколения и кандидаты.** `run.sh` собирает поколения 1 и 2 и кандидат `incompatible` отдельными вызовами cargo в `target/probe-update-gen/<N>/` и подписывает бандлы в `target/probes/update-lifecycle/bundle/`. Бандл пробы подписан `Shellio Dev` под `io.github.dsbasko.shellio.probe.update-lifecycle`, части — под `.helper`, `.host`, `.attach`, `.fixture`, бандл-контроль — под `.denied`. Кандидаты-отказники: `tampered` (файл изменён после подписи), `foreign` (тот же CN, другой сертификат во временной keychain), `wrong-id` ([ADR-0034](adr/0034-probe-code.md), «Уточнено в P0.5»).
- **Цели.** `make probe-update [SCENARIOS="…"]` запускает сценарии отдельными процессами под `caffeinate -dimsu` с временным `SHELLIO_STATE_DIR`. `make probe-update-tcc-grant` — шаг выдачи TCC владельцем между двумя запусками: единственное место, где вызывается `tccutil`.
- **Клетки.** Обязательные: A1 «Идентичность», A2 «Отказ до активации», B1 «Успешная замена», B2 «Убийства на границах», B3 «Ошибки среды», C1 «Владелец и второй запуск», D1 «Рантаймы», D2 «Несовместимость», H «Связный проход в окне». Наблюдения: E (TCC), F (Keychain), G (карантин через изолированный Homebrew). `not_run` наблюдений готовность плана не блокирует.
- **Стенд.** macOS 27.0.1 (26A434), Mac15,6, Apple M3 Pro. B3 идёт на томах APFS из `hdiutil` (64 и 32 МиБ) с настоящими ENOSPC, EXDEV и EACCES и инъекциями EIO. G клонирует `/opt/homebrew` в изолированный префикс без сети. F заводит временную файловую keychain, login keychain только читается. Синхронизация — квитанции, барьеры и `kqueue`, без `sleep`.
- **Два запуска.** Первый план строит стенд и проходит все клетки, кроме TCC. Второй — клетки TCC после шага выдачи, свежий полный прогон, приёмочный проход исполнителя, итог отчёта и ADR.

### Что получаем в результате

Пользовательских функций шаг не добавляет, потоки [ux.md](ux.md) не затронуты. Разработка получает выбранный протокол замены с таблицами переходов и восстановления, правило health, порядок владения при обновлении и измеренные длительности. Всё записано в [отчёте](probes/p0.5-update-lifecycle.md) и разделах «Уточнено в P0.5» трёх ADR. Продуктовый загрузчик P5.2 пишется по ним заново.

- **Протокол замены.** Выбран `renamex_np(RENAME_SWAP)` с журналом. Состояния журнала: `idle`, `staged-deferred`, `staged`, `intent`, `swapped`, `launched`, `committed`, `cleaning`, `aborting`, `rollback-intent`, `rolled-back`, `retired`. Журнал пишет только владелец `shellio.lock`, каждая мутация диска идёт после записанного решения. У каждой из 37 границ B2 один заранее записанный исход, второе восстановление шагов не делает. `EXDEV` при кандидате на другом томе прерывает попытку, остаётся прежняя версия.
- **Длительности.** От старта помощника: обмен `renamex_np` — 73,4 мс, `launched` — 326,7 мс, сторож видит законченную попытку на 480,8 мс. Восстановление в рубеже первого запуска — 76,5–421,1 мс, медиана 166 мс.
- **Health.** Новая версия подтверждается только при четырёх условиях: CDHash процесса из ядра и исполняемый файл ожидаемые; она единственный владелец блокировки, и сокет отвечает своим поколением; каждая живая сессия найдена, хвост без пропуска, ввод с квитанцией; PID и время старта хостов и нагрузок прежние. Срок — 60 с от `intent`. До `committed` прежняя версия хранится и проходит `codesign`. Откат после необратимой миграции схемы проба не доказывает.
- **Владение.** GUI N запускает помощника, убирает сокет и выходит; помощник берёт блокировку без сокета, запускает N+1, записывает его ключ (PID и время старта) и отпускает блокировку. Право стать владельцем даёт CDHash процесса из ядра, равный CDHash проверенного бандла. Двух владельцев нет, inode блокировки не меняется, второй запуск получает квитанцию или явный временный отказ.
- **Keychain.** Item версии N получает partition ID `cdhash:<CDHash N>`. Версия N+1 с тем же designated requirement при запрещённом взаимодействии получает `errSecAuthFailed` (-25293) без окна. CDHash меняется с каждой сборкой, поэтому каждое обновление самоподписанного кода меняет partition ID. Пределы вывода: наблюдалась временная файловая keychain; Data Protection keychain и чтение с разрешённым взаимодействием не проверялись; причина отказа выведена, а не трассирована.
- **TCC.** Не наблюдалось: `tcc-grant.json` нет, все 48 частей (два графа, два варианта запуска хоста) — `not_run`. Матрица частей при действительной выдаче не написана. `responsibility_spawnattrs_setdisclaim` — «выбор не подтверждён», приватный API не включается.
- **Brew.** Homebrew 7.0.14: `brew install` cask с `preflight_steps` занял 4,7–5,1 с, `open -n -W` установленного бандла вышел с кодом 0 за 311 мс без окна. Контроль с карантином Gatekeeper не запустил. `spctl --assess` отвергает оба бандла, запуску без карантина это не мешает.
- **Приёмочный проход.** Четыре пункта — `pass`: окно N+1 показывает ту же сессию (строки 1–33 без пропуска), синтетический ввод доходит до нагрузки, обычный `open` во время обновления не создаёт второго владельца, окно Gatekeeper снято и закрыто стендом. Путь от физической клавиатуры и диалоги TCC — `not_run`.

### Зачем этот шаг

`DiffView` — самый дорогой собственный компонент: он нужен панели изменений, истории и ревью. [ADR-0002](adr/0002-ui-stack-appkit.md) поручил P0.6 проверить его стоимость на `objc2` и записал условие пересмотра: если `DiffView` не укладывается в бюджеты, вопрос о Swift-оболочке возвращается владельцу. Бюджеты заданы в [architecture.md](architecture.md): открытие diff на 100 тыс. строк до 200 мс, прокрутка без потери кадров при 120 Гц, память GUI до 150 МБ, реакция на клавишу до 16 мс, CPU в простое до 1%. Проба также закрывает передачи P0.2: кадры на экране, отметка конца отрисовки, собственная доступность.

### Что входит

- **Проба `spikes/probe-diff-view`.** Общие модули `model` (разбор diff, строки показа, индекс высот, перенос, треды, зоны) и `highlight` (worker подсветки tree-sitter, грамматика `tree-sitter-rust`), два вида и общий стенд.
- **Два варианта отрисовки.** A — собственный `NSView` в `NSScrollView`, строки рисует Core Text, есть индекс высот. B — view-based `NSTableView`, строка таблицы — строка diff или блок треда. Оба реализуют unified и «Рядом» с переносом длинных строк, подсветку, inline-треды с черновиком, выделение строк и доступность для внешнего клиента.
- **Фикстуры.** `added` (100 000 новых строк), `modified` (каждая пятая изменена, около 120 000 строк показа), `sparse` (50 ханков, открытие на последнем, на строке 99 900, внутри многострочного комментария и raw-строки), `wrap` (строки 200–4 000 символов), `threads` (`modified` и 500 тредов), `real` (32 файла кода проекта). Генераторы детерминированы.
- **Сценарии.** 19 сценариев: стенд (`smoke`, `highlight`, `calibrate`), открытие (`open`, `open-warm`, `open-smoke`), кадры `frames` (S1 — равномерная прокрутка 4 800 точек/с, S2 — бросок, S3 — ресайз), `memory`, `keys`, `idle`, контракт (`ax`, `anchor`, `selection`, `threads`, `pairs`, `bounded`), `zones`, `theme` и приёмочный ход `accept`. Сценарий вида идёт процессом на пару «вариант × режим», `open` — 11 свежими процессами на ячейку.
- **Цели.** `make probe-diff [SCENARIOS] [VARIANTS] [MODES] [FIXTURES] [FRAMES_PATH]` и `make probe-diff-demo` для демонстрации без стенда. Терминалу нужны Accessibility и Screen Recording, AeroSpace выключен, `calibrate` требует встроенного дисплея 120 Гц.
- **Правила, записанные до прогонов.** Пороги, стимулы и сроки не меняются после результатов. Вариант для P3.2 выбирается по правилу из шести пунктов. Вердикт по кадрам выносится только после калибровки, которая доказывает связь «окно — дисплей — показанный кадр — шаг стимула» ([ADR-0034](adr/0034-probe-code.md), «Уточнено в P0.6»).

### Зачем этот шаг

[ADR-0015](adr/0015-forge-review.md) строит ревью на локальном журнале черновиков, раздельных шагах отправки с состояниями `planned → in_flight → confirmed|unknown`, двух ветвях GitHub и поштучной публикации `draft_notes` GitLab без `bulk_publish`. Решение записано по документации провайдеров. Проба проверяет, выполнимо ли оно на настоящих API: не заденет ли отправка чужие черновики, переживёт ли журнал сбой, как ведут себя якоря при смене head. Результат открывает P4.1 и определяет контракт продуктового `forge-fake`.

### Что входит

- **Проба `spikes/probe-review-api`**, бинарь `probe-review`. Модули: `model` (якоря, ревизия, смена head), `journal` (журнал черновиков на SQLite), `transport` (HTTP-клиент, след вызовов), `scrub` (очиститель данных), `fake` (оракул `forge-fake` для GitHub и GitLab), адаптеры `github` и `gitlab`, `submit` с `reconcile` (отправка и сверка), `live` (песочницы, сторож записи, уборка).
- **Зависимости.** `ureq` 3.5.2 с TLS и корнями платформы, `tiny_http` для `forge-fake`, `rusqlite` 0.43.0 без `bundled` на системной `libsqlite3`. Журнал пишет каждый переход в WAL с `synchronous = FULL`.
- **Обязательный стенд.** `make probe-review` — столбец `fake`: `forge-fake` на `127.0.0.1` с портом 0, процесс на пару «сценарий × столбец».
- **Живой контур.** `make probe-review-live [HOSTS="…"]` — столбцы `github_cloud`, `gitlab_cloud`, `gitlab_ce` и `ghes`. Облачные столбцы пишут только в приватные песочницы из `~/.config/shellio-probe-review/sandbox.toml` токенами login keychain. Сторож до первой записи проверяет, что репозиторий приватен и перечислен. Клетка создаёт ветки `probe/<run-id>-*` и PR/MR, убирает их и подтверждает уборку чтением.
- **Локальный GitLab CE.** Контейнер docker по digest из `gitlab/pin` с меткой `shellio.probe.run-id`, порт только на `127.0.0.1`, не меньше 6 ГиБ свободной памяти, готовность ждётся до 15 минут.
- **Матрица.** 18 строк: семь для GitHub (`gh-local-create`, `gh-pending-cycle`, `gh-pending-foreign`, `gh-anchors`, `gh-viewed`, `reconcile-foreign`, `capabilities`) и двенадцать для GitLab (`gl-draft-publish`, `gl-foreign-draft`, `gl-approve-sha`, `gl-request-changes`, `gl-anchors`, `head-change`, `journal-crash`, `reconcile-ambiguous`, `reconcile-deleted`, `reconcile-paged`, `partial`, `capabilities`); `capabilities` общая. Вне матрицы — `smoke`, `volume` и `rate-limit`.
- **Блокировка.** Обе цели держат машинную замерную блокировку `measure.lock` весь рецепт; не взята за срок — код 4 «не начат».

### Что получаем в результате

Пользовательских функций нет, потоки [ux.md](ux.md) не затронуты. Разработка получает матрицу возможностей, правило сверки `unknown`, выбранный по документации метод серверного `PENDING` GitHub, список расхождений `forge-fake` с живым GitLab CE и измеренную стоимость большого ревью ([отчёт](probes/p0.7-review-api.md)). Конфигурация `rusqlite` без `bundled` на системной SQLite позже повторена в хранилище P1.1 ([план](plans/completed/20261121-core-domain.md)).

- **Не наблюдалось.** Черновик, созданный в браузере (`not_run` во всех живых столбцах: его ставил второй API-клиент); стойкость журнала к сбою питания; лимиты на живом хосте (`rate-limit` — только `fake`).

## P0.8 `probe-resource-accounting` — учёт CPU и памяти

| | |
| --- | --- |
| Статус | ✅ выполнен |
| Зависит от | P0.3 |
| Готово, когда | Подтверждённые формулы и базовые бюджеты |
| Решения | [ADR-0011](adr/0011-resource-accounting.md), [ADR-0034](adr/0034-probe-code.md), [ADR-0004](adr/0004-process-model.md), [ADR-0036](adr/0036-autonomous-execution.md) |
| План | [20261120-probe-resource-accounting.md](plans/completed/20261120-probe-resource-accounting.md) |

### Зачем этот шаг

Требование — показывать CPU и память приложения и каждой панели. [ADR-0011](adr/0011-resource-accounting.md) делит показ на две сводки: «Измерено: процессы» по `proc_pid_rusage` и «Оценка `≈`» по учтённым аренам и исполняемым участкам, с одним общим сэмплером. Проба проверяет формулы против независимых квитанций нагрузки, атрибуцию процессов по сессиям в трудных случаях, искажение и цену учёта участков и стоимость сэмплера против бюджета 0,5% CPU. От итога зависит P2.4 `resource-metrics`.

### Что входит

- **Проба `spikes/probe-resource-accounting`**, бинарь `probe-resources`. Проба headless: без AppKit и поверхности libghostty. Модули: `proc` (источник процессов), `snapshot` (снимок и формулы), `attrib` (принадлежность), `fixture` (процессы-нагрузки с квитанциями), `spans` (учёт участков), `arena`, `sampler`, `observer`, `background` (проверка фона).
- **Сценарии формул и атрибуции.** `units`, `formula-cpu`, `formula-mem`, `sessions`, `git-shared`, `reparent`, `churn`, `attach-move`, `login`, `eperm-inject`, `list-bench`. Сценарий `login` запускает настоящий `/usr/bin/login -f` с setuid, как его вызывает поверхность Ghostty.
- **Сценарии оценки.** `clock-bench`, шесть `span-*` (`busy`, `wait`, `migrate`, `nested`, `parallel`, `blocking`) и `arena`.
- **Сценарий стоимости.** `cost` идёт процессом на точку оси: `pids-8`, `pids-32`, `pids-128`, `panels-16`, `background`, `idle`.
- **Цель.** `make probe-resources [SCENARIOS] [POINTS] [RUN=<run-id>]`, сборка `release`, процессы под `caffeinate -i`. `RUN` продолжает прогон: готовые процессы пропускаются.
- **Условия замера.** Пятнадцать замерных процессов (`smoke`, `units`, `formula-cpu`, шесть `span-*`, шесть точек `cost`) берут машинную блокировку `measure.lock` и под ней ждут тишины фона окнами по 10 с. Тихо — фон не выше 30% одного ядра и ни один посторонний процесс не выше 10%. Процесс, не дождавшийся за 5 минут, получает «не начат» (код 3 у `run.sh`), третий подряд записывает `not_run` «шумно» ([ADR-0034](adr/0034-probe-code.md), «Уточнено в P0.8»).

### Что получаем в результате

Пользовательских функций нет, индикаторов и плагина Resources нет, потоки [ux.md](ux.md) не затронуты. Разработка получает правила измеренной сводки и принадлежности с пометкой, чем каждое подтверждено, выбранные источник списка процессов и часы потока, а также механизм замерной блокировки и проверки фона для будущих замерных целей ([отчёт](probes/p0.8-resource-accounting.md)).

### Фактический итог

Полный прогон `20261120-214121-984`: 26 `pass`, 1 `fail`, 19 `not_run` (15 «шумно» и 4 «нет поверхности»), ошибок исполнения нет.

| Группа | Клетки | Итог |
| --- | --- | --- |
| Формула памяти и список | `formula-mem-16`, `-128`, `-512`, `-sum`, `eperm-inject`, `list-cost` | 6 `pass` |
| Список процессов | `list-fields` | `fail` — отрицательный вывод |
| Атрибуция | `sessions` (3), `reparent`, `churn` (4), `git-shared` (2), `attach-move` (2), `login` | 13 `pass` |
| Часы потока и арены | `clock-bench` (3), `arena` (4) | 7 `pass` |
| Единицы и формула CPU | `units`, `formula-cpu` | 2 `not_run` «шумно» |
| Учёт участков | шесть `span-*` | 6 `not_run` «шумно» |
| Стоимость и стенд | шесть точек `cost`, `smoke` | 7 `not_run` «шумно» |
| Поверхность | `surface-redraw`, `surface-memory`, `surface-gpu`, `surface-remainder` | 4 `not_run` «нет поверхности» |

- **Критерий шага выполнен частично.** Подтверждены формула памяти, атрибуция, правило неполноты и учёт арен. Перевод единиц CPU, формула CPU%, учёт участков на настоящих часах и стоимость сэмплера не наблюдались, базовых точек стоимости нет.
- **Причина `not_run` «шумно».** Фон машины в простое — около одного ядра при пороге 30%. В 1 305 окнах полного прогона медианы попыток 89–119% одного ядра, минимум окна 77%. За всё исполнение плана тихих окон 0 из 2 175. Порог не сдвигался, стенд ошибок исполнения не дал.
- **Память.** Σ `ri_phys_footprint` по прочитанным членам: снимок больше квитанции фикстуры на 16 КиБ при допуске 1 МиБ на 16, 128 и 512 МиБ, сводка 692 258 472 байт равна сумме записей точно.
- **CPU.** Формула `100 × Σ Δ(ri_user_time + ri_system_time) / ΔT` с переводом тиков Mach через `mach_timebase_info` проверена только юнит-тестами на подставном источнике. 100% — одно логическое ядро, значения выше не срезаются.
- **Список процессов.** `proc_listallpids` с `proc_pidinfo` отказал с EPERM у 273 PID из 801: родитель, группа и время старта процессов root есть только в `sysctl(KERN_PROC_ALL)`. Он же дешевле: 129,5 против 373,6 мкс CPU потока.
- **Атрибуция.** Источники принадлежности: запись владения от хоста, корень, потомки по родителю, члены сессии (`getsid`), члены группы. Каждый процесс учитывается один раз. Сирота после двойного `fork` находится по сессии и группе. Общая работа репозитория уходит в группу «Git», панелям не начисляется. Закрытие attach-клиента и перенос панели состав сессии не меняют.
- **Неполнота.** `/usr/bin/login` с setuid не читается (`errno` 1), его ребёнок читается, покрытие памяти 2 из 3, снимок помечен частичным. При быстром выходе: CPU 3 из 7, память 4 из 5. Покрытие памяти и CPU считается отдельно, неудачный замер не скрывается.
- **Часы потока.** Выбран `clock_gettime(CLOCK_THREAD_CPUTIME_ID)`: точность как у `thread_info`, чтение 92,9 против 406,3 нс. Два чтения на участок — около 0,19 мкс: нижняя граница цены участка, а не стоимость учёта.
- **Сэмплер.** Один поток и один срок следующего прохода, число панелей не меняет число пробуждений: проверено только юнит-тестами. Фоновый шаг 10 с — предложение для P2.4, замером не подкреплено. Условие пересмотра ADR-0011 вердикта не получило ни в одну сторону.
- **Ограничение.** Процесс, который сам вызвал `setsid` и не попал в запись владения, не находится.

### Что передано дальше

- → P2.4: до первого замера стоимости определить условия замера — машину или окно без фоновой нагрузки либо другой порог фона решением планирования.
- → P2.4: измерить по клеткам `not_run` с прежними оракулами: `units` и `formula-cpu` против `getrusage(RUSAGE_SELF)`; шесть `span-*` с допуском ±(0,2 мс + 2%); стоимость сэмплера против 0,5 п. п. при 8, 32 и 128 PID, 16 панелях, фоновом шаге и в простое; стоимость учёта участков против 1 п. п.; базовые точки — длительность прохода, пробуждения в минуту, footprint.
- → P2.4: список процессов одним вызовом `sysctl(KERN_PROC_ALL)`; зомби отделять по признаку списка и не считать неполнотой.
- → P2.4: на настоящей поверхности проверить, что обновление чисел не вызывает перерисовку терминала, и измерить память на поверхность (P0.3: +107,5 МиБ первая, +12,6 МиБ каждая следующая). Ресурсы GPU и необъяснённый остаток P0.3 показываются как «общее».
- → [architecture.md](architecture.md): строка «Стоимость сэмплера» оставлена целью «до 0,5% CPU» с записью «не измерено».
- → Будущие замерные цели: правила `measure.lock` и проверки фона ([ADR-0034](adr/0034-probe-code.md), «Уточнено в P0.8»).

### Границы
