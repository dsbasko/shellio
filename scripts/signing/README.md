# Идентичность подписи `Shellio Dev`

Бандл подписывается постоянной самоподписанной идентичностью `Shellio Dev` ([ADR-0019](../../docs/adr/0019-distribution-and-updates.md)). `create-identity.sh` создаёт её один раз, после этого её только восстанавливают из резервной копии. Новая идентичность меняет designated requirement, и уже установленные копии перестают принимать обновления.

## Bundle ID и requirement

- Bundle ID — `io.github.dsbasko.shellio`.
- `requirement.txt` хранит designated requirement:

  ```text
  designated => identifier "io.github.dsbasko.shellio" and certificate leaf = H"<SHA-1 сертификата>"
  ```

  SHA-1 записан в нижнем регистре, как в канонической форме `codesign -d -r-`. Сравнивается каноническая форма (`csreq -r requirement.txt -t`), а не исходный текст. Хэш сертификата публичен, закрытый ключ в репозиторий не попадает.
- Подпись выполняется по SHA-1 сертификата, а не по имени.
- Файл пишет только скрипт. Создание отказывает, если файл уже есть, а восстановление и завершение отказывают, если файл описывает другой сертификат. Файл коммитится после того, как владелец создал идентичность.

## Создание

```sh
scripts/signing/create-identity.sh --export ~/secure/shellio-dev.p12
```

Путь резервной копии указывает владелец, он должен лежать вне репозитория. Скрипт:

1. До любых действий проверяет: путь резервной копии вне репозитория и не занят, `requirement.txt` ещё нет, в keychain нет сертификата `Shellio Dev` и закрытого ключа с меткой `Imported Private Key`, `openssl` — OpenSSL 3 или новее. `/usr/bin/openssl` — это LibreSSL, поэтому нужен OpenSSL из Homebrew в `PATH` или путь в `OPENSSL`.
2. Создаёт ключ RSA 3072 и самоподписанный сертификат `CN=Shellio Dev` на 20 лет: `basicConstraints=CA:FALSE`, `keyUsage=digitalSignature`, `extendedKeyUsage=codeSigning`, все три критичны. Расширения проверяются по готовому сертификату.
3. Записывает `.p12` (AES-256-CBC, PBKDF2 с 200 000 итераций, MAC SHA-256) по указанному пути с правами `600`. Это происходит до импорта, поэтому ключ никогда не хранится только в keychain.
4. Импортирует `.p12` в keychain с доступом для `/usr/bin/codesign`.
5. Задаёт partition list `apple-tool:,apple:` только у этого ключа.
6. Записывает `requirement.txt`, подписывает копию `/usr/bin/true` по SHA-1, проверяет её `codesign --verify --strict` и сверяет requirement подписи с файлом.
7. Печатает SHA-1.

`--keychain <путь>` задаёт другой keychain вместо login keychain, а `--requirement <путь>` — другой файл requirement, это нужно тестам.

## Два пароля

- Пароль `.p12` шифрует резервную копию. Он нужен при создании, при восстановлении и при импорте в CI, где хранится в секрете `SHELLIO_DEV_P12_PASSWORD`. Длина пароля — не меньше 12 символов. Скрипт берёт его из `SHELLIO_DEV_P12_PASSWORD`, иначе запрашивает в терминале: при создании дважды.
- Пароль keychain разблокирует keychain и разрешает менять partition list. У login keychain это пароль входа в систему. Без `SHELLIO_KEYCHAIN_PASSWORD` его запрашивает в терминале сам `security`. Переменная нужна для временных keychain в тестах и CI.

`security` получает пароль `.p12`, а при заданной переменной и пароль keychain, в аргументах командной строки. Пока команда работает, их видят процессы того же пользователя. OpenSSL получает пароль через окружение.

## Partition list только у этого ключа

macOS даёт каждому закрытому ключу, импортированному из `.p12`, метку `Imported Private Key`. У `set-key-partition-list` выбор ограничивает только метка (`-l`). Фильтр `-a` не находит двоичный application label, а `-D` и `-j` игнорируются, и тогда команда меняет все ключи keychain. Поэтому скрипт:

- отказывается работать, если в keychain уже есть ключ с такой меткой;
- после импорта находит ключ по SHA-1 открытого ключа и требует, чтобы его метка была единственной;
- проверяет по выводу команды, что изменён только этот ключ.

Если в login keychain уже есть чужой ключ с такой меткой, скрипт останавливается и ничего не меняет. Тогда идентичность можно создать в отдельном keychain через `--keychain`. Чтобы его находил `codesign`, keychain добавляют в список поиска пользователя. `security list-keychains -d user -s` задаёт этот список целиком, поэтому в команде перечисляются и уже имеющиеся keychain.

## Завершение после частичного сбоя

- Сбой до импорта не меняет keychain. Если резервная копия уже записана, настройка продолжается восстановлением из неё (`--from-p12`), а не новым созданием: новое создание выпустит другой сертификат.
- Сбой после импорта при настройке partition list, записи requirement или проверке подписи оставляет сертификат и ключ в keychain, и повторное создание отказывает. Обычная причина — неверный пароль keychain. Настройку завершает команда:

  ```sh
  scripts/signing/create-identity.sh --finish
  ```

  Она находит единственный сертификат `Shellio Dev` и его закрытый ключ, задаёт partition list этого ключа, записывает `requirement.txt` и повторяет проверку подписи. Новый сертификат не создаётся.

## Восстановление из резервной копии

На новой машине или после потери keychain:

```sh
scripts/signing/create-identity.sh --from-p12 ~/secure/shellio-dev.p12
```

Скрипт читает сертификат из `.p12`, проверяет его назначение и совпадение с `requirement.txt`, импортирует, задаёт partition list и проверяет подпись. SHA-1 и requirement не меняются. CI импортирует тот же `.p12` во временный keychain средствами `security`.

`.p12` и его пароль хранятся вне репозитория и вне этой машины. Потеря ключа означает ручную переустановку у всех пользователей (ADR-0019).

## Подпись бандла

`sign.sh <путь>` подписывает бандл или бинарь: `codesign --force --sign <SHA-1> --identifier io.github.dsbasko.shellio --timestamp=none -r requirement.txt`. SHA-1 берётся из `requirement.txt`. Если идентичности с этим SHA-1 нет, скрипт завершается ошибкой, ad-hoc подпись и другая идентичность не подставляются. `SHELLIO_SIGNING_KEYCHAIN` задаёт keychain с идентичностью, например временный keychain CI, без неё идентичность ищется в списке поиска пользователя. Скрипт вызывают `make bundle` и `make test-bundle`.

## Доверие к сертификату

Для P0.1 доверие не нужно. Самоподписанный сертификат подписывает бинарь с явным requirement, и подпись проходит `codesign --verify --strict` без доверия. `security find-identity -p codesigning` показывает идентичность с `CSSMERR_TP_NOT_TRUSTED`, а с `-v` не показывает её вовсе, так и должно быть. `security add-trusted-cert` требует подтверждения пользователя, а настройки доверия не переносятся в `.p12` и задаются на каждой машине заново, поэтому скрипт их не меняет. Hardened runtime и сохранение разрешений TCC проверяет P0.5.

## Проверка

`scripts/signing/test-identity.sh` входит в `make test-scripts`. Он запускает скрипт на временных keychain вне списка поиска и проверяет:

- создание и отказы до любых действий;
- отказ повторного создания;
- подпись по SHA-1;
- путь CI;
- прерывание после импорта и `--finish`;
- восстановление;
- неверные пароли и чужой ключ с той же меткой;
- ввод паролей в терминале через `expect`.

Login keychain, список поиска и `requirement.txt` репозитория тест не меняет.
